> DeepSeek Harness 团队在 X 上发的 Super-agent 设计备忘，最值得当作“不让模型来判断是自己干还是交给别人”的一套构成方案来读。和单会话的对比实验里拉开差距的，恰恰就是这个判断。另一方面，最抢眼的那个功能，也就是没人叫它，它自己去读群聊然后提 PR，却建立在作者本人在最后一节写明“尚未解决”的安全问题之上。**我认为这个顺序是反的。**

## 瓶颈是人的注意力

问题设定一段话就够了。

> In our experience, a person can usually follow only 3 to 5 active sessions at once. With these designs, a single task is limited by model capability, but multi-tasking is limited by human attention.
>
> （按我们的经验，人同时能跟进的活跃会话通常最多3到5个。按现在的设计，单个任务受限于模型能力，而多任务受限于人的注意力。）

所以他们想把会话对用户隐藏起来，让它看起来像是“一个一直在运行的 agent”。为此列出了5个组成部分。

- 两层结构：只负责和人对话、分派工作的 Router，以及每次隔离一个任务的 Worker
- 事件驱动：聊天、邮件、CI、评审评论都作为 Trigger 接收
- 全双工：把耗时的工具做成 `start()` / `stop()` 的异步调用
- 计算、状态、执行环境分离：循环在云端，状态在 DB，执行在本地机器上的轻量守护进程
- Watchdog：在主体之外，用模型盯着 Worker 有没有在空转

这些都不是新发明，作者们自己也这么写。Fast Path / Slow Path，作为缓存的上下文（Inline 和 Spill），推测执行，计算与存储分离。就是把计算机系统里的老工具用到 agent 上的一种整理。我觉得这样读就可以了。

## 用结构来强制委派

最重要的是 7.1 的消融实验。他们灌入约300条消息（其中工作请求约20条），把编码工作换成“只会耗时间的工具”，只比较调度。每种配置跑5次。

Super-agent 的完成时间是 p50 12.4分钟，p95 15.7分钟。作为对照的“单会话＋子 agent 工具”，行为随提示词不同而分裂了。

> With the neutral prompt, the model did not call a subagent in any of the 5 runs.
>
> （在中性提示词下，5次运行中模型一次都没有调用子 agent。）

中性提示词下，全部由父会话自己干，不断被新消息打断，p95 是29.5分钟。优先委派的提示词是这样的。

> Prefer handing each piece of work to a subagent of its own, and do only small things yourself...

这一个，5次里有4次做了委派。剩下的1次，是模型判断这件事“small”，自己动手做了，那里就成了长尾。提示词允许“小事自己做”，所以模型并没有违背指示。只是把“什么算小”的判断交给了模型。

> A single session has to rely on prompt engineering and the model's on-the-spot judgment to decide whether to delegate. The two-level architecture mitigates this problem at the system level instead: the Router does not execute work itself, and each Worker receives only messages from the Threads it subscribes to.

Router 的设计是自己不执行任务，2.1 节里写着“没有 Bash 工具也能运行”。它有分派工作的工具和召回上下文的工具，但不需要有执行手段。没有的话，“这个很小，我自己来”这种判断从一开始就不会发生。不过，7.1 里的 Router 到底是真的被拿掉了工具，还是只是被提示词拦住了，我从正文里没能看出来。

这是我最有共鸣的地方。我在自己的配置里写过，设计应用时的原则是“路由、重试、状态判定这类能用 switch 写出来的东西，不用 LLM 的判断”。这个实验就相当于对它的一次实测。在提示词里写“优先委派，小事自己做”，只是在请求对方做判断，而不交出执行手段，则是消除了判断的余地。5次里有1次的离群值，我认为就是“请求”的极限原样显现了出来。

话虽如此，7.1 比较的是整个架构（Router 与 Worker 的分离、订阅与透传、Worker 的隔离），并不是把“不给执行手段”单独拎出来的实验。各部分贡献大小的排序，从这份数据里排不出来。

没有测的东西也很清楚。编码用的是相当于 sleep 的工具，所以 Worker 分开之后成果物的质量会怎样，他们没看。成本方面，正文里给出数字的只有有无透传的对比（去掉透传后 Router 的判断增加约30%，缓存读取从 23.2M 增加到 31.8M token，约增加37%）。比单会话多用了几倍，正文里没有，而我也没看到图表。“用 token 买来了速度和稳定”这种说法，是一笔没标价格的买卖。

## Router 的批处理不是有余量的证据

7.2 对 Router 单独做了压力测试。把需要判断的 Trigger 从每分钟约1条提高到约40条，平均批大小 1.0 → 2.8，单次请求时间 2.5秒 → 3.9秒，每次判断摊销的推理时间 6.4秒 → 1.6秒。结论是“还不需要拆分 Router”。

这里我稍微做一下减法。以下是我自己的估算，原文里没有。

每分钟40次判断，每次按1.6秒处理，每分钟需要64秒的推理。一分钟是60秒，所以直接读的话，利用率超过100%。换条路再算一遍。40条按每批2.8条处理，每分钟约14次请求，每次3.9秒的话约56秒。这样算也超过了9成。

原文写的是，即便如此 Router 也 “did not reach its throughput limit”。和我的估算对不上。也许“摊销推理时间”的定义（一次判断横跨多个请求的部分怎么算）或者“约40条”的取整能解释，但我从正文里没法判断。至少，这不是能读出有余量的数字。

说到底，批变大是因为上一次推理期间事件积压了。批大小2.8，也意味着事件在被迫等待。摊销时间下降是事实，但那是排起队之后产生的效率，每个事件各自的等待时间应该是变长了（原文没有测等待时间）。原文也写了上限由“上下文长度，以及一轮里能准确处理的 Trigger 数”决定，所以并不矛盾。只是，“按现在的团队规模足够”里的“现在的规模”就在每分钟40条之前，这一点最好从数字里读出来。

## 越主动，攻击面越大

原文最大的看点，是公司内部的 Super-agent 在公开群聊（public group chats）里，没有任何人 @ 它，就发现了缺陷、查明原因并提了 PR 的例子。3.4 节的“默默复现并修复”策略也是同一个方向。

在最后的 8.4 节，作者们是这样写的。

> If a server-side intrusion or a prompt injection compromises the Agent Loop, every endpoint device connected to it could be taken over.
>
> （如果服务端被入侵，或者提示词注入攻陷了 Agent Loop，所有与之相连的终端设备都可能被接管。）

> As long as credentials on an endpoint can enter the model's context, normal execution can expose them.
>
> （只要终端上的凭据能够进入模型的上下文，正常执行就可能把它们暴露出去。）

把这两段和刚才的看点摆在一起看。

- 输入是群聊里某个人的发言、邮件、GitHub 的评论。也就是外面的人能写的东西。
- 没人叫它也会动。不如说，没人叫也会动正是卖点。
- 本地机器上有守护进程，有未提交的改动和本地的凭据。

越主动，攻击者写下的文字驱动它行动的机会也就越多。3.1 节的事件过滤器有一条按“发送者、群组、白名单”来筛的 Fast Path，所以收窄这里就能防住。但这和收窄刚才那个“没人叫也会捡起来”，几乎是同一个操作。

所以我认为，8.4 不是“今后的课题”里的第4项，而是在生产环境里把 BYOM（连接本地机器的构成）和主动 Trigger 组合起来的前提条件。原文的写法是“不解决这个问题，就只能在非常小的、可信的范围内使用”，说的是同一件事。不同的是摆放的位置，要是我，会放在第2节之前。而且，看点里的例子是公开群聊和用户群，是“有人报告缺陷就会动”的设置。也就是把一个从小而可信的范围之外接收输入的例子，放在了最显眼的位置。

11月1日，我[写过](/articles/cursor-tampered-claude-code-extension)一篇关于被篡改的 Claude Code 扩展出现在 Cursor 扩展市场的文章。那篇讲的是分发路径，这篇讲的是输入路径，但两者最后都归结到“待在本地机器上的 agent 的权限”。

## 只带走一件事的话

不要把执行手段交给 Router。

事件驱动、计算与状态分离，不准备云端的常驻环境和守护进程就没法试。“不让指挥塔持有执行手段”，需要的部件更少。如果你让父会话拿着全部工具，只靠提示词来促进委派，那就和这个实验里单会话那一侧是同一个形状。中性提示词下，5次都是父会话自己干；就算让它优先委派，5次里也有1次是父会话判断“这很小”然后自己抱了下来。我没有在自己的配置里验证过，但我认为朝着削减父会话工具的方向，值得一试。

没试过的事我也写下来。原型没有跑过，Watchdog 对“偏离目标”的识别精度有多高，原文里也没有数字。
