先说结论。

> 添加 skill **不是加法，而是对已有的所有 skill 征税**。描述（description）占用的上下文预算有上限，一旦超出，**所有人的描述都会被缩短**。我自己的环境里其实一直在出这条警告，读到这篇文章之前我根本没明白它是什么意思。而且这只是一个更大问题的一部分：“skill 越攒越多，却没人去删”。模型更新，也许是做这次清点的**唯一一个来自外部的借口**。

## 关于这篇文章

- 原文：[Rethinking skills and prompts for GPT-6 Astra](https://x.com/i/article/2095989703967125509)，eric provencher（[@pvncher](https://x.com/pvncher/status/2095991462416490862)），2026 年 9 月 4 日

GPT-6 Astra 发布了，所以这篇文章说，该回头检查一下过去一年里攒下的各种指令（Skills、`AGENTS.md`、任务 prompt）。它的主张很简单：**去年为了弥补模型弱点而写下的指令，现在反过来成了束缚模型的一方。**

先坦白一点。原文里似乎有并排展示描述好坏示例的图片，但我只读到了文本部分。另外，作者在谈到 `$skill-creator` 的指引时写了“我们最近更新了它”，但我没有确认过作者的立场，所以只作为引用原样保留。

不过这一次，我手里有**一条一手证据**。就从它说起。

## 我的日志里出现过的警告

上周，我为了给文章生成插图，跑了 `codex exec`。返回的 JSON 里，混着这样一条错误项。

> Skill descriptions were shortened to fit the 2% skills context budget. Codex can still see every skill, but some descriptions are shorter. Disable unused skills or plugins to leave more room for the rest.
>
> （为了装进 skill 专用上下文预算的 2%，skill 的描述被缩短了。Codex 仍然能看到所有 skill，但部分描述变短了。禁用不用的 skill 或插件，可以给其余的 skill 腾出空间）

我当时直接跳过了。图片生成出来了，看上去没有实际损害。

读了 pvncher 的文章，我才明白这条警告在说什么。

> 很多人默认会往项目里下载大量 skill，这是错的。每个 skill 都带有名称和描述，它们会被载入模型的上下文，让模型判断什么时候用。**很多描述都太长，而 skill 一多，Codex 就会开始缩短描述来塞进去。** 模型看到的每条描述都变少了，也就更难判断该选哪个 skill。

也就是说，那条警告并不是“稍微省了一点”，而是**用来做选择的材料被削掉了**的通知。而且被削掉的不只是新加的 skill，**是所有人。**

于是我数了数自己环境里的情况。

| | `~/.claude/skills` | `~/.codex/skills` |
| --- | --- | --- |
| `SKILL.md` 的数量 | 118 | 8 |
| 描述总长度 | 12,127 字符 | 3,295 字符 |
| 描述长度的中位数 | **64 字符** | **461 字符** |
| 最长的描述 | 990 字符 | 990 字符 |
| 超过 300 字符的描述 | 4 条 | **4 条**（共 8 条中） |

数字呈现出一个有意思的形状。**发出警告的，不是有 118 个 skill 的那一边，而是只有 8 个的那一边。**

Claude 这边有多达 118 个，描述的中位数却只有 64 字符。Codex 这边只有 8 个，中位数却有 461 字符，8 个里有 4 个超过 300 字符。**吃掉预算的不是数量，而是每一条的长度。**

这与 pvncher 的第一条建议完全吻合。

> 第一，skill 的描述在讲清楚模型何时该使用它的前提下，应当**尽可能短**。

我原来以为是“别装太多 skill”，准确地说其实是“**别装太多长描述**”。描述短的 skill，就算有 118 个，成本也低。描述长的 skill，8 个就能把预算占满。

### 添加的真正成本

从这里开始是我自己的解读。

添加一个 skill 的时候，我想的是“这个 skill 有没有用”。有用就装进去，没用不去用就是了。我从没想过**装进去这件事本身就有成本**。

但如果预算是固定的，这就不是加法。**每多加一个，就从已有的全部 skill 那里各拿走一点。** 而且被拿走的，恰恰是模型判断“该用哪一个”的材料。

于是得出一个奇怪的结论：**即便每个 skill 单独看都有用，加在一起却会互相削弱。** 每个 skill 都是以“我的描述会被读到”为前提写的，实际上所有人都是在被削减过的状态下被筛选的。

原文还写了更狠的一层。

> 更糟的是，描述之间可能互相矛盾，或者“选我选我”的劲头太足，结果模型可能会载入一些对该任务其实没有帮助的指令。

先被削减，再让剩下的片段按自我主张的强弱顺序起作用。这是一个谁写的描述长谁就赢的结构。我环境里那条“990 字符”，大概也是这种竞争的产物。

## 指令不是资产，而是会贬值的负债

文章剩下的三节（`AGENTS.md`、决策边界、持久性）形状全都一样：**去年正确的指令，今年反而起反作用。**

- “编辑之前先读文档” → 对改个错别字来说是过度了。**烧上下文、拖慢工作的绝佳办法**
- “运行测试，检查自己的工作” → 以前的模型需要鼓励。GPT-6 Astra 自己就会做，同样的指令只会催生**不必要的测试**
- “不要擅自推进，先问” → 以前的模型会擅自行动，所以加了更重的措辞。现在的模型**把边界看得太认真，在你希望它继续的地方停了下来**

这三条都是**针对过去事故写下的补丁**。事故不再发生了，补丁却留了下来。而留下来的补丁，并不带着当初写它的理由。所以没法决定删不删。

我的 `CLAUDE.md` 也一样。“先写测试”“不要擅自提交”“token 预算 4000”。每一条在过去的某个时刻想必都需要过，但**没有任何机制能确认它现在是否还需要。**

这么一想，就会发现这两周读的文章，处理的全是同一个问题。

| 出处 | 对“越攒越多”的应对 |
| --- | --- |
| Cainex（医疗编码） | 从把个别案例编码进去、不断堆积补丁的失败中，得出**“改原则，不改个案”**，并对单次修改中可放入的具体示例数设了上限 |
| OpenAI（Codex） | 每周五（一周的 20%）都用来手工清理 → **golden principles 加后台清理 agent**（原文称之为 garbage collection） |
| Warp | 改进 skill **起草 diff**，再变成 PR（不过 review 队列会增加） |
| Uber | 把 MCP 的工具定义**赶出上下文**（同一个问题在工具上的版本） |
| momo5502 | 软性指令不管用，于是换成**机械式的拦截** |
| **pvncher（本篇）** | **因为模型变了，所以做清点** |

前五个讲的是搭建“让东西不要堆积”的机制。**只有 pvncher 讲的是，因为一个来自外部的理由来腾空货架。**

这是我这次最大的收获。删除指令的决定，几乎不会从内部产生。能不能删，取决于“现在的模型没有它还行不行”，可行不行得试了才知道，试很麻烦，而留着又没有看得见的成本（至少自己是这么认为的）。

**模型更新，也许是能从外部打破这种僵局的唯一事件。** 原文的最后一句说的正是这个。

> 新模型是打扫屋子的好时机。

## 停止条件，会直接变成目标

还有一条细小但很扎人的指出。

> 如果你习惯了 GPT-5.6 Sol 接到请求后一路跑很久，那么 GPT-6 Astra 在何时停下这件事上可能显得更谨慎。到达第一版实现时，即使还有活没干完，它也可能回来请你 review。
>
> 这时就轮到**开始之前先定义“完成”**发挥作用了。（中略）**要求在第一版实现之后停下来 review，会把模型拉向更早的停止点。** 请确认那真的是你需要做的决定。

“停下来 review”，写的时候是当作偏安全的指令来写的。但在模型看来，那是**需要达成的目标**。出于安全放下的条件，原封不动地变成了要到达的目标。

我觉得这和我之前读到的 TokenOps 那件事形状相同（HALT 是最后手段，因为停下这个动作本身就会引发它原本想避免的故障）。**设置“停下”的机制时，要把它会被当成目标来读这一点也一并考虑进去。**

我就是在 `CLAUDE.md` 里写了“不要擅自推进”的人，所以这一条扎到我自己了。我写的本意是“做危险操作前先问”，但读出来的意思也许是“早点停”。**即使意图和读法错位了，我也没有办法察觉。** 停下的次数能数，但“本不该停却停了的次数”数不出来。

## 仓库里的 skill，不只属于你自己

还有一条容易被忽略的指出。

> 仓库里的 skill 也会引导其他贡献者的 agent。他们**用的可能是不同的模型**。对 Sol 或 Luna 有用的指引，可能会让 GPT-6 Astra 受到过度约束，所以要想想你留下的指令会被哪个模型使用。

放进仓库的 `AGENTS.md` 和 `CLAUDE.md`，不是为你自己环境做的调优，而是**共享基础设施**。而且读它的是哪个模型，你自己选不了。

说实话，这一点我还看不到答案。按模型分别写指令文件，维护不过来；取最大公约数，又对谁都不是最优。非要说的话，大概是把“弥补模型弱点的指令”和“项目的事实（结构、规范、边界）”分开写，只把前者放在自己的本地一侧。**事实不容易腐烂，补丁会。**

## 我要做的事

文章最后的建议是“让 GPT-6 Astra 用这篇文章的内容来做审计”。我的环境用的模型不同，所以不会照搬，但我会按这个顺序来。

**1. 先数。** 生成上面那张表的脚本大约 30 行，只是把所有 `SKILL.md` 都捡出来，把 frontmatter 里 `description` 的长度排成一列。**看的不是数量，而是描述长度的分布。** 如果中位数是几百字符，吃预算的就是它。

**2. 先从长描述削起。** 就我而言，990 字符的描述占了预算相当大的一部分。只削掉一条，所有人的份额就会增加。

**3. 把补丁和事实分开。** 试着给 `CLAUDE.md` 的每一行标注“这是对过去事故的应对，还是项目的事实？”。属于事故应对的那些，**先试一次看问题还会不会复现，再决定留不留**。

第三项是我最不想做的工作。因为这些行之所以留着，正是由于去试太麻烦。不过我觉得 pvncher 这篇文章的作用，就在于从外部为这份麻烦提供了正当理由。

## 只带走一件事的话

**要知道，添加是有成本的。**

我原来以为 skill 也好，`CLAUDE.md` 里的一行也好，“不用就是零”。实际上预算是固定的，加进去多少，就从已有的东西那里拿走多少。而被拿走的，是**模型用来选对东西的材料**。

自己的日志里明明出现过那条警告，我却因为看不懂而跳过了。数一数，一个 30 行的脚本就够了。就我的情况而言，元凶不是数量，而是单条的长度。
