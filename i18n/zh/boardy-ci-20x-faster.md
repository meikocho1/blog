先把结论写在前面。

> Boardy 把 CI 的等待时间从最长40分钟压到2分钟，这篇文章与其当成提速的操作手册来读，不如当成一份记录来读：“为了变快而省掉某些东西，就会出现一条什么都没通过却显示绿色的路。”9个项目里，写到故意把这条路弄坏来验证的，只有1处。**在智能体相信 CI 的绿色就往下推进的开发方式里，我认为说谎的绿色比慢的 CI 代价更高。**

原文是 Boardy 的 head of engineering Owen Gretzinger 在2026年10月31日（日本时间）以 [X 的 Article](https://x.com/owengretzinger/status/2116291924219060319) 形式发布的《How I made our CI 20x faster (steal this)》。

先说明一下。我读的只有正文文本，文章里嵌入的图片（配置差异和图表）我没能看到。这9个项目我自己也没有在自己的 CI 里试过。文章里出现了好几个产品名，包括 runner 服务 Blacksmith，但作者和这些公司是什么关系，文章里一个字也没写。

---

## 时间不在测试里

文章的动机就是这一段。

> They push, wait for CI, fix the red check, push again. When writing code gets 10x faster and CI doesn't, CI is what you're waiting on.
>
> （智能体 push，等 CI，修掉红色的检查，再 push。写代码快了10倍而 CI 没有变快，那你等的就是 CI。）

这一点我认同。有意思的是缩短下来的时间的构成。

效果最大的是第一项：不再用 GitHub 的标准 runner。以前最长要等11分钟才分配到机器，现在8秒就开始了。文章说，光这一项就把最长40分钟的等待变成了大约10分钟。剩下8项，把这10分钟削到了2分钟。

测试任务也是同样的形状。服务端的测试任务从168秒变成了74秒，但里面的测试几乎没变。缩短的是准备阶段：依赖缓存没命中的问题、`node_modules` 的缓存，以及 git clone 的方式。他们也试过能不能砍测试，让智能体审计了2万个测试用例，结果是这样。

> An agent audited all 20,000 test cases in our server and found almost nothing worth cutting, and the time was never in the tests anyway.
>
> （一个智能体审计了我们服务端全部2万个测试用例，几乎没找到值得砍的，而且时间从来就不在测试里。）

从40分钟到10分钟的那30分钟，光换 runner 就缩下来了。新 runner 的机器性能差异应该也掺在里面，所以不能说全是等待时间，但文章写了单个任务最长有11分钟的等待。剩下从10分钟到2分钟，lint 和类型检查工具的替换也有贡献，所以也不全是等待和准备的事。即便如此，“觉得 CI 慢的时候，先怀疑等待时间和准备时间，再去看测试本身”，这个顺序和文章里的数字是吻合的。

## 为了变快而省掉的地方，会出现说谎的绿色

接下来是我自己的读法。从文章的9个项目里，挑出那些靠省掉某些东西、或者换成别的东西来提速的做法，再按“在哪里可能没经过检查就变绿”重新排一遍。

| 做法 | 省掉或替换的东西 | 文章里写了什么 |
| --- | --- | --- |
| Vitest 的 `isolate: false` | 每个测试文件各自干净的环境 | 提醒测试之间会开始互相泄漏。对策列了两个：每个文件重置状态的钩子，以及告诉智能体清理的范围 |
| `nx affected` | 没改动的项目的测试 | 把跳过判断本身也测了（下面细说）。在 main 上每晚跑全部测试 |
| ESLint → Oxlint、tsc → bun check | 检查工具本身 | 只有速度的数字。没写新工具能不能抓到旧工具抓到的问题 |
| shallow clone | git 的历史 | 说 shallow 会让读取历史的处理坏掉，推荐 blobless clone（保留历史，文件内容之后再取） |

第3行是我最在意的地方。把检查工具换成更快的，同时也是在换检查的内容。规则的对应或者类型的判定只要有差异，以前是红的东西就会变绿通过。文章写了一个月内换了3次类型检查器，但每次比较了什么，从正文里看不出来（嵌入图片的基准测试里也许有）。

其余的做法，比如换 runner、并行化、缓存，都不是“不做某项检查就过去”的做法。把并行数减半的那一条反而相反：文章写的是速度没变，一个不稳定的测试消失了。

这张表里最重要的是 `nx affected` 那一行。

> We hid a server change from Nx on purpose and all six shards skipped their tests and reported green. Now that fails the run.
>
> （我们故意把一处服务端改动对 Nx 藏起来，结果6个分片全部跳过了测试并报告绿色。现在这种情况会让整次运行失败。）

故意弄坏，确认会出绿色，然后再把口子堵上。像这样去攻击自己刚动过的机制，9个项目里只有这一处写到了。每晚在 main 上跑全部测试，文章虽然没有这样定位，但我读成是对付同一个漏洞的第二张网。

`isolate: false` 那边，文章列的对策是重置状态的钩子和给智能体的指示。但这些是防止泄漏发生的对策，不是泄漏发生时能察觉的机制。只要漏掉一处清理，某个测试就可能踩在另一个文件留下的状态上，碰巧通过。这样的测试，在 `isolate: false` 下是不会变红的。

## 只会重跑的智能体

为什么说谎的绿色问题这么大？文章里讲缓存的那段，有一个很接近的例子。

> That bug had been there all year. Nobody noticed because nobody was sitting there watching CI. The agents were, and they just retried instead of fixing the actual issue.
>
> （那个 bug 存在了整整一年。没人注意到，因为没有人坐在那里盯着 CI。盯着的是智能体，而它们只是重试，没有去修真正的问题。）

最常盯着 CI 的是智能体，而智能体没有去修那个奇怪的行为，只是重跑了事。明明有慢、需要重跑这种看得见的症状，还是被放过了一年。接下来是我的推测：说谎的绿色连这种症状都不会出现。如果智能体看到绿色就进入下一项工作，就没有任何人有机会发现。

文章的第9项也戳在同一个地方。这是 push 前的检查为什么不写进 AGENTS.md、而是做成钩子的理由。

> Put it in a hook rather than a line in AGENTS.md, because agents skip steps.
>
> （放进钩子里，而不是 AGENTS.md 里的一行，因为智能体会跳步骤。）

我完全赞成。而且我想把同样的逻辑再往前推一步。智能体会跳步骤，遇到奇怪的行为有时也不修就放过去。既然如此，为了提速省掉了什么，就需要用机制去确认：被省掉的那部分，是不是真的还能出红色。Boardy 用 `nx affected` 做到了。`isolate: false` 应该也能做同样的事。

比如，每晚的全部测试也用 `isolate: true` 跑一遍，数一数和白天 `isolate: false` 结果不一致的测试。如果有测试是踩着前一个文件留下的状态在通过，那它在隔离的那一侧应该会变红。或者，成对地放一个会留下状态的测试，和一个有这个状态结果就会变的测试，看钩子是不是真的在清理。这两种我都没试过，原文里也没有。只是把文章作者对跳过判断做的事，用到隔离这一侧而已。

## 每月4,300美元值不值，我判断不了

最后是费用。

> Our CI bill went from $230 a month to $4,300, but it's the cheapest money we spend on making agents faster.
>
> （我们的 CI 账单从每月230美元涨到了4,300美元，但这是我们为了让智能体变快花的钱里最便宜的。）

大约18.7倍，每月增加4,070美元。

不过值不值，从文章的数字里判断不了。因为没写每月有多少个 PR，也没写智能体的会话花了多少时间在等 CI。“最便宜的开销”是作者自己的感受，并不是读者能套到自己的 CI 上去验算的形式。

文章的结尾是一句话：下一个瓶颈是自己按合并按钮的速度。CI 变成2分钟之后，剩下的就是人的确认。我在另一篇文章里读到的 DeepSeek Harness 团队的设计备忘录里，也有这么一句：“在目前的设计下，单个任务的上限由模型能力决定，而多任务的上限由人的注意力决定。”两边走到了同一个地方。

## 要带走的话，只带一件

每加入一个让 CI 变快的做法，就故意把它弄坏，确认它会不会出说谎的绿色。

换 runner 只改了一行，就把最长40分钟的等待变成了大约10分钟，而且它什么都没省，所以不会增加新的出错方式。危险的是之后那些“省掉一部分来提速”的做法。我认为 Boardy 这篇文章里最值得照着做的，是那个把服务端改动对 Nx 藏起来、眼看6个分片返回绿色的实验。
