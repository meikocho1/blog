ひとつの PR が、一晩で50回以上レビューされていました。

人間のレビュアーではありません。エージェントが書いた PR を、エージェントのレビュアーが指摘し、作者側のエージェントが直し、また指摘する。作者が止めるまで一晩続いた、という話です。

出てくるのは、Claude Code チームが2026年10月15日に claude.dev に出した「How the Claude Code team does code review」です。著者は Addy Osmani、Morgan Westlee Lunt、Qing Wang の3人。Claude Code のコードの約9割は Claude が書いている、という前提から始まり、その量をどうレビューしているかを6つの層に分けて説明しています。6月から9月にかけてマージされた PR は2倍以上に増え、そのうち revert された割合は40%以上下がった、というのが看板の数字です。

先に結論だけ書くと、こうです。

> 8月に私は「AI にレビューの事前スクリーニングをさせるのは、壊れた計器の隣に同じ計器を並べるだけだ」と書いた。この記事はその半分を反証している。AI レビュアーを人間の好みではなく過去の事故で採点すれば、それは同じ計器ではなくなる。ただし残り半分、レビューのもう一つの仕事である「チームが自分たちのコードを分かっていること」について、この記事は「誰も全体像を持っていなくていい」と書いた。その同じ記事が人間に残した5つの判断は、どれも全体像がないとできない。

元記事は全文を読みました。記事中でリンクされている、モノレポのソース管理の再設計や CI のスケールについての別記事は読んでいません。もう一つ開示しておくと、これは Code Review という自社製品を持っている会社のチームが、自分たちの運用を書いた記事です。数字は全部、彼ら自身が測ったものです。

## 「人間が読んだか」をやめて、何を測っているか

前提の数字から。Anthropic のモノレポでは、1日に入る変更が5月の約2,500件から9月には3万件を超えたそうです。Claude Code 自体は別リポジトリですが、同じ圧力を受けている。

この量を行単位で人が読むのは無理だ、というところまでは誰でも言えます。この記事が一歩進んでいるのは、レビューの目的を言い直したところです。

> We think "did a human read the code?" is an imprecise proxy for "what could go wrong with this change, and which check—automated or human—is the right one to catch it?"
>
> （「人間がコードを読んだか」は、「この変更で何がまずくなりうるか、それを捕まえるのに正しいチェックは自動か人間か」という問いの、不正確な代理だと私たちは考えている。）

そして、何を最適化しているかをはっきり書いています。PR あたりの人間の承認数（中央値と95パーセンタイル）、人間のコメント数、PR が人を待っている時間。これを減らす。ただし revert とインシデントの率をガードレールにして、それが上がったら「人間の時間を節約したのではなく、後ろに移しただけ」とみなす。

> Cutting the first doesn't help if the time just shows up in the second.
>
> （レビューにかける時間を削っても、それが壊れたものを直す時間として現れるなら意味がない。）

この1文で、記事全体の採点基準が決まっています。あとの6層は、この基準に対してどう組んだかの説明です。

## 6層のうち、量を受け止めているのは1層目

6層は、PR を出す前の検証、全 PR への AI レビュー、ブロックするセキュリティレビュー、必須の CI、リスクで段階を変える人間の承認、マージキューとフラグと段階リリース、です。その下に「すぐ戻せる」が敷いてある。

この中で一番地味で、一番効いていると私が思うのは1層目です。

> Most review now happens before a PR exists. We give Claude something it can run—like tests, a build or a screenshot to compare against the design—and ask it to show the output instead of saying it's done.
>
> （今ではレビューの大半は、PR ができる前に起きている。Claude には実行できるもの、つまりテストやビルドや、デザインと見比べるスクリーンショットを渡し、「終わりました」と言わせる代わりに出力を見せさせる。）

そのあと、別のコンテキストのサブエージェントに差分を見せる。Claude Code を作った Boris Cherny は、Claude に自分の仕事を検証する手段を渡すことで最終結果が2〜3倍良くなる、と見積もっているそうです。

もう一つ、同じ層に入っている習慣があります。AI レビュアーが同じことを繰り返し指摘するなら、指摘を受けるのではなく発生源を直す。スキルを直すか、lint ルールにするか、`CLAUDE.md` か `REVIEW.md` に書く。`REVIEW.md` の良い例についての記述が具体的で、そのリポジトリで「失敗とは何か」を書く、というものです。ドキュメントなら「嘘をつくこと」、設定なら「誤ったところへ流すこと」。指摘はファイルと行を証拠として求め、名前からの推測は許さない。直すものがないときはそう言わせる。

この層は製品の宣伝とほぼ関係なく、明日から誰でも真似できます。

## AI レビュアーを、自分たちの事故で採点している

2層目が Code Review の製品そのものです。複数のエージェントが並列にバグを探し、別のエージェント群が各指摘に投票し、十分に合意が取れたものだけが投稿される。スタイルや掃除だけの指摘は落とす。研究プレビューの時点で、実質的なレビューコメントが付く社内 PR の割合は16%から54%に上がったそうです。

数字よりも私が読んで止まったのは、このレビュアーをどう良くしているかの節でした。

> The team collected past PRs that caused incidents, with their fix-forwards and reverts, and had engineers who know that code confirm each bug and where it lived. The reviewer runs against that set daily.
>
> （チームは過去にインシデントを起こした PR を、その fix-forward や revert と一緒に集め、そのコードを知っているエンジニアに、バグが本当にそこにあったかを確認させた。レビュアーはこのセットに対して毎日走る。）

インシデントが一件起きるたびに、評価セットが一件増える。プロンプトでもツールでもモデルでも、レビュアーを変えたら全件で採点し直し、点が上がらなければ変更を捨てる。

ノイズの測り方も同じ発想です。レビュアーのコメントを、PR の人間がどう反応したかで分類する。直した、間違いだと言った、意図した挙動だと言った、どうでもいいと判断した。さらに、問題がないと分かっている PR に走らせて、誤った修正を誘いかねない指摘をどれだけ出すかを数える。

この2つの仕組みは、レビュアーの出来を「人間がそれらしいと感じるか」で測っていません。本番で実際に壊れたかどうかと、人間が実際にどう動いたかで測っています。ここが後の見解で効いてきます。

## 50往復した夜

この記事で一番正直な節は、レビューが終わらなくなった話です。

> An agent author and an agent reviewer can keep each other busy indefinitely. One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it.
>
> （エージェントの作者とエージェントのレビュアーは、互いを無限に忙しくさせられる。ある CLI の PR は、作者が止めるまでに一晩で50回以上のレビューと修正を往復した。）

その前に置かれている一言が、この問題の核心を言っています。人間なら細かい指摘は数秒で流せる。エージェントは直す。直せばコミットが増え、レビューがもう一周する。ノイズのコストは、作者がエージェントだと跳ね上がる。

原因を調べるのに、彼らは git blame を使いました。レビュアーが繰り返し指摘していた箇所の約59%は、レビュアーが最初に見た時点ですでにあったコードだった。新しいバグを見つけていたのではなく、もとからある古いバグを、一周ごとに少しずつ多めに見つけていただけでした。

![](/images/claude-code-team-review-layers/01-fifty-rounds-overnight.png)

しかも、それを悪化させたのは自分たちだった、と書いています。一周ごとに何か新しく見つかるので、複数周を回すのが習慣になっていた。

対策は4つです。3周したら、レビュアーが作者に「やり方自体を考え直せ」と言う。最初の数周のあとは差分だけを再レビューする。1行ではなくバグの種類を指摘して、作者に全箇所を直させる。一度出した指摘は繰り返さない。結果として、1回のレビューと修正で通る PR は65%から78%に、5周以上かかる PR は8.9%から1.5%に、通るまでの平均レビュー回数は2.08から1.32になりました。

私はこの節を、レビューの品質の話というより、指標の話として読みました。彼らは recall（どれだけバグを拾えたか）と並べて rounds-to-pass（何周で通ったか）を追うようにした。拾えるバグを増やす方向だけを見ていると、レビュアーは古いコードを掘り続けて PR を終わらせなくなる。どちらか片方だけを測るとどちらかが暴れる、という当たり前のことを、50往復という実物で示しているのがこの記事の価値だと思います。

## 承認の段階は、作者ではなく変更が決める

5層目は、人間の承認をリスクで変える仕組みです。

| リスク | 例 | 必要な人間の承認 |
| --- | --- | --- |
| 低 | ドキュメント、文言、社内限定機能、フラグの裏の追加的な変更 | 自動レビューとセキュリティが緑なら不要 |
| 中 | 通常の製品変更、キャッシュ・自動アップデータ・システムプロンプトなど敏感な領域 | 1人 |
| 高 | 最もリスクの高いコードと、常に2人を要する一部のパス | 2人 |

段階を決めるのは分類器です。2つ目の分類器が「段階上は不要でも、この変更には別の人間が要るか」を判定する。CI のワークフローファイルと、オーナーが敏感だと登録したパスは、常に人間が要る。

細かい規則のほうが私には面白かった。軽い段階を使えるのは、そのリポジトリの信頼済みリストに載った作者だけ。エージェントの承認は、人間の承認の枠を絶対に埋めない。エージェントが書いた PR では、エージェントを指示した人間が、自分で書いた場合と同じく必要なレビュアーの一人として数えられる。承認は特定のコミットに対するもので、システムが保証できない新しいコミット（エージェントの push や、手で解決したマージ）が載ったら承認はやり直し。

最後の規則は、エージェント時代にはかなり効くはずです。承認後に作者のエージェントが勝手に「改善」を push する、という事故の形を先に塞いでいます。

その上に、「land したら、自分のもの」という規範が乗ります。小〜中規模の変更で何かが壊れたら、普通は land した人が直す。それが責めではなく、一番文脈を持っているのがその人だから、という理由づけです。変更が小さく、フラグと revert と段階リリースで数分で戻せる、という前提があるので成り立っている規範です。

## 私の見解

### 8月の記事の半分は外れた

8月に「レビューは詰まっていない、計器が壊れている」という記事を書きました。そこでの主張はこうでした。AI が書くコードは表面がきれいなので、「雑さ」を手がかりにしてきた人間のレビューの計器が効かなくなった。そして業界の処方である AI による事前スクリーニングは、流暢なコードを「妥当」と判定する同じバイアスを持つので、壊れた計器の隣に同じ計器を並べるだけだ、と。

Claude Code チームの記事を読んで、この後半は少なくとも彼らの運用には当てはまらない、と認めます。

理由は、彼らのレビュアーの校正先です。私が「同じ計器」と書いたのは、AI レビュアーが、人間のレビュアーが騙されたのと同じ表面に騙されると考えたからでした。表面で採点されたものは、表面に騙される。でも彼らのレビュアーは、過去に本番で壊れた PR の集合で毎日採点されています。ノイズは、人間がその指摘を受けて実際にどう動いたかで測られている。校正先が「それらしく見えるか」ではなく「実際に壊れたか」になっている計器は、私が想定した計器とは別物です。

8月の記事で私は、偽装できない信号として、変更前に落ちるテスト、経路を実際に動かすこと、revert 率の3つを挙げました。彼らの1層目は「出力を見せさせる」で、ガードレールは revert とインシデントの率です。処方の方向は、思っていたより近いところにありました。違ったのは、私が AI レビュアーをその処方の外側に置いていたことで、彼らはそれを処方の内側、事故から学ぶ側に入れていました。

と書くと、評価セットに入るのは「起きた事故」だけではないかと思うかもしれません。その通りで、まだ起きていない種類の事故は採点できない。ただ、それは人間のレビュアーも同じです。人間の勘も、過去に見た事故の分しか育ちません。

![](/images/claude-code-team-review-layers/02-gauge-calibrated-by-incidents.png)

### 40%減の分母

看板の数字についても一つ書いておきます。マージされた PR は2倍以上、revert された割合は40%以上の減少。

割合が下がったのは本物の改善です。ただ、もし PR がちょうど2倍、割合がちょうど40%減なら、revert された PR の絶対数は 2 × 0.6 で約1.2倍、つまり増えています。記事は「以上」としか書いていないので、実際の絶対数が増えたか減ったかは私には分かりません。

これは揚げ足取りのつもりではありません。彼らの目的は「PR あたりの人間の時間」を減らすことなので、ガードレールが PR あたりの率なのは筋が通っています。ただ、revert を直すのは結局人間で、その仕事の総量は率ではなく件数で効いてきます。PR が2倍になったチームでは、率が下がっていても、壊れたものを直す人の忙しさは減っていないかもしれない。記事の採点基準である「レビューの時間を削っても、それが直す時間として現れるなら意味がない」を、件数でも確かめてほしいところです。

### 人間に残した5つの判断は、全体像を要求している

ここが、この記事でいちばん引っかかったところで、この記事で私が立てたい主張です。

記事は冒頭で、コードレビューには2つの仕事があると書いています。出荷前に問題を見つけて直すことと、チーム全体でコードベースの理解を共有すること。そして本文のほとんどを1つ目に使い、2つ目は終盤の3段落で済ませています。

> Nobody on the team keeps a complete mental model of Claude Code in their head, and we don't think anyone needs to. When someone wants to understand a part of the codebase, they ask Claude to write an explainer for exactly that slice.
>
> （チームの誰も、Claude Code の完全なメンタルモデルを頭に持っていないし、誰も持つ必要はないと私たちは考えている。コードベースのある部分を理解したいときは、まさにその一切れについて Claude に解説を書かせる。）

一方で、同じ記事の「人間がループに残る場所」の節は、人間に残す判断を5つ挙げています。そもそも作るべきか。リスクの高いコード。他の人が真似するパターンを決めるアーキテクチャ。証拠を読むこと。結果に責任を持つこと。証拠を読む項目には、こう書いてあります。

> If you can't say what the checks would miss, ask for a real review rather than a quick approval.
>
> （チェックが何を見落とすかを言えないなら、手早い承認ではなく本当のレビューを頼め。）

チェックが何を見落とすかを言えるためには、その変更が触っていない場所まで含めて、システムがどうつながっているかを知っている必要があります。「他の人が真似するパターン」を判断するには、今どんなパターンがあるかを知っていないといけない。「そもそも作るべきか」には、既存の何とぶつかるかの見当が要る。

5つとも、一切れの解説では足りない判断です。

一切れの解説は、自分がどこを知らないかを分かっている人には効きます。でも人間に残された5つの判断で問われているのは、どこを知らないかが分からない場所です。チェックが見落とすものは、だいたいそこにある。

私の読みでは、この記事は2つ目の仕事を「必要なときに解説を引けばいい」に置き換えた結果、1つ目の仕事のうち人間に残した部分の前提を削っています。そしてそれは、彼らのガードレールには映りません。revert 率もインシデント率も、起きた事故を数えます。「チームの誰もこのモジュールの境界を説明できない」は事故ではないので、数字に出るのは、それが原因の事故がまとまって起きたあとです。

8月の記事で私が言った「壊れた計器」の話は、このチームでは1つ目の仕事についてはもう当てはまりません。私が今気にしているのは、2つ目の仕事に計器がまだ一つもないことです。

![](/images/claude-code-team-review-layers/03-slice-explainer-vs-whole-map.png)

### 私が間違っているとしたら

いちばんありそうなのは、全体像は一人が持つ必要がなく、チームとして持てていればいい、という反論です。記事にも、チームの多くが誰でも見られる公開チャンネルで仕事をしていて、持ち主ではない人からもフィードバックが来る、と書いてあります。全体像が誰か一人の頭ではなくチャンネルの会話の中に分散している、というのは十分ありえる形です。その場合、私の心配は一人ひとりの頭の中しか見ていないことになります。

もう一つ、彼らは「方向を変えるとき」の節で、作るべきでない仕事はチャンネルで誰かが早めに「なぜ？」と聞いて閉じさせる、と書いています。これは全体像を持った誰かがいないとできない動きなので、少なくとも今のチームには、それができる人がいるのだと思います。私の主張は、その人たちがどうやってそれを身につけたか、そして次に入ってくる人が同じ道を通れるか、という問いです。今のチームで回っていることは、記事の数字からも疑っていません。

ここに書いたのは記事の内部の整合性からの推論で、Claude Code チームの中で何が起きているかを見たわけではありません。

## まとめ

1つだけ持ち帰るなら、AI レビュアーを何で採点するかです。人間がそれらしいと感じるかで採点すれば、人間と同じものに騙されます。自分たちの過去の事故で毎日採点し、人間がその指摘を受けて実際にどう動いたかでノイズを測れば、別の計器になります。これは Code Review を使っていなくてもできて、必要なのは過去の revert を集めて、そのコードを知っている人にバグの場所を確認してもらうことだけです。

もう1つ挙げるなら、レビューを何周で終わらせるかを決めておくこと。作者もレビュアーもエージェントなら、放っておくと終わりません。

そして、レビューの2つ目の仕事を測る方法は、この記事にも、私の手元にもまだありません。
