## この記事について

Adam Waxman 氏（[@ajwaxman](https://www.ajwaxman.com/)）が2026年7月29日に公開したエッセイ **"Software for One"** を扱います。Hacker News で266ポイント・279コメントを集めた記事です。

この記事は2部構成です。

- **第1部**：Waxman 氏が何を作り、いくらかかったのか（原文の事実）
- **第2部**：**この現象について私が考えていること**。原文にも HN の議論にも書かれていない読み方

後半のほうが長いです。事実の整理は原文を読めば済むので。

先に開示しておきます。私は Waxman 氏のアプリを使っていませんし、彼のスタックで個人アプリを作った経験を語れる立場でもありません。読んだのは原文と HN スレッド、そして Robin Sloan 氏の2020年のエッセイ原文です。第2部は、その3つを突き合わせて出てきた解釈であって、実測ではありません。

---

## 第1部 — 何が起きたのか

### 結論を先に

> 個人アプリのコストが崩れたのは AI がコードを書けるようになったからだが、**そのコストの大半は最初からコードではなかった**。消えたのは「他人に対して負う義務」のほうで、AI はそれを消す条件（ユーザーを1人にする）を、初めて現実的な選択肢にした。

### 2020年：4人のためのアプリ

出発点は Robin Sloan 氏が2020年2月に書いた「An app can be a home-cooked meal」です。彼は家族のためのメッセージアプリ **BoopSnoop** を作りました。ダウンロード数は4。3つのタイムゾーンに散らばった4人が、それから何年もデイリーアクティブユーザーであり続けた。彼はこれを大成功と呼びました。

アプリは家庭料理でいい。スケールも、ユーザー数も要らない。愛している相手のために作ればいい。

ただし、当時のコストは正直に書かれています。制作に1週間かかり、**その半分はコード署名の地獄に溶けた**。

> より良い世界であれば、私はこれを1日で作れていただろう。何らかの、モダンで柔軟な iOS 版 HyperCard を使って。
>
> （Sloan 氏、2020年2月。以下引用の訳はすべて拙訳）

![家庭の食卓で4人ぶんだけ料理を作るすみと、その隣で工場のラインが同じ皿を大量に流している対比](/images/software-for-one-cost-of-users/01-home-cooked-vs-factory.png)

このエッセイには続報のシリーズがあって、そこに走るギャグがあります。毎年の更新で「私は母のリクエストにより、機能を1つ（1つ）追加した」と書き続けるのです。2020年の世界では、それが正しい頻度でした。1回の変更が Xcode との格闘を意味したからです。

### 2026年：スムージーが走行距離を知っている

6年後、Waxman 氏は半年で「作りすぎた」と自分で書く量の個人ソフトウェアを作ります。

- 睡眠コンサルタントの計画をそのまま動かす**睡眠アプリ**
- その朝の走行距離に合わせて**スムージーの量を決めるフィットネスアプリ**
- 年齢ではなく自分のレース記録から組む**マラソン計画**
- ピアノのレッスンで出たコードボイシングを出題する**「ジャズ版 Duolingo」**
- 専門医の受診前に記録の欠落を洗い出す**医療記録ツール**

睡眠アプリの動機がいちばん具体的です。コンサルタントの計画は、条件分岐だらけの PDF で届きました。起きていられる時間の上限、昼寝の上限、昼寝が失敗したときの対応。それを彼は夜の時間1週間ぶんでアプリにした。結果、妻とナニーと本人が、**昼寝が短く終わると自動で組み直る1つのスケジュール**を共有するようになった。

フィットネスアプリのほうは、4つのアプリに散っているデータ（Strava、Oura、Withings、FatSecret）を1か所に集めて、走った距離と強度からその日のカロリー目標を動かします。

### スタックと値段

原文にスタックが列挙されています。ここは事実として押さえておきます。

- **フレームワーク**：Next.js on Vercel
- **フロント**：Tailwind + shadcn/ui
- **認証**：Better Auth
- **DB**：Neon の Postgres + Drizzle ORM
- **ジョブ**：GitHub Actions
- **AI**：Claude Code、Vercel AI SDK、自作の skills

月額は約 **160ドル**。内訳は Claude Code Max が100ドル、Anthropic API が10ドル、Vercel が20ドル、Neon が30ドル。ただし本人が注記しているとおり、Neon と API の大半は個人アプリではなく別プロジェクト（nycjazz.guide と Claude Code Daily）のぶんです。Claude Pro から Max に上げる前は100ドルを切っていた。アプリ1〜2本なら、月20ドルのコーディングサブスクと5〜10ドルの API 利用料に収まるだろう、と書いています。

### 制作時間

ここが2020年との差がいちばん出るところです。

- 睡眠アプリ：夜の作業1週間
- フィットネスアプリ：週末1回
- ジャズのクイズ：子どもを寝かしつけたあとの1晩

> 1〜2年前なら、私はこのどれも作ろうと考えなかった。作るのが遅すぎるし、保守はもっと大変だったからだ。**いまや制約は想像力のほうだ。**

保守についても、Sloan 氏の「年に1機能」と対照的なことを書いています。バグ修正も機能追加も依存関係の更新も、かつてないほど簡単になった。10回のうち9回は、スクリーンショットを Claude に共有すれば済む。

## 第2部 — 私の見解

ここからは原文にも HN にも書かれていない読み方です。

### 一番過激な行は「使い捨てでいい」

原文の学びは6つ挙がっていますが、私が読んで手が止まったのは4番目でした。

> **使い捨てで構わない。** 睡眠アプリは4か月ほど使った。息子が朝まで寝るようになったので、引退させた。もしこのアプリに何か月もかかっていたら、それは少し痛かったかもしれない。1週間だったから、必要なときに動いてくれてよかった、としか思わない。

これはコストの話に見えて、実はソフトウェアの前提を1つ壊しています。

私たちは「動くソフトウェアは保守するもの」を、選択ではなく物理法則のように扱ってきました。だからライブラリを選ぶときにメンテナンス頻度を見るし、社内ツールを作るときに「作った人が辞めたらどうするのか」と言われる。この心配は正しい。**ソフトウェアの寿命が無期限だと仮定するかぎりは。**

Waxman 氏の睡眠アプリの寿命は4か月でした。しかもそれは失敗ではなく、**設計の一部**です。息子が朝まで寝るようになる、という終了条件が最初から存在していた。

寿命が有限だと分かっているソフトウェアには、私たちが習慣的に払っているコストの半分が要りません。将来の拡張に備えた抽象化も、他人が読む前提のドキュメントも、5年後のフレームワーク移行の心配も。これは手を抜いているのではなく、**要件が違う**のです。

私が面白いと思うのは、この発想が個人アプリの外に持ち出せることです。社内ツールの提案書に「想定稼働期間：6か月。以降は破棄」と書ける組織が、どれだけあるでしょうか。ほとんどないと思います。でも実際には、6か月しか使われないツールを永続前提で作って、誰も使わなくなったあとも保守要員を1人張り付けている、という状況はいくらでもある。

![4か月と書かれた札を付けたアプリを、役目を終えて満足そうに畳んでいるすみ](/images/software-for-one-cost-of-users/02-designed-lifespan.png)

### 同じ2026年に、プロの現場は遅くなっている

ここで矛盾に見えるものを並べます。

Waxman 氏は「保守が驚くほど簡単」と書いています。一方で、私が別の記事（「AIコーディング論争は、事実では揉めていない」）で扱った AI コーディング論争のデータでは、プロの現場の数字は逆を向いています。METR の統制実験では、経験豊富な開発者は AI 利用時に **19%遅く**なっていたのに本人たちは速くなったと信じていた。DORA / Faros AI のデータでは、マージされる PR が98%増えた一方でレビュー時間は91%膨らんでいた。

同じ道具、同じ年、正反対の結果。どちらかが嘘をついているのでしょうか。

私はそうは思いません。**測っているコストが違うだけ**だと考えています。

プロの現場でコードを高くしているものを分解すると、こうなります。

コードを書く時間。他人がそれを読んで承認する時間。書いた本人以外が理解できる状態に保つ時間。仕様が誰の口から出たのかを確認する時間。壊れたときに誰が起こされるかを決める時間。使っている人に変更を知らせる時間。

このうち AI が直接削るのは、**最初の1つだけ**です。残りは全部「他人がいること」から発生している。だから生成だけが速くなると、残りが相対的に膨らんでボトルネックがレビューに移る。DORA の数字はそれをそのまま示しています。

Waxman 氏の環境では、その残り全部がゼロです。レビュワーがいない。仕様の出どころは自分。壊れたら自分が直す。使っている人は自分と妻とナニーの3人で、全員が同じ家にいる。

つまりこういうことです。**AI がソフトウェアを安くしたのではない。ユーザーを1人にすることが安くしたのであって、AI はその設定でも実用的なものが作れるようにした。** 順番が逆に語られやすいポイントだと思っています。

![左：1人のユーザーに向けて軽やかに作るすみ。右：大勢の窓口とレビュー待ちの列に埋もれて同じ作業をしているすみ](/images/software-for-one-cost-of-users/03-one-user-vs-many.png)

### だから正しい問いは「何人に絞れるか」になる

この読み方が正しいなら、AI で社内ツールを作るときの問いが変わります。

よくある問い：「これは AI で作れるか」

私が有効だと思う問い：「**このツールのユーザーを、何人まで減らせるか**」

なぜなら、前者の答えはたいてい「作れる」で、そして作れることは何も保証しないからです。作った瞬間に「他部署も使いたい」「権限管理はどうする」「担当が変わったら」が始まって、コストは AI 以前の水準に戻る。増えたのはコード量だけです。

一方、後者の問いには実務的な答えがあります。1人なら認証が要らない。3人で全員が同じチームなら権限管理が要らない。部署全体なら要る。ユーザー数は要件の量をほぼ直接決めます。

「ユーザーを減らす」は普通、事業としては敗北です。個人ソフトウェアの文脈でだけ、それが**戦略**になる。ここが今回の話のいちばん非直感的な部分だと思います。

Waxman 氏自身も似た方向のことを、市場の言葉で書いています。

> AI は大きな市場を氾濫させ、小さな市場を解き放つ。

前半（AI 製の使い捨てアプリがストアに溢れる）は誰でも言っています。私が重いと思うのは後半のほうです。**ビジネスとしては小さすぎるが、対応する価値はある**という領域が初めて実行可能になった、というのが彼の主張です。1世帯しか市場がないなら、そもそも誰も作りに来ない。

### 私が疑っている点：作れることと配れることは別

ここは楽観に対する私の留保です。

Waxman 氏は「まだほとんどの人には技術的すぎる」と自分で認めています。ターミナル、データベース、デプロイパイプラインに慣れている必要がある。そのうえで彼は、その障壁は長く続かないと予測します。根拠として、Sam Altman 氏が携帯から1メッセージ送るだけで「9人の友人の旅行計画・調整用サイト・招待メール」ができた、という投稿を引いています。

HN のスレッドで、私が原文より重いと思った指摘がこれでした。

> これはいい。だが Apple はサイドロードを事実上ブロックしている（TestFlight 環境の外では）し、Google も同じ方向に動いている。**個別化されたソフトウェアを作ることがこれほど容易になったことはないのに、公式プラットフォーム上でそれを動かすことがこれほど難しくなったこともない。**

これが効いてくる理由は、Waxman 氏の記事の楽観が「配布相手が自分（と家族）だけ」という条件の上に成り立っているからです。彼の主要スタックは Next.js on Vercel — つまり Web です。列挙されたスタックを見るかぎり、App Store を通っていない。だから成立している。

そして3人目、4人目が入った瞬間に、消えていたコストが順番に戻ってきます。認証が要る。データを分ける必要が出る。誰かのブラウザだけで動かない、という報告が来る。「昨日まで動いていた」への説明責任が生まれる。

Sloan 氏が2020年に格闘したコード署名の地獄は、**技術的な難しさではなく、他人に届けるための関門**でした。AI はコード署名の問題を解いていません。関門をまたがない使い方が現実的になっただけです。

これは反論ではなく、範囲の確定です。この現象が本物なのは「自分と、すぐ隣にいる数人」までで、そこから先は2020年と同じ世界が待っている。少なくとも今のところは。

![小さな家の中では、すみが手にしたアプリが問題なく動いている。家の外には壁のない門だけが施錠されて立っていて、その足元でもう1台のアプリが止まっている](/images/software-for-one-cost-of-users/04-build-vs-distribute.png)

### 「少なくとも今のところは」という但し書き

原文で私がいちばん誠実だと思った箇所を挙げておきます。保守について書いた学びの、最初の一句です。

> 保守は驚くほど簡単だ。**少なくとも今のところは。**

この "at least so far" が付いているのが大きい。彼のデータは半年ぶんです。Next.js のメジャーアップグレードを何回またいだのか、Neon の料金体系が変わったらどうなるのか、Claude Code のサブスクを解約した月に何が起きるのか。半年では出ない話です。

Sloan 氏の BoopSnoop は6年後の記事でもまだ言及されている。個人ソフトウェアの本当の評価は、そのくらいの時間軸でしか出ないのだと思います。だから私は、今回の記事を「個人ソフトウェアが解決した」ではなく「**個人ソフトウェアが、初めて始められるようになった**」という報告として読んでいます。

そのうえで、AI 生成コードの寿命について私が具体的に心配していることを1つ書いておきます。使い捨て前提で作ったアプリは、たいてい**使い捨てにならない**ということです。4か月で捨てた睡眠アプリは、明確な終了条件があったから捨てられた。でもマラソン計画アプリに終了条件はありません。ジャズのクイズにもない。終了条件のない個人アプリは、そのうち「動いてはいるが誰も中身を覚えていないソフトウェア」になる。ユーザーが1人でも、これは起きます。むしろ、レビュワーがいないぶん静かに進行します。

## 1つだけ持ち帰るなら

「AI で何でも作れる」ではありません。それは半分正しいだけで、行動が変わらない。

持ち帰るなら、**ソフトウェアのコストの大半はコードではなく他人への義務であり、義務の量はユーザー数でほぼ決まる**、という診断のほうです。

これが手元にあると、判断が2つ変わります。個人や少人数のためのツールでは、今までなら「作るほどではない」と切っていたものが実際に作る価値のある側に移動する。逆に、社内で AI を使ってツールを増やすときは、コードが速く出ることではなく、**ユーザーを何人に閉じ込められるか**が費用対効果を決める。

Sloan 氏は2020年に「モダンで柔軟な iOS 版 HyperCard」を願いました。Waxman 氏の締めくくりを引いておきます。

> 彼が手にしたのは、もっと奇妙なものだった。欲しいものを平易な英語で説明すると、エージェントがそれを作る。彼の望んだより良い世界は、到来した。

私は、到来したのは半分だと思っています。作る側は本当に変わりました。届ける側は、まだ2020年です。
