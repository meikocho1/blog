先に結論だけ書くと、こうです。

> Boardy の CI の待ち時間を最大40分から2分にした記事は、高速化の手順書として読むより、「何かを省いて速くすると、通っていないのに緑になる道ができる」記録として読むほうが役に立つ。9項目のうち、その道をわざと壊して確かめた話が書かれているのは1か所だけです。**エージェントが CI の緑を信じて次へ進む開発では、遅い CI より嘘の緑のほうが高くつく、と私は思っています。**

元記事は Boardy の head of engineering の Owen Gretzinger さんが、2026年10月31日（日本時間）に [X の Article](https://x.com/owengretzinger/status/2116291924219060319) として出した「How I made our CI 20x faster (steal this)」です。

開示しておきます。読んだのは本文のテキストだけで、記事に埋め込まれた画像（設定の差分やグラフ）は見られていません。私自身はこの9項目を自分の CI で試していません。記事にはランナーの Blacksmith をはじめ製品名がいくつも出てきますが、書き手とそれらの会社との関係については、記事に何も書かれていません。

## 時間はテストの外にあった

記事の動機はこの1段落です。

> They push, wait for CI, fix the red check, push again. When writing code gets 10x faster and CI doesn't, CI is what you're waiting on.
>
> （エージェントは push して、CI を待ち、赤いチェックを直して、また push する。コードを書くのが10倍速くなっても CI が速くならなければ、待っているのは CI だ。）

ここはそのとおりだと思います。面白いのは、縮んだ時間の内訳です。

いちばん効いたのは最初の1項目、GitHub の標準ランナーをやめたことでした。マシンが割り当てられるまで最大11分待っていたのが、8秒で始まるようになった。これだけで、最大40分の待ちが約10分になったと書いています。残りの8項目で、10分を2分まで削った。

テストのジョブも同じ形です。サーバーのテストジョブは168秒から74秒になりましたが、中のテストはほとんど変わっていない。縮んだのはセットアップで、依存キャッシュの効き漏れ、`node_modules` のキャッシュ、git の clone の仕方でした。テストを削れないかとも試していて、エージェントに2万件のテストを監査させた結果はこうです。

> An agent audited all 20,000 test cases in our server and found almost nothing worth cutting, and the time was never in the tests anyway.

40分から10分への30分は、ランナーを替えただけで縮んだ。新しいランナーのマシン性能の差も入っているはずなので、全部が待ち時間とは言えませんが、ジョブ1つで最大11分の待ちがあったと書いてあります。残りの10分から2分には、lint や型チェックのツール交換も効いているので、全部が待ちと準備の話ではありません。それでも、CI が遅いと感じたらテストの中身より先に待ち時間と準備の時間を疑う、という順番は、記事の数字と合っています。

## 省いて速くした所に、嘘の緑の道ができる

ここからが私の読み方です。記事の9項目から、何かを省いたり別物に替えたりして速くした手を拾い、「どこで確かめずに緑になりうるか」で並べ直してみます。

| 手 | 省いた・替えたもの | 記事に書かれていること |
| --- | --- | --- |
| Vitest の `isolate: false` | テストファイルごとのまっさらな環境 | テスト同士が漏れ合うようになる、という注意。対策として、ファイルごとに状態を戻すフックと、エージェントに後片付けの範囲を伝えることを挙げている |
| `nx affected` | 変更していないプロジェクトのテスト | スキップ判定そのものをテストした（下で詳しく）。main では毎晩全テストを回す |
| ESLint → Oxlint、tsc → bun check | 検査するツールそのもの | 速さの数字だけ。前のツールが拾っていた指摘を新しいツールも拾うかは書かれていない |
| shallow clone | git の履歴 | shallow だと履歴を読む処理が壊れる、として blobless clone（履歴は残し、ファイル本体だけ後から取る）を勧めている |

3行目は、私がいちばん気になった所です。検査ツールを速いものに替えるのは、検査の中身を替えることでもあります。ルールの対応や型の判定に差があれば、前は赤だったものが緑で通る。記事は1か月で型チェッカーを3回替えたと書いていますが、そのたびに何を比べたかは、本文からは分かりません（埋め込み画像のベンチマークに何か載っている可能性はあります）。

残りの手、たとえばランナーの交換や並列化、キャッシュは、何かを確かめずに済ませる手ではありません。並列数を半分にした件はむしろ逆で、速さは変わらず、不安定なテストが1本消えたと書かれています。

この表で一番大事なのは `nx affected` の行です。

> We hid a server change from Nx on purpose and all six shards skipped their tests and reported green. Now that fails the run.
>
> （サーバーの変更をわざと Nx から隠したら、6つのシャードがすべてテストをスキップして緑を返した。今はこれで実行が失敗するようにしてある。）

わざと壊して、緑が出ることを確かめてから塞いでいる。手を入れた仕組み自体をこうやって攻撃した話が書かれているのは、9項目のうちここだけです。夜間に main で全テストを回しているのも、記事はそう位置づけていませんが、同じ穴への2本目の網として働くと私は読みました。

`isolate: false` のほうで記事が挙げている対策は、状態を戻すフックとエージェントへの指示です。でもこれは、漏れを起こさないようにする対策で、漏れが起きたときに気づく仕組みではありません。片付け漏れが1件あれば、あるテストが別のファイルの残した状態に乗って、たまたま通るかもしれない。そういうテストは、`isolate: false` のままでは赤になりません。

## 再実行で済ませるエージェント

なぜ嘘の緑がそこまで問題なのか。記事のキャッシュの話に、近い例が書いてあります。

> That bug had been there all year. Nobody noticed because nobody was sitting there watching CI. The agents were, and they just retried instead of fixing the actual issue.

CI を一番よく見ていたのはエージェントで、エージェントはおかしな挙動を直さず、再実行で済ませていた。遅い、再実行が要るという目に見える症状があっても、1年見過ごされたわけです。ここからは私の推測ですが、嘘の緑はその症状すら出しません。エージェントが緑を見て次の作業に進むなら、誰も気づく機会がない。

記事の9番目の項目も、同じところを突いています。push 前のチェックを AGENTS.md に書かず、フックにした理由です。

> Put it in a hook rather than a line in AGENTS.md, because agents skip steps.

私はこれに全面的に賛成です。そして、同じ理屈をもう一歩進めたい。エージェントは手順を飛ばすし、おかしな挙動も直さず流すことがある。だとすると、速くするために何かを省いたら、その省いた部分がちゃんと赤を出せるかを、仕組みで確かめておく必要があります。Boardy は `nx affected` でそれをやった。`isolate: false` でも、同じことができるはずです。

たとえば、夜間の全テストを `isolate: true` でも回して、昼間の `isolate: false` の結果と食い違うテストを数える。前のファイルの残した状態に乗って通っているテストがあれば、隔離した側で赤になるはずです。あるいは、状態を残すテストと、その状態があると結果が変わるテストを対で置いて、フックが本当に片付けているかを見る。どちらも私は試していませんし、元記事にもありません。ただ、記事の著者がスキップ判定にやったことを、隔離の側にも当てはめただけです。

## 月4,300ドルの元が取れているかは分からない

最後に費用です。

> Our CI bill went from $230 a month to $4,300, but it's the cheapest money we spend on making agents faster.

約18.7倍で、月に4,070ドルの増加です。

ただ、元が取れているかは、記事の数字からは判断できません。月に何本の PR が出て、エージェントのセッションがどれだけ CI を待っていたかが書かれていないからです。「一番安い出費」というのは著者の実感で、読者が自分の CI に当てはめて検算できる形にはなっていません。

記事の締めは、次のボトルネックは自分がマージボタンを押す速さだ、という一文です。CI が2分になれば、人間の確認が残る。別の記事で読んだ DeepSeek Harness チームの設計メモにも、「今の設計では、単一タスクはモデルの能力で頭打ちになるが、マルチタスクは人間の注意力で頭打ちになる」という一文がありました。同じ地点に行き着いています。

## 持ち帰るなら1つ

CI を速くする手を1つ入れたら、それが嘘の緑を出せないかを、わざと壊して確かめる。

ランナーの交換は1行で最大40分の待ちを約10分にしましたが、これは何も省いていないので、壊れ方が増えません。危ないのは、そのあとの「省いて速くする」手のほうです。Boardy の記事で一番真似する価値があるのは、サーバーの変更を Nx から隠して、6つのシャードが緑を返すのを見たあの実験だと思います。
