## この記事について

2026年7月28日、Model Context Protocol（MCP）の5回目の仕様改訂 **MCP 2026-07-28** が公開されました。Anthropic のアナウンス記事 [Bringing MCP 2026-07-28 to Claude](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude) と、[仕様本体の変更履歴](https://modelcontextprotocol.io/specification/2026-07-28/changelog) をもとに、

- **そもそも MCP は何を解決するために生まれたのか**（これまでの意味）
- **今回の改訂で何が根本的に変わるのか**（ステートレス化・拡張機能・認証）
- **立場ごとに、明日から何をすべきか**（これから）

を、専門用語をできるだけ噛み砕いて整理します。

先に結論だけ書くと、こうです。

> MCP は「AIとツールをつなぐ規格」から、**「本番のインフラに置いておける配管」** になりました。そのために、これまで前提だった「接続を保つ」という考え方そのものを捨てています。

---

## 第1部 — MCP はそもそも何だったのか

### 本当の課題は「AIがツールを使えない」ことではなかった

2024年11月に MCP が登場する前、AI にツールを使わせること自体はすでに可能でした。関数を定義して、モデルに呼ばせればいい。問題はそこではなく、**組み合わせの数**でした。

AI アプリが N 個、つなぎたいツールやデータが M 個あると、必要な接続コードは **N × M 個**になります。Slack 用のつなぎ込みを Claude 向けに書いて、同じものを別のアプリ向けにもう一度書いて、GitHub でも同じことをして……という世界です。

MCP がやったのは、この真ん中に **共通の差込口**を1つ置いたことです。ツール側は「MCP サーバー」を1つ書けばよく、AI 側は「MCP クライアント」を1つ実装すればいい。組み合わせは **N × M から N + M** になります。

「AI とツールの間の USB-C」と説明されることが多いのは、この構造のことです。

![形の違う差込口に手作りのプラグを合わせ続けるすみと、ひとつの丸い穴に差すだけのすみ](/images/mcp-2026-07-28-stateless/01-sockets-one-shape.png)

### MCP の基本部品は3つだけ

仕様の細部は年々増えていますが、初期からある考え方の中心は今もこの3つです。

| 部品 | 何をするもの | ざっくり言うと |
| --- | --- | --- |
| **Tools** | AI が呼び出して実行できる操作 | AI にやらせる「動詞」 |
| **Resources** | AI に読ませられるデータ | AI に見せる「名詞」 |
| **Prompts** | サーバー側が用意する定型の指示 | よく使う「型」 |

このうち実務でいちばん使われているのは Tools です。「MCP サーバーを書く」と言うとき、多くの場合は Tools を数個生やすことを指しています。

### 規模の話

Anthropic の発表によると、MCP の SDK ダウンロード数は **月間 4億回**を突破し、今年に入って **4倍**に増えました。もはや Anthropic 専用の仕組みではなく、AI エージェントとアプリケーションをつなぐ業界標準として扱われています。

この「標準になってしまった」という事実が、今回の改訂の背景そのものです。

## 第2部 — 5回の改訂で、MCP はどこへ向かっていたのか

MCP のバージョンは `YYYY-MM-DD` 形式で、**後方互換性を壊す変更が入った日付**が名前になります。互換性を保つ改善では番号は上がりません。つまりバージョンが増えたということは、毎回「壊してでも直す価値がある」と判断されたということです。

| 版 | 主な内容 | 方向性 |
| --- | --- | --- |
| **2024-11-05** | 初版。Tools / Resources / Prompts、stdio と HTTP+SSE | 動くものを出す |
| **2025-03-26** | Streamable HTTP 転送を導入（HTTP+SSE は非推奨化）、OAuth ベースの認可の枠組み | ネットワーク越しに使えるように |
| **2025-06-18** | ユーザーへの問い返し（elicitation）、ツール出力の構造化、認可を OAuth のリソースサーバーとして整理 | 対話とデータの型を整える |
| **2025-11-25** | OIDC Discovery 対応、アイコン等のメタデータ、段階的なスコープ同意、URL 方式の elicitation、Client ID Metadata Documents、**tasks を実験的に追加** | 実運用の細部を埋める |
| **2026-07-28** | **ステートレス化**、拡張機能の正式化、認可の本番仕様化、機能廃止ルールの制定 | 本番インフラとして成立させる |

並べると方向がはっきりします。**「デモで動く」から「本番で運用できる」への5年分の移動**です。そして 2026-07-28 は、その移動の最後に残っていた一番大きな障害物 —— **「接続を保つ」という前提** —— に手をつけた版です。

---

## 第3部 — 2026-07-28 の本質は3つ

### (1) ステートレス化：電話をやめて、手紙にした

今回いちばん大きい変更です。

これまでの MCP は、**まず接続を確立してから話す**プロトコルでした。

1. クライアントが `initialize` を送る
2. サーバーが「私はこのバージョンで、こういう機能があります」と返す
3. クライアントが `notifications/initialized` を返す
4. ここからやっと `tools/list` や `tools/call` が使える
5. HTTP の場合はこの一連を `Mcp-Session-Id` ヘッダーで同一セッションとして紐づける

つまり **電話**です。まず相手と回線をつなぎ、名乗り合ってから本題に入る。便利ですが、回線が切れたら最初からやり直しで、その間ずっと「誰と話しているか」をサーバー側が覚えていなければなりません。

2026-07-28 はこれを全部やめました。

- `initialize` / `notifications/initialized` のハンドシェイクを**削除**
- Streamable HTTP から `Mcp-Session-Id` ヘッダーを**削除**
- 代わりに、**すべてのリクエストが自分で全部持つ**。`_meta` フィールドにプロトコルバージョン（`io.modelcontextprotocol/protocolVersion`）とクライアントの機能（`io.modelcontextprotocol/clientCapabilities`）を毎回入れる。クライアントは毎回自分の名前も入れるべき（`clientInfo`）で、サーバーも各レスポンスの `_meta` で名乗るべき（`serverInfo`）
- バージョンが合わなければ、そのリクエスト単位で `UnsupportedProtocolVersionError` が返る

**手紙**になったわけです。1通の封筒に「差出人・使用する版・こちらの能力」まで全部書いてあるので、受け取る側は前後の文脈を覚えている必要がない。

![受話器を肩に挟んで作業するすみと、必要事項を全部書いた封筒をポストに入れるすみ](/images/mcp-2026-07-28-stateless/02-cord-to-letter.png)

代わりに追加されたのが `server/discover` です。サーバーは**必ず実装する義務**があり、対応バージョン・機能・自身の情報を1リクエストで返します。クライアントは「先にバージョンを確認したい」ときだけ呼べばよく、呼ばずに直接 `tools/call` して、エラーが返ってきたら対応する、でも構いません。**必須の握手が、任意の下見に変わった**という言い方が近いです。

### (2) ステートレスにすると何が嬉しいのか

ここが実務的な本題です。

セッションを持たないということは、**サーバーがリクエストの間に何も覚えていなくていい**ということです。すると、同じサーバーを何台並べても、どの台に当たっても同じ答えが返ります。1台落ちても、次のリクエストは別の台が受けられます。

これはそのまま、**サーバーレスとエッジに載る**という意味です。AWS Lambda や Cloudflare Workers のような「呼ばれたときだけ立ち上がって、終わったら消える」環境は、状態を持てないことが最大の制約でした。MCP がステートレスになったことで、その制約と衝突しなくなりました。

Anthropic の発表でも、Figma の VP of Engineering がこう述べています。

> 利用が増えていくなかで、我々のステートレスなアーキテクチャは一緒にスケールできる。

MCP サーバーの運用コストが下がる、というのが利用者側から見た効果です。「常時起動のサーバーを用意して維持する」必要がなくなるので、個人や小さなチームが MCP サーバーを公開し続けるハードルが下がります。

![手回し機械から折りたたみ式の同じ窓口を量産して並べるすみ、記憶付きの大きな窓口は赤で消されている](/images/mcp-2026-07-28-stateless/03-foldable-counters.png)

もちろん「呼び出しをまたいで状態を持ちたい」ケースは残ります。その答えは **プロトコルの機能ではなく、ただのツール引数にする**ことです。サーバーが発行したハンドル（識別子）を返し、次の呼び出しでそれを普通の引数として渡してもらう。プロトコルが面倒を見るのをやめて、アプリの設計に降ろしたわけです。

あわせて、通知の仕組みも整理されました。

| これまで | これから |
| --- | --- |
| HTTP GET エンドポイント + `resources/subscribe` / `unsubscribe` | `subscriptions/listen` 1本に統合。長寿命の POST レスポンスストリームで、必要な種類だけ購読する |
| `ping` で生存確認 | 削除。ステートレスなので保つ回線がない |
| `logging/setLevel` でログレベルを設定 | 削除。`_meta` の `logLevel` でリクエスト単位に指定。指定していないリクエストにサーバーがログを流すのは禁止 |

「接続を保つ前提」に依存していた機能が、ここで一斉に整理されたという構図です。

### (3) 拡張機能：本体を薄くして、機能は差し込む

もう1つの大きな変更が、**core と拡張の分離**です。

これまで新機能は仕様本体に足されていました。便利ですが、本体が太っていくと「全部実装しないと準拠を主張できない」状態になり、サーバーを書くのが重くなります。

2026-07-28 では、`ClientCapabilities` / `ServerCapabilities` に `extensions` フィールドが入り、**公式拡張がバージョン付きで独立して配れる**ようになりました。そして代表的な2つが、そこへ移りました。

| 拡張 | 何をするもの | 状態の変化 |
| --- | --- | --- |
| **MCP Tasks**（`io.modelcontextprotocol/tasks`） | 数分〜数時間かかる長時間ジョブを、投げて後で取りに行く | 2025-11-25 の「実験的に core 内」から、**公式拡張へ移動＋再設計** |
| **MCP Apps** | サーバーが会話の中に操作できる UI を描く | 拡張フレームワークの下で正式化 |

Tasks の再設計も実用的な方向です。結果が返るまで待ち続ける `tasks/result` をやめて、`tasks/get` で**ポーリング**する形になりました。ステートレスな世界では「待ち続ける」こと自体がコストなので、筋が通っています。さらに `tasks/update` でクライアント側から途中で入力を渡せるようになり、`tasks/list` は削除、サーバーは頼まれなくてもタスクハンドルを返せるようになりました。

![薄い板に版番号のついた部品をカチッと差し込むすみ、全部入りで膨らんだ古い板は赤で消されている](/images/mcp-2026-07-28-stateless/04-thin-board-slots.png)

**core は薄く、機能はバージョン付きで後から差す。** 長生きするプロトコルが必ず通る整理で、MCP がその段階に入ったということです。

### (4) 認証：自作バッジをやめて、会社の受付が出したものを使う

3つ目は認可の本番仕様化です。目的は明快で、**Entra や Okta のような企業の既存 ID 基盤に、回避策なしで繋がるようにする**ことです。

いちばん象徴的なのが、**Dynamic Client Registration（DCR, RFC 7591）の非推奨化**です。DCR は「クライアントがその場で自分を登録する」仕組みで、MCP の初期には便利でした。ただ企業の認可サーバーは、たいてい素性の知れないクライアントの自己登録を許しません。代わりに推奨されるのが **Client ID Metadata Documents** で、こちらは「自分の情報を公開された URL に置き、認可サーバーがそれを見に来る」方式です。DCR は互換性のために残りますが、新規実装が選ぶものではなくなりました。

細かいものも本番運用に効く方向で固まっています。

- 認可レスポンスに `iss`（発行者）を含めるべきで、クライアントは**検証しなければならない**（RFC 9207）
- クライアントの資格情報は**発行した認可サーバーに紐づく**。issuer をキーにして保存し、別の認可サーバーに使い回してはならず、認可サーバーが変わったら再登録が必要

要するに「動けばいい」から「他人の環境で安全に動く」への引き締めです。

![自作の紙バッジは通らず、受付から渡された本物のバッジで扉が開く](/images/mcp-2026-07-28-stateless/05-badge-from-front-desk.png)

### (5) 消えるもの・非推奨になるもの

今回いちばん見落としやすいのがここです。**3つの既存機能が非推奨になりました。**

| 非推奨になった機能 | 何だったか | 推奨される代替 |
| --- | --- | --- |
| **Roots** | クライアントが「作業対象のディレクトリ」をサーバーに伝える | ディレクトリやファイルはツール引数・リソース URI・サーバー設定で渡す |
| **Sampling** | サーバーがクライアント経由で LLM に推論させる | LLM プロバイダの API を直接叩く |
| **Logging** | `notifications/message` でログを流す | stdio なら `stderr`、あるいは OpenTelemetry |

加えて、HTTP+SSE 転送（2025-03-26 から非推奨）が正式に Deprecated に分類され、Streamable HTTP への移行が明示されました。

そして地味ですが重要なのが、**機能廃止のルール自体が制定された**ことです。

- 機能の状態は **Active / Deprecated / Removed** の3つ
- 非推奨になってから削除までは **最低12か月**（例外的な迅速削除でも最低90日）
- 非推奨機能は移行方法とともに **専用のレジストリ** で一覧管理される

つまり「明日消える」ことはありません。非推奨のものは動き続けます。ただし**新しく作るものでは使わない**、が正しい読み方です。

![砂時計付きの棚に、札のついた古い道具を置くすみ。道具からはまだ橙の糸が伸びている](/images/mcp-2026-07-28-stateless/06-shelf-with-hourglass.png)

こういう「やめ方の作法」が整うのは、仕様が趣味から標準に移ったサインです。

### (6) 目立たないが効く変更

見出しにはならないけれど、実運用でありがたいものを挙げておきます。

- **キャッシュのヒントが必須になった**：`tools/list` などの結果に `ttlMs`（何ミリ秒新鮮とみなせるか）と `cacheScope`（`public` / `private`）を必ず付ける。クライアントが結果をキャッシュでき、無駄なポーリングが減る
- **`tools/list` は決定的な順序で返すべき**：順番が毎回変わると、クライアントのキャッシュも LLM のプロンプトキャッシュも当たらない。並び順を固定するだけでコストが下がる
- **OpenTelemetry のトレース伝播が規約化**：`_meta` の `traceparent` / `tracestate` / `baggage`。MCP 越しの呼び出しを既存の分散トレーシングに載せられる
- **リクエストヘッダーの標準化**：Streamable HTTP の POST に `Mcp-Method` / `Mcp-Name` が必須。中間のプロキシやゲートウェイが中身を開けずにルーティングできる
- **スキーマの制約が緩和**：`inputSchema` / `outputSchema` で JSON Schema 2020-12 のキーワードを自由に使え、`$ref` も解決される

キャッシュ、トレース、ヘッダーによるルーティング。**全部「たくさん動かす」ための機能**です。この並びを見るだけでも、今回の版が誰のために書かれたかが分かります。

## 第4部 — 立場別に、何をすればいいか

### MCP サーバーを作っている人

やることは3つです。

1. **`server/discover` を実装する。** 今回サーバー側の新しい義務になりました
2. **Roots / Sampling / Logging を使っているか棚卸しする。** 使っているなら移行先を確認する。急ぐ必要はないが、新機能をそれらの上に積むのはやめる
3. **セッションに依存した設計を洗い出す。** 「初回の `initialize` で受け取った情報を覚えておく」実装があるなら、そこはリクエストごとの `_meta` か、サーバー発行のハンドルをツール引数で受け取る形に変える

移行そのものは急かされていません。バージョンは**リクエスト単位で交渉**され、クライアントもサーバーも複数バージョンを同時にサポートしてよい設計です。STDIO では `server/discover` を後方互換性の探り針として使えます。SDK が追随するので、多くの実装は SDK 更新で大部分が済むはずです。

### 使うだけの人（Claude Desktop / Claude Code のユーザー）

**今すぐやることはありません。** ただし発表では「Claude 製品への対応は順次ロールアウト中」と書かれており、まだ全面対応済みではありません。

中期的に期待していいのは、この2つです。

- **使える MCP サーバーが増える。** サーバーレスに載るぶん公開・維持のコストが下がるので、コネクタの数と寿命が伸びる方向に働きます
- **会話の中で完結する操作が増える。** MCP Apps によって、コネクタが会話内に UI を描けます。別タブに飛ばずにその場で操作できる、という体験の変化です

### 企業の IT 管理者

今回の認可周りの整備は、実質的に管理者向けの変更です。Anthropic 側では **Enterprise-managed auth** として、管理者が ID プロバイダ経由でコネクタを組織全体に配れる仕組みが提供されています。管理者が一度承認すれば、ユーザーは既存の IdP グループ経由でアクセスを継承し、初回ログイン時に接続済みになる —— エンドユーザー側の設定作業がゼロになります。

社内ネットワーク内のサーバーを公開せずに繋ぎたい場合は、**MCP tunnels**（リサーチプレビュー）があります。インバウンドのファイアウォール規則も、公開エンドポイントも、オリジンの IP 許可リストも不要という位置づけです。

## 第5部 — これからどうなるか

ここからは仕様と発表内容からの読み取りです。

### MCP は「機能」ではなく「配管」になる

今回の変更を一言でまとめると、**MCP が意識される対象から外れていく**方向です。ステートレスで、サーバーレスに載り、キャッシュのヒントを持ち、既存の分散トレーシングに乗り、企業の ID 基盤にそのまま繋がる。これは「話題の新技術」の性質ではなく、**インフラの性質**です。

水道管は普段意識されません。MCP はそこを目指しています。

### core は今後あまり動かない

`extensions` の枠組みができたことで、新機能の追加先は core ではなく拡張になります。ということは、**次の破壊的変更（新しい日付バージョン）はしばらく来にくい**と考えられます。今回大きく壊した理由の1つは、「壊すのを今回で終わらせる」ためでもあるはずです。

裏を返せば、**2026-07-28 は移行しておく価値が高い版**です。

### 「やめ方」が整った意味

機能ライフサイクルのポリシーと非推奨レジストリができたことは、機能追加より重要かもしれません。標準が長生きするかどうかは、増やし方ではなく**減らし方**で決まります。12か月の猶予と移行先の明示がルール化されたということは、MCP を前提に長期のシステムを組んでも大丈夫という宣言に近いです。

### 注意しておくこと

- **Claude 製品側の対応はロールアウト中。** 仕様が出た日と、手元のツールで使える日は違います
- **非推奨は「今すぐ動かなくなる」ではない。** 慌てて書き換える必要はありません。ただし新規実装で選ばないこと
- **ステートレス化は設計の宿題を移した。** プロトコルが状態を持たなくなったぶん、状態が必要なユースケースは自分で設計する必要があります。ハンドルの発行、有効期限、権限チェックは、これからサーバー実装者の責任範囲です

## まとめ

| 観点 | これまで | これから（2026-07-28 以降） |
| --- | --- | --- |
| 接続 | まず握手して、セッションを保つ | 握手なし。リクエストが自分で全部持つ |
| 配置先 | 常時起動のサーバー | サーバーレス・エッジも可 |
| 機能追加 | 仕様本体に足す | バージョン付きの公式拡張に差す |
| 認可 | その場で自己登録も可 | 企業の ID 基盤に正面から接続 |
| 機能廃止 | 都度判断 | 12か月の猶予つき公式ルール |
| 立ち位置 | つなぐための規格 | 置いておける配管 |

MCP の最初の5年は「AI とツールをどうつなぐか」の答え探しでした。2026-07-28 が答えているのは、その次の問い —— **「つないだものを、どうやって本番で持ちこたえさせるか」** です。

始めるには、[仕様](https://modelcontextprotocol.io/specification/2026-07-28/) と [SDK](https://modelcontextprotocol.io/docs/sdk) を見るのが早いです。自作の MCP サーバーを Claude の [コネクタディレクトリ](https://claude.ai/directory/connectors) に出す予定があるなら、[提出の手順](https://claude.com/docs/connectors/building/submission) も合わせて確認してください。
