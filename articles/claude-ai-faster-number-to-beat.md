先に結論だけ書くと、こうです。

> Anthropic は2週間で claude.ai とデスクトップアプリを約3倍速くしました。3,000件を超える変更の大半を書いたのは Claude です。でも私がこの記事でいちばん重要だと思ったのは、Claude が書いた修正ではありません。**計測の単位を「秒」から「命令数」に変えたこと**です。壁時計の時間はノイズが多すぎて、エージェントが「勝った／負けた」を判定できない。決定的に数えられる数字に置き換えたとき、パフォーマンス改善は**エージェントが解ける問題**になりました。

## この記事について

扱うのは、Anthropic の開発者向けブログ claude.dev に載った **"How we made claude.ai 3x faster in two weeks"**（2026年9月下旬）です。スプリントそのものは8月に行われました。Claude Code を作った Boris Cherny 氏も Threads で紹介していて、「プロンプトと手法も載せた」という触れ込みです。

**正直な開示。** 私の作業環境のネットワーク設定で claude.dev も、それを報じた Help Net Security などの記事も開けず、**原文は読めていません**。以下の数字と事実は、検索エンジンが返した原文と報道の要約から組み立てたものです。原文に載っているというプロンプトは確認できていないので、この記事では扱いません。数字は要約どうしで食い違いがないものだけを使いました。

## 何をしたのか

### 結果

| 計測（75パーセンタイル） | 前 | 後 |
| --- | --- | --- |
| claude.ai を新しく開いて入力できるまで | 約3.1秒 | **0.55秒**（5.6倍） |
| Claude Code のデスクトップ会話を開始 | 837ms | **347ms** |
| デスクトップアプリで会話を読み込む | 1.35秒 | 0.5秒未満 |
| クラウドセッションでメッセージを送信 | 928ms | **48ms**（−95%） |

13項目の幾何平均で **3.1倍**。2週間で**3,000件超**の変更をマージし、**顧客に影響する障害もロールバックも出なかった**そうです。

### 体制

- Slack のひとつのチャンネルにエンジニアと Claude がいる。Claude は **Claude Tag（ベータ）** 経由で、Opus 5.5 相当の社内研究モデル
- Claude がベンチマークを作り、PR を開き、デプロイを見張る
- 人間は**目標を決め、判断が必要なところを判断し、すべての変更を承認する**

### 手順

1. **どこを速くするかを実データで決める。** Real User Monitoring（実ユーザーの計測データ）を見て、利用の約95%を占める**4つのユーザー行動**に絞った
2. **決定的なベンチマークを作る。** 壁時計の時間はノイズが多すぎて、コードの合否判定に使えない。そこで Claude に次のような「数えられる数字」を作らせた
   - Valgrind で計る **CPU 命令数**
   - **React のコミット回数**
   - **V8 の関数呼び出し回数**
   - スタイル再計算、DOM 変更、レイアウトシフトの回数
3. **ラボの改善が本番に効いたかを、実ユーザーのデータで確かめる**
4. **ラチェット（逆戻り防止）を CI に入れる。** その経路の命令数を増やす PR は CI で落ちる。そして**命令数が下がったら、毎日のジョブが上限を自動で引き下げる**

### 印象的だった具体例

ある2つのホットパスを Valgrind でプロファイルすると、片方の命令の**4分の1が megamorphic な辞書検索**で、しかも**同じメッセージ ID を3回ずつ引き直していた**。1時間後、命令数は2つの経路でそれぞれ **48%と31%** 減り、壁時計の時間は **78%と44%** 減っていた。

### 安全に出すための仕掛け

- 約**200個のフィーチャーフラグ**で段階的に出し、後から半分以上を削除
- リスクの高い変更は、まず社員向けに出す
- 体感速度のための製品上の判断もしている。たとえば **static composer**。React のページ全体が読み込み終わる前に、入力欄だけ先に出して打ち始められるようにした

## 私の見解 — エージェントに渡すべきは「タスク」ではなく「勝ち負けの判定」

ここからは原文にない、私の読み方です。

### 秒はエージェントの報酬として使えない

普段 Next.js でパフォーマンス改善をするとき、私は Lighthouse や Web Vitals の**秒数**を見ています。でも正直、同じページを3回計ると3回とも違う数字が出る。100ms 縮めたつもりが、ノイズに埋もれて本当に縮んだのか分からない。人間なら「たぶん速くなった」と感覚で進められますが、**エージェントはそうはいきません**。

エージェントに「速くして」と頼むと、修正を入れて計測し、数字が良くなったかで次の手を決めます。その数字が毎回ぶれるなら、エージェントは**ノイズを成果と取り違える**か、**本物の改善をノイズとして捨てる**。どちらにしても、同じ場所をぐるぐる回ることになります。

命令数は違います。同じコードを同じ入力で走らせれば、**毎回同じ数字**が出る。1命令減れば1命令減ったと分かる。これで初めて、「この修正は効いたか」という問いに機械が答えられるようになります。

原文の要約に「Claude は倒すべき数字があるときに一番よく働いた」という趣旨の一文がありました。私はこれがこの記事の核心だと思っています。**Claude が速さを生んだのではなく、「数えられる数字」が、Claude の作業量を速さに変換した**。

### ただし、命令数は「代理指標」でしかない

一方で、ここには落とし穴もあります。命令数はユーザーの体感そのものではありません。**代理指標**です。

例の数字をもう一度見ると、命令数 −48% で時間は −78%、命令数 −31% で時間は −44%。比例していません。命令数では見えない、キャッシュミスやメモリ割り当て、I/O 待ちが効いているはずです。逆に言えば、**命令数は減ったのに体感は変わらない修正**も、たぶん大量にありえます。

代理指標を最適化し続けると、指標だけ良くなって本当の目的から外れていく。いわゆるグッドハートの法則です。そしてエージェントは人間よりずっと速く、ずっと愚直に指標を最適化します。

Anthropic はここを**手順2と手順3の組み合わせ**で押さえています。高速に回すループは命令数で判定し、それが本当に効いたかは実ユーザーのデータで確かめる。**速いけれど嘘をつく計器と、遅いけれど正直な計器を分けて使っている**わけです。私が真似するなら、この二段構えは絶対に外せないと思います。

### ラチェットは、エージェントの「忘れっぽさ」を補う

もうひとつ感心したのが、CI のラチェットです。命令数が下がったら、毎日のジョブが上限を自動で引き下げる。

これはエージェントの弱点をうまく補っています。エージェントはセッションをまたいで「前回ここを速くした」を覚えていません。3,000件の変更のうち、どれかが別の誰かの改善を黙って打ち消していても、エージェント自身は気づけない。**記憶を CI という外部装置に持たせた**と言えます。改善は上限として固定され、逆戻りはマージの時点で機械的に止まる。

3,000件の変更で障害ゼロという数字は、Claude が優秀だったというより、**200個のフラグ、社員への先行リリース、ラチェットという「失敗しても戻れる仕組み」**の成果だと私は読みました。

### 自分のプロジェクトでやるなら

Next.js と Rails で仕事をしている立場で、明日から真似できそうなことを書いておきます。

- **Next.js**：Web Vitals の秒数ではなく、**React のコミット回数や再レンダリング回数**を React Profiler で数えて CI に載せる。JS バンドルのサイズも決定的な数字なので、ラチェットにしやすい
- **Rails**：レスポンス時間ではなく、**1リクエストあたりの SQL クエリ数**を数える。N+1 が1個増えたら CI で落とす。これは昔からあるテクニックですが、エージェントに改善させる前提だと価値がまるで変わります
- **Postgres**：クエリの実行時間ではなく、`EXPLAIN (ANALYZE, BUFFERS)` の**バッファ読み込み数**を見る。キャッシュの温まり具合に左右されにくい
- **体感速度の工夫は別枠で**：static composer のような「先に入力欄だけ出す」判断は、数字の最適化からは出てきません。Next.js なら Streaming や Suspense で骨組みを先に返すのと同じ発想で、これは**人間が決める製品の判断**です

最後の1つが、原文でいう「人間は判断をする」の中身だと思います。**何を数えるか、どこまでを代理指標に任せるか、どこで体感のために数字を曲げるか**。そこを人間が決めれば、残りの3,000件はエージェントに渡せる。この記事が「Claude が3倍速くした」と読まれがちなのは、少しもったいないと思っています。
