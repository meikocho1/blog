## この記事について

Thomas Ptacek 氏（[@tqbf](https://sockpuppet.org/blog/)）が2026年8月20日に公開したエッセイ **"Stop Making TUIs"** を扱います。Hacker News には翌8月21日に投稿され、428ポイント・561コメントを集めました。

この記事は2部構成です。

- **第1部**：Ptacek 氏が何を主張し、どの反論をどう潰したか（原文の事実）
- **第2部**：**この主張の本体について私が考えていること**。原文にも書かれていない読み方

後半のほうが長いです。原文の要約は原文を読めば済むので。

先に開示しておきます。読んだのは原文と Simon Willison 氏の8月21日のリンク記事です。HN スレッドは投稿本体と票数・コメント数だけ確認して、561件のコメントは読み切れていません。だから「HN ではこういう反論が優勢だった」という話は書けません。私は macOS のネイティブアプリをエージェントに作らせた経験もありません。第2部は原文の論理構造だけを相手にした解釈で、実測ではありません。

---

## 第1部 — Ptacek 氏が何を言ったか

### 結論を先に

> CLI と TUI を1つにまとめて語るな。CLI は代替不可能なものだが、TUI は1970年代のテレタイプ端末の制約に真空パックされた形式にすぎない。そして TUI が生き残った理由は2つしかない。モデムと、Unix 屋が Motif を覚えたくなかったこと。エージェントが GUI の値段をほぼゼロにした今、その2つはもう理由になっていない。

原文の一文がいちばん強いので、そのまま引きます。

> command-line interfaces and terminal user interfaces are both products of the 1970s, shrink-wrapped around the constraints of teletype interfaces and dumb video terminals. （中略）But these tendencies are intrinsic to TUIs, and not to CLIs. CLIs have purposes for which they're irreplaceable. Building a CLI is almost always a good idea. Building a TUI almost never is.
>
> （CLI と TUI はどちらも1970年代の産物で、テレタイプ端末とダム端末の制約に真空パックされている。だがこの性質は TUI に固有のもので、CLI のものではない。CLI には代替不可能な用途がある。CLI を作るのはほぼ常に良い判断だ。TUI を作るのはほぼ常にそうではない。以下、引用の訳はすべて拙訳）

ここが読み飛ばされやすい。この記事は「ターミナルをやめろ」ではありません。**CLI は守り、TUI だけを撃つ**という切り分けが最初に置かれています。

![「同じ箱」に詰められていたものを割り機で割るすみ。出てきた左の箱には配管の口があり、右の箱は偽のボタンとスクロールバーで膨れて口がない](/images/tui-is-a-fused-frontend/01-cli-tui-split.png)

### 撃たれているのは1999年のエッセイ

Ptacek 氏はまず Neal Stephenson 氏の1999年の "In The Beginning Was The Command Line" を名指しします。あのエッセイが HCI の分野を20年後退させた、と。

Unix 屋を、業界全体を肩に担いだモーロック族として描き、GUI を使う側をイーロイ族として描く。よくできたファンサービスであり、だからこそ「我々の分野の聖典」になった。25年経ってほとんど成立していないのに。

そのうえで出てくるのが、この記事でいちばん引用される一文です。

> TUIs exist for just two reasons: modems, and because Unix nerds didn't want to learn Motif.
>
> （TUI が存在する理由は2つしかない。モデムと、Unix 屋が Motif を覚えたくなかったことだ。）

Ptacek 氏は Motif を擁護しません。1990年代半ばに少し触って、その後29年 UI 開発から遠ざかったと書いています。curses のほうが5分で覚えられた。つまり「TUI は正しかったから残った」ではなく「GUI 側の開発体験が地獄だったから逃げた」という説明です。

### 反論を1つずつ潰していく

エッセイの中盤は、TUI 擁護論への応答で構成されています。ここは原文が丁寧なので、要点だけ。

**「TUI は情報密度が高く、経済的で、キーボードで完結する」**。Ptacek 氏はこれを真だと認めます。ただし「〜だけが」と書いたら嘘になる、と。GUI が密度を持てないのではなく、GUI が nerd 向けに設計されていないだけ。密で経済的な GUI を作るのを妨げているものは何もない。実例として Bloomberg ターミナルを挙げています。

だから彼にとって、Magit や Lazygit の良さは GUI をやめる理由ではなく、**GUI でやるべき仕事が残っている証拠**になります。

**「TUI は SSH 越しに動く。prod に UI が必要ならそれは TUI だ」**。ここへの応答が、私が第2部でいちばん重く見る一文です。

> you probably don't need a user interface on prod. You need a command line interface on prod that a user interface on your Macbook can drive.
>
> （prod にユーザーインターフェースは要らないだろう。prod に必要なのは CLI で、それを手元の Macbook の UI が駆動する形だ。）

bpftrace で何かやった人なら、ハッシュ記号で棒グラフを3回目に組み立てるころには骨身に染みているはずだ、と。前例として Emacs TRAMP を挙げています。SSH 接続を隠し、リモートのファイルに対してネイティブな（望むならグラフィカルな）編集体験を出す仕組み。LSP も Magit も動く。

![本番側の柱には画面がなく裸のレバーだけがあり、すみは手元の自作コンソールから長いケーブルでそれを引いている。結果だけが紙テープで戻ってくる](/images/tui-is-a-fused-frontend/02-prod-cli-local-ui.png)

**「TUI はアクセシブルだ」**。これは「おそらく偽」と書かれています。SwiftUI は視覚ツリーと意味的なアクセシビリティツリーの2本を持っている。TUI 側でも charmbracelet/huh のように真面目に取り組んでいるものはある。ただし結論は限定的です。

> I'm not here to tell you TUIs can't be accessible; just that accessibility is not a reason to prefer TUIs to GUIs.
>
> （TUI がアクセシブルになれないと言いたいのではない。アクセシビリティは TUI を GUI より選ぶ理由にはならない、と言いたいだけだ。）

**「TUI はクロスプラットフォームだ」**。これだけは彼が認めます。原文では "one strong argument"、唯一の強い論拠という扱い。エージェントに Windows と Linux のネイティブ UI を書かせれば、それなりのものは出てくると思っている。ただし彼は Windows と Linux のデスクトップを持っておらず、確かめられない。

論者が自分で潰せなかった論点を「これは強い」と書いて残しているのは、エッセイとしては誠実な形だと思います。

### 実際に彼がやっていること

第1部の最後に、手順の話。ここは読者が真似できる部分なので事実だけ並べます。

彼は skill を集めるところから始めています。ceorkm 氏の macOS デザイン skill、タイポグラフィの skill、Paul Hudson 氏（twostraws）の SwiftUI skill、それに Airbnb の Swift 言語 skill。最後のひとつを入れる理由は「生成されるコードが慣用的かどうかを、まだ気にする性分だから」。

そのうえで `computer-use` 系（Codex 側の呼び名は何であれ）を有効にしておけと書いています。理由が具体的です。投げてから昼食を作りに行き、戻ってきたときに「デバッグして楽しい程度には動くアプリ」があってほしい。それはエージェントがアプリを**見て動かせる**ときにずっとうまく回る、と。

それから、最大の QoL 改善として挙げているのが Xcode を一度も開かないこと。友人の Josh 氏が Makefile 駆動のビルドを組んだ（`tqbf/mdv` を自分でコンパイルしようとした副産物）ので、それを新規プロジェクトごとに Claude にコピーさせている。

彼の工程は最終的にこれだけになります。テンプレートアプリのディレクトリ（`tqbf/swiftui-app`）をコピーし、そこで Claude か Codex を開き、作りたいものを言う。

成果物は Apple TV とRoku TV と Denon のレシーバを叩けるメニューバー常駐のユニバーサルリモコン、といった類のものです。そしてここに注記が入ります。

> (I have no intention to distribute them). They're artifacts of me making my computer do stuff for me, the way I want it to.
>
> （これらを配布する意図はない。自分のコンピュータに自分の望むやり方で仕事をさせた、その痕跡にすぎない。）

締めの一文はこうです。

> We build terminal interfaces because we have to, not because we should.
>
> （我々がターミナルインターフェースを作るのは、そうしなければならないからで、そうすべきだからではない。）

## 第2部 — 私の見解

### 結論を先に

> このエッセイの本体は「GUI のほうが良い」ではない。**prod には CLI を置き、UI は手元から駆動する**という一文のほうだ。これは見た目の趣味ではなくアーキテクチャの主張で、TUI の罪は古いことではなく、**エンジンとフロントエンドを1つのプロセスに融合させてしまうこと**にある。そして GUI が安くなったのは初版だけで、配布のコストは1円も下がっていない。だからこの主張は「自分ひとりのための道具」では正しく、「配るための道具」では成立しない。

### 中心にあるのは分離の話だ

Ptacek 氏は SSH への反論として、ほとんど通過するように書いています。prod に要るのは CLI で、それを手元の UI が駆動する。

私はこれが記事の中でいちばん再利用できる文だと思います。理由は、この文が UI の趣味について何も言っていないからです。

言っているのは、**コアと表示面を別のプロセスに置け**ということです。prod 側に置くのは引数を取って結果を吐く機械。人間に見せる仕事は、その出力を受け取る別の何かがやる。それが SwiftUI アプリでも、ブラウザでも、`jq` にパイプするシェルでも、Grafana でも構いません。境界がプロセス境界として存在していることが要点です。

この読み方をすると、TUI がなぜ狙われたのかが変わって見えます。**TUI は、その境界を消すことでしか成立しない形式だから**です。

curses アプリは、状態も描画もキー入力の解釈も、ぜんぶ同じプロセスの中で持ちます。画面がインターフェースであって、その下に呼び出し可能な API が残るとは限らない。というより、TUI を先に作った場合、まず残らない。画面を描く都合でロジックが分解されていくので、あとから「この機能だけスクリプトから呼びたい」が通らなくなる。

CLI は逆です。CLI は境界そのものです。引数と標準出力という細い口しかないから、コアと表示面が最初から分かれている。だから Ptacek 氏の「CLI はほぼ常に良い判断」と「TUI はほぼ常にそうではない」は、見た目の新旧では説明できません。**片方は境界を作る形式で、もう片方は境界を潰す形式**だから、評価が真逆になる。

![左は全体を溶接で封じられて開かない塊の機械。右は二段に分かれた機械で、すみが上段を持ち上げて外し、別形状の予備の上段が足元に待っている](/images/tui-is-a-fused-frontend/03-fused-vs-separated.png)

これが分かると、記事の処方も変わります。「TUI を作るな」を字面で受け取ると、次に作るものを GUI にするかどうかの話になる。そうではなくて、**まず CLI を作り、表示面を後から選べる状態にしておけ**、が実行できる形です。そして CLI が先にあるなら、そのうえに薄い TUI を貼るのは何も悪くない。`fzf` や `gh` の対話モードがそうです。悪いのは TUI が唯一の入口になっている状態です。

私は Ptacek 氏がこの順序で書かなかったのは損だったと思っています。彼の結論は正しいのに、いちばん強い根拠が SSH 論への反駁の中に埋まっているので、読者は「GUI 派 vs ターミナル派」の話として受け取る。実際 HN のタイトルだけを見た人の反応はそうなっていました。この構図で議論が始まると、勝ち負けは趣味の問題になります。分離の話なら、趣味の話ではありません。

### 安くなったのは初版だけだ

もうひとつ。Ptacek 氏の主張が成立する範囲を、彼自身が括弧の中で限定しています。

配布する意図はない、という一文です。

私はこれを軽い注記だとは思いません。ここが主張の適用範囲を決めています。

このブログでは以前、[「安くなったのはコードではない、他人への義務だ」](/articles/software-for-one-cost-of-users)という記事を書きました。Adam Waxman 氏の "Software for One" を扱ったもので、要点は、個人アプリのコストの大半は最初からコードではなく、消えたのは「他人に対して負う義務」のほうだった、というものです。Robin Sloan 氏が2020年に家族4人向けのメッセージアプリを作ったとき、制作1週間のうち半分がコード署名の地獄に溶けています。

同じ構図がここにあります。エージェントが崩したのは「動く初版までの距離」です。崩していないものを並べると、こうなります。

コード署名と公証。OS メジャーバージョンごとの追従。3つのプラットフォームぶんの UI。他人のマシンで再現しないバグ。他人の期待。そして、他人の期待に応え続けるという時間の約束。

TUI が世界に大量にある理由の少なくとも一部は、この列にあります。vim、htop、tmux、lazygit、k9s、mutt。全部、**配られている**ソフトウェアです。TUI はそこで、配布コストをほぼゼロにする形式として機能してきました。ターミナルがあれば動く。tarball とバイナリ1個で終わる。OS の UI フレームワークのバージョン地獄に入らない。

そして Ptacek 氏が唯一潰せなかったと認めた論拠、クロスプラットフォーム性は、まさにこの列の別名です。配布しないなら、その論拠は効きません。手元の Mac1台しか相手にしないので。配布するなら、その論拠が支配的になります。

つまり "Stop Making TUIs" は、こう読むと矛盾がなくなります。

- **自分ひとりのための道具**：ほぼ全面的に正しい。TUI を選ぶ理由はもう残っていない
- **配るための道具**：成立しない。彼が唯一認めた論拠が、そのまま最大の論拠になる

そして世界にある有名な TUI は、ほぼ全部が後者です。彼の主張は正しく、そして彼が撃ちたかった対象にはあまり当たっていない。私はここが一番惜しいと思っています。

![動く初版までの坂はなだらかになったのに、その先の配布の壁が同じ高さで残っている図を、すみが見上げている](/images/tui-is-a-fused-frontend/04-first-version-only.png)

### モデムでも Motif でもない第3の理由

「理由は2つしかない」という主張は、反例を1つ挙げれば削れます。挙げます。

**CLI 型のコーディングエージェントは、いまだに TUI です。**

Claude Code のコマンドラインは TUI です。Codex CLI も TUI です。しかもこれは「GUI を作る余裕がなかったから」ではありません。Claude Code にはデスクトップアプリも Web もあります。GUI 版が存在したあとも、CLI 版は TUI のまま残っている。

理由はモデムでも Motif でもないと思います。**埋め込まれる先が端末だから**です。

エージェントの実行環境は、ssh 先のサーバ、tmux のペイン、CI のジョブ、コンテナの中、他のツールが起動するサブプロセス、です。この列に GUI は入れません。プロセスとして起動され、標準入出力で会話し、終了コードを返せる形でなければ、そもそも置き場所がない。

これは1970年代の遺物ではありません。2026年の実行環境の制約です。Ptacek 氏の二分法（モデム／Motif 忌避）には、この第3の理由の枠がありません。

面白いのは、これが彼の主張と衝突しないことです。彼の分離論で読めば、Claude Code の TUI は「CLI の上に貼られた薄い表示面」であって、境界を潰した TUI ではない。`claude -p "..."` は引数を取って標準出力を吐きます。エンジンは別にある。だから合格です。

だとすると、彼の主張はもう一段だけ書き換えられます。

> TUI が悪いのではない。**TUI しかない**のが悪い。

私はこの形なら、配布されるソフトウェアにもそのまま適用できると思っています。

![端末の枠の中にある作業台で、すみが窓枠を組んで枠の外に手渡している。枠の底は太いケーブルでどこかに差し込まれている](/images/tui-is-a-fused-frontend/05-agent-in-terminal.png)

### 1つだけ持ち帰るなら

次に個人ツールを書くとき、UI の形式を先に決めるのをやめること。

決める順番はこうです。引数と出力を持つコアを1つ作る。それを叩くものを、必要になった時点で足す。手元で毎日使うものなら、2026年のエージェントはネイティブ GUI をたぶん一晩で出してきます。ssh 先で使うなら、コアだけをそこに置いて、駆動は手元からやる。

TUI が要るかどうかは、その次に考えれば間に合います。

そして配るソフトウェアなら、Ptacek 氏の記事は判断材料としてそのまま使えません。彼が自分で潰せなかったと書いた論拠が、あなたの側では最大の論拠になっているからです。
