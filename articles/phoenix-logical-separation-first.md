先に結論だけ書くと、こうです。

> Microservices の**論理的な分離**は欲しい。でも**物理的な分離**は必要になるまでやらない。

Phoenix に惹かれている理由を自分で言語化しようとして、たどり着いたのがこの一行でした。リアルタイム（Channels や LiveView）が好きだから、ではありません。順序が逆で、リアルタイムは結果のほうです。

先に断っておくと、この記事は運用報告ではありません。大規模本番で BEAM を回した経験にもとづく話ではなく、設計判断の言語化です。数字が出てくる箇所はありません。

## この立場自体は、まったく新しくない

「まずモノリスで作れ、分割は必要になってから」は、Sam Newman も DHH も言ってきたことです。modular monolith、majestic monolith、いろいろな名前がついています。目新しさはありません。

問題は、この主張がたいてい**負け惜しみとして使われてきた**ことです。Microservices を組む体力がないチームが、分割しない理由を後付けするときの言い回しになっていた。私自身、この言い方には長いこと胡散臭さを感じていました。

## BEAM では、この主張が言い訳にならない

理由ははっきりしています。ほとんどの処理系で「論理的分離」と呼ばれているものは、**実行時には何も守られていない**からです。

モジュールを分け、レイヤーを切り、依存の向きを決める。それはすべてコーディング規約です。誰かが `import` を一本足せば壊れます。共有された可変状態は、設計図の上でどれだけ分離されていても、メモリの上では同じ場所にあります。だから「本気で分離したいならプロセスを分けろ、つまりネットワーク越しにしろ」という話になる。Microservices が買っていたのは、**分離を強制してくれる物理的な壁**でした。

BEAM は、この壁を別の場所に置いています。

BEAM のプロセスはそれぞれ独立したヒープを持ちます。共有可変状態がありません。通信はメッセージパッシングだけです。プリエンプティブにスケジューリングされるので、1つのプロセスが暴走しても他が止まりません。そしてスーパーバイザが、落ちたプロセスを決められた戦略で再起動します。

つまり、隔離・再起動・メッセージ通信という、Microservices が Kubernetes とネットワークを使って手に入れていたものを、**1つの deployment unit の中で処理系が保証している**。規約ではなく、処理系が。

ここが、私が Phoenix に感じている魅力の中心です。「分割しない」という選択が、諦めではなく設計判断になる。

![チョークで引いた線は猫に踏み越えられるが、同じ線が本物の壁になると猫は止まる](/images/phoenix-logical-separation-first/01-convention-vs-wall.png)

## 何が減るのか

構成として消えるものを並べると、こうなります。

| 従来なら足していたもの | BEAM/Phoenix でのかわり |
| --- | --- |
| Realtime 基盤（Pusher, Socket.io + Redis） | Phoenix Channels / PubSub / Presence |
| キャッシュ・軽い共有状態（Redis） | ETS / GenServer / Registry |
| ジョブキュー（Sidekiq, SQS） | Oban（実体は Postgres） |
| サービス間の死活監視・再起動 | Supervision tree |
| サービスディスカバリ | libcluster + 分散 Erlang |

deployment unit が減れば、CI パイプラインも、サービス間契約も、デバッグのために横断するログの本数も減ります。これは効きます。

## ここまでが主張で、ここからが自分への反論

上の表は、書いていて自分でも気持ちよくなってしまう類のものです。だから自分で刺しておきます。

**「安全」が2種類混ざっています。**

BEAM が保証しているのは、プロセスがクラッシュしたときの隔離です。物理的分離が買っていたのは、それとは別の爆発半径 — デプロイ事故、メモリリーク、VM そのものの停止です。NIF が落ちれば VM ごと死にます。悪いデプロイを打てば、論理的に分離された30個のコンポーネントが同時に死にます。ここは BEAM では隔離できません。プロセス分離は、この種の障害に対しては何もしてくれない。

![箱ひとつの小火は蓋を閉めて消せるが、箱を載せている台の脚が折れて全部が傾いている](/images/phoenix-logical-separation-first/02-isolation-vs-blast-radius.png)

**Redis が要らなくなる、は条件付きです。**

ETS や GenServer で Redis を置き換えると、永続性とノード間共有を失います。プロセスが死ねば状態も消える。それを取り戻そうとして Mnesia や Horde を足すと、今度はネットスプリットと結果整合性という、Redis を使っていれば抱えずに済んだ問題を抱え込むことになります。上の表の「Redis → ETS」は、**状態が揮発してよい場合にだけ**成り立つ置き換えです。

**独立デプロイは技術要求ではなく、組織要求です。**

多くのチームが Microservices を選ぶ本当の理由は、性能でも障害隔離でもなく、「他チームのリリースを待ちたくない」でした。Conway の法則の話です。BEAM はここを解決しません。1つの deployment unit である以上、リリースは1本です。チームが3つになった時点で、この設計は組織のほうから圧力を受けます。

だから正確には、この主張はこう限定されるべきです。**チームが小さいうちは、論理的分離だけで十分に本物である。** 物理的分離が必要になるのは、負荷ではなく人数が先です。

## AI 時代の評価 — 追い風と逆風は同じ天秤に載る

「この考え方は AI 時代にはむしろ以前より合理的になる」と言われて、方向性としては同意しました。ただ、追い風だけを数えるのはフェアではないと思っています。

追い風のほうは分かりやすい。コーディングエージェントが最も落ちるのは、**文脈が切れる場所**です。リポジトリをまたぎ、サービス境界をまたぎ、契約が別ファイルにあり、実際の挙動が別のデプロイ単位にある。そういう構造では、エージェントは「呼び出し側は直したが呼ばれる側を見ていない」を平気でやります。単一コードベースなら、それが起きる余地が構造的に減ります。deployment unit が少ないということは、エージェントが読むべき境界が少ないということです。

私は以前、サブエージェントを分離したらコミットが増えた、という話を書きました。隔離には重複というコストが必ずつく。人間の組織でもエージェントの構成でも同じで、境界を増やすと、境界の両側で同じことを二度やる羽目になります。この構図はアーキテクチャにもそのまま当てはまります。

逆風のほうは、あまり語られません。**エージェントの実力は、学習データの量に露骨に比例します。** Elixir は TypeScript や Python に比べて、書かれたコードの絶対量が桁で少ない。同じモデルに書かせても、出てくるものの質が違います。OTP のパターン、スーパービジョン戦略の選択、`handle_info` の取りこぼし。このあたりでエージェントは静かに間違えます。

そして「AI が生産性を上げる」という前提に立つほど、この差は**選択の理由として重くなります**。単一コードベースで文脈が閉じる利得と、モデルがその言語をうまく書けない損失は、同じ天秤に載っている。片方だけ数えると結論を間違えます。

![天秤の片側に閉じた文脈の重い箱、もう片側に薄い学習データ。猫が乗っても足りない](/images/phoenix-logical-separation-first/03-context-vs-training-data.png)

私の判断はこうです。**書く量が人間の律速になっているチームでは、逆風が勝ちます。読む量と障害対応が律速になっているチームでは、追い風が勝ちます。** BEAM の利得は書くときではなく、落ちたときと追いかけるときに出るからです。新規機能を量産している段階の Phoenix はそこまで速くない。運用に入ってからのほうが、選んでよかったと言える設計です。

## 一つだけ持ち帰るなら

Phoenix を選ぶかどうかは、リアルタイム機能が要るかどうかでは決まりません。決まるのは、**分離をネットワークで買うか、プロセスで買うか**です。

ネットワークで買えば、独立デプロイと爆発半径の縮小が手に入り、運用コストと文脈の断絶を払います。プロセスで買えば、隔離と再起動が deployment unit の中で手に入り、独立デプロイを諦めます。

![二つの投入口を持つ券売機。ネットワーク硬貨とプロセス硬貨で出てくるものが違う](/images/phoenix-logical-separation-first/04-which-coin.png)

前者が必要になるのは、たいてい負荷の前に人数が来たときです。それまでは後者で十分だし、BEAM を使っているなら、それは妥協ではありません。
