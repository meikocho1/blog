先に結論だけ書くと、こうです。

> 論理的には細かく分ける。物理的には必要になるまで分けない。

Phoenix に惹かれている理由を自分で言語化しようとして、たどり着いたのがこの一行でした。リアルタイム（Channels や LiveView）が好きだから、ではありません。順序が逆で、リアルタイムは入口のほうです。

先に断っておくと、この記事は運用報告ではありません。大規模本番で BEAM を回した経験にもとづく話ではなく、学びながら組み立てている設計判断の言語化です。

:::message
**この記事の前提用語**

- **BEAM** — Erlang / Elixir が動く仮想マシン。JVM の Erlang 版だと思えば近いですが、設計の中心が「並行処理と障害からの回復」に振られている点が違います。
- **OTP** — BEAM の上に載っている標準ライブラリ群と設計作法のセット。GenServer やスーパーバイザはここに含まれます。
- **プロセス** — OS のプロセスとは別物。BEAM の中で動く軽量な実行単位で、1つ数KBから作れます。数十万個動かせます。
- **deployment unit** — 「1回のデプロイでまとめて入れ替わる単位」。マイクロサービスはこれを増やす設計、モノリスは1つに保つ設計です。この記事の中心語です。
:::

## 分割する理由を、いつのまにか問わなくなっていた

ここ数年、バックエンドはマイクロサービスが一つの理想形として扱われてきました。Go や Node.js で小さなサービスを作り、Docker で固め、Kubernetes に載せる。サービス間は REST か gRPC、非同期は Kafka か SQS、共有状態は Redis、監視は Datadog。

合理的な構成です。ただ最近、そこまで細かく分ける必要があるのか、という疑問のほうが強くなりました。考えるほど、BEAM と OTP の設計思想に引き寄せられていきました。

## ほとんどの処理系で「論理的分離」は規約でしかない

モジュールを分け、レイヤーを切り、依存の向きを決める。それはコーディング規約です。誰かが `import` を一本足せば壊れます。共有された可変状態は、設計図の上でどれだけ分離されていても、メモリの上では同じ場所にあります。

だから「本気で分離したいならプロセスを分けろ、つまりネットワーク越しにしろ」という話になる。マイクロサービスが買っていたのは、**分離を強制してくれる物理的な壁**でした。

BEAM は、この壁を別の場所に置いています。

![チョークで引いた線は猫に踏み越えられるが、同じ線が本物の壁になると猫は止まる](/images/phoenix-logical-separation-first/01-convention-vs-wall.png)

BEAM のプロセスはそれぞれ独立したヒープとメールボックスと状態を持ち、共有メモリを直接触らず、メッセージパッシングだけで通信します。プリエンプティブにスケジューリングされるので、1つが暴走しても他が止まりません。そしてスーパーバイザが、落ちたプロセスを決められた戦略で再起動します。

```text
BEAM

Supervisor
├ UserProcess #1
├ OrderProcess #100
├ AudioJobProcess #200
└ NotificationProcess
```

:::message
**登場する OTP の部品**

- **GenServer** — 状態を持ち、メッセージを受けて応答するプロセスの雛形。「小さなサーバー」を1つ立てる感覚に近いです。
- **スーパーバイザ** — 子プロセスを監視し、落ちたら決められた戦略で再起動する親プロセス。Kubernetes の再起動ポリシーを、VM の中でやっていると考えると分かりやすいと思います。
- **メッセージパッシング** — プロセス同士が共有メモリを触らず、メッセージを送り合って通信する方式。ロックを取り合う設計にならないのが利点です。
:::

つまり、隔離・再起動・メッセージ通信という、マイクロサービスが Kubernetes とネットワークを使って手に入れていたものを、**1つの deployment unit の中で処理系が保証している**。規約ではなく、処理系が。

ここが魅力の中心です。「分割しない」という選択が、諦めではなく設計判断になる。

## Go が劣っているという話ではない

単純な API サーバーなら Go は非常に強い。起動が速く、メモリが小さく、1バイナリで配布でき、コンテナ密度を稼げる。大量の HTTP リクエストを安く捌くのが目的なら、素直に優れた選択肢です。Phoenix のほうが速い、という話ではありません。

そして規模の議論は、たいてい数字に戻すと落ち着きます。1日1000万リクエストは、平均すると約116 req/s です。ピークが10倍でも1000〜2000 req/s。この程度ならどちらでも扱えます。

効いてくるのはリクエスト数ではなく、同時接続数 × 保持する状態 × 通信頻度のほうです。チャット、配送位置、キッチンディスプレイ、POS、共同編集、音声処理の進捗。こういう「生きている接続と状態」を大量に抱えるアプリケーションで、1接続1プロセスというモデルが自然になります。

## 複雑さは、分けたあとに来る

最初は Go の API 1本でも、育つとワーカーが要り、スケジューラが要り、WebSocket サーバーが要り、Redis とキューが増えます。そこからサービスに割ると、それぞれについて Docker、Deployment、ヘルスチェック、ログ、メトリクス、CI/CD、API スキーマ、サービスディスカバリ、リトライ、タイムアウト、サーキットブレーカ、分散トレーシングを考えることになります。

個々のサービスは単純になります。システム全体は複雑になります。

10〜20人のチームが User / Email / Profile / Preference / Notification と何十個にも割ると、単純な機能追加のたびに、ネットワーク障害、タイムアウト、結果整合性、分散トランザクション、スキーマ互換性が顔を出す。

:::message
**分割すると増える宿題**

- **結果整合性** — 複数のサービスに分かれたデータが、一瞬ズレることを前提にした設計。「注文は入ったが在庫にまだ反映されていない」状態を、アプリ側で扱う必要が出ます。
- **サーキットブレーカ** — 呼び先が落ちているとき、呼び出しを止めて即座に失敗させる仕組み。入れないと、1つの障害が呼び出し元へ連鎖します。
- **分散トレーシング** — 1リクエストが複数サービスを横断した経路を追跡する仕組み。単一プロセスならスタックトレース1本で済んでいたものが、専用基盤を要する作業になります。

どれも単体では正しい対策です。問題は、分けなければ**そもそも要らなかった**ということです。
:::

つまり、**コードを整理するために、ネットワーク障害という新しい問題を作っている**。これはかなり大きな代金です。

Redis も同じ構図です。Go サーバーを複数台にすると、A のメモリに持った状態は B から見えません。だから共有ストレージに逃がす。Redis は優秀ですが、魔法ではありません。実体は**別サーバー上の RAM** です。アプリから見れば TCP とシリアライズを挟んだ先の RAM です。

Phoenix なら一部の状態を、プロセスや ETS で VM 内部に持てるので、その往復が消える場面がある。Redis が不要になるのではなく、**導入を後ろに倒せる**という話です。

:::message
**ETS / PubSub / Presence / Oban**

- **ETS**（Erlang Term Storage）— BEAM 組み込みのインメモリのテーブル。プロセスをまたいで読み書きでき、非常に速い。ただし RAM の上にあるので、VM が落ちれば消えます。
- **PubSub** — 同じアプリ内（クラスタを組めばノードをまたいでも）でイベントを配る仕組み。Redis Pub/Sub を外に置かずに済みます。
- **Presence** — 「今誰が接続しているか」をノードをまたいで共有する仕組み。オンライン表示や同時編集で使います。
- **Oban** — Elixir のジョブキュー。実体は PostgreSQL のテーブルなので、Sidekiq と違って Redis を増やさずに済みます。
:::

## ここまでが主張で、ここからが自分への反論

上の話は、書いていて自分でも気持ちよくなってしまう類のものです。だから自分で刺しておきます。

**BEAM のクラスタは共有メモリではありません。** Node A と Node B の RAM が一つになるわけではない。User #123 のプロセスが A にあるなら、B からはメッセージを送って取りに行きます。distributed processes であって、分散共有メモリではない。ここを混同すると設計を間違えます。

**プロセスはデータベースではありません。** 接続中のユーザー、実行中のジョブ、進捗42%といった「今どうなっているか」はプロセスや ETS に向いています。注文、決済、在庫、ポイント残高といった「何が起きたか」は PostgreSQL に入れる。消えてはいけない事実を BEAM に置いてはいけない。ETS は速いですが RAM の上にあり、source of truth にはなりません。

**プロセスのクラッシュ以外は隔離できません。**

![箱ひとつの小火は蓋を閉めて消せるが、箱を載せている台の脚が折れて全部が傾いている](/images/phoenix-logical-separation-first/02-isolation-vs-blast-radius.png)

スーパーバイザが守ってくれるのは、プロセスが落ちたときです。物理的分離が買っていたのは、それとは別の爆発半径 — デプロイ事故、メモリリーク、VM そのものの停止です。NIF が落ちれば VM ごと死にます。悪いデプロイを打てば、論理的に分離された30個のコンポーネントが同時に死にます。ここは BEAM では隔離できない。

:::message alert
**NIF**（Native Implemented Function）とは、Elixir から C や Rust のネイティブコードを呼ぶ仕組みです。画像変換や暗号処理のような重い計算を逃がすときに使いますが、**NIF の中でクラッシュすると VM ごと落ちます**。スーパーバイザは助けてくれません。BEAM の障害隔離が効くのは、あくまで BEAM の中で書かれたコードに対してです。
:::

**独立デプロイは技術要求ではなく、組織要求です。** 多くのチームがマイクロサービスを選ぶ本当の理由は、性能でも障害隔離でもなく「他チームのリリースを待ちたくない」でした。決済チームが自分たちだけでデプロイとロールバックを回せることには、はっきりした価値があります。BEAM はここを解決しません。1つの deployment unit である以上、リリースは1本です。

だから正確には、主張はこう限定されます。**チームが小さいうちは、論理的分離だけで十分に本物である。** 物理的分離が要るのは、負荷より人数が先です。

## 何を統合し、何を外に出すか

巨大 EC を想像しても、全部を1つにするのは極端です。私なら Accounts / Cart / Orders / Checkout / Inventory / Promotion / Point / Notification までは1つの Phoenix に入れて、PubSub と Oban とスーパーバイザで内部を組む。

外に出すのは、統合する理由がないものだけです。検索エンジン、決済、不正検知、AI と推薦、オブジェクトストレージ、分析基盤。AI/ML は Python、CPU を焼く音声処理は Rust か C++、全文検索は専用エンジン。ランタイムが違うものを無理に Elixir に寄せる意味はありません。

Phoenix を万能言語として使うのではなく、**アプリケーションのオーケストレータとして使う**。これが今いちばん納得している形です。

## AI 時代 — 追い風と逆風は同じ天秤に載る

モノリスが嫌われた理由の一つは、コードベースが大きすぎて人間が理解できないことでした。コード検索、AST、Git 履歴、依存、テスト、型を横断して読めるエージェントが実用になるほど、**認知負荷を下げるためだけに分割する理由は弱くなります**。「この変更は Orders と Inventory と Promotion に影響します」と言えるなら、巨大コードベースの不利の一部は消える。

エージェントが最も落ちるのは、文脈が切れる場所です。リポジトリをまたぎ、サービス境界をまたぎ、契約が別ファイルにあり、実際の挙動が別のデプロイ単位にある。そこでは「呼び出し側は直したが呼ばれる側を見ていない」を平気でやります。deployment unit が少ないということは、エージェントが読むべき境界が少ないということです。

ここまでが追い風です。逆風のほうは、あまり語られません。

![天秤の片側に閉じた文脈の重い箱、もう片側に薄い学習データ。猫が乗っても足りない](/images/phoenix-logical-separation-first/03-context-vs-training-data.png)

**エージェントの実力は、学習データの量に露骨に比例します。** Elixir は TypeScript や Python に比べて、書かれたコードの絶対量が桁で少ない。同じモデルに書かせても、出てくるものの質が違います。OTP のパターン、スーパービジョン戦略の選択、`handle_info` の取りこぼし。このあたりでエージェントは静かに間違えます。

そして「AI が生産性を上げる」という前提に立つほど、この差は選択の理由として重くなる。単一コードベースで文脈が閉じる利得と、モデルがその言語をうまく書けない損失は、同じ天秤に載っています。片方だけ数えると結論を間違えます。

私の判断はこうです。**書く量が律速のチームでは逆風が勝ち、読む量と障害対応が律速のチームでは追い風が勝ちます。** BEAM の利得は書くときではなく、落ちたときと追いかけるときに出るからです。新規機能を量産している段階の Phoenix はそこまで速くない。運用に入ってからのほうが、選んでよかったと言える設計です。

なお、セキュリティ境界、独立スケーリング、チームの所有権、ランタイムの違い、障害ドメインの分離 — マイクロサービス本来の利点は、AI が進んでも消えません。消えるのは「コードを整理するための分割」のほうだけです。

## 一つだけ持ち帰るなら

Phoenix を選ぶかどうかは、リアルタイム機能が要るかどうかでは決まりません。決まるのは、**分離をネットワークで買うか、プロセスで買うか**です。

![二つの投入口を持つ券売機。ネットワーク硬貨とプロセス硬貨で出てくるものが違う](/images/phoenix-logical-separation-first/04-which-coin.png)

ネットワークで買えば、独立デプロイと爆発半径の縮小が手に入り、運用コストと文脈の断絶を払います。プロセスで買えば、隔離と再起動が deployment unit の中で手に入り、独立デプロイを諦めます。

前者が必要になるのは、たいてい負荷の前に人数が来たときです。それまでは後者で十分だし、BEAM を使っているなら、それは妥協ではありません。まず BEAM の中でプロセスとして分離して、本当に必要になった境界だけを外部サービスに昇格させる。今の私にはこれが一番しっくり来ています。
