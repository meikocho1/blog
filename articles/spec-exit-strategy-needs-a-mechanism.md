## 第1部 — Eisele が言っていること

### 結論を先に

> spec-driven development で6か月走ったリポジトリを開くと、コードの隣にもう一つのシステムが建っている。要件、調査ノート、上位設計、下位設計、実装計画、タスクリスト、レビューレポート。コードは先週の火曜に大きく変わったのに、ドキュメントの最終更新は数週間前だ。だから仕様書には出口戦略が必要になる。書かれた言葉はデルタ（これから起こす変更）のためにあり、リリース後に残すべき事実はネイティブな成果物へ昇格させ、残りは失効させる。

### 「第二のコードベース」

冒頭の一段落がこの記事の全部です。原文はこう始まります。

> Open a repository after six months of spec-driven agent work and you may find a second system sitting next to the code.

そのうえで Eisele は、これは新しい現象ではないと言います。ソフトウェアとドキュメントが並行して別々に育つのは、彼の記憶にある限りずっとそうだった。ウォーターフォールと呼んでいたあれです。週末にフォルダいっぱいの紙を読んで月曜からプロジェクトに入る、あの。「管理上は完全で、エンジニアリング上はほぼ無用」だったと書いています。

新しいのは速度です。エージェントは、あの過剰なドキュメント群を短時間で再生産できる。

特に彼が危険視しているのは、**仕様の初版をエージェントに生成させるパターン**。1回のワークフロー実行が、調査からそのまま要件・設計・計画を導出し、さらにレビュー成果物までその上に積む。完成度が高そうに見えて、実際にはレビューして承認すべき材料が大量に増える。混沌から本当の一貫性を作るのは、モデルが速くなっても難しいままだ、と。

### 書かれた言葉はデルタのためにある

必要な記述は短い、というのが処方です。意図した結果、非目標、現在の挙動と異なる制約、受け入れに必要な証拠。新機能がアーキテクチャ境界を跨ぐ場合や、コードにまだ存在しないパターンを持ち込む場合には技術設計要素も入る。変更を巻き戻すコストも考えておく価値がある、とも書いています。既存システムに同じパターンの実装が何通りもある場合、エージェントがもう一種類を発明するリスクが高いから。

調査ノート、プロトタイプ、設計記録のような追加の散文は「不確実性がそれを正当化するときだけ」プロジェクトに足す。**すべてのプルリクエストの必須ステージにしてはならない。**

### 恒久的な事実は、ネイティブな形で持つ

ここが具体的で好きな部分です。「恒久的な制約を昇格させる」と言うとき、すべての判断を永続的な Markdown にすることではない、と Eisele は明言します。それは古いドキュメント問題を別の形でやり直すだけだから。ソフトウェア工学は、恒久的な事実のほとんどについて、すでにもっとマシな置き場所を持っています。

- API の形と互換性 → OpenAPI、AsyncAPI、プロトコルスキーマ、型、互換性テスト
- データ不変条件 → 型、DB制約、バリデーション、マイグレーションチェック
- アーキテクチャ境界 → モジュール構造、依存ルール、アーキテクチャテスト
- 信頼性要件 → 負荷試験、SLO、テレメトリ、アラート
- リリース規則 → CI/CD ポリシー

そして決定的な一文。

> A failed schema check or alert needs to be fixed and handled while the corresponding paragraph in an old design folder does not.

スキーマチェックの失敗やアラートは対処されなければならない。古い設計フォルダの中の対応する段落は、そうではない。

自然言語にも残る役目はあります。ビジネスポリシー、トレードオフ、アーキテクチャの根拠。実行可能な成果物に収まらないもの。ただし散文は短く、説明する対象のすぐ隣に置く。将来のチームが高価な調査を繰り返してしまう場合、そしてコードコメントでは実装を正当化できない場合に限り、小さな ADR を残す価値がある。

> Recording every local choice just hides the few decisions that matter and confuses the agents that are supposed to build the software.

ローカルな選択をすべて記録することは、本当に重要な数個の判断を隠し、そのソフトウェアを作るはずのエージェントを混乱させる。

### 5ステップ

彼が提案する運用モデルはこれだけです。

> 1. リポジトリの証拠から始める（既存の挙動を読む）
> 2. 意図したデルタ、重要な境界、既知の未知を記した小さな change brief を書く
> 3. リスクが要求する場合にのみ、調査・プロトタイプ・設計合意・強い検証を足す
> 4. 計画ではなく実装を読んでレビューする
> 5. リリース時に、一時的な推論を破棄し、生き残った事実をそれぞれのネイティブな正典成果物に保存する

Research-Plan-Implement の反省も引かれています。人間のレビューを実装前に移した結果、チームは1,000行に達する計画を抱え、エンジニアはその計画をレビューしながら生成コードをほぼコンパイラ出力のように扱った。実装は計画からドリフトできる。

なお「エージェントに判断させる」部分は Simon Willison の2026年7月3日の記事を引いています。テストを書くべきかどうかを分岐表で規定するより、判断そのものを委ねたほうがいい、という Claude Code チームからの示唆です。

## 第2部 — 数字を一次資料に当たった

Eisele は「この挙動は研究に裏付けられている」として3本を引きます。3本ぶんのアブストラクトを自分で取ってきました。

### 「約31%」の分母

原文の記述はこうです。

> Choosing a more targeted repair approach around the identified defects (change brief) improved the results by roughly 31%.

該当論文は Jia らの「Automated Repair of Ambiguous Problem Descriptions for LLM-Based Code Generation」（arXiv:2505.07270）。SpecFix というツールを GPT-4o / GPT-4o-mini / DeepSeek-V3 / Qwen2.5-Coder-32B-Instruct の4モデル、HumanEval+ / MBPP+ / LiveCodeBench の3ベンチマークで評価しています。アブストラクトの該当箇所。

> Without human intervention or external information, SpecFix modified 43.58% of descriptions, improving Pass@1 on the modified set by 30.9%. This yields a 4.09% absolute improvement across the entire benchmark.

Eisele の「約31%」は**正しい**。誤報ではありません。ただし正確に言うと、SpecFix が書き換えたのは記述全体の 43.58% で、30.9% はその書き換えた部分集合における Pass@1 の改善です。ベンチマーク全体で見た絶対改善は 4.09%。

31% と 4.09% は、どちらも同じ実験の同じ数字です。それでも読者の頭に残る像は違う。「曖昧さを狙って直せば3割よくなる」と「曖昧さを狙って直せばベンチ全体で4ポイントよくなる」は、社内で予算を取るときに通る通らないが変わります。私はこの種の分母を、この2週間で二度目に見ています。数字が嘘でないまま誤読を誘う形のとき、書き手は分母を1フレーズで添えるべきだと思います。

ちなみに転移の数字も面白い。あるモデル向けに修復した記述は、他モデルの性能を 10.48% 改善する。**曖昧さはモデル固有の弱点ではなく、記述そのものの欠陥だ**という証拠になっています。これは Eisele の主張（ブリーフは短くても曖昧であってはならない）の直接の支えなので、彼が引かなかったのが少し意外でした。

![天秤の高いほうの皿に大きく「31%」の札、低いほうの皿に小さく「4%」の札。すみが31%側の皿の下から、それを支えている小さな踏み台をしゃがんで引き抜いていて、皿が傾きはじめている](/images/spec-exit-strategy-needs-a-mechanism/02-denominator.png)

### SWT-Bench はそのまま正しい

> SWT-Bench found that generated tests could filter proposed fixes and double the precision of a software repair agent.

Mündler らの SWT-Bench（arXiv:2406.12952）のアブストラクトに、そのまま書かれています。

> we find that generated tests are an effective filter for proposed code fixes, doubling the precision of SWE-Agent

生成テストは提案された修正のフィルタとして有効で、SWE-Agent の precision を2倍にする。Eisele が「実装を提案するエージェントが、その要件とテストの唯一の出所であってはならない」と書くときの根拠はここです。彼の要約は正確でした。

### TLA+ の数字は 27/9 ではなく 26.6/8.6

3本目。「Can LLMs Write Correct TLA+ Specifications?」（arXiv:2606.05792）。Eisele は「27% の構文的正しさ、9% の意味的正しさ」と書いています。アブストラクトの実数はこうです。

> LLMs achieve up to 26.6% syntactic correctness but only 8.6% semantic correctness, with successes exclusive to progressive prompting.

26.6% と 8.6%。丸めの方向としては上向きですが、大した違いではありません。それより中身です。30モデル・8ファミリ、205本の TLA+ 仕様のデータセット、オープンウェイト25モデル×4プロンプト戦略で2,600ラン、プロプライエタリ5モデルの few-shot で130ラン。SANY パーサと TLC モデル検査器で検証。

そして私が Eisele より重く見る所見が2つあります。

> model size does not predict quality, e.g., DeepSeek r1:8b outperforms its 70B variant across all strategies

モデルサイズは品質を予測しない。8b が同系の 70b を全戦略で上回る。

> Code-specialized models consistently underperform due to negative transfer from mainstream language training.

コード特化モデルは一貫して劣る。主流言語の学習からの負の転移が原因。

構文が通るのが 26.6%、意味が合っているのが 8.6%。この2つは「up to」つきの最良値どうしなので割り算して比率を出すのは乱暴ですが、それでも**パーサを通った仕様の大半は、通ったうえで別のことを言っている**という桁感は動きません。自分で分母に文句をつけた記事なので、ここは目安だと書いておきます。Eisele はこれを「形式記法は間違いの検出を助けたが、正しさや原意の保存を保証しなかった」とまとめています。控えめすぎると思います。この数字が言っているのは、自然言語の意図を機械可読な形に「翻訳」する工程自体が、現状ほぼ機能していないということです。

そしてこれは、私の見立てでは第1部の主張にとって31%よりずっと強い論拠になります。仕様書を Markdown で厚く書くのが無駄なのは、単に腐るからではない。**厚い散文から意味を保ったまま形式に落とす経路が存在しないから**です。だから昇格先は、翻訳を必要としないもの——型、DB制約、テスト、CIポリシー——でなければならない。Eisele のリストが全部「翻訳せずに済むもの」で構成されているのは偶然ではないはずです。

## 第3部 — 私の見解：出口戦略は方針では実装できない

ここからが本題です。

Eisele の5ステップのうち、4つは書けば実行されます。リポジトリの証拠から始める。ブリーフを書く。リスクに応じて足す。実装を読む。全部、やる人が能動的に得をする行為です。ブリーフを書かなければエージェントが暴走するし、実装を読まなければバグが出る。動機と行動が一致している。

ステップ5だけが違います。

> At release, discard temporary reasoning and preserve each surviving fact in its native authoritative artifact.

**これは誰も能動的に得をしない行為です。** そして期待されている実行タイミングは、リリースという、最も注意力が余っていない瞬間です。

私は以前、GitHub Actions の注入事故について書いたときに同じ構造を見ました。「安全な書き方」がコードの形としてだけ存在して、なぜその形なのかを強制する仕組みがどこにもなかったから、書き直しの過程で静かに消えた。人間のレビューもAIのレビューも気づかなかった。設定ゼロのリンタは一発で指した。あのときの教訓は「守るべきだったのは注意力ではなく機械可読なルールだ」でした。

「リリース時に一時的な推論を破棄する」は、**それとちょうど逆向きの、同じ間違いです。** 削除を、注意力に依存した方針として書いている。

### なぜ捨てられないのか

3つの摩擦が働くと思っています。重いと思う順に。

1つめ。削除は、レビューで褒められない。`docs/plans/2026-08-payment-refactor/low-level-design.md` を消す PR に「LGTM」が付くまでの心理的コストは、それを追加する PR より高い。追加は情報を増やす行為として見え、削除は情報を失う行為として見えます。実際には逆で、腐った下位設計が1本あるだけで、次にそのディレクトリを読むエージェントの判断が汚染されるのですが、その損失は誰のレビューにも現れません。

2つめ。生成コストがゼロに近いことが、削除のハードルを上げる。ここが AI 以前と違うところです。人間が3日かけて書いた設計書は、3日ぶんの価値があるように見えるから捨てにくい。これは分かる。ところがエージェントが40秒で生成した設計書も、同じくらい捨てにくいのです。理由が入れ替わっている。「せっかく作ったから」ではなく「これだけ整っているものを消すのは何か間違っている気がするから」。整形された Markdown は、内容の当否と無関係に、権威の見た目を持ちます。Eisele が「完成度の高さがすべてを統制されて定義されているように見せる」と書いているのは生成時の話ですが、同じ効果が削除時にも効きます。

3つめ。「エージェントが読むから残す」という誤解。これが一番反論されやすいところなので先に潰します。「仕様書を消したら、次にエージェントが仕事するときに文脈がなくなるじゃないか」。

なりません。次のエージェントが読むべきなのはコードとテストと型定義です。リリース済みの機能について、実装計画はコードより古い情報源です。Eisele も同じことを書いています。「リリース後はコードと本番の挙動が、システムが何をするかの一次証拠になる」。にもかかわらず、リポジトリに `docs/` があってそこに詳しい散文があると、エージェントはそれを読みます。読むだけならまだしも、コードと矛盾していた場合、どちらを信じるかは運です。**腐った仕様書はコンテキスト予算を食うだけでなく、能動的に嘘をつく。**

### 提案：ブリーフをリポジトリに入れない

私の結論はこうです。

> 出口戦略を「リリース時に捨てる」という運用ルールとして書くのをやめる。**捨てなくても消える場所に最初から置く。**

具体的には、change brief の正典をプルリクエストの本文にする。リポジトリのファイルとしてはコミットしない。

これで何が変わるか。ブリーフは変更中は完全に生きています。人間もエージェントも読める（`gh pr view` で取れる）。レビューの議論もそこに集まる。そしてマージした瞬間、それは自動的に「過去のPRの本文」になります。誰も削除の判断をしていないのに、`main` のツリーからは消えている。ブリーフが持っていた「これは今から起こす変更の説明である」という時制が、Git の構造によって強制されます。

作業中のワークツリーに置きたい場合は `.brief.md` を `.gitignore` に入れる。エージェントには「ブリーフはここ、ただしこれは今回のセッション限りの文書で、恒久的な事実はここに書くな」と伝える。私はこの運用をまだ長期に回していないので、これは提案であって実績報告ではありません。

そして残す価値のあった事実は、Eisele のリストどおりネイティブな形へ。ここで大事なのは、**昇格が起きたかどうかを機械が確認できる形にする**ことです。「ADR を書きましたか」というチェックリスト項目は機能しません。機能するのはこの種のものだと思います。

- `AGENTS.md`（および `CLAUDE.md`）に行数上限を設けて CI で落とす。上限に当たったら、内容を削るか、どれかの規則をリンタルールに昇格させるしかなくなる
- `docs/` 以下の Markdown が参照している識別子（クラス名、エンドポイントパス、設定キー）が実際にコードに存在するかを検査する。存在しない識別子を含むドキュメントは、腐っている証拠が機械可読になる
- API 変更を含む PR に OpenAPI 差分を必須にする。散文で「後方互換性に注意」と書く経路を塞ぐ

3つめだけは既に多くのチームがやっています。2つめは、私が知る限りあまり見ません。実装は難しくないはずです。文法解析すら要らない、`docs/` の中のバッククォート内文字列を拾って `rg` で照合するだけでも、腐った段落の8割は見つかると思います。

### 逆に、方針で足りる部分

公平のために書きます。ステップ3（リスクに応じて重さを変える）は、仕組みにしないほうがいい。ここを CI で強制した瞬間、それは Eisele が批判している「すべての変更が同じ文書とレビューとテスト分類を通る」重量級メソッドに戻ります。判断は判断のまま残す。Willison が引いた「テストを書くかどうかをエージェント自身の判断に委ねたほうがいい」というのも同じ話です。

判断を仕組みにすると官僚制になる。削除を判断に委ねると腐る。分けるべきなのはここです。

## 1つだけ持ち帰るなら

Eisele の記事の価値は「仕様書を薄くしろ」ではありません。それは前から言われています。価値は**「恒久的な事実には、それぞれ既に正典の置き場所がある」**という一覧を出したことです。API の形は OpenAPI に、不変条件は型と DB 制約に、境界はアーキテクチャテストに。散文はその隙間だけを埋める。

そのうえで私が足したいのは1行です。出口戦略に必要なのは、捨てる決意ではなく、**捨てなくても残らない置き場所**。プルリクエストの本文は、Git がすでに用意してくれているそれです。

一次資料についても一言。この記事で一番強い数字は、Eisele が3番目に控えめに置いた TLA+ の 8.6% だと思います。自然言語から形式仕様への翻訳が意味を保つ確率が1割を切るなら、厚い仕様書を書くという行為の投資対効果は、腐る前の時点ですでに悪い。
