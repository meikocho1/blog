Felix Rieseberg が2026年10月13日に、自分のブログに「How to be more ambitious: A tutorial for humans with models」という文章を出しました。Rieseberg は Anthropic のエンジニアリングマネージャーで、Claude.ai、Cowork、Claude Code Desktop のエンジニアリングを率いてきた人です。Electron の共同メンテナでもあります。

AI 業界の人は、すごい使い方を見るたびに「みんな野心が足りない」と言う。でも、そう言われても何をすればいいのか分からない。だから手順にした、という文章です。

私はこれを読んで、このブログの下書きを作っているハーネスに当てはめてみました。このブログは下書きを Claude Code に書かせていて、毎日自動で1本、ほかに頼んだときに1本出てきます。そこに Rieseberg の手順を当てた、という記録です。

先に結論だけ書くと、こうです。

> Rieseberg は野心を4種類に分け、省いた「速さ」以外の3つにプロンプトの例を付けている。ただ、「終わったかどうかをどう知るか」まで書いてあるのは「深さ」の中の「外部の審判を立てる」だけで、私にはほかの軸がそれに乗っているように見える。彼自身の「高度」の例を分解すると、目標を上げる前に検証の仕組みを作っていた。審判がないまま目標だけ上げると、モデルは「できました」と言う。私のハーネスで実際に効いたのも審判だった。

---

## 終わりの判定まで書いてあるのは1項目

Rieseberg の分け方はこうです。

> I think of ambition in four types: Speed, Altitude, Depth, and Range.
>
> （野心には4つの種類があると考えている。速さ、高度、深さ、幅。）

速さは「同じ仕事を短い時間で」。もう確立していて、AI への向き合い方に工夫がほとんど要らないので省く、と本人が書いています。残りの3つが本題です。

**高度**は、作業ではなく成果を頼むこと。本人の例が分かりやすくて、去年の初めはクラッシュを1件ずつ直させていたのを、最終的には「アプリをクラッシュしない状態に保て」と頼むようにした。

**深さ**は、その分野の一流の人がやるやり方でやらせること。ここには小技が5つ並んでいます。一流の道具を使わせる、無茶な目標を与えて無茶ではないと言う、自分たちの思い込みを生データで検証させる、新しい知見を作らせる、外部の審判を立てる。

**幅**は、ほかの分野の視点を持ち込むこと。名詞を動詞に言い換える（四半期レビューは「資料」ではなく「忙しい人に因果の話を信じさせ、不確かなまま30分で決めさせること」）、映画の強盗チームのように専門家を集める。

3つの軸のどれにも、そのまま使えるプロンプトの例が付いています。高度なら四半期レビューを3段階で引き上げるプロンプト、深さなら「チャーンはオンボーディングの問題だと思っている。生データから再現してみろ」、幅なら専門家チームの組み方。

ただ、読んでいて気づいたのは、どれも「モデルに何をさせるか」は書いてあっても、「できたかどうかを誰がどう判定するか」はほとんど書いていないことです。それを1つの項目として正面から扱っているのは、深さの中の「外部の審判」だけでした。

> Use an outside judge: Do not ask the model to judge itself. I assume that this will eventually be solved with increasing model intelligence, but in October 2026, I implore you to insist on outside validation. Ideally that's a tool the model can run to get feedback immediately.
>
> （外部の審判を使え。モデルに自分自身を採点させるな。いずれモデルが賢くなれば解決すると思うが、2026年10月の時点では、外部での検証を強く求めてほしい。理想は、モデルが自分で走らせてすぐに結果を受け取れる道具だ。）

![](/images/rieseberg-four-ambitions/01-only-one-is-a-procedure.png)

## 「高度」の例は、審判を作る話だった

クラッシュの例には続きがあります。私はこちらのほうが本題だと思いました。

> Doing this well often involves changing your workflow - in order to let Claude make sure our app is crash-free, I first had to make sure it can easily fetch crash reports, understand which app version maps to what git commit, and give it access to Windows, macOS, and Linux computers so it can actually independently reproduce and verify fixes.
>
> （これをうまくやるには、たいてい自分の仕事の流れを変えることになる。アプリがクラッシュしないことを Claude に保証させるために、私はまず、Claude がクラッシュレポートを簡単に取れること、どのアプリのバージョンがどの git コミットに対応するかを分かること、そして Windows・macOS・Linux のマシンを使えて、修正を自分で再現・検証できることを整えなければならなかった。）

並んでいる3つは、どれもモデルの外にある「本当に直ったか」の判定材料です。クラッシュレポートは直す前の状態の証拠、バージョンとコミットの対応は原因の場所の証拠、3つの OS は直ったことの証拠です。

「クラッシュしない状態に保て」という高い目標は、これがあって初めて頼めるようになっています。逆に、これがない状態で同じことを頼めば、モデルは何かを直して「直しました」と報告し、それが本当かを確かめるのは人間の仕事に戻ります。目標の高さは上がっても、人間の手間は減りません。

深さの節の「無茶な目標を与えて、無茶ではないと言え」も同じ構造です。

> Does something seem impossible to the model? Reiterate that it's very much solvable, it just needs to keep going.
>
> （モデルにとって不可能に見えることがあるか。それは十分解ける、続ければいいだけだと繰り返し伝えよ。）

10秒かかるページを5秒にしたいなら、200ミリ秒を頼め、という例が出てきます。計測の道具があるならこれはいい助言です。道具がないなら、モデルが「200ミリ秒になりました」と書いて終わる可能性がある。私はこの2つの助言は、セットでしか成り立たないと読みました。Rieseberg は別々の項目として書いていますが、審判がなければ、無茶な目標はただの「できましたと言ってくれ」というお願いになります。

## 私のハーネスに当てたら、審判しか選べなかった

ここからは私の手元の話です。

このブログのハーネスは、文体のルールを書いた skill、挿絵の skill、毎日の自動実行のプロンプト、それにいくつかのメモでできています。Rieseberg の3軸を当てて、Claude に改修案を4つ出させました。

高度の案は、目標を「1本書く」から「手直しなしで公開できる1本を書く」に上げるものでした。2026年10月18日の時点で、Zenn に公開した記事は41本、リポジトリに入れないまま1週間以上たった下書きは27本あります。公開した記事と止まった下書きの違いを判定基準にしよう、という案です。

深さの案は、記事の自己採点をやめて、別のコンテキストのレビュアーに事実と文体を判定させるものでした。幅の案は、編集者やファクトチェッカーの仕事を工程として書き込むもの。残りの1つは、重複した設定の掃除です。

私は深さだけを選びました。

あとから考えると、理由は Rieseberg のクラッシュの例と同じでした。高度の案には審判がありません。27本がなぜ止まったのか、理由を書き残したものは手元に見つかりませんでした。「公開できる」を判定する材料が、私の頭の中にしかないわけです。その状態で目標を「公開できる1本」に上げても、モデルは公開できると思う記事を書いてくるだけで、それを判定するのはやはり私です。

## 審判を作って、昨日の記事に当てた

作ったのは2つです。

1つは、記事の中の原文引用を元ソースと機械的に突き合わせるスクリプト。英語の引用が元ソースに一字一句あるかを照合して、なければ失敗で終わります。ソースに出てこない数字も一覧にします。昨日公開した「Claude Code チームのレビュー6層」に当てると、引用7行はすべて一致しました。引用の1語を "indefinitely" から "forever" に書き換えた版では、ちゃんと失敗しました。ソースに無い数字として出てきたのは、本文で私が試算した 0.6 と 1.2 の2つだけでした。元の記事に当てたときの出力はこうです。

```text
原文引用: 7行を照合、NG 0行
数字: 27種類、ソースに無いもの 2種類（要確認）
  0.6, 1.2
```

もう1つは、別のコンテキストで動くレビュアーです。書いたときのメモは渡さず、記事のパスとソースの URL だけを渡して、ソースを自分で取ってきて読ませます。見るのは5つで、事実、ソースに無い盛り、根拠の無い書き手の体験談、見解の節があるか、文体です。

同じ記事に当てると、84秒で返ってきました。必須の指摘は0件、推奨が8件です。

中身はこういうものでした。私は本文で、元記事がレビューの2つ目の仕事を「終盤の3段落で済ませている」と書いていた。数えると4段落でした。元記事の "Noise costs more when the author is an agent"（作者がエージェントだとノイズはより高くつく）を、私は「跳ね上がる」と訳していた。「数字は全部、彼ら自身が測ったもの」と書いた中には、別記事からの引用と、Boris Cherny 個人の見積もりが混ざっていた。

どれも小さい。でも、書いた側の確認ではどれも通っていました。書いた側が持っているソースの記憶は、書いたときの要約そのものなので、そこから外れていないかを自分で確かめることはできません。原文の "costs more" を覚えていたつもりで、頭の中ではもう「跳ね上がる」になっていた。

この記事を書いている時点で、8件はまだ公開記事に反映していません。

## 私の見解

### 審判は「ロール」ではなく「やること」で書く

幅の節に、私がいちばん実務的だと思った一文があります。

> Don't ask the model to write like a short seller, ask it to do what a short seller does to research their position.
>
> （空売り屋のように書けとモデルに頼むな。空売り屋が自分のポジションを調べるときにやることを、やらせよ。）

深さの節にも似た指摘があって、プロのように振る舞えと言うと、モデルは方法ではなく語彙だけを切り替えることが多い、と書いています。

自分のレビュアーへの依頼文を見返すと、1行目は「あなたは日本語の技術記事のファクトチェッカー兼編集者です」でした。まさにロールの指定です。ただ、効いたのはそこではなかったと思います。4段落を数え直せたのは「ソースは自分で取得して全文を読んでから判定すること。記事の要約を信用しない」という行があったからで、"costs more" を拾えたのも、訳を原文と並べて比べろと書いたからです。ロールの1行を消しても結果は変わらないと思っていますが、試してはいません。

### 審判は、書き手が気づかない種類の誤りを拾う

もう一つ、このハーネスにはもともと似た仕組みがあって、昨日の記事を書いている途中で別のモデルにも読ませていました。そこで止まった文があります。下書きの「私が間違っているとしたら」の節に、モデルが私の経歴として「私は個人開発者で、チームの承認ルールを運用した経験はありません」と書いていた。謙遜の形をした開示で、記事の信頼性を上げる方向の一文に見えます。根拠はどこにもありませんでした。公開前に消したので、この文が入った下書きは残っていません。読者が確かめる手段はないことを書いておきます。

この種類の誤りは、書き手が自分で採点する限り見つかりません。書き手には、正直に開示しているつもりしかないからです。文体のルールには「事実の捏造で体験を作らない」と書いてありましたが、否定形の体験談も捏造だ、という読み方は書いた本人には出てこなかった。

Rieseberg は、モデルに自分を採点させる問題は、モデルが賢くなればいずれ解決すると書いています。私は少し違う見方をしています。書いた本人が見落とすのは、能力が足りないからというより、書いたときの文脈をそのまま持っているからです。その文脈を持っていない読み手を用意する、というのが審判の役割だと思います。そうだとすると、モデルが賢くなってもこの役割は残ります。

### 高度は、審判で買う

ここが、この記事で私が言いたいことです。

Rieseberg の4つの軸は横に並んでいますが、私には上下に積まれているように見えます。外部の審判が一番下にあって、その上に乗った分だけ高度を上げられる。クラッシュの例では、レポートとコミットの対応と3つの OS がそろって初めて「クラッシュしない状態に保て」が頼めるようになった。私のハーネスでは、引用の照合とレビュアーができた今、ようやく「元ソースと食い違わない記事を書け」が、確かめられる目標になりました。「公開できる記事を書け」にはまだ上げられません。27本が止まった理由を判定する材料が、まだないからです。

だから次にやることは、高度の目標を考えることではなく、止まった下書きの理由を1本ずつ記録することだと思っています。それがたまれば、「公開できる」の審判が作れます。

![](/images/rieseberg-four-ambitions/04-altitude-stacked-on-judges.png)

### 私が間違っているとしたら

いちばん大きいのは、審判の出来をまだ測っていないことです。必須の指摘が0件だったのは、記事に重大な誤りがなかったからかもしれないし、レビュアーが甘いからかもしれない。昨日の記事で書いた Claude Code チームは、レビュアーを過去の事故の集合で毎日採点していました。私のレビュアーは1本の記事に1回当てただけです。

もう一つ、毎日の自動実行にはこの工程がまだ入っていません。自動実行は使えるツールを許可リストで絞っていて、レビュアーの起動とスクリプトの実行がそこに無いからです。権限を広げる変更なので、まだ足していません。今のところ、この審判が働くのは私が頼んで書かせたときだけです。

それと、Rieseberg の文章の後半、自己効力感（自分にできると信じる度合い）の話には、ここでは触れていません。人間側の野心の話で、ハーネスに当てる種類の話ではなかったからです。

---

## まとめ

1つだけ持ち帰るなら、目標を上げる前に審判を作ることです。Rieseberg のクラッシュの例も、私のブログのハーネスも、先に「本当にできたか」をモデルの外で確かめる道具を作って、それから頼める目標が一段上がりました。審判の無いまま目標だけ上げると、増えるのは「できました」という報告です。
