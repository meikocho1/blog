先に結論だけ書くと、こうです。

> PostgreSQL 19 のある機能は、コミット前に複数の LLM でレビューされ、敵対的なテストもかけられていました。それでも、コミット後に見つかった見落としを**どのモデルも拾えませんでした**。理由は「LLM が弱いから」ではないと私は考えています。そのバグは**差分の中になかった**からです。書かれていなかった1行を見つけるには、システム全体の地図が要ります。それを持っているのがメンテナです。

## 何が書かれているのか

### 主張は1つ

要約するとこうです。

- LLM はソフトウェア開発で非常に役に立つ。**特にバグ探しは得意**
- ただしそれが一番効くのは、**経験のあるエンジニアが方向を示したとき**
- LLM には「システムの頭の中の地図」も「プロダクトがどうあるべきか」というビジョンもない。それを持つメンテナとセットで使う必要がある
- 機能がどう振る舞うべきかを決めるのは、ユーザーと一緒に全体を見るメンテナの仕事。**作り直しや設計の転換が必要なタイミングを見極める**のもメンテナの責任

ここまでは、よく聞く話です。この記事が良いのは、それを裏付ける具体例が PostgreSQL 本体から出てくるところです。

### 具体例：PostgreSQL 19 の all-visible

PostgreSQL 19 では、**通常のクエリのテーブルスキャン中にページを all-visible としてマークできる**ようになりました（リリースノートでは Melanie Plageman 氏の名前が挙がっています）。これまでは VACUUM と `COPY FREEZE` にしかできなかったことです。

all-visible が立ったページは、Index-Only Scan でヒープを見に行かずに済みます。つまり読み込みが速くなる、筋のいい改善です。

この機能は徹底的にテストと検証を経てコミットされました。**複数の LLM にコードレビューをさせ、敵対的なテストもさせた**そうです。

それでもコミット後に見落としが見つかりました。そのひとつが、**ページを all-visible にするとき、Free Space Map（FSM）を更新していなかった**というものです。結果として**ブロート（テーブルの肥大化）**につながる。そしてこれを見つけた LLM は、ひとつもありませんでした。

## 私の見解 — 見つからなかったのは「書かれなかった1行」だった

ここからは原文にない、私の読み方です。

### なぜ FSM の更新漏れがブロートになるのか

私はこう理解しています（原文の説明ではなく、私の推論です）。

1. VACUUM は all-visible のページを**スキップできる**。全部見えているなら、掃除することはないので
2. VACUUM は、ページを見たついでに**空き領域を FSM に記録**している
3. 新しい機能では、VACUUM ではなくクエリが先にページを all-visible にする
4. すると VACUUM はそのページを飛ばし、**空き領域が FSM に載らないまま**になる
5. INSERT は FSM を見て空きを探すので、そのページの空きを使えず、テーブルの末尾にページを足していく。これがブロートです

ポイントは、**このバグがどこにも「書かれていない」**ことです。

新しいコードは、書いてあることは正しい。all-visible は正しく立つし、Index-Only Scan も正しく動く。問題は「all-visible を立てる人は FSM も面倒を見る」という、**VACUUM が暗黙に担っていた責任**を引き継がなかったことにあります。その責任はコードのコメントにも、関数のシグネチャにも書かれていません。VACUUM の実装を読み、FSM と可視性マップの関係を知っている人の頭の中にだけあります。

### LLM のレビューは差分に閉じる

LLM にレビューさせるとき、渡すのはたいてい**差分**です。差分に書かれたコードに矛盾があるか、境界条件を外していないか、型が合っているか。こういう「書かれたものの誤り」を探す作業は、LLM が本当に得意です。

でも今回のバグは、差分のどの行にもありません。**差分に含まれるべきだったのに、含まれていない1行**です。書かれたものしか読まないレビュアーには、原理的に見つけられません。

これはモデルの賢さの問題ではないと思います。人間の新人レビュアーに同じ差分を渡しても、たぶん見つけられません。見つけられるのは「all-visible を立てる場所が増えた」と聞いた瞬間に「じゃあ FSM は？」と連想する人です。**その連想のもとになる地図が、メンテナの頭の中にしかない。**

### 敵対的テストでも見つからなかった理由

「敵対的なテストもかけたのに」という点も、同じ形をしていると思います。

敵対的テストは「壊れる入力」を探します。でもこのバグは、どの入力でも**壊れません**。クエリは正しい結果を返し、クラッシュもしません。ただテーブルが、時間をかけて少しずつ太っていくだけです。**不正確さではなく、劣化**です。

テストの合否は「期待した出力が出たか」で決まります。「1週間運用したらディスク使用量がどうなるか」は、テストの形になりにくい。そこに気づくのは、本番のテーブルが太っていくのを何度も見てきた人です。

### 自分の仕事に置き換えると

私は普段 Rails と Supabase（中身は Postgres）で仕事をしているので、同じ形の穴がすぐ思い浮かびます。

- **Supabase の RLS**：新しいテーブルを追加するマイグレーションを LLM がレビューすると、SQL としては完璧と判定されがちです。でも「このテーブルに RLS ポリシーを付けていない」は差分に書かれていない。既存テーブルはすべて RLS 前提で設計されている、という**プロジェクトの暗黙の約束**を知らないと気づけません
- **Rails のコールバック**：`update_column` で直接書き換える処理を足すと、コードとしては正しい。でも既存の `after_save` が担っていた検索インデックスの更新やキャッシュの破棄が、黙って飛ばされます
- **カウンタキャッシュや非正規化カラム**：新しい書き込み経路を1本足すたびに「同期を担っていた誰か」を引き継ぐ必要がある。PostgreSQL の FSM と同じ構造です

どれも、**既存のコードが暗黙に担っていた責任を、新しいコードが引き継がなかった**というバグです。そして全部、差分だけ見ても分かりません。

### だから私は、レビューの頼み方を変えている

この記事を読んで、LLM へのレビュー依頼を少し変えることにしました。

- 差分だけでなく、**「この変更と同じ責任を持っている既存コード」**も一緒に渡す（今回なら VACUUM の該当箇所）
- 「この差分にバグはあるか」ではなく、**「この変更で、既存の誰かが暗黙にやっていた仕事を飛ばしていないか」**と聞く
- そもそも「既存の誰か」を思い浮かべるのは自分の仕事だと割り切る

最後の1つが、原文のいう「メンテナの視点」だと思います。LLM はレビューを速く、広くしてくれる。でも**何を読ませるかを決めるのは、地図を持っている人**です。地図を持たないまま LLM にレビューを任せると、「書かれたものは全部正しい」という安心だけが増えていきます。今回の PostgreSQL の例が怖いのは、まさにそこです。
