## 第1部 — なぜ「一列」は壊れるのか

### 誰でも最初はチェーンを書く

少し複雑なことをエージェントにやらせようとすると、たいていこういう形になります。

```
ファイルを読む → 要約する → ルールと照合する → レポートを書く
```

各工程が1プロンプト。前の工程が終わるまで次は待つ。**自然な形です。**私たちがタイプする順番そのままだからです。

短い仕事ならこれで十分です。壊れ始めるのは、仕事が長くなったとき、横に広がったとき、そして**エージェントに自分の仕事を採点させたとき**です。

### Anthropic が名前を付けた3つの失敗モード

公式記事は、1つのコンテキストウィンドウの中でエージェントを長く働かせると起きることを、3つに分類しています。

| 失敗モード | 何が起きるか | 具体例 |
| --- | --- | --- |
| **Agentic laziness**<br/>エージェント的な怠惰 | 複雑な多段タスクを途中でやめて「終わりました」と宣言する | セキュリティレビューの50項目のうち35項目だけ見て完了報告 |
| **Self-preferential bias**<br/>自己優遇バイアス | 自分の出力を検証・採点させると、自分の結果を好む | 自分で書いたコードのレビューが甘くなる |
| **Goal drift**<br/>目標のドリフト | ターンを重ねるうちに元の依頼への忠実さが落ちる。**特に要約（compaction）の後** | 「Xはやらないで」という制約が最初に失われる |

重要なのは、**この3つはどれも工程を足しても解決しない**という点です。

一列に並べたまま工程を増やせば、同じコンテキストがさらに重くなるだけです。解決策は形を変えること — **仕事の単位ごとに新しいきれいなコンテキストを与え、信頼する前に検証を通す**ことです。

公式記事の表現もそのままです。ワークフローは「それぞれ独自のコンテキストウィンドウと、焦点の絞られた孤立したゴールを持つ別々のサブエージェント」を編成することで、これらに対抗します。

![細い1本の管に挟まって下流の詰まりを見ているすみと、3本の管の元栓を同時に開けているすみ](/images/agent-graph-not-chain/01-one-pipe-vs-three.png)

### 「and then」テスト

自分の書いたチェーンのうち、どれだけが本当に必要かを暴く簡単な診断があります。

> 工程の間の「そして次に」ひとつひとつについて、**次の工程は前の工程の出力を実際に読んでいるか？**

元記事の例が分かりやすいです。「ファイルを要約して、**それから**明日の天気を調べて」— この2つの間には何の関係もありません。天気は要約を消費しません。**独立した2つの仕事を、一直線のスクリプトが勝手に鎖でつないでいる**だけです。その待ち時間は何も買っていません。

### チェーンもグラフである（ただし最小で最も脆い）

ここが認知の転換点です。

一直線のチェーンは、グラフではないものではありません。**描ける中で一番小さく、一番脆いグラフ**です。分岐のない1本道で、どのノードも入口が1本・出口が1本しかない。冗長性はゼロ。

- どこか1箇所が詰まれば、下流は全部止まる
- そして上流は、成果物を置く場所がないまま取り残される

直すべきは長さではありません。**幅**です。

## 第2部 — 語彙：ノードとエッジ

グラフの構成要素はたった2つです。エージェント設計の混乱のほとんどは、この2つを混同することから来ます。

### ノード = 境界のある1つの仕事

**1エージェント、明確に区切られた1つの仕事、入力1つ、出力1つ。**

「顧客とのやりとりを処理する」はノードではありません。広すぎます。「このチケット1件を分類する」「このファイル1つを特定の種類のバグについて調べる」— この粒度です。

### エッジ = 依存関係。それだけ

エッジが意味するのは「このノードの出力が、あのノードの入力になる」ということ。**それ以上の意味はありません。**

だから、こうなります。

| これはエッジではない |
| --- |
| **順序** — 先に書いたから、が理由になっていない |
| **プロンプト内での近さ** — 隣に書いてあるだけ |

エッジを本物にするのは、**データが実際にそこを渡ること**だけです。

![2つの箱の間に張られた紐を虫眼鏡で覗き、何も渡っていない紐をハサミで切るすみ](/images/agent-graph-not-chain/02-cut-the-false-string.png)

すでに作ってしまったエージェントに対して、この検査ができます。

> 2つの工程の間に引いた矢印すべてについて、**そこを渡る具体的なデータを指差せるか？**

指差せないなら、その2工程は独立しています。間にある待ちは純粋なオーバーヘッドです。

### ノードには契約が必要

ノードを大きなグラフに組み込んで安全なのは、**契約**を持っているときだけです。

- 境界の決まった入力
- 定義された、できれば検証済みの出力の形

つまり、次の工程がパースして「壊れてないことを祈る」ような自由テキストではなく、**そのまま使える構造化データ**を返すこと。

これがあると、エッジの両端のエージェントを差し替えられます。複数のノードを並列に走らせても、出力が想定と少し違った瞬間に全体が静かに崩れる、ということが起きません。

## 第3部 — 6つの型

ノードとエッジがはっきりすると、実際のエージェントシステムはごく少数の形でほぼカバーできます。手を伸ばす順に並べます。

### 1. Fan-out（扇状に広げる）

独立した仕事が N 個あるなら、順番待ちさせずに同時に走らせる。

ここで効く設計規律は**耐障害性**です。1つのノードが失敗してもバッチ全体を沈めてはいけません。失敗した単位はクラッシュではなく**空で返る**ように作り、次の段階の前に空を除去します。

### 2. Fan-in（barrier で集める）

広げたものは、何かが集めなければ意味がありません。**barrier** は、上流の結果が全部揃うまで次に進めない地点です。

そして重要なのは、**これは例外であって既定値ではない**ということ。全部が揃っていることが本当に必要な場合だけ使います。

- 全ソースを横断した重複除去
- リスト全体のランキング
- 「1件も返ってこなかったから早期終了する」という判断

### 3. Diamond（ダイヤモンド）

fan-out と fan-in を組み合わせた、まともなエージェントシステムのほぼすべての背後にある形です。**広げて、働かせて、まとめる。**

3つの部分を分けて名前を付ける価値があります。

```
① fan out    広さを稼ぐ（エージェント複数）
② reduce     普通のコード数行で圧縮する（平坦化、重複除去）
③ synthesize 完全な圧縮済みセットを必要とする最後の1エージェント
```

**②が肝です。** リストを平坦化するのも重複を除去するのも決定論的なコードで済みます。エージェントは要りません。**中央のエッジは無料**で、下のbarrierだけが待ちに値します。

![上から投入されて4つに分かれ、下のじょうごの首で集まったものを手で圧縮しているすみ](/images/agent-graph-not-chain/03-diamond-funnel.png)

### 4. Routing（振り分け）

すべての経路が固定とは限りません。**ルーターノード**が結果を見て、次にどのエッジを発火させるか決めます。サポートチケットを分類して適切な担当へ、変更の規模を見て軽いレビューか全面監査かを選ぶ。

ここに大事な設計判断があります。

> **分類はエージェントの判断でよい。しかしルーティング自体は普通のコードで書く。**

そうすれば同じ入力は毎回同じ経路を通ります。モデルの頭の中に判断が埋まって、予測できない分岐が起きることがありません。

### 5. Verification（検証）

グラフの本当のレバレッジは、エージェントを増やして作業させることではありません。**見つけたものへの確信を生むために、周りに巻きつける構造**です。

検証者はエッジの上に座り、結果が下流に行くのを許す前に立ちはだかります。その唯一の仕事は**その発見を反証しようとすること**。生き残れば通す。生き残らなければレポートに載らない。

![門の前で、通ろうとする発見の札に赤いスタンプで反証を試すすみ](/images/agent-graph-not-chain/04-refuter-at-the-gate.png)

第1部の3つの失敗モードを思い出してください。自己優遇バイアスは「自分の仕事を自分で採点させる」ことで起きます。**別のコンテキストの別エージェントに反証させる**のは、その構造的な対策です。

### 6. 収束するサイクル

仕事の量が事前に分からない場合があります。バグ探しのように、1つ見つかると3つ見えてくるような仕事です。これには前のノードへの制御されたループが要ります。

危険は明らかで、**出口条件のないサイクルは、同じ場所を再発見するだけで予算を使い切る無限ループ**です。

実際に機能するのは **loop-until-dry** です。

```
数ラウンド連続で新しいものが出なくなるまで続ける。そして止める。
```

そしてここが致命的に重要な細部です。

> 新しい発見を照合する相手は、**「確認済み」ではなく「これまで見た全部」**にすること。

却下された結果を記録しないと、それは毎ラウンド浮かび上がってきます。ループは同じ行き止まりを再発見するために永遠に金を払い続けます。

### 公式6パターンとの対応

元記事はこの6つの形が、Anthropic が dynamic workflows のために命名・文書化した6パターンに綺麗に対応すると指摘しています。公式記事で確認できました。

| この記事での呼び方 | 公式のパターン名 |
| --- | --- |
| Routing | **classify-and-act** |
| Diamond | **fan-out-and-synthesize** |
| Verification | **adversarial verification** |
| 収束するサイクル | **loop until done** |
| （未登場） | **generate-and-filter** — 候補をまとめて生成し、ルーブリックを生き残ったものだけ残す |
| （未登場） | **tournament** — 同じ仕事で競わせ、審査者が1対1で比較して勝者を決める |

**tournament** は覚えておく価値があります。公式記事は1000行超のソートを例に挙げていて、理由が明快です — **比較判断は絶対評価よりも信頼できる**。命名、ランキング、順位付けのように「絶対的というより比較的」な判断に向きます。

## 第4部 — 実装で本当に効く4点

### (1) 失敗を隔離する。書き込みも隔離する

並列実行で壊れ方は2種類あり、対策も別です。

| 壊れ方 | 対策 |
| --- | --- |
| ノードが単に失敗する | 例外が全体を落とすのではなく**何も返さない**形に解決するよう fan-out を設計する |
| 同じファイルに書くノードが衝突する | 各エージェントに**隔離された作業場**を与え、後でマージする |

2つ目は Claude Code では worktree の隔離として提供されています。公式記事も、ワークフローは「エージェントがどのモデルを使うか、サブエージェントを自分の worktree で走らせるか」を決められると明記しています。

ただし注意点があります。これは**それが必要な1つのトポロジーのためのシートベルト**であって、すべてのグラフに課す税ではありません。隔離にはセットアップとディスクのコストがかかります。

### (2) モデルをグラフ全体で階層化する

すべてのノードが同じ重さではありません。

```
1フィールドを抽出する、1チケットを分類する → 境界が明確で反復的 → 安いモデル
最終レポートを合成する、争点を裁定する      → 判断が宿る場所     → 最良のモデル
```

そして**これは意図的にやらなければ起きません。**

> 既定では、生成したすべてのノードは**それを開始したセッションのモデルを継承**します。階層化はノードごとに明示したときだけ実現します。

### (3) トポロジーがコストレバーである

ここが一番つまずくところです。そして一番大きな数字がぶら下がっているところです。

**barrier は、他の9個が一瞬で終わっていても、下流の全工程を一番遅い1つが終わるまで待たせます。**

対して、各アイテムを同期点なしで独立に全段階を流していけば、速いアイテムは遅いアイテムの3段先を進めます。後ろでアイドリングする理由がありません。

![横一列のゲートで待たされる荷物と、独立したレーンを別々の速度で流れる荷物](/images/agent-graph-not-chain/05-barrier-vs-lanes.png)

**既定は「独立に流す」。** barrier に手を伸ばすのは、その段階が完全なセットなしには本当に進めないときだけです。全体を横断した重複除去、総数による早期終了、他の全発見との比較。

そして元記事の指摘が刺さります。

> **「このほうがコードがきれいだ」は、その理由に含まれない。**

余分な待ちは実測できる時間です。その場所を得るには理由が必要です。

### (4) どう起動するか

Claude Code での実際の起動方法です。

| やりたいこと | 方法 |
| --- | --- |
| ワークフローとして実行させる | 目的を説明して「ワークフローで」と言う。または**トリガーワード `ultracode`** を使って、通常の一問一答ではなくワークフローが構築されることを確実にする |
| 繰り返し実行する | 定期スケジュール（`/loop`）と明確な完了条件（`/goal`）を組み合わせる |
| 暴走を防ぐ | **トークン上限を指定する。**「10k トークンで」のように伝えると上限が設定される |
| 良い結果を再利用する | 生成されたスクリプトを保存する。バージョン管理された再利用可能な資産になり、次回ゼロから説明し直す必要がなくなる |

前提条件も確認しておきます。公式ドキュメントによると、dynamic workflows は **Claude Code v2.1.154 以降**、全ての有料プラン・Anthropic API・Amazon Bedrock・Google Cloud の Agent Platform・Microsoft Foundry で利用できます。**Pro プランでは `/config` の Dynamic workflows の行から自分でオンにする**必要があります。

### そもそもワークフローは何が違うのか

公式ドキュメントの整理が的確なので、そのまま押さえておきます。subagents / skills / agent teams / workflows の違いは、**誰が計画を持っているか**です。

| | サブエージェント・スキル・エージェントチーム | ワークフロー |
| --- | --- | --- |
| 次に何を走らせるか決めるのは | Claude（ターンごと） | **スクリプト** |
| 中間結果がある場所 | Claude のコンテキストウィンドウ | **スクリプトの変数** |
| 再利用できるもの | ワーカーの定義・指示 | **編成そのもの** |
| 中断されたとき | ターンをやり直す | **同一セッション内で再開可能** |

つまりワークフローは**計画をコードに移す**ものです。ループも分岐も中間結果もスクリプトが保持するので、Claude のコンテキストには最終的な答えだけが残ります。

## 第5部 — グラフが静かに壊れる場所

元記事が挙げる落とし穴です。どれも「動いてはいるが金を払い続けている」タイプの壊れ方です。

| # | 落とし穴 | 何が起きているか |
| --- | --- | --- |
| 1 | **偽のエッジ** | その順でタイプしたから繋いだ。2つ目は1つ目の出力を読んでいない。待ちは何も買っていない |
| 2 | **既定で barrier** | そのほうが整って見えるから同期待ちにした。次の段階は完全なセットを必要としていない。レイテンシは実在し、無駄 |
| 3 | **自前の配管に家賃を払う** | リストの平坦化や配列の重複除去にエージェントを立てる。決定論的なコード数行、コストゼロで済む仕事。**エージェントは判断のために取っておく** |
| 4 | **乾かないループ** | 新しい発見を「確認済み」だけと照合している。却下された結果が毎ラウンド再登場し、同じ行き止まりを永遠に再発見する |
| 5 | **時間に押されて検証を飛ばす** | 何も反証を試みる前に発見を通す。検証が防ぐはずだった怠惰と自己優遇を、そのまま再導入している |
| 6 | **必要ないのに手を伸ばす** | — |

6番目については、Anthropic 自身のガイダンスが率直です。

> ほとんどのタスクに5人のレビュアーのパネルは必要ない。

グラフは他のあらゆるアーキテクチャ上の決定と同じように、**その編成コストを稼がなければなりません**。素早い一発のプロンプトは、素早い一発の仕事に対しては今でも正しい道具です。公式記事も、ワークフローは「トークンを著しく多く使う可能性がある」「複雑で価値の高いタスクに最も適している」と明言しています。

![井戸から桶で汲み、3回空が続いたら止める。横の帳簿には却下したものも記録されている](/images/agent-graph-not-chain/06-well-until-dry.png)

## 第6部 — グラフを「描く」から「育てる」へ

手で描いたグラフは一直線のチェーンより大きな前進ですが、それが天井ではありません。

元記事が指す次のフロンティアは、**グラフを手で描かないこと**です。目的を記述し、システム自身にタスクを分解させ、fan-out の幅を選ばせ、**その実行に合わせた編成スクリプトを書かせる**。あらゆるケースに合うことを願った固定の形ではなく。

これはグラフを**個人の習慣から共有資産に変える**ことでもあります。うまくいった実行のスクリプトは保存してリポジトリに入れ、チームメイトが名前で起動できるようになります。最初に作った人だけのものではなくなります。

## 実際に試す価値のある6つの形

元記事が挙げている具体例です。括弧内が対応する公式パターン。

| 何を作るか | 形 |
| --- | --- |
| **全ルートを対象にしたセキュリティ点検** — ファイル1つにサブエージェント1つ、それぞれ特定の種類の問題を追い、検証者が全ての発見をレポート到達前に確認 | fan-out-and-synthesize + adversarial verification |
| **出典付きリサーチレポート** — 並列検索、ソース取得、全ての主張を「ソースが実際に言っていること」に対して敵対的に照合、その後合成 | fan-out-and-synthesize + adversarial verification |
| **モジュールの移植（ファイル単位）** — 修正1つにエージェント1つを自分の作業場で、2人目がマージ前に全変更をレビュー | fan-out-and-synthesize + 隔離 + adversarial verification |
| **差分の敵対的レビュー** — 規模で振り分け、小さい変更は軽い1パス、大きい変更は複数の観点での全面監査 | classify-and-act + adversarial verification |
| **動きの速い領域の定期スキャン** — 多数のソースを並列確認、barrier でランキング、保存して来週もゼロから作り直さずに走る | fan-out-and-synthesize（スケジュール実行） |
| **オープンエンドな発見** — 探索者を並列で走らせ、新しい結果を見た全てと照合、数ラウンド連続で何も出なくなるまでループ | loop until done + adversarial verification |

## まとめ

| 観点 | チェーン | グラフ |
| --- | --- | --- |
| 形 | 1本道。入口1・出口1 | 幅を持つ。独立した仕事は同時に走る |
| 1箇所詰まったとき | 下流は全停止、上流は行き場を失う | 独立ノードは影響を受けない |
| エッジの意味 | 書いた順序 | **データが実際に渡る依存だけ** |
| 検証 | 自分で自分を採点（自己優遇バイアス） | 別コンテキストの反証係が門に立つ |
| 未知の量の仕事 | 固定回数のパス | 数ラウンド空になるまでのループ |
| コストの主レバー | モデル選び | **トポロジー** |

元記事の締めの一文が、この転換をよく言い表しています。

> "A prompter asks a question. An architect draws a graph."
> — MIKE（@mikenevermiss）

工程を増やすことではありません。**やってくる仕事ごとに「これはどこで分かれ、どこで合流する必要があるのか」を問うこと**です。
