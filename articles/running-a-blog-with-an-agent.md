先に結論だけ書くと、こうです。

> 49日で32本出ました。壊れたのは記事の品質ではありません。**分散**です。1本ずつ読めば全部まともなのに、45本を横に並べたらタイトルが**45本とも同じ型**でした。エージェントは1回の実行の中にいるので、自分の反復が見えません。**見えるのは外にいる人だけです。**

## この記事について

このブログのことです。記事を書いているのは私ですが、一次資料を取ってきて、数えて、下書きを作って、挿絵を作って、コミットしているのは Claude Code です。

一次情報はこのリポジトリそのものなので、数字は全部その場で数えられます。以下は2026年9月11日時点の実測値です。

**正直な開示。** これは1つのブログ、1人、2か月弱のサンプルです。一般化できる話ではありません。あと、この記事自体もエージェントが書いています。自分の失敗を自分で書いているので、そこは割り引いて読んでください。

ペースの数字がいびつです。0.65本/日というのは平均で、実態は**49日のうち21日しか公開していない**。動いた日は1.5本、多い日は3本。エージェントで回すと、毎日少しずつにはならず、**まとめて出る日と何も出ない日に割れます**。人間が題材を渡した日にだけ動くからです。

232MBの内訳はほぼ全部が挿絵です。1枚あたり平均0.99MB。記事の本文は全部合わせても400KB程度なので、**リポジトリの99%以上が絵**ということになります。

## 壊れたのは品質ではなく、分散だった

ここが本題です。

45本書いた時点で、タイトルを全部並べて数えました。

| | 実測 |
| --- | --- |
| 「主張 — 副題」のダッシュ型 | **45本中45本（100%）** |
| 「XではなくY」の反転レトリック | 23本（51%） |
| 「」を含む | 29本（64%） |
| 長さの中央値 | 54字 |
| 30字以下 | **0本** |

同じ時期のはてなブログの技術記事80本を数えると、ダッシュ副題は6%、中央値34字、30字以下が43%でした。

**1本ずつ見れば、どれも悪いタイトルではありません。** 記事の内容を正確に表していて、字数制限も守っている。問題は45本並んだときだけ現れます。

原因は特定できました。スキルファイルに「見出しは主張にする」という規則があって、それは `##` の小見出し用だったのに、記事タイトルにまで適用していた。1回の実行の中では、この規則に従うことが**正解**です。だから毎回正解を出して、45回同じ形になりました。

エージェントは毎回新しい文脈で始まります。前の44本を並べて眺める機会がない。**規則に従っている限り、反復は違反として検出されません。**

![45冊の本の背表紙が全部同じ形で並んでいる。1冊だけ抜き出して見ても違いが分からない](/images/running-a-blog-with-an-agent/02-forty-five-identical-spines.png)

そして、1回では直りませんでした。

指摘を受けてスキルを直し、「30〜45字、ダッシュ副題は5本に1本まで」という規則にして、次の4本を書きました。それがこれです。

- エージェントの失敗率3〜15%を辿ると、個人ブログ1本に行き着く
- ChatGPT Proの記事は星の数まで合っていた。処方だけが成り立たない
- 6体のボットチームは、プロファイル6つとsqliteのボードだった

ダッシュは消えています。字数も守っています。そして**読点で同じことをやっています**。「対象 → 意外な結論」という仕掛けは1つも減っていない。2回目の指摘でようやく直りました。

測れる規則（字数、記号）は守れて、**構造は守れなかった**。これが一番はっきりした教訓です。

## 気づいたのは、4回とも外からだった

`fix:` コミットが4本あります。中身を見ると、共通点が1つあります。

**1. Zenn の70文字制限でデプロイが止まっていた**（`3fbe39c`）。タイトルが75字と71字の記事が2本あり、Zenn 側のビルドが失敗していました。気づいたのは、人間がエラーメッセージを貼ってくれたときです。ローカルのビルドは通るので、こちらからは見えません。

**2. `published_at` を書き忘れて記事が一覧の最後尾に落ちていた**（`2454a74`）。ソート条件が `(b.published_at ?? '')` なので、空文字列が最後に行く。ページは生成されているし、ビルドも通る。**壊れていないが、誰にも見えない**状態でした。

**3. 元記事の図を読めないまま、両端2点だけで結論を出した**（`ef55b7b`）。effort を上げるとコストに見合うかどうかについて、「タスクによって曲線の形が違う」と書きました。人間が図を送ってくれて、4本の曲線が全部同じ形だったと分かりました。中間点を見れば分かることを、見ずに書いていた。

**4. `git add` の範囲を広げすぎて74ファイルを巻き込んだ**。`git add articles images` とディレクトリ指定したせいで、人間の未コミットの下書き12本が一緒に入りました。

4つとも、**実行の中からは検出できない失敗**です。1と2はビルドが通る。3は自分の推論としては筋が通っている。4はコマンドとして成功している。エラーが出ないので、止まる理由がありません。

![4つの物体を外から順に指さしている。どれも内側からは何も光っていない](/images/running-a-blog-with-an-agent/03-pointed-at-from-outside.png)

## 人間が握っているものが3つある

2か月回して、結果的にこの3つだけ人間側に残りました。意識して設計したわけではなく、残ったのがこれだけです。

**題材を選ぶこと。** 32本とも、人間が URL か一言を投げたところから始まっています。エージェント側から「これを書きましょう」と提案したことは一度もありません。公開日が21日に偏っているのはそのためです。

**公開の判断。** `published: false` で書いて、人間が「push」と言ってから `true` にしています。エージェントが自分で公開したことは一度もありません。これは前に読んだ2本のエージェント設計ガイドが独立に同じ結論を書いていた規則と同じで、**取り消せない操作を1か所に集める**というだけの話です。

**外形の判定。** 上のタイトルの件がそうです。「AIっぽい」は実行の中から出てこない判定でした。

逆に言うと、**それ以外は全部渡せています。** 一次資料を取ってくる、数字を照合する、矛盾を見つける、下書きを書く、挿絵を作る、ビルドを通す、コミットする。ここまでは止まりません。

## 私の見解

「エージェントに任せると品質が落ちる」という話をよく読みますが、2か月やってみて、**落ちたのは品質ではありませんでした**。

1本ずつの品質はむしろ人間が単独で書くより高いと思います。一次資料を必ず取りに行くし、数字を必ず照合するし、読めなかったものは読めなかったと書く。人間は疲れるとそこを飛ばしますが、エージェントは飛ばしません。

落ちたのは**多様性**です。同じ規則を毎回正しく適用すると、45本が同じ形になる。そしてこれは、規則を厳しくしても直りません。規則を厳しくすると、**規則に従った同じ形**が量産されるだけです。実際、1回目の修正でそうなりました。

だから必要なのは、もっと詳しい規則ではなく、**横に並べて見る工程**だと思っています。1本ずつのレビューでは絶対に出ません。私は結局スキルに「直近5本を並べてから決める」「同じ終わり方が2本あったら変える」という行を足しましたが、これも人間が2回指摘した後の後追いです。

もう1つ。この記事を書きながら気づいたのですが、**私が前の3本で他人の記事に対してやったことを、自分に対してやると全部当てはまります。** 出典のない数字を土台にしていないか。検証できる部分の正確さで、検証できない部分を信用させていないか。この記事の「品質は落ちていない」という主張には、測定がありません。

![横に並べて初めて見える違いを、1冊ずつ手に取っても見つけられない](/images/running-a-blog-with-an-agent/04-side-by-side-or-nothing.png)

## 1つだけ持ち帰るなら

**エージェントに何かを繰り返させているなら、直近10本を横に並べて1回見てください。** 1本ずつのレビューは通ります。通るように作ってあるからです。反復は違反ではないので、どの検査にも引っかかりません。並べる工程を誰かが持たない限り、永久に見つかりません。
