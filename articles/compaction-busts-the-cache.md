先に結論だけ書くと、こうです。

> プロンプトキャッシュが効く環境では、**削るべき指標は「トークン数」ではなく「接頭辞の書き換え」**だった。要約による圧縮は文脈を短くする代わりにキャッシュを捨てるので、送るトークンが減っても請求は増える。実測で、41%少ないトークンを送った圧縮設定が、何もしない設定の約2倍払っていた。

## この記事について

Towards AI の Louis-François Bouchard、Omar Solano、Samridhi Vaid の3人が AI Engineer World's Fair でやったワークショップの内容を、Bouchard が記事化したものを読みました。本番稼働中の AI チューター（オープンソース）を題材に、数百ドルぶんの eval を回して、自分たちの本番設定が「何もしない」より悪かったという結果を出しています。

- 記事: [Context Engineering in 2026: Why We Stopped Compacting Our Agent's Context](https://www.louisbouchard.ai/context-engineering-2026/) — Louis-François Bouchard（Towards AI）
- ワークショップ動画: [Context Engineering in 2026 — Bouchard, Solano & Vaid, Towards AI](https://www.youtube.com/watch?v=WP3hjUXd918)
- コード: [towardsai/ai-tutor-app](https://github.com/towardsai/ai-tutor-app)
- 実験結果のデモ: [Hugging Face Space](https://huggingface.co/spaces/towardsai-tutors/context-engineering-experiments)

正直に開示します。**私は自分でこの eval を再現していません**。数字は記事からの引用で、私の立場は検証者ではなく読者です。それでも書く価値があると判断したのは、私自身が Claude Code で `/compact` を「詰まってきたら押すもの」として反射で使っていた側で、その反射の根拠が崩れたからです。あと1点、記事の正確な公開日を確定できませんでした（URL にも本文にも日付表記が見つからず）。ワークショップ由来なので、2026年の記事であることまでは言えます。

後半のほうが長いです。数字の整理は原記事を読めば済むので。

## 圧縮したほうが高かった

まず素の数字から。Gemini 3.5 Flash、11〜13ターンのセッションで、`full_history`（何も触らない）と本番プリセット（要約＋ツール出力クリア）の直接対決:

| | full_history | 本番プリセット |
| --- | --- | --- |
| ターンあたりコスト | $0.11 | $0.24 |
| 初回トークンまで | 17秒 | 21秒 |
| メモリ再現率 | 92% | 38% |

3つ全部で「何もしない」が勝っています。安く、速く、覚えている。

種明かしはキャッシュ会計です。圧縮プリセットはトークンを約41%少なく送っていたのに、約2倍払った。`full_history` は入力の約87%をキャッシュ割引で請求されていて、要約側は接頭辞を書き換えるたびに全額を払い直していたから。

もう1つ、私が読んで一番効いた数字。

> 全アームの中で一番多くのトークンを請求されたのが `full_history` で、1ターンあたり約296kトークン、その97%がキャッシュヒット。それでも $0.0063/ターンで最安だった。36ターンの会話で送ったトークンは合計178万。

一番大量に送っている設定が、一番安い。DeepSeek のキャッシュ割引が50倍なので、キャッシュに乗っているトークンは「ほぼ無料の水増し」として振る舞います。

要約の副作用もついていました。ツール出力をクリアした結果、エージェントがさっき取得した情報を再取得しに行く。コストを下げるための操作が、コストの発生源を増やしています。

![圧縮機で書類の束を潰して41%減らしたのに、横につながった請求メーターの針が振り切れている](/images/compaction-busts-the-cache/01-compressed-but-billed-double.png)

## キャッシュはバイト一致でしか効かない

機序は一行です。

> キャップは接頭辞を短くするが、ターン間でバイト単位では同一に保つので、キャッシュはヒットし続ける。要約は接頭辞を「違うもの」にすることで短くするので、キャッシュはミスする。**Shrink the context, don't rewrite it.**

プロバイダのキャッシュ割引は「すでに処理した接頭辞をそのまま再送したとき」にしか適用されません。DeepSeek で最大50分の1、Gemini で約90%オフ。ここに要約を挟むと、割引の前提そのものを壊します。

言い換えると、要約は圧縮ではなくキャッシュ無効化のための書き込みです。50倍の割引に対して自分の元を取るには、必要な詳細を落とさずに文脈を極端に縮めないといけない。そんな要約は存在しません。

![長い紙の帯の末尾に1枚足すのは無害だが、途中を1箇所切ると、そこから先の全部が剥がれ落ちる](/images/compaction-busts-the-cache/02-append-vs-rewrite.png)

## 効いた圧縮は、モデルを呼ばない圧縮だった

ここが実務的に一番持ち帰れる部分です。彼らは DeepSeek 上で2×2（ツール出力をキャップする/しない × 要約する/しない）を、1アーム414ターン×3試行で回しました。

- キャップだけ: $0.189/ターン → $0.117/ターン。38%削減。15組のペア軌跡のうち14組で勝ち
- キャッシュヒット率: 96.0% → 95.9%（ほぼ動かない）
- メモリプローブ精度: キャップなしと同一
- 要約: 素の full_history に対して約+50%、キャップ済み full_history に対しても+32%

**タダの38%**です。そして要約は、どの構成に足しても請求を増やした。

Codex がやっている賢い回避策も試したとのこと。履歴を置き換えるのではなく、変更していない履歴＋「チェックポイント要約を作れ」という指示を1本送る。要約器自身の呼び出しについてもキャッシュが生きる設計で、「宣伝どおりに動いた」と書かれています。それでも彼らの本番設定にはならなかった。

彼らが今動かしている構成:

- モデル: DeepSeek V4 Flash（キャッシュが効くクラウドモデル）
- 検索: hybrid（dense + BM25 + rerank）
- メモリ: 全部保持。ただし全ツール出力に安定したキャップ
- ツール出力のクリア: オフ
- 要約トリガー: 30k → 800k（実質ほぼ発火しない）

そして著者はここで自分に厳しいことを書いています。長いセッションのピークは約287kなので、800k というトリガー自体は本番で検証されていない。「チューニングされたパラメータではなく、まだ当たっていないガードレール」だと。この一文があるかどうかで、記事の信頼度は変わると思います。

## ただしこの結論は $0.55 の関数だ

ここを飛ばして「/compact は無駄」と要約すると事故ります。彼らは同じ記録済みトレースを各社の価格で再請求して、閾値を出しています。

> DeepSeek 価格（キャッシュ入力 $0.0028/Mトークン）では keep-everything が13%勝つ。同一のトレースをフロンティア価格（キャッシュ入力 $0.50/M）で再請求すると、2つのアームはほぼ引き分ける。交点を解くと、**キャッシュ入力が約 $0.55/Mトークンを下回る限り、全履歴保持が勝つ**。

DeepSeek はこの閾値の200分の1に位置するので、そこでは勝負にならない。問題はフロンティアモデルがちょうど閾値の上に乗っていることです。同じ再請求で、full_history は22ターンのセッションでは勝ち、36ターンでは負けました。価格の崖があるわけではなく、履歴が長くなって線を越えただけ。

![細い柱の上でほぼ水平に釣り合った天秤。片方に紙の山、片方に折りたたんだ紙1枚。すみがクランクを回すと傾きが反転する](/images/compaction-busts-the-cache/03-threshold-flips.png)

つまり Claude や GPT クラスを使っている私たちは、答えがセッション長で反転する領域にいます。「圧縮するな」は結論ではなく、価格表と自分のセッション長を見てから決めることです。著者もそう書いています。要約のコードを1行書く前に、自分のプロバイダのキャッシュ入力価格を調べろ、と。

## 逆を向いて見える主張は、実は同じことを言っている

同じ2026年に、方向が逆に見える主張が出ています。Zencoder のニュースレター [Bigger Context Windows Stopped Helping. Memory Is the New Compiler.](https://zencoder.ai/newsletter/the-context-engine-ai-coding-agents)（Neeraj Khandelwal、2026年5月18日）です。

> あるシリーズC のフィンテックのスタッフエンジニアが、チームの2Mトークンモデルを切ったと言ってきた。バグ修正の精度は上がった。（中略）ウィンドウを64kに削り、小さなリポジトリグラフを足して、プロンプトに前倒しで詰めるのではなく必要に応じてシンボルを取得させた。同じモデルで、社内 eval のバグ修正精度が 71% → 84%。タスクあたりの推論コストは約5分の1に。

一見、Bouchard の「全部保持しろ」と正面衝突しています。でも読むと衝突していません。片方は履歴を書き換えるなと言っていて、もう片方は知識を前倒しで詰め込むなと言っている。対象が違います。

Bouchard 側のデータも同じ方向を裏づけています。ドキュメントについては「stuff するな、retrieve しろ」で、ローカルモデルではレッスンを丸ごとウィンドウに突っ込むと全モデルサイズで破綻し、RAG 側は回答品質100%、スループット約5倍、文脈は38kではなく約3k。ワークショップで一番再利用可能な枠組みとして紹介されているのが Samridhi の一言です。

> コンテキストは1つのものではない。チャット履歴は毎ターン伸びる。貼り付けたドキュメントや巨大なツール出力は一発でウィンドウを吹き飛ばす。形が違えば壊れ方が違い、必要な対処も違う。

だから統合ルールはこうなります。**履歴は追記のみでキャッシュに載せる。知識は取得する。ツール出力は決定的に切る。** 3つとも「モデルに書き換えさせない」で一貫しています。

![左手で山に1枚足し、右手で棚から1冊だけ引き抜く。手前には「詰めこむ」用の巨大な漏斗が倒れて使われていない](/images/compaction-busts-the-cache/05-append-and-fetch.png)

証拠の質が対称でないことも書いておきます。Bouchard 側は数百ドルの eval、414ターン×3試行、ペア比較、価格再請求。Zencoder 側は「あるスタッフエンジニアが火曜に言ってきた」＋「同じ話を今月ほかの3人からも聞いた」。方向は合っていますが、同じ重みで引用するものではありません。私は前者を根拠に使い、後者は「業界の体感がどっちを向いているか」の指標として読んでいます。

## 私の見解：トークン数はずっと代理指標だった

ここから先は原記事にも Zencoder にも書かれていない、私の読み方です。

### 1. 壊れたのは手法ではなく指標

私たちが「コンテキストを減らす」と言うとき、本当に減らしたいのは課金される計算であって、トークン数はその代理指標でした。両者は長いあいだ比例していたので、区別する必要がなかった。プロンプトキャッシュがこの比例を切りました。

切れた瞬間、トークン数を最小化する行為は最適化ではなく指標ハッキングになります。41%少なく送って2倍払った、という結果はまさにそれです。ダッシュボードの「送信トークン数」は下がる。請求は上がる。片方だけ見ていれば成功に見える。

この構造は既視感があります。CDN のキャッシュキーを毎回変えてしまう配信、不変データ構造を捨てて「その場で書き換えたほうが速いはず」とやって GC を殴る実装、`ETag` を無効化しながら圧縮率を誇る設定。共有された不変の接頭辞を、局所的な節約のために書き換えるという失敗の同型です。LLM 推論が突然この仲間に入った、というだけの話だと思っています。

だから覚えるべきルールは `/compact` の可否ではありません。**接頭辞は追記専用だと思って扱う。** これは価格が変わっても生き残ります。

### 2. 一番怖いのは38%が「良い」に見えたこと

私がこの記事で背筋が寒くなったのは、コストの数字ではなく、この組み合わせです。

- 本番プリセットのメモリプローブ: 38%
- コスト: 何もしない場合の約2倍
- ブラインド判定者による回答の評価: 良い

品質の見え方が壊れているのではなく、測っていた品質指標が、忘却を検出できていなかった。回答単体は妥当に見える。だって忘れたことは回答に書かれないから。欠落は沈黙として出力されます。

![回答に「良い」の判を押しているが、その紙には穴が空いていて、穴の真下の床にターン1の札が落ちている](/images/compaction-busts-the-cache/04-silent-omission.png)

これは実装上の含意があります。エージェントのメモリを守りたいなら、回答品質の LLM-as-judge では足りません。ターン1で与えた制約が、ターン45で守られているかを直接問う探索（memory probe）が別に必要です。原記事の冒頭の例がまさにそれで、ターン1で1つルールを与え、grep と diff とログを45ターン挟んだあと、エージェントは「やるな」と言われたことを堂々とやって報告する。私も自分の Claude Code のセッションで、まったく同じものを何度も見ています。

品質 eval を持っているチームでも、「忘却の eval」は持っていないことが多いんじゃないでしょうか。少なくとも私は持っていませんでした。

### 3. Claude Code 使いにとっての実務的な含意

ここは原記事の対象（AI チューター、LangChain の1エージェント）と、私たちの環境（コーディングエージェント）がズレるところなので、慎重に書きます。**推論であって検証結果ではありません。**

転用できる確度が高い順に:

**確度が高い: ツール出力のキャップ。** コーディングエージェントは文脈のほとんどがツール出力です。ファイル読み、grep、テスト出力、ビルドログ。原記事の環境でも「会話は高い部分ではなかった、丸め誤差だった」「ターンは約200k入力トークンに着地していて、その大半は取得した素材」と書かれています。コーディングエージェントはこの偏りがもっと極端です。つまりモデルを呼ばずに決定的にキャップする38%の勝ち筋は、コーディングエージェントでこそ効くはず。`rtk` のような出力圧縮 CLI プロキシを噛ませる発想は、たぶんここに効いています（私は効果を計測していません）。

**確度が中くらい: セッション途中で `CLAUDE.md` や MCP のツール定義を書き換えないこと。** これは接頭辞の先頭にあります。先頭を1バイト変えれば、その後ろのキャッシュは全部無効になる。理屈上、セッション中盤の CLAUDE.md 編集は `/compact` より広範囲にキャッシュを壊すはずです。原記事はこの検証をしていないので、私も断言はしません。ただ「設定ファイルを触るのは、セッションを切るタイミングと合わせる」という運用は、コストを1円も測らなくても安全側です。

**確度が中くらい: `/compact` は制約に名前を付けてから押す。** 原記事の整理をそのまま借りると、制約は3つあって処方はそれぞれ違います。

- ウィンドウに入らない → 取得（retrieve）に逃がす。要約ではない
- 請求が伸びる → キャッシュ入力価格を $0.55/M と比べて、要約を書く前に安いキャッシュモデルへ寄せる
- 品質が実際に劣化している → どこで劣化したかを測る。彼らの環境では 800k まで保った

3つの制約、3つの処方、そのうち圧縮なのは1つだけ。私が反射で押していた `/compact` は、たいてい1つ目（ウィンドウ）と3つ目（なんとなく調子が悪い）の混線でした。混線しているなら、押す前にどっちなのかを言えるべきです。

### 4. それでも私は Claude Code で /compact を完全には捨てない

反論を先回りしておくと、「じゃあ全部保持でいいのか」と言われると、フロンティア価格の側では No です。$0.55 の閾値の上にいて、セッションが36ターンを越えていくなら、再請求の実験では要約側が勝っていました。長時間のコーディングセッションは平気で36ターンを越えます。

私の落としどころはこうです。**`/compact` は残す。ただし「詰まってきたから」では押さない。** 押す条件を、ウィンドウ上限に触りそうなときと、タスクが切り替わるときに限る。タスクが切り替わるなら、そもそも圧縮ではなく新しいセッションのほうが正しい（履歴を書き換えるのではなく、捨てる）。書き換えを避けるという原則は、そこでも一貫します。

## 1つだけ持ち帰るなら

要約はコンテキストの操作ではなく、キャッシュへの書き込みです。長さを減らす前に、書き換えを減らす。

そして数字を1つだけ覚えるなら、$0.55/Mトークン。自分のプロバイダのキャッシュ入力価格をこれと比べるまでは、圧縮するかしないかは決められません。
