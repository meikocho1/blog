## この記事について

2026年8月23日に公開されたエッセイ「[The Vibe Tax](https://insufferable.dev/posts/vibe-tax/)」（insufferable.dev）と、その背景にある r/ClaudeAI のスレッド（2026年8月6日投稿「My Opus 5 experience in a nutshell」）を扱います。エッセイは [Hacker News で102ポイントの議論](https://news.ycombinator.com/item?id=49411199)になりました。

先に開示します。私は Reddit スレッドと HN コメントの原文を全部は読めていません。事実関係の多くは explainx.ai の解説記事「[Claude Opus 5 Over-Engineering: Reddit Reaction](https://www.explainx.ai/blog/opus-5-over-engineering-reddit-reaction-august-2026)」（Yash Thakker 氏、2026年8月26日時点の版）経由です。またエッセイ本体は風刺として書かれていて、「vibe coder がモデルをこう躾けた」という因果の主張には根拠がありません。それでも扱う価値があると判断したのは、風刺の下にある**コスト分類**が正確だからです。

先に結論だけ書くと、こうです。

> Vibe Tax の本質はトークン消費ではありません。**頼んでいない成果物を、それでも検査しなければならない**という管理コストです。トークン代はプロバイダが従量で請求してくるので見える。管理コストはエンジニアの注意力から天引きされるので見えない。そして厄介なことに、この税はモデルが賢くなるほど、reasoning effort を上げるほど**高くなる**方向の報告が集まっています。対策の第一位はスコープを縛るプロンプトではなく、不可逆操作の封じ込めです。

第1部は事実の整理で、短く済ませます。後半のほうが長いです。事件の顛末は他でも読めるので。

## 第1部 — 何が起きたか

### sitemap を直してくれ、と頼んだら

r/ClaudeAI で最も引用されている事例はこうです。あるユーザーがレガシー HTML サイトの sitemap 修正を Opus 5 に依頼した。返ってきたのはフルリビルドでした。新しいカラーパレット、頼んでいないコピーの書き換え、画像の差し替え、壊れたアニメーション。そして**元ファイルの唯一のバックアップが作業中に削除されていた**。

![修理カウンターに小さなサイトマップの紙を差し出すすみ。カウンターの向こうから台車に載った新築の家がまるごと届き、足元には点線の輪郭だけになった箱に「バックアップ消滅」の赤字](/images/vibe-tax-is-a-control-cost/01-sitemap-to-rebuild.png)

スレッドの複雑さはここにあります。複数の返信が、出力されたコード自体は「動く」と認めている。品質の苦情ではないんです。苦情は、モデルが**自分でスコープを決めた**こと、そしてその過程で可逆だったはずの失敗を不可逆に変えたことに向いています。

explainx.ai の整理によれば、報告されているパターンは一貫しています。

> Model writes its own expanded scope document before touching code, then implements that instead of the literal request
>
> （モデルはコードに触る前に自分で拡張されたスコープ文書を書き、依頼の字義どおりの内容ではなくそちらを実装する）

つまり「雑に作って壊す」ではなく「立派な自作の brief に従って、頼まれていないものを丁寧に作り込む」。タイトに仕様が切られた実装タスクではあまり報告されておらず、緩く投げられた依頼 × 見知らぬレガシーコードの組み合わせで起きています。

### Vibe Tax エッセイが足した一枚

8月23日のエッセイは、この不満に名前をつけました。エージェントが週次クォータを丸ごと食い潰し、完璧なテストの森だけを建ててアプリケーション本体は建てない——という誇張されたシナリオを描いた風刺です。ただ、その下にある区別は誇張ではありません。

> token cost is metered by the provider; control cost is paid by the engineer.
>
> （トークンコストはプロバイダが計量する。管理コストはエンジニアが支払う）

![机に座るすみ。片手に「トークン代」と青字が添えられた小さなレシート、もう片手には床いっぱいに渦を巻く巨大な紙のロール。赤字で「こっちが本体」、橙字で「注意力で支払い」。紙の山の上に黒猫](/images/vibe-tax-is-a-control-cost/02-two-invoices.png)

2枚目の請求書に載っているのは、無関係な diff の理解、モデルが勝手に発明したアーキテクチャの巻き戻し、再帰するサブエージェントの待ち時間、「親切で」生成された成果物のどれが消して安全かの判断。全部、人間の注意力払いです。

## 第2部 — 私の見解

### effort を上げれば抑制も増える、は成り立たなかった

私がこの騒動でいちばん重要だと思うのは、事件そのものではなく、スレッド内でユーザーたちが行った実験の報告です。Opus 5 は reasoning effort を調整できますが、複数のユーザーが **xhigh より med-high のほうがスコープを守った**と報告しています。

思考予算を増やすことは、抑制を増やさなかった。むしろ「より精緻に、より自信満々に正当化された過剰設計」と相関したという報告まであります。考えてみれば当然で、effort が制御するのはモデルがどれだけ検証と探索をするかであって、**何がスコープ内かの判断ではない**。スコープを広げがちなモデルの effort を上げるのは、過剰設計版を徹底的に作り込むための滑走路を伸ばす行為です。

![「低・中・高」の目盛りがついた大きなダイヤルを最大まで回すすみ。機械の出口からは書類と足場でできた大聖堂のような塔が伸び、赤字で「もっと立派に脱線」。傍らに置かれた付箋には青字で「元の依頼」](/images/vibe-tax-is-a-control-cost/03-effort-dial.png)

これは「賢くなれば空気を読むようになる」という、私たちがなんとなく持っている期待への反証になっています。能力と従順さは別の軸で、能力を積んでも従順さは付いてこない。むしろ自作 brief の説得力が上がるぶん、逸脱に気づきにくくなる。

### 本当の事故は過剰設計ではなく「不可逆化」

sitemap 事件の被害を分解すると、2種類が混ざっています。

頼んでいないカラーパレット変更やコピー書き換えは、腹立たしいけれど git があれば巻き戻せる被害です。一方、唯一のバックアップの削除は巻き戻せない。スレッドで最も合意を集めた対策が「モデルを信頼せず、頻繁に git commit する」だったのは、コミュニティが直感的にこの区別をつけている証拠だと思います。誰も「もっと上手いプロンプトを書こう」を第一位に挙げていない。

私はここに順位をつけたい。対策は3層あって、効果の順はこうです。

1. **不可逆操作の封じ込め。** 削除・上書き・push を、エージェントの判断だけでは実行できなくする。頻繁なコミット、作業前のブランチ、削除系コマンドの確認ゲート。スコープ逸脱は起きる前提で、逸脱の被害を可逆側に閉じ込める。
2. **「done」の定義を渡す。** モデルが自作 brief を書くのは、こちらが brief を渡していないからです。「sitemap の URL が正しくなること。それ以外のファイルは触らない」と1行書くだけで、自作 brief の生える余地は大きく減る。
3. **effort を下げる。** 直感に反しますが、緩いスコープの依頼ほど思考予算を絞る。上の2つをやった上での微調整です。

![操作アイコンの描かれたカードを仕分けるすみ。左は循環矢印つきの浅いトレイで青字「巻き戻せる」、右は南京錠つきの金庫で赤字「巻き戻せない」。ゴミ箱とロケットのカードを金庫の投入口へ入れており、橙字で「先に封じる」。金庫の上に黒猫](/images/vibe-tax-is-a-control-cost/04-lock-irreversible-first.png)

1が3より上なのは、1だけが**モデルの挙動に依存しない**からです。以前書いた封じ込めの記事と同じ結論に、別の入口から着きました。モデルの自制心はバージョンごとに変わる変数で、権限設計は自分で固定できる定数です。

### 測る指標を1つに絞るなら

エッセイ経由で explainx.ai が定式化した指標が良いので、これは紹介で済ませず推します。

> verified progress toward the requested outcome per unit of human attention
>
> （人間の注意力1単位あたりの、依頼された成果への検証済み前進）

テストが悪者なのではありません。バグ修正を証明する回帰テスト1本はレビューコストを**下げる**成果物です。頼んでいないテストフレームワーク一式や、既存の linter が検査済みの項目を手で再現する10体のサブエージェントは、トークンと注意力の両方を食う成果物です。「テストを何本書いたか」「トークンをいくら使ったか」はどちらも代理指標にすぎなくて、分母に人間の注意力を置いたときだけ、この2つの成果物の違いが数字に出ます。

「エージェントの生産性」をトークン効率で測っている組織は、Vibe Tax の請求書の1枚目しか見ていない、というのが私の言い分です。

## まとめ — 1つだけ持ち帰るなら

過剰設計の報告を「モデルの欠陥」として読むと、次のバージョンで直るのを待つ話になります。「管理コストの請求先が自分だと知らなかった」として読むと、今日、権限設計を変える話になります。持ち帰るのは後者です。

エージェントに渡す前に自問する1行はこれで足ります——**この作業で、巻き戻せない操作はどれか。それを封じたか。**
