## この記事について

2026年8月5日、Cloudflare が「**Cloudflare OS**」をオープンソースとして公開しました。一次情報は [公式ブログの発表記事](https://blog.cloudflare.com/cloudflare-os/) と [GitHub リポジトリ](https://github.com/cloudflare/cloudflare-os) です。

先に開示しておくと、私はまだ自分の Cloudflare アカウントにデプロイして触れていません（発表の翌日に書いています）。この記事はブログとリポジトリの記述を読み込んだ整理と、その上での私の解釈です。動かした所感は含まれていません。

先に結論だけ書くと、こうです。

> Cloudflare OS の面白さはチャット UI でもアプリ生成でもなく、**「エージェントが何を見たか」を全部記録して、その記録ごと権限を伝播させる**セキュリティ基盤にあります。MCP が積み残した問題——ツールの呼び出しは制御できても、見たデータの行き先は制御できない——を、初めてプラットフォームの標準機能として塞ぎに来ました。

なので、この記事はワークスペース機能の紹介を短く済ませて、セキュリティモデルに字数を使います。

---

## 第1部 — 発表されたもの（短く）

### 名前は OS、中身は「会社ごと文脈を持ったエージェント基盤」

Cloudflare OS は3つの部品でできています。

- **エージェントワークスペース**：会社がキュレートした文脈とスキルを土台に、隔離されたランタイムでコードを書いて実行できる
- **セキュリティ・ガバナンス基盤**：社内データとサービスへの安全なアクセス制御（本記事の主役）
- **アプリのプラットフォーム**：個人が作って、共有して、共有相手が改造し続けられるアプリ

ブラウザで会話を始めると、それがドキュメントにもアプリにも継続的なワークフローにもなる、という体験です。Cloudflare 社内では今年5月から全社員が使っており、エンジニア以外の職種も日常的に資料作成・定型作業の自動化・データ可視化アプリの作成に使っているとのこと。

「OS」という名前について、リポジトリ自身がこう断っています。

> これは伝統的なコンピュータの OS ではない。「会社が AI で生産的になるための OS」「AI ワークロードを管理する OS」という2つの意味で使っている。

ライセンスは Apache 2.0。コア本体（cloudflare-os）と、Cloudflare 社内の運用を模した例示デプロイ（cloudflare-os-starter)の2リポジトリ構成で、コアにパッチを当てずに自社カスタマイズを重ねる設計です。

![「OS」と書かれた大きな箱を開けたら、中身はカーネルではなく会社の道具と手順書の棚で、すみが棚卸しをしている](/images/cloudflare-os-agent-platform/01-not-a-kernel.png)

機能の紹介はここまでです。「AI ワークスペース」自体は2026年にはもうコモディティで、各社が似たものを出しています。差がつくのは次の部分です。

## 第2部 — 本体：認可を「データの行き先」まで追いかける

### MCP は「何を呼べるか」までしか守れない

社内で AI を使い始めた人が最初に言うのは「API キーをください」です。しかしキーの手渡しは広すぎる権限を長期間ばら撒くことになり、制限も監査もできない。ここまでは既知の問題で、MCP が解決したのもここまでです。MCP サーバーが資格情報を預かり、定義されたツールだけを見せる。

Cloudflare が社内運用で突き当たったのは、その先でした。

> MCP へのアクセスは、エージェントが**どのツールを呼べるか**は教えてくれるが、**どのリソースを観測したか**は教えてくれない。エージェントは複数システムの情報を組み合わせ、より制限の緩い場所へ送り、元のリソースを見る権限のない人にアプリや成果物を通じて晒すことができる。認可は、データが**次にどこへ行けるか**まで考慮しなければならない。

具体例で言うと：エージェントがデータウェアハウスの機密テーブルを読んでダッシュボードを作ったとき、そのダッシュボードの共有が「テーブルを見る権限のない人にテーブルを見せる抜け道」になってはいけない。ツール呼び出しの制御だけでは、これを防げません。

![水道の蛇口には立派な錠前が付いているのに、すみが汲んだバケツの水は柵の外の別の容器へ自由に注げてしまい、赤い書き込みが行き先を問うている](/images/cloudflare-os-agent-platform/02-bucket-past-the-lock.png)

### エージェントは「何も見えない」状態から始まる

Cloudflare OS では、すべてのエージェントとアプリは**アクセスゼロ**から始まります。エージェントが特定のリソースへのアクセスを申請し、人間が許可すると、生成コードには型付きのバインディングとして渡されます。

```ts
const issues = await env.PROJECT.listIssues({
  teamId: "ENG",
  state: "open",
});
```

`env.PROJECT` は「特定のポリシーの下で特定のリソースを使う許可」を表すケイパビリティで、資格情報そのものはエージェントからも生成コードからも完全に隔離されています。サーバーコードは外向きネットワークを全て塞いだ Dynamic Worker で、クライアントコードはブラウザのサンドボックスフレームで動き、明示的に与えられたケイパビリティ以外ではインターネットに出られません。

### Gatekeeper：サービスごとの関所

外部サービスとの間には **Gatekeeper** という Worker が挟まります。対象サービスの API・リソース・操作を理解していて、たとえば GitHub なら：

- リポジトリ1つだけにアクセスを絞る
- Issue は読めるがソースコードは読めない、にする
- 特定フィールドをマスクする
- PR のマージには人間の承認を必須にする

といった粒度で制御します。OAuth と資格情報の保持、ポリシーの強制、**何が読まれたかの記録**、外部に副作用が出る操作の仲介——全部 Gatekeeper の仕事です。エージェント側からは小さな TypeScript API に見えるだけ。

![小さな窓口の中に座ったすみが、鍵束は窓口の内側に掛けたまま、窓越しに決まった形の道具だけを手渡している](/images/cloudflare-os-agent-platform/03-gatekeeper-window.png)

### ここが新しい：ポリシーが「見たもの」に付いて回る

そして本丸です。Cloudflare OS はエージェントが観測したリソースを全部記録し、その観測記録はエージェントとその成果物に**付随し続けます**。

> 別の人がそのワークスペースを開こうとしたり、エージェントと対話したり、成果物を見ようとしたとき、Gatekeeper はその人が「観測済みリソース」への権限を持つかを検証する。

さらに同じ観測ログが、外向きの行動も縛ります。機密データを一度読んだエージェントは、特定の場所への書き込み・新しいコラボレーターの招待・他のエージェントへの作業引き継ぎ・外部リクエストをポリシーで止められる。

つまり権限が「入口」だけでなく、**データと一緒に旅をする**。アプリを作る人もエージェントを使う人も、この仕組みを自分で実装する必要はなく、プラットフォームが下で持っています。社内運用の第1バージョンで「共有を始めた途端にこれが必要になった」というのが、作り直しの直接の動機だったと書かれています。

## 第3部 — 「ファイル」が全部アプリになる（中くらいの分量で）

アプリ機能で押さえるべき点は2つだけです。

**1つ目：すべてのアプリは Worker である。** エージェントがアプリを作ると、ブラウザ側の UI コードと、状態と挙動を持つサーバーコードの2つを書きます。サーバー側はこのプロジェクトのために新しく作られた **Dynamic Worker**（V8 isolate なので専用コンテナ不要）として必要時にロードされ、**Durable Object Facet** としてアプリごとに独立した SQLite を持ちます。クライアントとの通信は Cap'n Web（オブジェクトケイパビリティ型 RPC）で、サーバーのメソッドは人間の UI からもエージェントからも同じように呼べます。

**2つ目：共有が2種類ある。** アプリそのものを共有すると同じ状態をリアルタイムに共同利用でき、「設計図（blueprint）」を共有すると相手は自分のコピーを作ります。設計図にはコードだけが入っていて、SQLite のデータ・会話履歴・資格情報・接続リソースは含まれません。受け取った人は機能要望を出す代わりに、自分で AI に改造させられる。

![すみが書類棚から一枚の紙を引き出すと、紙がその場で小さな歯車の生えた機械に立ち上がり、隣では設計図だけを受け取った黒猫が自分用の別の機械を組んでいる](/images/cloudflare-os-agent-platform/05-file-becomes-app.png)

「ドキュメント・スプレッドシート・スライドという固定のアプリ一式」ではなく「ファイルひとつひとつが専用アプリ」というのは、プロダクトの形として率直に新しいと思います。

## 私の見解 — 評価している点と、疑っている点

### 情報フロー制御が「製品の標準機能」に降りてきたのは初めてだと思う

「読んだデータにラベルが付いて回り、行き先を縛る」という考え方自体は新発明ではありません。情報フロー制御（IFC）として学術的には何十年も前からあり、軍用システムや一部の研究 OS で実装されてきました。ただ、**普通の会社が普通に使う SaaS プラットフォームの、ユーザーが意識しない標準機能**として載ったのは、私の知る限りこれが初めてです。

そしてこれは MCP エコシステム全体への問題提起でもあります。MCP サーバーを立てて満足していた組織は多いはずですが、「エージェントが見たものの行き先」は誰も守っていなかった。Cloudflare はそこに名前と実装を与えました。他のプラットフォームが追随するか、MCP 仕様側に類似の概念が入るか、どちらかが起きると予想します。

### 「組織のスキルライブラリ」は Claude Code の学びの組織版

共有ライブラリに会社の用語・手順・定型作業のやり方をスキルとして貯めて、「誰かが良いやり方を見つけたら全員が使える」ようにする——これは Claude Code の CLAUDE.md やスキルでエンジニアがやってきたことの、そのまま組織スケール版です。個人の道具だったコンテキストのキュレーションが、会社の資産管理になる。この流れは Cloudflare 固有ではなく、来年にかけて各社で起きると思います。

### 疑い：これは「オープンソース」だが「どこでも動く」ではない

一番引っかかっているのはここです。Apache 2.0 でコードは読めますが、実行基盤は Dynamic Worker、Durable Object Facet、Cloudflare Access と、**このプロジェクトのために作られたものを含む Cloudflare 専用機能**の上に成り立っています。自社のサーバーや他のクラウドでセルフホストする道は、現状事実上ありません。

「会社の働き方・手順・スキル・アプリ」という組織の中核資産を全部このランタイムに載せるということは、載せた後の移行コストが極めて高いということです。オープンソースであることはコードの透明性は担保しますが、可搬性は担保しない。導入を検討するなら、「Cloudflare と心中できる範囲の業務から」が現実的な線だと思います。

### 疑い：「OS」というネーミングは実態より野心を語っている

リポジトリ自身が「伝統的な OS ではない」と2回言い訳しているのは、裏を返せばこの名前が実態の記述ではなく**ポジショニング宣言**だからです。「AI 時代の業務基盤のデフォルトレイヤーを取りに行く」という宣言としては上手い名前ですが、読者としては名前に引っ張られず「権限システム付きエージェント実行基盤」として評価するのがよいと思います。

## まとめ — 1つだけ持ち帰るなら

この発表から1つだけ持ち帰るなら、機能一覧ではなくこの問いです。

> **あなたの組織のエージェントが「見たもの」は、いまどこまで行けますか？**

ツールの呼び出し制御（MCP サーバーを立てる）で止まっている組織がほとんどのはずで、その先——観測したデータの行き先の制御——に製品レベルの答えが出たのが今回の発表の意味です。2番目に重要なのが「ファイル=アプリ+設計図共有」というプロダクトの形。3番目が Cloudflare 専用基盤というロックインの重さで、ここは導入判断の分水嶺になります。
