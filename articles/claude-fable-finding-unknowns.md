## この記事について

Anthropic の Thariq Shihipar 氏が書いた [A field guide to Claude Fable 5: Finding your unknowns](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)（2026年7月6日）を読み解きながら、**「AIエージェントに仕事を任せるときの品質は、モデルの性能ではなく自分の unknowns（わかっていないこと）の量で決まる」** という考え方と、その具体的な実践方法を日本語で整理します。

元記事は5分程度で読める短いエッセイですが、書かれている内容は「明日から使えるプロンプト集」としてかなり実用的です。この記事では、元記事の主張を噛み砕きつつ、実際のワークフローに落とし込める形にまとめました。

---

## 1. 地図と現地（Map and Territory）

元記事はまず、こんな比喩から始まります。

> **地図（Map）** = あなたが Claude に渡すもの。プロンプト、Skill、コンテキスト。
> **現地（Territory）** = 実際に作業が行われる場所。コードベース、現実世界、本当の制約。

![手にした地図には描かれていない穴が、現地の作業台には空いている](/images/claude-fable-finding-unknowns/01-map-territory.png)

そして、**この地図と現地のズレこそが「unknowns」** だと定義します。

ここが記事の核心です。Claude が unknowns にぶつかったとき、Claude は「たぶんこれが欲しいんだろう」という**推測で意思決定をするしかない**。そして、

> 任せる作業量が多くなるほど、Claude がぶつかる unknowns も増える。

つまり「AIに大きな仕事を任せる」＝「AIに推測させる回数を増やす」ということです。

### なぜ今この話が重要なのか

著者はこう書いています。

> Claude Fable は、**仕事の品質が「自分が unknowns を明確にできる能力」でボトルネックになる最初のモデル**だと感じている。

言い換えると、こういう時代の変化が起きているという主張です。

| 以前 | 今（Fable 以降） |
| --- | --- |
| モデルの実装能力が足りない | モデルは十分に実装できる |
| 「AIが書けなかった」がボトルネック | **「自分が説明できなかった」がボトルネック** |
| プロンプトエンジニアリング＝AIの操縦 | プロンプトエンジニアリング＝**自分の要件の発掘** |

そして重要な注意点として、

> **単に事前に計画するだけでは不十分**。unknowns は実装の深いところで見つかることもあるし、そもそも「別のやり方で解くべきだった」と気づかせてくれることもある。

だから著者は、unknowns の発見を **実装の「前・中・後」で繰り返す反復プロセス**として扱っています。

## 2. unknowns の4分類

著者は問題を持ち込むとき、いつも4つに分解するそうです。有名なラムズフェルド・マトリクスの応用ですね。

| 分類 | 定義 | 具体例 |
| --- | --- | --- |
| **Known Knowns**<br/>既知の既知 | プロンプトに書いてあること。自分がAIに伝えている要求そのもの | 「この API に認証を追加して」 |
| **Known Unknowns**<br/>既知の未知 | まだ決めていないが、決めていないと自覚していること | 「トークンの有効期限、何分にすべきか決めてない」 |
| **Unknown Knowns**<br/>未知の既知 | あまりに当たり前で書き留めもしないが、**見たら「それだ」とわかる**こと | 「エラー画面のトーン」「ボタンの余白」「この会社の慣習」 |
| **Unknown Unknowns**<br/>未知の未知 | そもそも考えたことすらないこと。**「これがどこまで良くできるか」を知らない**状態 | 「実は既存のライブラリで解決できた」「もっと良いUXパターンがある」 |

![4段の引き出しのうち、一番下だけ取っ手がなく開けられない](/images/claude-fable-finding-unknowns/02-four-drawers.png)

上の3段は苦労すれば開きますが、一番下は**引く場所そのものが無い**ので開きません。これが Unknown Unknowns です。

### 一番厄介なのは Unknown Knowns

個人的にこの4分類で一番刺さるのは **Unknown Knowns** です。

「言われれば当たり前だが、自分では絶対に言語化しない」もの。ここが埋まっていないと、AIの出力は**技術的には正しいのに、なぜか納得できない**という結果になります。デザインのレビューで「なんか違う」しか言えないときの正体がこれです。

### 上手い人は unknowns が少ない、だが「ある」ことを前提にしている

著者は、Claude Code を作った Boris Cherny 氏や Bun の Jarred Sumner 氏のプロンプトを見ていると、

> **彼らが何を求めているかを詳細に把握しているのは明らかだ。**コードベースとモデルの挙動の両方に深く同期している。

と述べつつ、こう続けます。

> **しかし彼らも unknowns の存在を前提にしている。**多くの意味で、unknowns を減らし、unknowns に備えることがエージェンティック・コーディングの「スキル」だ。だが幸運なことに、これは **Claude と協働することで上達できるスキル**だ。

「うまく指示できないのは才能の問題」ではなく、練習で伸びるスキルとして扱われているのがポイントです。以降の章は、そのための具体的な手法になります。

## 3. 実装前（Pre-implementation）

ここからが実践パートです。元記事では4つの手法が挙げられています。

### 3-1. ブレインストーム & プロトタイプ

**狙う unknowns: Unknown Knowns（見ればわかるが言語化できないもの）**

著者は、「見て初めて基準を定義できる」領域では、Claude にブレストとプロトタイプを一緒にやってもらうそうです。

なぜ前倒しするのか。理由が明確に書かれています。

> **プロトタイピング段階で unknown knowns を特定し言語化することは極めて価値が高い。実装中に見つかると（相対的に）高くつくからだ。**機能や仕様の小さな変更が、コード上では劇的に異なる実装を引き起こすことがあり、エージェントが以前の変更を巻き戻すのはより難しい。

たとえば「フレームにボタンを追加したときの見た目を確認したいだけ」なら、バックエンドのルートを繋いだりフロントの状態管理を増やしたりする必要はない、という話です。

さらに著者は、**ほぼ全てのコーディングセッションを探索・ブレスト段階から始める**と書いています。その効果は：

- 意図を持ってプロジェクトのスコープを定義できる
- Claude が自分では見落としていた高価値なアプローチをよく見つけてくれる
- 逆に「木を見て森を見ず」になることもある
- 結果として **スコープを狭すぎ／広すぎに設定するのを防げる**

**プロンプト例（元記事より）**

```text
このデータのダッシュボードが欲しいんだけど、自分にはビジュアルのセンスがなくて
何が可能なのかも分からない。まったく方向性の違うデザイン案を4つ入れた
HTMLページを作って。それに対して反応する形で決めたい。
```

```text
何も配線する前に、新しい編集画面をモックした単一のHTMLファイルを作って。
```

![4案を物干しに並べ、赤い洗濯ばさみで1枚を選ぶ](/images/claude-fable-finding-unknowns/03-four-drafts-on-line.png)

:::message
ポイントは「**選ばせる**」形にしていること。ゼロから言語化させるのではなく、複数案に反応させることで Unknown Knowns を釣り上げています。「4つの全然違う案」というのが効きます。
:::

### 3-2. リファレンス（参照）

**狙う unknowns: 説明コストが高すぎる Known Unknowns**

詳細に説明できない、あるいは説明するのに時間がかかりすぎる場合。

> 図やドキュメント、画像も含められるが、**最高のリファレンスは「ソースコード」**だ。

著者はこう書いています。

> ある挙動を特定の方法で実装しているライブラリや、気に入っているデザインコンポーネントがあるなら、**そのフォルダを Fable に指し示して、何を見ればいいか伝えるだけでいい。たとえ別の言語で書かれていても構わない。** スクリーンショットなどと比べて、マークアップや構造についてはるかに豊かなディテールを Claude に提供できる。

**プロンプト例（元記事より）**

```text
vendor/rate-limiter にある Rust crate が、まさに自分が欲しいバックオフ挙動を
実装している。それを読んで、同じセマンティクスを我々の TypeScript の
API クライアントで再実装して。
```

:::message
「言語が違ってもいい」というのは実務的にかなり効く指摘です。参考にしたい挙動が別言語のライブラリにある、というのは日常的に起きます。
:::

### 3-3. インタビュー

**狙う unknowns: Known Unknowns の洗い出し**

ブレストを十分にやっても、まだ unknowns は残っている。そこで著者は **Claude に自分をインタビューさせます**。

> Claude にインタビューを頼むときは、質問を導くために問題のコンテキストを与えるようにする。

**プロンプト例（元記事より）**

```text
曖昧な点について、1問ずつ私にインタビューして。
私の答えによってアーキテクチャが変わるような質問を優先して。
```

:::message alert
この短いプロンプトには2つの重要な工夫が入っています。
1. **「1問ずつ」** — 10個まとめて質問されると人間は雑に答えます。
2. **「アーキテクチャが変わる質問を優先」** — 質問に優先順位をつけさせることで、どうでもいい確認に時間を使わせない。
:::

### 3-4. 実装計画（Implementation Plans）

実装できると思った段階で、レビュー用の実装計画を書いてもらいます。ここでも工夫があります。

> 計画は、**最も変更されそうな部分**にフォーカスさせる。データモデル、型インターフェース、UXフローなど。こうすることで、Claude は「自分が実際に変更する必要があるかもしれないもの」を浮かび上がらせてくれる。

**プロンプト例（元記事より）**

```text
実装計画をHTMLで書いて。ただし、私がいじる可能性が最も高い決定事項を
冒頭に持ってきて: データモデルの変更、新しい型インターフェース、
ユーザーに見える部分すべて。
機械的なリファクタリングは一番下に埋めていい、そこは君を信頼してる。
```

:::message
「機械的なリファクタは下に埋めていい、信頼してる」という指定が秀逸です。**レビューする人間の注意力は有限なリソース**なので、それを決定的な部分に集中させる設計になっています。長大な実装計画を全部真面目に読んで疲弊した経験がある人には刺さるはず。
:::

## 4. 実装中（During implementation）

### 4-1. セッションを切り替えて成果物を渡す

計画に満足したら、著者は**新しいセッションを作り、成果物（アーティファクト）をプロンプトで渡します**。

> これにより Claude には**新しいコンテキストウィンドウ**が与えられるが、計画段階で集めた情報はすべて手元にある状態になる。

たとえば spec ファイルとプロトタイプを渡して、実装させる。計画段階の試行錯誤のノイズを持ち込まずに、結論だけを引き継ぐ発想です。

### 4-2. implementation-notes.md を書かせる

> **どれだけ計画しても、unknown unknowns は必ず潜んでいる。** エージェントは作業中に、コード内で見つけたエッジケースのせいで別の方針を取る必要があると気づくことがある。

そこで著者は、Claude Code に一時的な `implementation-notes.md`（または `.html`）を持たせ、**下した決定を記録させます**。「次の試行で学べるように」というのが目的です。

**プロンプト例（元記事より）**

```text
implementation-notes.md を維持して。
計画から逸脱せざるを得ないエッジケースに当たったら、保守的な選択肢を選び、
'Deviations'（逸脱）セクションに記録して、そのまま進めて。
```

![主フローは止めず、横穴から落ちる逸脱票だけを箱で受け止める](/images/claude-fable-finding-unknowns/04-deviation-box.png)

:::message
このプロンプトは3つの指示が組み合わさっています。
- **判断基準を先に与える**（「保守的な選択肢を選べ」）→ 迷ったときの挙動が予測可能になる
- **記録させる**（Deviations に書け）→ 後から人間が検証できる
- **止めさせない**（keep going）→ 些細な確認で作業が止まらない

「毎回確認してくる」と「勝手に進めて後で判明する」の間を取った設計です。そして記録された Deviations は、**次の計画時に消せる unknowns のリスト**そのものになります。
:::

## 5. 実装後（Post implementation）

### 5-1. クイズ（自分がテストされる）

長いセッションの後、Claude は自分が思っていたよりずっと多くのことを達成しているかもしれない。

> コードの差分を読むだけでは軽い理解しか得られない。**振る舞いの多くは既存のコードパスに依存しているから**だ。

そこで著者は、Claude に十分なコンテキストを与えた上で、**変更について自分をクイズさせます**。

> **私はクイズに完璧に正解してから初めてマージする。**

**プロンプト例（元記事より）**

```text
この変更で起きたことを全部理解できているか確認したい。
変更についてのHTMLレポートを作って。コンテキスト、直感的な理解、
何をやったか等を含めて、私が読んで理解できる形で。
そして一番下に、私が合格しなければならないクイズを付けて。
```

![クイズに合格しないと、変更を通す扉が開かない](/images/claude-fable-finding-unknowns/05-quiz-gate.png)

:::message
「AIが書いたコードをレビューする」から「**AIが自分の理解度をテストする**」への反転です。差分を眺めて「まあ大丈夫そう」でマージしてしまう問題に対する、かなり実効性のある対策だと思います。
:::

### 5-2. ピッチと説明資料

> 何かを出荷する上で最も重要な部分のひとつは、**賛同と承認を得ること**だ。

ピッチや説明のアーティファクトを最終ドキュメントに含めておくと、こう効くと書かれています。

- **レビュアーがあなたと同じ unknowns からスタートするとき、理解を加速する**
- **専門家が「自分なら予想したはずの unknowns や典型的な失敗点」を、あなたが考慮済みだと確認したいとき、承認を加速する**

**プロンプト例（元記事より）**

```text
プロトタイプ、spec、implementation notes をひとつのドキュメントにまとめて。
Slack に投げて賛同を得られる形にして。デモGIFを先頭に。
```

:::message
これも unknowns フレームの延長で一貫しています。**レビュアーもあなたと同じ unknowns を持っている**。だから、あなたが unknowns を潰した過程そのものが、そのままレビュー資料になる。
:::

## 6. 地図と現地を一致させる（結論）

元記事の締めはこうです。

> モデルが良くなるほど、**正しいアプローチを取ったときに達成できることは増える**。長期的なタスクが間違った結果で返ってきたときは、おそらく unknowns の定義にもっと時間をかけるべきか、あなたと Claude が unknowns に適応しながら進められる実装計画を作るべきだ。

そして、この記事で一番好きな一文がこれです。

> **すべての説明資料、ブレスト、インタビュー、プロトタイプ、リファレンスは、「修正が高くつく前に、知らなかったことを知る」ための安価な手段だ。**
>
> だから次のプロジェクトは、Claude に unknowns を見つける手伝いを頼むことから始めよう。

## 実践チェックリスト

元記事の手法を、そのまま使えるチェックリストにまとめました。

### 実装前

- [ ] **ブレスト**: いきなり実装させず、「全然違うアプローチをN個出して」から始める
- [ ] **プロトタイプ**: 見た目・UXは配線前に単一HTMLでモックし、反応して決める
- [ ] **リファレンス**: 参考にしたい実装があるなら、スクショではなく**ソースコードのパス**を渡す（言語違いOK）
- [ ] **インタビュー**: 「1問ずつ、アーキテクチャが変わる質問を優先して」と依頼する
- [ ] **実装計画**: 変更しそうな決定（データモデル・型・UI）を冒頭に、機械的作業は末尾に

### 実装中

- [ ] 計画が固まったら**新セッション**を作り、spec とプロトタイプを渡して開始
- [ ] `implementation-notes.md` に **Deviations（逸脱）を記録**させる
- [ ] 迷ったときの**判断基準を先に与える**（例: 保守的な方を選べ）

### 実装後

- [ ] **クイズに合格してからマージ**する
- [ ] プロトタイプ + spec + notes を**1枚のピッチ資料**に統合する

### 振り返り

- [ ] `implementation-notes.md` の Deviations を読み、**次回消せる unknowns** を CLAUDE.md や Skill に落とす

## おわりに：所感

このフィールドガイドを読んで一番効いたのは、**「AIへの指示が下手」という問題を「自分の要件が曖昧」という問題に読み替えている**点です。

「プロンプトのコツ」の話は世の中に大量にありますが、この記事の主張は逆方向を向いています。**モデルが十分に賢くなった以上、改善すべきなのはモデルへの伝え方の技巧ではなく、伝える内容が自分の中で固まっていないという事実**だと。

そして4分類のうち、Unknown Knowns と Unknown Unknowns は**定義上、自分ひとりでは見つけられません**。だから Claude に「見つける手伝い」を頼む。この記事の手法（ブレスト、複数案、インタビュー、クイズ）が全部「AIに問いを立てさせる／選択肢を出させる」形をしているのは、そのためです。

実装を頼む前に、**「これから作るものについて、私が決めていないことを質問して」**の一行を足すだけでも、体験は変わると思います。
