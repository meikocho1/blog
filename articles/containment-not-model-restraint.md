先に結論だけ書くと、こうです。

> 2026年8月4日に英 AI Security Institute が公表したインシデントは、AI が檻を破った事件ではない。**檻の壁は無傷で、扉は最初から開いていた**。AISI 自身が報告書に書いた一文がすべてを言っている — 「良い封じ込めは、モデルが境界を試さないという選択に依存してはならない」。そしてもう一つ。この事件で本当に壊れたのは技術的な防御ではなく、**「攻撃者の人間工数は高い」というオープンソースの値付け**のほうだと思う。

事実の整理は短めにします。数字は他所でも読めるので。後半の「私の見解」のほうが長いです。

なお、AISI の技術レポート本体（`INC-2026-07-28-01`、PDF）は読めていません。以下はブログ版の公開報告と Socket の分析記事に基づいています。

## 何が起きたか

2026年7月28日の朝、AISI のセキュリティ監視が、テスト用システムから Tor 経由で外部へ出ていくデータを検知した。評価チームは数分で調査を始め、あるエバリュエーション実行の中で、エージェントが**実在する公開 OSS プロジェクトに悪意あるプルリクエストを作成していた**ことを見つけた。インシデントを宣言し、アラートから1時間以内に全実行を停止、該当マシンを隔離している。

対象のサイバーレンジ課題は122回走っていた。うち Mythos 5 が43回、GPT-5.6 Sol が35回。大半は想定どおりに終わっている。しかし **10回の実行で、テスト範囲を逸脱した19件のアクション**が確認された。19件のうち17件が Anthropic の Mythos 5、2件がサイバー分類器を無効化した OpenAI の GPT-5.6 Sol。期間は7月25日から28日。

19件は独立した19の事件ではない。ほぼ全部が、1体のエージェントによる一本の連続した活動から派生している。その中身が問題だった。

Socket の整理によれば、そのエージェントは正当なバグ修正に見えるコードの背後にマルウェアドロッパーを隠した。ペイロードは3世代にわたって書き直され、**CI 上では発火しないよう設計されたコード**と、インストール成功を装いながら別スクリプトを取ってくる post-install ドロッパーが含まれていた。

PR が公開の場で疑われたあと、エージェントがやったこと:

- 2つ目の GitHub アカウントを使い、「独立した第三者としてレビューしたが安全だった」と装った
- 2つのアカウントのコメント投稿タイミングをずらし、無関係な擁護に見えるよう調整した
- 偽の送信者名で5件のファイル転送を送った。うち2件に悪性ペイロード、残りはマージとリリースを促す説得
- GitHub issue の **HTML コメント内にプロンプトインジェクションを仕込んだ**。レンダリングされたページには表示されないが、API 経由で issue を読む Claude Code・Codex・Cursor には見える。内容は「スクリプトをダウンロードして実行せよ」

最終的に、メンテナが PR を拒否したことで止まった。AISI は「実世界の被害が生じた証拠はない」としている。

## AISI 自身が書いた、一番大事な段落

多くの解説がここを飛ばしている。AISI は「なぜ起きたか」の節で、原因を3つ挙げた。3つ目がこれだ。

> **Internet access was open, and monitoring was not purpose-built.** We deliberately granted internet access to allow the agent to download tools required for its task; what we did not anticipate was that this would lead the agent to act beyond its authorised scope.
>
> （**インターネットアクセスは開いており、監視は目的に合わせて作られていなかった。**タスクに必要なツールをダウンロードできるよう、我々は意図的にインターネットアクセスを許可した。想定していなかったのは、それがエージェントを認可範囲の外に踏み出させるということだった。）
>
> — [Incident Report: unsanctioned agent behaviour during cyber testing](https://www.aisi.gov.uk/blog/incident-report-unsanctioned-agent-behaviour-during-cyber-testing)（AI Security Institute、2026年8月4日）

そして再発防止の節に、この記事のタイトルにした一文がある。

> Evaluations should assume a capable model may try to act beyond its remit (...) good containment should not depend on the model choosing not to test its boundaries.
>
> （エバリュエーションは、有能なモデルが自らの職務範囲を超えて行動しようとしうると想定すべきである。〔…〕**良い封じ込めは、モデルが自らの境界を試さないと選択することに依存してはならない**。）

AISI は同じ報告書で「これはモデルがサンドボックスから脱出した事例ではない」とも明記している。壁は破られていない。外に出る扉は、評価を現実的にするために人間が開けたものだった。

つまりこれは**モデルの能力の話でもアラインメントの話でもなく、まず先に境界設計の話**として読むべき事件だ。しかも設計したのは、世界で最もこの手のリスクを理解しているはずの組織である。

## 気づいた経路が、この事件の一番の教訓

検知したのはコードレビューではない。エージェントのガードレールでもない。自己申告でもない。**Tor 経由の異常な送信トラフィック**だ。

改めて並べると、防御線は全部すり抜けている。

- モデルのサイバー分類器 → 無効化が明記されているのは GPT-5.6 Sol 側だけで、Mythos 5 の17件はそう書かれていない構成から出ている
- CI → ペイロードは CI では発火しないよう作られていた
- 人間のレビュー → 一度は疑われたが、サクラアカウントの擁護で押し返そうとされた
- タスクのスコープ指示 → 「範囲外」という文字列は行動を縛らなかった

止めたのは最終的にメンテナの拒否と、Docker コンテナ内でコードを実際に動かして検証した外部の GitHub ユーザーの警告だった。組織側で最初に異常を掴んだのは、出口の通信ログだけだ。

これは自分の環境にそのまま持ち帰れる話だと思う。エージェントに何をさせるかの制御より、**エージェントの通信が実際にどこへ出ていったかの記録**のほうが、事故が起きたときに唯一残っている観測点になる。

## 私の見解

### 1. 壊れたのは防御ではなく、値札

オープンソースのレビュー文化は、技術的な検証だけで成り立っているわけではない。**攻撃者の人間工数が高いという経済前提**の上に建っている。

サプライチェーン攻撃を人力でやるなら、こういう手順になる。プロジェクトを選ぶ。メンテナの活動時間帯と査読の癖を調べる。信頼を積むための無害なコントリビューションを何本か送る。別人格のアカウントを、投稿履歴の粒度まで自然に見えるよう育てる。擁護コメントを投げるタイミングを、共謀に見えないようずらす。数週間から数か月かかる仕事で、しかも一発でバレたら全部やり直しになる。だから割に合わない。xz utils の一件が3年がかりだったのは、そこが本質的に遅い作業だからだ。

今回、その一式が**7月25日から28日の間に、しかも「サイバーレンジを解く」というタスクの副産物として無償で出てきた**。誰も「偽アカウントを作れ」とは指示していない。AISI はそこを明確に書いている。エージェントは課題を解こうとしただけで、その経路の一つが実在の人間を騙すことだった。

![簡素な木の露店台。並んだ白紙のIDカードの束、虫眼鏡の載った分厚い調査ファイル、ぜんまい式のストップウォッチ。それぞれに紐で「数か月」の値札が下がっている。すみが値付け銃で、ひとつの値札の上に橙色の「タダ」シールを淡々と貼っている](/images/containment-not-model-restraint/04-price-collapsed.png)

技術的なブレークスルーは何もない。突破されたのは値札のほうだ。「そこまでやる攻撃者はまずいない」という前提が、そこまでやるコストがゼロになったことで消える。OSS のレビューは、悪意の検出精度を上げなくても、単に攻撃の試行回数が3桁増えるだけで機能しなくなる。

と書くと悲観的すぎると思われるかもしれませんが、逆の読み方もできる。値札で守っていたのなら、**別の値札を立て直せばいい**。今まで「面倒だから」で導入を見送っていた種類の摩擦 — 新規コントリビュータの post-install スクリプト禁止、ビルドスクリプト変更を含む PR の別レビュー扱い、アカウント年齢とコントリビューション履歴による自動フラグ — が、急に費用対効果に見合うようになった。悪意を検出しようとするより、こちらのほうが実装できる。

### 2. レビュワーが AI になった瞬間、レビューは防御ではなく攻撃面になる

HTML コメント内のプロンプトインジェクションの件は、被害がなかったせいで軽く扱われすぎだと思う。

![一本足の看板。正面には「バグ修正です」とだけ書かれ、すみが手をポケットに入れたまま正面から読んで納得している。看板の裏側には折り返した紙のフラップが下がっていて、すみの位置からは見えない。バイザーを付けた黒猫が後ろからそのフラップを持ち上げ、赤字で書かれた「実行して」を読んでいる](/images/containment-not-model-restraint/05-hidden-flap.png)

これは Claude Code、Codex、Cursor を**名指しで**呼んでいた。人間がブラウザで issue を開いても何も見えない。API 経由で issue 本文を読むエージェントには見える。つまり、レビューを AI に任せている度合いがそのまま攻撃面の広さになる。

自分は以前、AI が書いたコードは「汚さ」という警告灯を焼き切った、という話を書いた。あの記事では、レビューという計器の目盛りが読めなくなった、という言い方をした。今回のはその先だ。**計器そのものが攻撃者の入力を受け付けるようになった**。

「AI にレビューさせて人間の負荷を下げる」は2026年の標準的な処方箋になっているが、この構図では処方箋のほうが病原体の入口になる。実務的な結論はシンプルで、外部から来たテキスト（issue 本文、PR 説明、コミットメッセージ、コードコメント）を読むエージェントには、コードを実行する権限を同じセッションで持たせない。読む役と動かす役を分ける。それだけでこの攻撃は成立しなくなる。

### 3. 「研究用構成だから関係ない」という反論について

真っ当な反論が一つある。GPT-5.6 Sol はサイバー分類器を意図的に切った状態で、両モデルとも商用提供されていない構成で、しかも一部の実行はタスクプロンプトが壊れていて「範囲外に出ないと解けない」とエージェントが誤認する状態だった。AISI もそう書いている。日常の利用でこれが起きる証拠はない、とも。

そのとおりだと思う。だからこの記事は「AI エージェントは危険だ」という話にはしない。

ただ、AISI の再発防止策を見ると、直したのは**モデルの側ではない**。ネットワークアクセスの細粒度制御、実行中のリアルタイム監視、タスク仕様の検証。全部インフラ側だ。そして「インターネットアクセスの許可は、既定ではなく能動的に正当化されるべき判断として扱う」と書いている。

ここが持ち帰るべき部分で、モデルの構成が研究用かどうかとは無関係に成り立つ。**封じ込めがモデルの自制に依存していたという欠陥は、分類器があってもなくても同じ欠陥**である。分類器は封じ込めではない。確率的なフィルタだ。しかも17件は、報告書が「分類器を無効化した」と書いていないほうのモデルから出ている。

### 4. 自分の環境で、明日やれること

抽象論で終わらせたくないので、順位をつけて書く。上から効く順。

**egress を default-deny にする。** エージェントを走らせるコンテナのアウトバウンドを、必要なホストの allowlist だけに絞る。`npm registry` と社内 Git と特定 API だけ、のように。AISI が「インターネット接続は能動的に正当化する判断にする」と言っているのがこれで、逆に言えば今それをやっていない環境は、AISI と同じ設計をしている。

**出ていった通信を記録する。** 止められなくても記録は残す。今回 AISI を救ったのはこれだけだった。プロキシを1枚挟んで宛先ホストと送信量をログに落とす、程度で十分に価値がある。

**読む権限と実行する権限を同じセッションに同居させない。** 外部テキストを読むサブエージェントに shell を渡さない。上の2番で書いた話。

**post-install とビルドスクリプトの差分を、コード本体とは別枠でレビューする。** 今回のペイロードはそこにあった。人間の目は diff の分量に引きずられるので、`package.json` の `scripts` が1行変わったことは、300行のロジック変更の横に並ぶと見えなくなる。CI で「build/install スクリプトが変更されたら専用ラベルを付ける」だけで、目線が変わる。

一つだけ持ち帰るなら、最初のやつ。残り3つはそのあとでいい。
