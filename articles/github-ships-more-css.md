`@primer/react` の npm パッケージには、2023年10月に出た v36.0.0 の時点で CSS ファイルが1つもありませんでした。2026年9月18日の v38.40.0 では、`dist/` の下に CSS が104ファイル、合計 337KB あります。GitHub のデザインシステム Primer が、styled-components を使った CSS-in-JS から CSS Modules へ移った跡です。

GitHub Blog の記事のタイトルは「Improving site performance by shipping more CSS」（CSS を多く届けて、サイトを速くした）でした。読み終えてから配布物を開いてみると、このタイトルは比喩ではなく、ほぼ字義どおりだと分かります。

私の読みを先に置きます。

> 「CSS を増やして速くした」は、ページを描くたびに払っていた計算を、キャッシュが効くバイトに払い替えたという話だ。記事は受け取った側（SSR が55%速くなった）を書いているが、払った側（CSS がどれだけ増えたか）は1行も書いていない。そして何年もかかった移行を最後まで運んだのは Copilot ではなく、`sx` の残り個数を数え続けたダッシュボードと、その数がゼロになった日に廃止された互換パッケージのほうだと思う。

出典は GitHub Blog の [Improving site performance by shipping more CSS](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)、著者は Josh Black と Marie Lucca、2026年9月25日公開です。

先に断っておきます。記事の性能の数字（SSR −55% など）は GitHub の自己申告で、私には検証する手段がありません。私が自分で確かめたのは、npm レジストリに残っているパッケージの版と日付とファイルサイズだけです。github.com が実際にブラウザへ送っている CSS の量は測っていません。

## 記事に書いてあること

短くまとめます。2023年ごろ、一部のページでコンポーネントの数が爆発的に増えて、CSS-in-JS の実行時コストが目に見えるようになった。クライアントでのスタイル初期化で初回表示が遅れ、SSR ではスタイルの収集が重くなり、コンポーネントが増えるほどスタイル更新が膨らんだ。

移行先は CSS Modules です。スタイルはコンポーネントの隣の `.css` ファイルに書き、クラス名は既定でローカルになる。クライアントにもサーバーにも実行時の処理が残らず、スタイルは静的なスタイルシートとして HTML と一緒に届く。

進め方はコンポーネント1つずつで、手順が4つありました。

- 既存のスタイルを CSS Modules に訳した新しいファイルを足す
- 新旧のスタイルを切り替えるフィーチャーフラグに、そのコンポーネントを載せる
- 既存のビジュアルリグレッションテストで、新旧のスナップショットが同一か確かめる
- フラグをチーム → GitHub 社員 → 全ユーザーの順に広げる

2024年12月に Primer の全コンポーネントが移り終わって、記事はこう書いています。

> 55% less time to server-side render a page
> 25% less time for components on a page to initialize
>
> （ページの SSR 時間が55%減り、ページ上のコンポーネントの初期化時間が25%減った。）

どのページの数字なのかは書かれていません。

難しかったのはここからです。Primer のコンポーネントには `sx` という prop があって、インラインのオブジェクトでスタイルを何でも上書きできた。GitHub 本体のコードでは何年もこれが事実上の標準で、ピーク時には約7,760個あった。これを全部 CSS Modules に書き直さないと、styled-components を外せない。

そこで作ったのが [`@primer/styled-react`](https://github.com/primer/react/blob/main/packages/styled-react/README.md) という中継ぎのパッケージです。移行済みのコンポーネントに `sx` を渡せるようにするラッパーで、`sx` を使っている箇所はここから import し、使っていない箇所は `@primer/react` から直接 import して速さを得る。あとはパッケージ単位で `sx` を CSS Modules に訳し、import を差し替え、本番前環境で試して出す。

作業は2025年4月に始まり、社内製の VS Code 拡張と codemod でほぼ自動化され、8人の輪番で6か月かけて6,419個を移した。SSR 時間はページによって1%〜22%改善した。2026年4月に作業を再開したときには残りが895個で、これを2人のエンジニアと「大量の Copilot coding agent」が3週間でゼロにした。そのあと、7種類あるテーマ（それぞれにハイコントラスト版がある）の JavaScript 側を styled-components から切り離すのに2か月。2026年6月時点で、GitHub は100% CSS Modules で動いている、と記事は締めています。

## npm に残っていた移行の跡

記事にはパッケージの話がほとんど出てこないので、npm レジストリから `@primer/react` の tarball を落として中身を数えました。比べるのは `dist/` の下だけです（v37 までは `lib/` と `lib-esm/` に同じ中身がもう2組入っているので、全体で比べると膨らんで見えます）。

| 版 | 公開日 | styled-components への依存 | `dist/` の CSS | `dist/` の JS |
| --- | --- | --- | --- | --- |
| 36.0.0 | 2023-10-31 | あり | 0 | 836KB |
| 37.0.0 | 2024-10-21 | あり | 26KB | 1,315KB |
| 37.31.0（v37 の最終版） | 2025-08-12 | あり | 173KB | 1,198KB |
| 38.0.0 | 2025-10-27 | **なし** | 268KB | 1,251KB |
| 38.40.0（最新） | 2026-09-18 | なし | 337KB | 1,346KB |

3つ読み取れます。

1つ目。CSS は0から337KB に増えています。タイトルの「more CSS」は文字どおりです。

2つ目。`dist/` の JS は減っていません。836KB から1,346KB に増えています。この間にコンポーネント自体が増えているので単純には比べられませんが、少なくとも「JS を削って CSS に置き換えた」という形ではない。減ったのは Primer の外、つまり styled-components という別パッケージの実行時コードと、それが毎回のレンダリングで行っていた処理のほうです（styled-components 自体のサイズは測っていません）。

3つ目。「2024年12月に全コンポーネントが移った」あとも、v37 系は2025年8月まで styled-components に依存し続けています。依存が外れたのは 2025年10月27日の v38.0.0 で、記事の「2025年後半に `@primer/react` を移したとき」と合います。コンポーネントの見た目は CSS Modules に移っていたが、`sx` を受け付けるために依存は残っていた、ということです。

中継ぎの `@primer/styled-react` も npm で確かめられます。

- 初公開は 2025年7月30日（`0.0.0-20250730150946`）
- 最終版 1.0.8 は 2026年5月12日。以後は新しい版が出ておらず、現在この版には非推奨の印が付いている。文言は「The styled version of @primer/react is no longer maintained. Use @primer/react instead.」

最後の版が出た日付は、記事の「`sx` がゼロになったのは2026年5月」と合います。ただ、npm の非推奨の印には日付が残らないので、印がいつ付いたかは分かりません。パッケージ情報の最終更新は 2026年9月25日で、これはブログ記事の公開日と同じです。styled-components 側のメンテナンスモード宣言は [Open Collective の投稿](https://opencollective.com/styled-components/updates/thank-you)で 2025年3月17日。記事の「作業を始める直前に宣言が出た」とも合っていました。

## 数字がきれいに合わないところ

記事には「Total SX props」という面グラフが載っていて、これを読むと本文の数字と少しずれます。

- 本文はピークを「約7,760個」としているが、グラフの左端は7,300前後で、7,760に届くのは5月初めの一瞬の山だけ
- 7,760から6,419を引くと1,341。再開時の残りは895なので、446個の差がある
- グラフは 2025年10月から2026年3月まで、約2,500個でほぼ平らになっている。約5か月、残りの数がほとんど動いていない
- 8月から11月にかけて、数日で数千個跳ね上がってすぐ戻る山がいくつもある

平らな区間は、本文の「作業を再開した（picked this work back up）」という言い方と合います。途中で止まっていたわけです。止まった理由は書かれていません。446個の差は、止まっている間に誰かが別の形で消したのか、新しい `sx` が足されては消されたのか（跳ね上がる山はその可能性を示唆しますが、集計の不具合かもしれない）、グラフからは判断できませんでした。

SSR 改善の表にも1つ気になる点があります。13行のうち、4.54% が4回、6.01% が3回、3.05% と 7.46% が2回ずつ、互いに関係のないコントローラーで同じ値として出てくる。生の測定値というより、何かの区間に丸めた値に見えます。本文は「1%〜22%」と書いていますが、表の最小値は 3.05% で、1%の行は載っていません。

もう1つ、時系列です。`sx` がゼロになったのが2026年5月、その後にテーマの切り離しが「2か月」、そして「2026年6月時点で100% CSS Modules」。順番どおりに足すと7月になります。テーマの作業が `sx` と並行して走っていたのかもしれませんが、記事には書かれていません。

## 私の見解

### 1. 「CSS を増やす」は、計算をバイトに払い替えること

タイトルが面白いのは、フロントエンドの性能の話で「減らした」ではなく「増やした」と言っている点です。これは言葉遊びではなく、トレードの向きを正直に書いていると思います。

CSS-in-JS のコストは、ページを描くたびに払われます。リクエストごとに SSR でスタイルを集め、クライアントで初期化し、コンポーネントが増えればその分だけ増える。CSS Modules のコストは、スタイルシートのバイト数として一度払われ、あとはキャッシュされる。毎回の計算を、使い回せるバイトに払い替えたわけです。GitHub のように同じ人が同じ画面を何度も開くサービスでは、この払い替えはほぼ確実に得になる。

ただ、記事は受け取った側しか書いていません。SSR が55%速くなった、初期化が25%速くなった。払った側、つまりユーザーに届く CSS がどれだけ増えたか、初回訪問（キャッシュが空のとき）の表示がどうなったかは出てこない。npm で見ると `dist/` の CSS は0から337KB です。GitHub が実際に送っている量はこれとは別物（使うコンポーネントだけを束ねているはず）なので、この数字を github.com の値として読むのは間違いですが、ゼロではないことだけは確かです。

「増やして速くした」とタイトルで言うなら、何をどれだけ増やしたのかも数字で見たかった。そこが書かれていれば、同じ移行を検討している読者が自分のサービスで損得を見積もれます。

### 2. Copilot が片付けたのは、6か月かけて作った足場の上の最後の895個

記事で一番引用されそうなのは、2026年4月の3週間で895個をゼロにした話だと思います。数字にするとこうです。

| 期間 | 人数 | 個数 | 1人1週あたり |
| --- | --- | --- | --- |
| 6か月（約26週） | 8人 | 6,419 | 約31個 |
| 3週間 | 2人 + Copilot coding agent | 895 | 約149個 |

約4.8倍。ただ、この比較をそのまま「エージェントで5倍速くなった」と読むのは、たぶん違います。

後半の3週間が始まった時点で、揃っていたものがあります。`sx` を1個ずつ CSS に訳す VS Code 拡張、ファイルごと訳す codemod、`sx` の値を CSS 変数に対応づける移行ガイド、新旧の見た目が同じかを確かめるビジュアルリグレッションテスト、壊れたら戻せるフィーチャーフラグ、そして残りの個数を毎日数えるダッシュボード。エージェントは、この足場の上で「次の1個を訳して、テストが通ることを確かめる」を繰り返したはずです。足場を組んだのは前半の6か月の人間です。

もう1つ。グラフの平らな区間を見ると、残り約2,500個は約5か月間ほとんど動いていません。エージェントはその間も存在していました（記事自身、Copilot coding agent を「作業の途中で出した」と書いています）。数が再び動き出したのは、人間が作業を再開したときです。エージェントが速かったのは確かですが、止まっていた仕事を動かし始めたのは、エージェントではなく再開するという決定のほうでした。

それから、最後の895個が簡単な残りだったのか、難しい残りだったのかも分かりません。codemod をすり抜けて残ったものなら難しいはずで、担当者のいない雑多なものなら簡単なはずです。記事には書かれていません。

### 3. 互換層を置くなら、消す日ではなく、ゼロに向かう数を持たせる

私がこの記事で一番よくできていると思ったのは、`@primer/styled-react` の扱いです。

互換層は、置いたら最後、なかなか消えません。「移行が終わったら消す」と書いても、終わったかどうかを誰も判定しないからです。Primer の場合、この中継ぎパッケージには最初から「GitHub のコードに残っている `sx` の個数」という、ゼロに向かって減っていく数が付いていました。そして npm の日付を見ると、その数がゼロになった5月を最後に、パッケージの更新は止まっています。初公開から約9か月半です。

判定を人の感覚ではなく1つの数字に預けたから、互換層に寿命があった。同じ理屈で、styled-components への依存を外す作業にもフィーチャーフラグを付けています（"we even feature flagged that"）。依存を消すことすら、戻せる形でやった。

逆に言うと、ゼロに向かう数を持たない互換層は置かないほうがいい、というのがこの記事から持ち帰れることだと思います。「いつか消す」は数えられませんが、「残り895個」は数えられます。

## 1つだけ持ち帰るなら

CSS-in-JS からの移行を考えているなら、始める前に「移行対象が残り何個か」を毎日数えるダッシュボードを作ってください。GitHub の記事で、フィーチャーフラグとビジュアルリグレッションテストと互換パッケージを最後まで一本につないでいたのは、あの「Total SX props」のグラフでした。そしてそのグラフは、5か月止まっていたことも正直に見せています。

## 出典と、確かめた方法

- Josh Black, Marie Lucca, ["Improving site performance by shipping more CSS"](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/), The GitHub Blog, 2026年9月25日
- styled-components, ["Thank you"](https://opencollective.com/styled-components/updates/thank-you), Open Collective, 2025年3月17日（メンテナンスモードの宣言）
- npm レジストリ: [`@primer/react`](https://www.npmjs.com/package/@primer/react)、[`@primer/styled-react`](https://www.npmjs.com/package/@primer/styled-react)（2026年9月28日に取得）

npm の数え方を書いておきます。`registry.npmjs.org` から各版の tarball を取得し、tar のヘッダからファイル名とサイズを読んで、拡張子 `.css` と `.js`/`.mjs` のサイズを最上位ディレクトリ別に合計しました（型定義 `.d.ts` は含めていません）。styled-components への依存は、各版の `dependencies` と `peerDependencies` に `styled-components` があるかで判定しています。数字は未圧縮のサイズで、gzip 後の転送量ではありません。

グラフと表の読み取りは、記事に載っている画像を目で読んだものです。元データは公開されていません。

### 検証できなかった点

- SSR −55%、初期化 −25%、SSR 1%〜22% という性能の数字。どのページで、どの期間を比べたのかも記事にない
- github.com が実際にブラウザへ送っている CSS の量と、移行前後の初回表示の変化
- ピーク7,760個と「6,419個移して残り895個」の間の446個の差、グラフの約5か月の横ばいの理由、数千個跳ね上がる山の正体
- 記事は `@primer/styled-react` を最初の CSS 移行（2024年12月完了）の一部として書いているが、npm での初公開は2025年7月30日。それ以前に社内だけで使われていた可能性はある
- 「`sx` ゼロが5月、そこからテーマに2か月、100% CSS Modules が6月」の時系列のずれ
- `@primer/styled-react` に非推奨の印が付いた日。npm には記録がなく、パッケージ情報の最終更新（2026年9月25日）がそれかどうかも判断できない
- Copilot coding agent が具体的に何を担当し、人間がどこをレビューしたか
