先に結論だけ書くと、こうです。

> OCaml の cohttp メンテナが、パストラバーサル修正の PR を公開した約10分後に、自分のサーバのログでその脆弱性を狙う実際のプローブを観測した。エージェント時代のエクスプロイト生成が「バグの噂だけで十分」になったという話だ。ただ、**この事件で無効化されたのは禁輸（embargo）そのものではない。禁輸が本当に売っていた商品が「秘密」ではなく「時間」だったことが露出しただけ**だと思う。そしてもう一つ、この記録には誰もあまり触れていない気味の悪い一行がある — **AI の安全ブロックが作動したのは、攻撃者側ではなくメンテナ側だった**。

事実の整理は短めにします。元記事が読めば済む長さなので。後半の「私の見解」のほうが長いです。

出典は Anil Madhavapeddy（ケンブリッジ大、MirageOS / OCaml cohttp メンテナ）の記事「[Just a rumour of a bug is enough to find a security exploit these days](https://anil.recoil.org/notes/rumour-is-the-exploit)」、2026年8月22日公開、約1,868語。8月28日に Hacker News のフロントページに上がっています（392ポイント）。

先に開示しておくと、引用されている一次資料のうち、bugonomics 論文（arXiv 2605.24632, Pesoli et al.）、Google Cloud の M-Trends 2026、Fang et al. の 2024年論文は、いずれも本文を読んでいません。数字は Anil の記事からの孫引きです。

## 何が起きたか

cohttp（OCaml の HTTP ライブラリ）にパストラバーサルの脆弱性があった。`OSEC-2026-16`。修正自体は単純なもので、Anil の言葉を借りれば「平時であれば、非公開で直し、影響を受ける利用者に伝え、そのあと公開アドバイザリを出す」という定型の手順を踏むはずだった。

そうならなかった。時系列はこうです。

報告はその数日前に、Jane Street 経由で Slack のプライベートチャンネルに届いた。**その報告自体が Claude Fable で見つけられたもの**だった。

パッチを詳しく見る前に、Anil は自分の Claude を当該コードに向けて、他に何が潜んでいるか調べさせようとした。ここで一度止まる。

> Fable frustratingly refused outright due to its security block since I don't have access to Glasswing, but DeepSeek V4 Pro obliged me and independently turned up several related issues. My agent also trivially created an exploit to probe a local live server in under a minute.
>
> （Fable は Glasswing へのアクセスがない私に対して、セキュリティブロックによって腹立たしくも即座に拒否した。しかし DeepSeek V4 Pro は応じてくれて、独立に関連する複数の問題を掘り出した。私のエージェントは、ローカルの稼働サーバを叩くエクスプロイトも1分足らずで難なく作った。）

そのあと、報告者と修正方針をやり取りしてから、**より多くの目を入れるために** `cohttp#1145` を公開で開いた。ここは通常なら数日かけて議論し、1〜2週間でリリースする箇所です。

約10分後。Anil のサイトのログに、パーセントエンコードされたトラバーサル列を試すプローブが並び始めた。

彼自身のコメントが刺さる。「自分でエクスプロイトを作るのに1分しかかからなかったのなら、自動攻撃のウィンドウが開くまでに10分というのは、むしろ長すぎるように見える」。

## 数字の側

Anil が並べている数字のうち、私が重いと思った順に3つだけ。

**Fang et al. (2024)**：GPT-4 エージェントに CVE の記述を与えると、15件のベンチマークのうち **87%** をエクスプロイトできた。記述を与えないと **7%**。つまり「何の話か」という一行が、成功率を12倍にする。禁輸が守ろうとしているのは、まさにこの一行です。

**M-Trends 2026 の mean time to exploit（平均エクスプロイト到達時間）は −7日**。マイナスです。エクスプロイトがパッチに先行している。2018〜19年頃は63日前後、2024年にゼロを切った。

**marimo の `CVE-2026-39987`**：公開 PoC が存在しない状態で、アドバイザリから最初のエクスプロイト試行まで **9時間**。Langflow の `CVE-2026-33017` は **20時間**。

そして May 2026 の "bugonomics" 論文が言っているのは、ボトルネックが**攻撃側の生成能力**から**防御側の修復スループット**へ移った、ということ。LLM は嬉々としてエクスプロイトを生成しているが、メンテナの検証・トリアージ・リリース速度は平坦なままです。

## Anil の3つの案

短く。彼自身が「短期的には3つの組み合わせが要る」と言っている。

1. **もっと秘密の場所でパッチを開発する** — GitHub の temporary private fork は建前上これをやる。ただし CI が繋がらない（GitHub が意図的に切っている）、fork にマージできる PR は1本だけ、レビュアーは admin が1人ずつ登録する必要がある。複数リポジトリにまたがる問題や、8月の OSS のような「たまたま空いている人がレビューする」文化には噛み合わない。そして Anil 自身が「これは間違った穴を塞いでいる」と書いている。
2. **禁輸をやめて、公開で速く直し、継続的に出す** — Chrome は週2回リリースし、再起動なしのダイナミックパッチまでやる。Linux カーネルは最大7日、例外的に14日しか遅らせない。ただし OSS のライブラリは下流の無数の製品に埋め込まれているので、パッケージングが最大の障害になる。
3. **プロトコル層で先回りして防ぐ** — 今回の cohttp のバグには単純な緩和策があった。「リクエスト URL のパーセントエンコードされたパス区切りを正規化する」。このルールは**報告が届いた瞬間に実装可能**で、本修正がレビュー・テスト・パッケージングを通る間も配布できた。Cloudflare は Log4shell のときにマネージドルールでこれをやった。問題は、OSS には商用 CDN の外側にこういうルールを配る仕組みがないこと。

## 私の見解

ここからが本題です。

### 1. 禁輸は「秘密」を売っていたのではなく「時間」を売っていた

「セキュリティ禁輸はもう効かない」という見出しは、正しいけれど、少しだけ間違った方向に読者を連れて行くと思う。

禁輸の目的が「詳細を秘匿すること」だったと読むと、対策は「もっと上手に秘匿する」になる。実際 Anil の案1はそれで、彼自身が行き止まりだと結論している。

そうではなくて。禁輸という制度が実際に**メンテナに供給していた商品は時間**です。報告を受けてから、再現し、影響範囲を確定し、修正を設計し、レビューを回し、リリースを組み、下流に伝えるまでの日数。秘匿はその時間を作るための**手段**にすぎなかった。手段が壊れただけで、必要な時間の量は1分も減っていない。

この読み替えをすると、3つの案の評価が変わります。

- 案1（秘密の場所）は、壊れた手段を修理しようとしている。しかも Fang et al. の 7% → 87% が示しているのは、守るべきものがパッチではなく「何の話か」という一行だということ。パッチを private fork に隠しても、Slack にも Matrix にもメーリングリストにも orphan branch にも、その一行は漏れる経路がある。Anil も「パッチが秘密であることは、issue の記述が正確に正しい人にだけ届くことほど重要ではない」と書いている。ここが一番の急所です。
- 案2（継続的リリース）は、時間の**必要量そのものを削る**。方向としては正しい。ただし削れるのはメンテナ側の工程であって、下流の採用までの時間は削れない。埋め込みライブラリでは、リリースしてもユーザに届くまでが本番です。
- 案3（プロトコル層の仮想パッチ）だけが、**別の手段で時間を買い直している**。修正が終わる前に、緩和を先に配る。時間を買う商品として、これが唯一まともな代替品だと思う。

「禁輸をやめるべきか」という議論の立て方が、そもそも問題を隠している。問うべきは「**時間をどこから買うか**」です。秘密という調達先が枯れた。仮想パッチという調達先はまだ市場が存在しない。今は、その間の空白にいる。

### 2. 拒否は防御側にだけ命中した

私がこの記事で一番背筋が寒くなったのは、10分のプローブではなく、その2段落前です。

Anil は cohttp のメンテナ本人です。自分がメンテしているコードに、報告済みの脆弱性の類縁を探させようとした。Fable はこれを**即座に拒否した**。DeepSeek V4 Pro は応じ、関連する複数の問題を独立に見つけた。

この一件で、拒否は何を達成したか。

エクスプロイトの生成は止まっていない。同じ日に別のモデルが同じ作業をした。攻撃者の側も、当然ながらモデルを自由に選べる。**モデル選択が制約されていない相手に対して、モデル単位の拒否は防御にならない**。

一方で拒否が確実に達成したことがある。**その脆弱性を修正できる唯一の人物の手を、一度止めた**こと。もし DeepSeek が応じていなければ、「関連する複数の問題」は今も cohttp に残っていたはずです。しかもそれらは、報告者の Claude Fable がすでに一度掘り当てた領域の隣にある。

私はこの構造を、以前の記事で書いたことの続きだと思っている（[サンドボックスは破られていない](/articles/containment-not-model-restraint)）。あのとき AISI が報告書に書いたのは「良い封じ込めは、モデルが境界を試さないという選択に依存してはならない」でした。今回はその裏面です。**良い防御は、モデルが応じてくれるという選択に依存してはならない**。依存すると、防御側だけが止まる。

「意図が検証できないから一律に断る」という設計は、意図を検証できない側の問題を、意図が正しい側に押し付けている。Anil が Glasswing（Anthropic のアクセス制御された枠組み）を持っていれば通ったのだろう、と読める。つまり **OSS メンテナは、審査を受けた組織の外側にいるという理由で、自分のコードのセキュリティ調査を断られている**。cohttp を使っている下流の全員が、その帰結を共有します。

これは「AI は攻撃者を利する」という粗い話ではないと思う。攻撃者と防御者の**摩擦の量が非対称**なだけです。攻撃者は断られたら次のモデルに行く。それだけ。防御者は断られたら、たいてい「じゃあ手でやるか」になる。手でやると1分が数時間になる。−7日という数字は、その差が積算した結果に見える。

### 3. 「多くの目」が、そのまま攻撃トリガーになった

Anil が PR を公開した理由は、記事にはっきり書かれている。**より多くの目を入れるため**（"to get more eyes on it"）です。

これは Linus の法則の実装そのものです。OSS のセキュリティ上の優位性は、ずっとここにありました。公開してレビュアーを集められる。その代わり攻撃者にも見えるが、修正が速いから割に合う、という賭けだった。

10分。

この賭けの収支が反転している。公開レビューという**メカニズム自体が、リークチャネルになった**。しかも自動監視されている。Anil の推測どおり、パッケージリポジトリを見張っている攻撃者なら「10分どころか数秒で」到達できる。

ここで GitHub の temporary private fork の制約を思い出してほしい。**CI が繋がらない**。これは事故ではなく、GitHub が「脆弱性情報を安全に保つため」に意図的にそうしている。

つまりメンテナは、こう選ばされている。

- 公開して人間のレビューと CI を得る → 10分後に攻撃が始まる
- 非公開にして情報を守る → 人間のレビュアーを admin が1人ずつ登録する必要があり、CI は使えない

どちらを選んでも、**検証手段のどれかを差し出す**ことになる。パッチの正しさを確認する能力を削って秘密を買うか、秘密を捨てて正しさを買うか。二択です。そして今、秘密のほうは Fang et al. が言う7% → 87% の一行が漏れた時点で、もう買えていない可能性が高い。

「じゃあ非公開のまま CI を回す環境を自前で持てばいい」と思うかもしれませんが、それは資金のある企業がやることで、OSS のメンテナが8月の休暇中にやることではない。bugonomics 論文が「防御側の修復スループット」と呼んでいるボトルネックの正体は、たぶん半分くらいこれです。技術ではなく、**メンテナ1人あたりの可処分時間**。

### 4. メンテナでない私たちにとって何が変わるか

ここは短く。ただ、実務的にはたぶん一番効く。

mean time to exploit が −7日だということは、「アドバイザリが出たら速やかにパッチを当てる」という運用ポリシーが、**すでに設計として遅れている**という意味です。アドバイザリが出た時点で、攻撃は平均して1週間前に始まっている。パッチ適用の速度をどれだけ磨いても、この符号は変わらない。

だから問いが変わる。「どれだけ速くパッチを当てられるか」ではなく、「**リリースを待たずに10分で打てる手が、うちにいくつあるか**」です。

- WAF / リバースプロキシのルールを追加できるか。誰が、何分で、誰の承認で
- 特定のエンドポイントを落とす、あるいはレートを絞る判断が、営業時間外にできるか
- そのライブラリを使っている場所を、10分で列挙できるか（これができない組織のほうが多いと思う）

Anil の案3を組織の内側でやる、ということです。今回の cohttp なら「パーセントエンコードされたパス区切りの正規化」というルール1本で、報告到着の瞬間から本修正までの窓を塞げた。**その1本を書いて配る筋肉が、どこにもない**。CDN を契約している組織だけがそれを持っていて、持っていない組織はパッチを待つしかない。

私はこの格差のほうが、エージェントがエクスプロイトを書けること自体より深刻だと思っている。攻撃能力の民主化は起きた。緩和策の配布能力の民主化は、まだ起きていない。Anil が antibotty ネットワークという名前で研究アイデアとして出しているのは、まさにこの穴です（ケンブリッジの MPhil のテーマとして募集されている。攻撃エージェントと防御エージェントに同じ「噂」を与えてどちらが先に到達するか競わせる CTF を組む、という案が添えられていて、これは正直かなり面白い実験だと思う）。

## 1つだけ持ち帰るなら

順位をつけます。

**1位。時間をどこから買い直すかを決める。** 禁輸が調達先として枯れたことより、代替の調達先を誰も持っていないことのほうが問題です。組織の側なら「リリースを待たずに10分で打てる手」の在庫を数える。ゼロなら、それが今日いちばん大きい穴です。

**2位。モデルの拒否を防御の一部として数えない。** 拒否は攻撃者を止めない（別のモデルに行くだけ）。止まるのは、モデルを選べる立場にない防御側です。安全機構を設計に組み込むなら、それが誰の手を止めるかまで数える。

**3位。「多くの目」のコストが変わったことを認める。** 公開レビューはもうタダではない。10分の露出という値札がついた。だからといって OSS が公開レビューをやめるべきだとは思わないが、「公開すれば安全になる」という前提だけは、そのままでは使えない。

最後に、私がこの記事を強いと思った理由を書いておきます。数字ではなく、Anil が**自分のログを見た**ことです。ベンチマークでも予測でもなく、自分が押した PR の10分後に、自分のサーバに来たリクエストを数えた。エージェントのセキュリティ影響についての議論は、この1年ほとんどが評価環境の中で行われてきた。これは外で起きたことの記録です。
