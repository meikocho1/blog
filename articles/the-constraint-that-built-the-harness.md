> 「harness engineering」の解説記事を読んで、引用元の一次資料まで戻ったら、**要約で落ちていたのは項目ではなく制約**でした。OpenAI がやったのは「手書きコード0行」を**意図的に課した**実験で、7つのやることはその制約から逆算して出てきた結論です。制約なしで項目だけ真似すると、たぶん順番も優先度も分かりません。ついでに、その制約には適用条件も付いていて、原文は「低スループットの環境ではこれは無責任だ」と自分で書いています。

解説記事のほうは、エージェントが壊れる原因はモデルの知能ではなく**周りの環境（＝ハーネス）**だ、という主張で、本番のハーネスがやるべき7つの仕事を並べています。良い整理だと思います。名前が付いていること自体に価値がある。

正直な開示を2つ。**解説記事の本文には画像ブロックが大量に入っていて、私はそれを読めていません**（記事の売りであるチェックリスト本体も画像側です）。読めたのはテキストブロックだけです。もう1つ、Anthropic 側の一次資料は未読で、引用の引用として扱っています。

一方、OpenAI の記事は原文を読みました。読んだら、話が変わりました。

## 解説記事が言っている7つ

先に骨格だけ。

1. **リクエストを契約にする** — 行動の前に、要求を境界のあるオブジェクトに変換する
2. **地図を渡す** — 全ドキュメントではなく、どこを見ればいいかを教える小さな root guide
3. **正しい環境に正しいツールを出す** — 目的・予測可能な出力・明示的な失敗状態・権限境界
4. **メモリを永続状態に外出しする** — 会話は記録の正本ではない
5. **自律の前にセンサーを付ける** — 観測できないものは修正できない
6. **権限をモデルの外で強制する** — モデルは提案でき、認可はハーネスがやる
7. **トレースを記録し、局所的に回復する**

そして全体の主張がこれです。

> プロンプトエンジニアリングはモデルに何をするかを伝える
> コンテキストエンジニアリングはモデルが何を見るかを決める
> **ハーネスエンジニアリングはモデルが行動する世界を作る**

異論はありません。ただ、7つのどれをまずやるべきかは書かれていない。それを決めているのが、一次資料のほうにある制約です。

## 一次資料にあって、要約に無いもの

OpenAI の記事は、冒頭でこう宣言します。

> この5か月、我々のチームはある実験を走らせてきた: **手で書いたコード0行**でソフトウェア製品の社内ベータを構築し、出荷する。

そして次の一文が、この記事全体の設計を決めています。

> **我々はこの制約を意図的に選んだ。**エンジニアリング速度を桁で上げるために必要なものを、否応なく作ることになるからだ。

つまり「0行」は成果の自慢ではなく、**自分たちに課した縛り**です。手で書けないので、詰まったときに人間が代わりに書くという逃げ道がない。だから毎回こう問うしかなくなる。

> 何かが失敗したとき、修正はほとんど決して「もっと頑張れ」ではなかった。前に進む唯一の方法は Codex に仕事をさせることだったので、人間のエンジニアは必ずタスクに入ってこう問うた。「**どの能力が欠けているのか、そしてそれをエージェントにとって可読かつ強制可能にするにはどうすればいいのか**」

この「逃げ道を塞いだから、環境を直すしかなくなった」という順序が、解説記事の7項目には出てきません。7項目は結論であって、動機ではない。

規模も書いておきます。5か月、約100万行、約1,500 PR、エンジニア1人あたり1日3.5 PR、チームは3人から7人へ。手で書いた場合の約10分の1の時間、という見積もり。

そして**適用条件も明記されています**。ここが一番効きました。

> リポジトリは、マージをブロックするゲートを最小限にして運用している。プルリクエストは短命だ。テストの flake は、無期限にブロックするのではなく追試で対処することが多い。エージェントのスループットが人間の注意力を大きく上回るシステムでは、**訂正は安く、待つのは高い**。
>
> **これは低スループットの環境では無責任だろう。**ここでは、しばしば正しいトレードオフになる。

自分たちのやり方が、ある条件下でしか成立しないと明言している。要約はここを落とします。落とすと「マージゲートを減らせ」だけが残って、それは条件次第で普通に事故です。

## 7項目に、値段を付けてみる

ここからは私の作業です。この2週間、たまたま近い話題の記事を続けて読んでいたので、解説記事の7項目に対して「実測がある一次資料はどれか」を並べてみました。

| 解説記事の項目 | 対応する一次資料と、その中身 |
| --- | --- |
| 1. 契約にする | **見つからず**（後述） |
| 2. 地図を渡す | OpenAI: `AGENTS.md` は**約100行**の地図。詳細は構造化した `docs/` に置き、そこが正本 / Uber: AI コンテキストグラフ（2,400万ノード、8,000万エッジ）。接地した agent が38秒で答えた問いに、接地なしは20分かけて誤答 |
| 3. 正しいツールを正しい環境に | Uber: 100ツールで**5万〜7万トークン**のスキーマが毎ターン再送 → CLI 解決とツール検索でコンテキストから排除、code-mode で50〜90%削減 |
| 4. メモリを永続状態に | OpenAI: リポジトリ知識を system of record にする / Warp: skill ファイルを PR で更新 / momo5502: `STATUS.md` が10MB超に膨れてコンテキストを溢れさせ、GitHub issues に移行 |
| 5. 自律の前にセンサー | OpenAI: Chrome DevTools Protocol を runtime に配線、worktree ごとに独立した可観測性スタック。**LogQL / PromQL で問い合わせ可能にしたことで「起動を800ms以内に」が実行可能な指示になった** / Cainex: golden set と back-test |
| 6. 権限はモデルの外で | momo5502: 4週間言い続けても聞かないので、テスト実行をコード側で無効化 / TokenOps: 「統治される対象に、自分を止めるかどうかを決めさせたくない」から enforcement パスにモデルを置かない |
| 7. トレースと局所回復 | Uber: セッション分析ダッシュボードが**16種類のアンチパターン**を金額付きで検出 / momo5502: 2GBのセッションログ監査 |

7つのうち6つに、規模の違う複数の実測が並びます。**そして1番だけが空欄です。**

これは私の探し方の問題かもしれません。ただ、空欄になった理由の推測はできます。**「タスクが静かに再定義されていないこと」を測る方法がない**からです。他の6つは全部、数えられる量（トークン、時間、回数、金額）に落ちます。契約の遵守は落ちない。エージェントが「別の仕事を完了して、しかも成功と宣言した」ことを検出するには、元の要求が何だったかを判定する主体が要る。それは今のところ人間です。

面白いのは、**測れないその項目が、解説記事では1番目に置かれている**ことです。順序としては正しいと思います（契約がなければ他の6つは何を守っているのか分からない）。ただ、実測で背中を押せない項目が先頭に来る構成は、読者が「まず何をするか」を決めるときには効きません。私なら3番（ツールとコンテキストの整理）から始めます。効果が今日数えられるので。

## 唯一、比率を言っている一文

解説記事の中で、私が一番重いと思ったのはこの一文です。

> **ハーネスは、それが制御する故障面より小さくあるべきだ**（The harness should be smaller than the failure surface it controls）

他の記述は「〜すべきだ」で、これだけが「どれくらい」を言っています。しかも反転させて使える。**ハーネスが故障面より大きくなったら、ハーネス自身が新しい故障面**です。

これは抽象論ではなくて、私は直前に実例を1つ見ています。Warp の自己改善スキルループ（フィードバックを集めて、改善エージェントが base skill への差分 PR を出す仕組み）を読んだとき、自動化されているのは差分の起案までで、その先は人間がレビューしてマージする、という構造でした。つまりあの仕組みは、**レビューのキューを1本増やしています**。数百人が数千件のコードレビューを回している組織では割に合う。1人でやっているなら、増えたキューのほうが元の故障面より大きいかもしれない。

同じ判定は OpenAI 側にも当てはまります。彼らのハーネスは巨大です（カスタム linter 群、構造テスト、worktree ごとの可観測性スタック、CDP 配線、背景の掃除エージェント）。でも制御している故障面はもっと大きい（100万行、1,500 PR、手書き0行）。比率としては成立している。

解説記事はこの一文を、他の主張と同じ扱いで途中に置いています。私はここが結論だと思いました。

## いちばん小さくて、いちばん真似しやすかったもの

OpenAI の記事から、規模に関係なく明日できることを1つだけ挙げるなら、これです。

> lint はカスタムなので、**エラーメッセージに修正手順を注入するように書いている**（we write the error messages to inject remediation instructions into agent context）

lint が落ちたとき、エージェントが読むのはエラーメッセージです。そこが「命名規約違反」で終わっていたら、エージェントは推測して直す。そこに「この場合は X に従って Y に直せ」まで書いてあれば、その1回で直る。**エラーメッセージが、そのままエージェントへの指示チャネルになる。**

これは前に読んだ話とも噛み合います。「守らせたいルールは、お願いの置き場ではなく機械が弾く場所に書く」。ただ機械が弾くだけだと、エージェントは弾かれた理由を知りません。**弾く場所に、理由と直し方も一緒に書く**というのが、この一文の内容です。ゲートと教材を同じ場所に置く。

OpenAI の記事にはもう1つ、同じ発想の一般化があります。

> ドキュメントで足りないときは、**ルールをコードに昇格させる**（When documentation falls short, we promote the rule into code）

昇格（promote）という語が良い。書き足すのではなく、置き場所を上げる。

## エントロピーの話は、たぶん一番実感が近い

最後に、解説記事には無くて OpenAI の記事にあった、地味だけど生々しい部分。

> Codex はリポジトリに既に存在するパターンを複製する。**ムラのあるもの、最適でないものも含めて。** 時間とともに、これは必然的にドリフトにつながる。
>
> 当初、人間がこれを手作業で対処していた。**我々のチームは毎週金曜（週の20%）を「AI slop」の掃除に使っていた。** 驚くことでもないが、それはスケールしなかった。

週の20%です。そして対処が、掃除の人員を増やすことではなく、「golden principles」をリポジトリに書き込んで、背景で走る掃除エージェントに定期的にスキャンさせ、逸脱を見つけて小さな修正 PR を開かせることでした。ほとんどは1分以内にレビューできて自動マージされる。

原文はこれを **garbage collection** と呼んでいます。そして技術的負債を高金利ローンに喩えて、まとめて痛みを伴って返すより、継続的に少しずつ返すほうがほぼ常に良い、と書いています。

私がここを引いたのは、**エージェントが自分の出したものを教材にして劣化する**という指摘が、あまり他で見なかったからです。人間のチームでも同じことは起きますが、複製の速度が違う。金曜20%は、その速度の請求書だと思います。

## 1つだけ持ち帰るなら

**要約を読んだら、制約を探しに一次資料へ戻る。**

今回落ちていたのは項目ではありませんでした。7項目は正確に要約されています。落ちていたのは「なぜその7つなのか」を決めた制約（手書き0行）と、その制約が成り立つ条件（高スループット環境）です。

制約が無い状態で項目だけ受け取ると、チェックリストになります。チェックリストは悪くないのですが、**順番と、やらなくていい場合が分かりません**。私が7項目の中で1番に実測が無いことに気づけたのも、一次資料を並べたからでした。

もう1つだけ足すなら、解説記事のあの一文を自分のハーネスに当ててみることです。**それが制御している故障面より、小さいですか。**
