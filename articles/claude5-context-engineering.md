## この記事について

2026年7月24日、Claude Code チームの Thariq 氏（[@trq212](https://x.com/trq212/status/2080710971228918066)）が「**最新世代のモデル向けに、Claude Code のシステムプロンプトを約80%削除した**」と発表しました。しかも、コーディング評価のスコアは**測定可能な低下なし**。同じ内容は [Claude 公式ブログ](https://claude.com/blog)にも「The new rules of context engineering for Claude 5 generation models」として掲載されています。

「プロンプトは長く・詳しく・例をたくさん」が常識だった時代からすると、かなり逆張りに見える話です。この記事では、

- **なぜ8割も削れたのか**（削除の背景にある考え方）
- **「昔の常識」と「今のやり方」6つの対比**（Then / Now）
- **自分の CLAUDE.md やスキルにどう反映するか**（実践）

を整理したうえで、最後に私自身の見解を書きます。

先に結論だけ書くと、こうです。

> 古いモデルのために書いた「ルール」は、新しいモデルにとって**能力を縛る足かせ**になる。Claude 5 世代では、ルールを与えるより**判断材料を与える**方が結果が良い。

---

## 第1部 — 何が起きたのか

### システムプロンプトの8割を消して、評価は落ちなかった

Claude Code のシステムプロンプトは、ユーザーのプロンプトが届く前に毎回読み込まれる「土台の指示書」です。ここにはツールの使い方、コーディング規約、禁止事項などが大量に書かれていました。

Anthropic はこれを、Claude Opus 5 や Claude Fable 5 といった最新世代モデル向けに80%以上削除しました。社内のコーディング評価に劣化は出なかったとのことです。削った量に対して、結果が静かすぎるくらいです。

![巨大な巻物のような指示書を庭ばさみで刈り込み、小さな芯だけを残すすみ](/images/claude5-context-engineering/01-pruning-80.png)

### なぜ削れたのか — 「過剰な制約」が逆にコストだった

チームが社内の利用ログを読み返して気づいたのは、**1回のリクエストの中で指示同士が衝突している**ことでした。

たとえば「適切にドキュメントを残せ」という指示と「コメントを書くな」という指示が、システムプロンプト・スキル・ユーザーの依頼のそれぞれから同時に届く。Claude はユーザーの意図を汲んでだいたい正しく振る舞えるものの、矛盾した指示を捌くために余計な思考を使うことになります。

かつてこれらの制約は「最悪ケースの回避」のために必要でした。ファイルを勝手に消す、コメントだらけのコードを書く——古いモデルの事故を防ぐガードレールです。新しいモデルは周囲の文脈から判断できるため、ガードレールの多くは削除して判断に任せた方がよくなった、というわけです。

![両側の立て札が正反対の指示を出す中、荷物を運ぶすみが札の間で立ち止まる](/images/claude5-context-engineering/02-conflicting-signs.png)

## 第2部 — 「昔の常識」と「今のやり方」6つの対比

スレッドで挙げられていた Then / Now は6つ。実務へのインパクトが大きいのは前半の3つ（ルール・例示・段階的開示）だと思うので、そこに字数を使います。4〜6は短く流します。

| | Then（昔の常識） | Now（今のやり方） |
| --- | --- | --- |
| 1 | ルールを与える | 判断に任せる |
| 2 | 例をたくさん見せる | インターフェースを設計する |
| 3 | 全部先頭に書く | 段階的開示（progressive disclosure） |
| 4 | 大事なことは繰り返す | ツール記述に一度だけ書く |
| 5 | CLAUDE.md がメモリ | 自動メモリに任せる |
| 6 | シンプルな仕様書 | リッチな参照物 |

### 1. ルールを与える → 判断に任せる

旧システムプロンプトにはこんな一文がありました。

> コードでは原則コメントを書くな。複数段落の docstring や複数行コメントブロックは絶対に書くな——最大でも短い1行。

この指示は多くの場面で正しい一方、**複雑なコードに複数行の説明が必要な場面では間違い**になります。旧モデルではこのトレードオフを受け入れるしかなかった。新しいシステムプロンプトでは、こう変わりました。

> 周囲のコードと同じように読めるコードを書け。コメントの密度・命名・イディオムを周囲に合わせろ。

禁止ではなく、**判断基準**を渡しています。「何をするな」ではなく「何に合わせろ」です。

### 2. 例をたくさん見せる → インターフェースを設計する

「ツールの使い方は例で教える」はツール利用の鉄則でした。しかし最新モデルでは、**例がかえって探索空間を狭める**ことが分かったそうです。例を見せられたモデルは、その例の周辺しか試さなくなる。

代わりに推奨されるのは**ツール自体の設計**です。たとえば Todo ツールのステータスを `pending / in_progress / completed` の列挙型にしておけば、それだけで使い方のヒントになる。「in_progress は常に1件だけ」という制約を書けば、望む挙動が定義できる。**パラメータの型と名前が、例文よりも雄弁**だということです。

![例の足あとが小さな円を描いて閉じる横で、道具のダイヤルそのものを削って設計するすみ](/images/claude5-context-engineering/03-example-footprints.png)

### 3. 全部先頭に書く → 段階的開示

旧システムプロンプトには、コードレビューや検証の詳細な手順が常に含まれていました。必要なときには重要だが、**必要ない場面でも毎回コンテキストを消費する**情報です。

現在の Claude Code はこれらを**独立したスキル**に切り出し、必要なときだけ読み込みます。ツールも同様で、一部のツールは「遅延ロード」——エージェントが `ToolSearch` で定義を検索するまでコンテキストに載らない仕組みです。

これは自分の CLAUDE.md にもそのまま適用できます。「Claude が見つけられないと困るから、知っているプラクティスは全部 CLAUDE.md に書いておく」はよくある誤解で、**ファイルのツリーを作って、必要なときに必要なファイルが読まれる構造**にする方がよい、とされています。

![たくさんの引き出しがある棚から、必要な一段だけを開けて中身を取り出すすみと、棚の上で寝る黒猫](/images/claude5-context-engineering/04-drawer-cabinet.png)

### 4. 大事なことは繰り返す → ツール記述に一度だけ書く

旧世代のモデルは、指示を繰り返さないと従わないことがあり、コンテキストの末尾に書いた指示の方が効きやすい癖もありました。そのためシステムプロンプト本文とツール記述の両方に、同じツールの説明が重複して書かれていた。

新世代ではこの重複を削除し、**ツールの使い方はツールの description に一度だけ**書くようになりました。

### 5. CLAUDE.md がメモリ → 自動メモリに任せる

以前は `#` ホットキーで CLAUDE.md に覚えさせるのが推奨でした。現在は Claude が**作業とユーザーに関係するメモリを自動保存**するため、CLAUDE.md を記憶置き場として使う必要が薄れています。

### 6. シンプルな仕様書 → リッチな参照物

プランモードの計画やスペックは、これまで Markdown ファイルとして保存するのが定石でした。しかし新しいモデルは**もっと複雑な参照物**を扱えます。

- Markdown の仕様書ではなく、Artifacts で作った HTML モックアップ
- 文章の仕様ではなく、詳細なテストスイートや別コードベースの移植元関数
- 好みの言語化ではなく、ルーブリック（評価基準表）を渡して検証エージェントに採点させる

「デザインの説明文やスクリーンショットより、HTML モックアップの方が良い結果を生む」と明言されています。**Claude がよく知っている言語＝コードで渡すのが、いちばん忠実度の高い仕様書**だという話です。

![メモ書きを脇にどけて、作業台の上に小さな家の模型を置くすみ](/images/claude5-context-engineering/05-mockup-on-bench.png)

## 第3部 — 自分のコンテキストにどう適用するか

スレッド後半では、レイヤーごとの書き分けが整理されています。

**システムプロンプト**
プロダクト文脈そのもの。「Claude がどの製品の中で何をしているか」を伝える場所。Claude Code を使うだけなら触ることはないが、自作エージェントを作るならここに一番時間をかける。

**CLAUDE.md**
軽量に保つ。リポジトリの目的を短く書き、トークンの大半は**コードベース内の「引っかかりどころ」**に使う（例:「型定義はこの1ファイルに集約し、他の場所には書かない」）。ファイルシステムを見れば分かる「自明なこと」は書かない。詳細は検証スキルなどに切り出して、CLAUDE.md からは参照だけする。

**スキル**
「必要なときに情報を見つけるための軽量なガイド」と考える。重要領域以外では縛りすぎない。長いスキルは複数ファイルに分割して段階的開示にする。**自分やチーム固有の意見・知識・ベストプラクティス**を載せるのに向く。

**参照物**
`@` メンションでファイルを渡す。スペック、モックアップ、コードベースそのもの。**できるだけコードの形で渡す**のが原則。

そして仕上げとして、この「右寸法化（rightsizing）」を自動でやってくれる **`/doctor` コマンド**が Claude Code に追加されています。自分のスキルと CLAUDE.md が過剰か不足かを診断してくれます。

![システムプロンプト・CLAUDE.md・スキル・参照物の4段の棚に、それぞれ合う大きさの荷物を仕分けて置くすみ](/images/claude5-context-engineering/06-four-shelves.png)

## 私の見解 — 「制約はモデル能力に連動した負債」

ここからは私の解釈です。

### ガードレールには「賞味期限」がある

今回の話の本質は「短いプロンプトが良い」ではなく、**制約は書いた時点のモデル能力を前提にした負債**だ、という点だと思います。「コメントを書くな」は旧モデルの事故防止としては正しかった。しかしモデルが賢くなった瞬間、その制約は事故防止ではなく**能力の上限**として機能し始めます。

これはコードの技術的負債とよく似ています。書いた当時は正しかった回避策が、環境が変わった後もそこに残り続け、静かに足を引っ張る。違うのは、プロンプトの負債は**モデルのアップデートのたびに一斉に発生する**ことです。モデルを乗り換えたら、CLAUDE.md の棚卸しもセットでやるべき、ということになります。

### 自分の CLAUDE.md は、たぶんあなたが思うより過剰

この記事を書きながら、自分のグローバル CLAUDE.md と rules ファイルを grep してみました。ALWAYS・NEVER・MANDATORY で始まる命令だけで11箇所。心当たりのある人は多いはずです。うまくいかなかった経験のたびにルールを1行足していくと、CLAUDE.md は**過去の失敗の化石層**になります。そしてその多くは、当時のモデルの失敗であって、今のモデルの失敗ではない。

「ルールを足す」前に「判断基準に言い換えられないか」を考える。`DO NOT add comments` ではなく `match the surrounding comment density`。この言い換えパターンだけでも持ち帰る価値があります。

### ただし「判断に任せる」が困る現場もある

一点だけ留保を付けたいのは、**再現性が必要なチーム運用**です。ルールベースの指示は窮屈ですが、出力のブレは小さい。判断ベースの指示は賢く振る舞いますが、**メンバーごと・セッションごとの揺れ**は増えます。レビュー規約やコミット規約のように「賢さより一貫性」が欲しい領域では、明示的なルールを残す判断も依然として合理的です。スレッド内でも「重要領域では縛ってよい」と述べられており、全部を判断任せにしろという話ではありません。

### 段階的開示は MCP の流れと同じ

もうひとつ面白いのは、この「必要なときに必要な分だけロードする」方向性が、MCP 2026-07-28 のステートレス化や遅延ロードツールと完全に同じ思想だということです。コンテキストウィンドウは広がり続けていますが、業界は「全部載せる」ではなく「**載せない技術**」に投資している。コンテキストは大きいほど良いのではなく、**その瞬間の課題に対して純度が高いほど良い**——この原則は当分変わらなそうです。

## まとめ — 1つだけ持ち帰るなら

この記事から1つだけ持ち帰るなら、`/doctor` でも段階的開示でもなく、**「禁止令を判断基準に言い換える」**という書き換えパターンです。`DO NOT add comments` を `match the surrounding comment density` に。この1手だけで、CLAUDE.md に積もった負債の大半は返せます。

2番目が `/doctor` の実行。3番目が、モデルを乗り換えるたびに CLAUDE.md の棚卸しをセットでやる習慣。ここまでで、この記事の中身はほぼ回収できます。
