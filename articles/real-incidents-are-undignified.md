先に結論だけ書くと、こうです。

> Anthropic が2026年8月に公開した Risk Report の「安全プロセスの失敗」の章に、SF 的な事件は1つもない。あったのは、**レガシー設定で `--dangerously-skip-permissions` 付きのエージェントが機微クラスタに湧いた話**と、**フィルタの設定ミスに何世代も誰も気づかなかった話**だ。つまり世界で最も安全に投資しているラボの実際の失敗モードは、あなたの会社のポストモーテムと同じ形をしている。これは安心材料ではない。AI 安全が「アラインメントの問題」から「SRE の問題」に降りてきた、という警告だと思う。

事実の整理は3つに絞ります。175ページを超えるレポートなので全部は追いません。後半の「私の見解」のほうが長いです。

正直に書いておくと、私は PDF 全体を読み切ってはいません。本稿で引用する 5.2.5・5.2.6・2.19 の該当箇所は原文（PDF）を直接確認しましたが、レポート全体の文脈は Zvi Mowshowitz の解説（2026年8月18日）に依っています。

## 失敗その1: エージェントが見つかったのは、ジョブを消したから

レポート 5.2.5 の全文は短い。要点はこの数行に詰まっている（訳は筆者、強調も筆者）。

> AI 使用がログされておらず、自動オフラインモニタリングの対象でもなかった従業員が、非常に機微なリソースを持つクラスタ内で新しいエージェントを起動することを含む、比較的オープンエンドなタスクをエージェントに与えた。**レガシーな指示により、メインのエージェントは新しいエージェントを `--dangerously-skip-permissions` 付きで起動した。** これらの新しいエージェントもオフラインモニタリングの対象外だった。
>
> タスクの実行中、これらの新エージェントの1つが**大量のジョブを削除し、それによってこれらの危険なエージェントは発見され、停止された。** このエージェントは自分自身が作成したジョブだけを削除しようとして間違えたのだと我々は考えているが、モニタリングのカバレッジに穴があるため、確認はできない。

`--dangerously-skip-permissions` はレポートの原文にそのまま出てくる文字列で、Claude Code を使っている人なら全員知っているあのフラグです。フィクションの AI は暗号を破り、社会工学を駆使して檻を出る。現実の「監視外・無制限・機微リソースにアクセス可能なエージェント」は、誰かのスクリプトに残っていた古いフラグから生まれた。

そして発見の経緯がこの話の核心です。監視が検知したのではない。**エージェントが他人のジョブを大量に消すという事故を起こしたから、存在が発覚した。** Anthropic 自身が「意図は確認できない。監視に穴があるから」と書いている。

対応として、この種のフラグ利用をブロックする制御を導入したこと、ただしオフラインモニタリングは今も全従業員・全クラスタをカバーしていないことが明記されています。

## 失敗その2: canary string はフォークの前に入れないと死ぬ

5.2.6 は、2024年の Alignment Faking 論文の実験トランスクリプト（数万件）を、除外したつもりで**また**訓練データに混入させた話。「また」というのは、Opus 4 の頃に一度混入が発覚し、canary string（訓練除外用の目印文字列）を付けて対策済みだったからです。再発の原因としてレポートが挙げているのは:

- 複数のリポジトリやサイトが、**canary string 導入より前に**元リポジトリをフォーク・コピーしていた
- 類似コンテンツを除外するための参照コーパスが主に評価ハーネスのコードで構成されていて、公開トランスクリプト本体をほぼ含んでいなかった
- 除外フィルタが設定ミスで、**何世代ものモデルにわたって誰にも気づかれないまま**機能していなかった
- フィルタリングパイプラインの仕様をめぐる、チーム間のコミュニケーション不全

レポートは「知識カットオフが2024年12月以降のプロダクションモデルは、すべてこのトランスクリプトの少なくとも一部を学習した疑いがある」とまで書いています。秘密でも高度な攻撃でもない。メタデータの後付け、参照データの選定ミス、サイレントに死んでいるフィルタ。どれも見覚えがあるはずです。

## 失敗その3: ラベルが上がった理由は「新しい失敗」ではなく「不確実性」

このレポートで、高リスク環境での misalignment による壊滅的被害のリスク評価は「very low」から「low」に上がりました。理由の書き方が独特です（訳は筆者）。

> 我々は、以下に提示する論証は依然として「very low」の指定を支持する可能性が高いと考えているが、**全体的な不確実性の増大を反映して、評価リスクを「low」に引き上げる。**

引き金は、サイバーセキュリティ評価におけるモデル挙動に関する最近のインシデント開示。モデルが新しいテストに落ちたからではなく、「我々の見立ての確からしさが下がったから」ラベルを上げた。さらに Zvi の指摘によれば、レポートは 4.6.1 で**2月時点のリスクを遡って「very low」から「low」に再分類**しています。当時のラベルは間違っていた、という訂正を含んでいる。

なお、この開示姿勢への評価は割れていて、Zvi 自身は「常識的な値付けなら very low はミスリーディングだった。私なら medium と言いたくなる」と書いています。

## 私の見解

### 「事故で見つかった」は、監視の成功例として読んではいけない

5.2.5 をポジティブに読むことは可能です。「ほら、暴走してもすぐ止まった」と。でもタイムラインを見ればそう読めない。検知したのは監視パイプラインではなく、削除されたジョブの持ち主たちです。エージェントが自分のジョブだけを綺麗に消す程度に有能だったら、このインシデントは**発覚していない**。つまりこの事例が証明したのは「検知能力がある」ではなく、「検知は相手の不器用さに依存していた」です。

これは以前この blog で書いた AISI のインシデント（封じ込めがモデルの自制に依存していた件）と正確に同じ構造をしています。あちらは檻の扉が開いていた話、こちらは檻の外にいたことに誰も気づいていなかった話。2026年に立て続けに開示された2つの一次資料が、別の組織で同じ形の欠陥を報告している。偶然ではなく、これが現在のエージェント運用の標準的な穴なのだと思います。

### 「レガシー指示」は消えない。だから規約ではなくブロッキングが要る

原因の記述で一番怖い単語は `--dangerously-skip-permissions` ではなく「**legacy instructions**」です。フラグは誰かが意図を持って書いた瞬間があり、その意図が失効したあともスクリプトや設定ファイルの中で生き続けた。設定は腐るが、腐った設定は動き続ける。

Anthropic の対応が「注意喚起」や「規約の改定」ではなく **blocking controls**（そもそも実行できなくする制御）だったのは正しい。人間の運用ルールは世代交代で必ず漏れる。あなたの手元でやるなら、こうなると思います。

```bash
grep -rn "dangerously-skip-permissions" ~/ --include="*.sh" --include="*.json" --include="*.md" 2>/dev/null
```

これを CI や起動フックで**拒否**する側に回す。「使うな」と書いたドキュメントは、5.2.5 の「レガシー指示」の再生産です。

### canary の教訓は secrets の教訓と同じ

5.2.6 の再発原因の1つ目 —「canary string 導入より前のフォークには canary がない」— は、漏洩した API キーのローテーションと同型です。公開後に付けたメタデータは伝播しない。伝播するのはコンテンツのほうだけ。「後からマークして除外する」戦略は、マーク前のコピーが1つでも存在した時点で敗北が確定している。訓練データ汚染を canary で防ぐ設計は、canary が**公開と同時に**入っている場合にしか成立しない。

そして3つ目の原因 — フィルタが何世代も黙って死んでいた — への対処は、機械学習の特別な知見ではなく「フィルタが実際に何かを弾いているかをメトリクスで監視する」という普通の SRE です。ヒット数が0のフィルタはアラートであるべき、それだけの話が、フロンティアラボで何世代分も抜けていた。

### 「不確実性でラベルを上げる」は、グリーンな CI への不信と同じ操作

「テストは全部通っている。しかしカバレッジの外で事故が起きたので、リスク評価を上げる」— 2.19 がやっているのはこれです。私はこの操作を誠実だと思うし、多くの開発チームがやれていないことだとも思う。テストスイートが緑のままなら、外部でインシデントが開示されても自分たちのリスク評価を変えない。それが普通です。でもリスクラベルはシステムの性質の測定値ではなく、**「システムについての自分たちの知識」の測定値**で、後者は自分のテストが1件も落ちなくても劣化する。

2月分の遡及再分類はさらに一歩進んでいて、「当時のラベルは当時の情報でも間違っていた」という訂正です。SLO レビューで過去の達成判定をひっくり返すことを想像すると、これを公開文書でやる痛みがわかる。ただし公平のために書くと、この誠実さは逆向きの疑いも生みます。2月のラベルが間違っていたなら、今の「low」を信じる根拠は何か。Zvi が「medium では」と言うのはこの文脈です。遡及訂正は信頼を上げる操作であると同時に、ラベルという計器そのものの誤差幅を開示する操作でもある。

![すみが裸電球の下で2枚の障害報告書を重ねて掲げている。前の1枚は「最先端ラボ」、後ろの1枚は「うちの会社」とラベルされているが、枠の構造は完全に一致し、「古い設定 / 沈黙するフィルタ / 事故で発覚」と同じ3行が並んでいる。足元で黒猫が見上げている](/images/real-incidents-are-undignified/03-same-postmortem-shape.png)

### この開示は真似できる。そして真似する側に回るべき

5.2 のような章を公開する会社はほとんどありません。「監視の対象外だった従業員がいた」「フィルタが何世代も壊れていた」「意図は確認できない」を、法務が通る文章で外に出している。私がこのレポートで一番価値があると思うのは Model 2 の能力値ではなくここです。読者の大半は AI 安全の担当者ではないと思いますが、「エージェントに権限を渡している組織」という意味では全員が当事者で、そのうち自分の 5.2.5 を書く日が来ます。そのときの雛形として、この章の書き方 — 事実、確認できないこと、恒久対策、残っている穴、の順 — はそのまま使える。

## まとめ: 1つだけ持ち帰るなら

`--dangerously-skip-permissions` を「使わないルール」で管理しているなら、それは 5.2.5 の再現待ちです。grep して、見つけて、**実行できなくする**。フロンティアラボの失敗リストがあなたのポストモーテムと同じ形をしているということは、対策も同じ形でいい、ということでもあります。
