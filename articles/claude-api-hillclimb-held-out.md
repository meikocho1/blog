Anthropic の claude.dev ブログに載ったカスタマーサポートの例で、最後に出てくる数字は「held-out の14チケットで 90.5%、元の構成は 78.6%」です。割合から逆算すると、どちらも42回の試行（14チケット × 3回ずつ）とつじつまが合います。38回と33回。差は5回です。

同じ記事が紹介している `/claude-api hillclimb` のガイドには、テストセットの誤差の目安として `1/sqrt(n·reps)` という式が書いてあります。42回に当てはめると ±15ポイント。記事の例の差11.9ポイントは、スキル自身の物差しで測ると誤差の中に入ります。

私の読みを先に置きます。

> この記事で一番大事な図は、OCR の例（Figure 5）だと思う。ところが、そのすぐ後に挙がっている対策の筆頭、train と test の分割は、OCR 型の過学習をそもそも検出できない。eval のケース全部が OCR を必要とするなら、train も test も一緒に上がるからだ。分割が防ぐのは「特定のケースへの過学習」で、「eval と本番のずれへの過学習」は防がない。後者は hillclimb の中では止められず、build-eval の段階で本番のトラフィックから入力を取ることでしか防げない。

出典は claude.dev ブログの [Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)、著者は Lance Martin、2026年9月28日公開です。

先に断っておきます。私は `/claude-api build-eval` も `hillclimb` も動かしていません。読んだのはブログ本文と図9枚、それから GitHub の [anthropics/skills](https://github.com/anthropics/skills/tree/main/skills/claude-api) にあるスキル本体のうち、eval 関係の4ファイルです（2026年9月29日のコミット #1930 の時点）。記事の実験の数字はすべて Anthropic の自己申告で、私には確かめる手段がありません。

## 記事に書いてあること

前半は eval の設計原則です。良い eval の条件として4つ挙がっています。

> 1. Eval tasks mirror production.
> 2. Performance improves with stronger models and more thinking.
> 3. There is "passable" headroom at the frontier.
> 4. Low run-to-run variance.
>
> （eval のタスクは本番を映していること。強いモデルほど、考える量を増やすほど点が上がること。最上位のモデルでも100%に届かない余地があること。回ごとのばらつきが小さいこと。）

2と3の組み合わせが実用的です。強いモデルで点が上がらないなら、タスクが曖昧か採点器（grader）がずれている。どの回でも必ず落ちるタスクは、難しいのではなく壊れている。「専門家2人が同じ判定をするか」を基準にしろ、と書いてあります。

「adversarial sampling」の節も効きます。今のモデルが落とすケースだけを集めると、eval はそのモデルの苦手の指紋を測るものになる。難しいケースは、人間が「なぜ難しいか」を言えるものだけ入れろ、という話です。

`/claude-api build-eval` はこれを対話の手順にしたもので、入力を本番のトランスクリプト → バグ報告・問い合わせ → 手書きの5〜10件 → コードベースからの合成、の順で集めます。採点は安い順に選ぶ。出力の形が決まっていればコードで判定し、自由記述なら LLM に採点させる（ルーブリックは5段階評価ではなく、確かめられる主張の形で書く）。ベースラインを走らせたあと、同じ出力を2回採点して判定が変わらないか、タイムアウトや途中で切れた回答がないかを確かめ、ベースラインが95%を超えていれば「品質ではなくコストかレイテンシを狙え」と警告します。

後半が hillclimb です。

1. 改善したいもの（性能か、性能を保ったままのコストか）を聞く
2. eval のケースをランダムに train と test に分ける
3. 毎ラウンド、train のトランスクリプトだけを読んで、変更を1つだけパッチとして出す
4. train と test の両方が上がれば採用し、train だけ上がって test が平らなら過学習を疑って戻す
5. 2〜3ラウンド点が止まったら、残った失敗を原因別に仕分ける（採点器のバグ、ハーネスの不具合、ばらつき）

例は2つ載っています。1つ目はカスタマーサポートの44チケット（探索用30、held-out 14）で、Opus 4.8・effort high の 74.4%・1チケット4.6セントから始めて、プロンプトの監査と Opus 5.5・effort low への移行で 87.8%・1.9セント、Sonnet 5・effort low で 88.9%・約1セント、プロンプトにルーティングの規則を足して 98.9%。held-out の14チケットでは 90.5% 対 78.6%、コストは約5分の1。2つ目は claude-api スキル自身の性能を上げた例で、66% から約88%まで上がっています。

## スキル本体に書いてあったこと

ブログは要約なので、スキル本体の eval ガイドを開きました。4ファイル合わせて英文で約18万文字あります。

| ファイル | 行数 | 中身 |
| --- | --- | --- |
| `build-eval.md` | 234 | eval の組み立て |
| `eval-hillclimb.md` | 339 | 性能の hillclimb |
| `cost-hillclimb.md` | 442 | コストの hillclimb |
| `eval-audit.md` | 205 | eval の監査 |

ブログより踏み込んでいる箇所が3つありました。

1つ目は誤差の目安です。`eval-hillclimb.md` はこう書いています。

> For a binary pass-rate the 95% CI half-width is roughly `1/sqrt(n·reps)` - 25 test cases at 2 reps is about ±14 points, 50 at 2 reps about ±10
>
> （合否の割合なら、95%信頼区間の半幅はおよそ `1/sqrt(n·reps)`。テスト25件を2回ずつなら約±14ポイント、50件を2回ずつなら約±10ポイント。）

2つ目は「test」という言葉の扱いです。同じファイルの既定の分け方では、test は毎ラウンド採点され、「its score picks the winning round and is the headline」（その点数で勝ったラウンドを選び、それを見出しの数字にする）。3つ目の validation スライスを作って test を最後まで取っておく形は、「~150+ cases」の大きなセットにだけ任意で勧めていて、「For most evals the extra bookkeeping isn't worth it」（たいていの eval では手間に見合わない）とあります。

ところが `cost-hillclimb.md` のほうには、こう書いてある。

> **Selection set != holdout.** The split whose score picks winners each round is a selection set, even if the guide calls it "test". Pre-register confirm runs for the headline and expect train->holdout shrinkage.
>
> （選抜用のセットは holdout ではない。毎ラウンド勝者を選ぶのに点数を使う分割は、ガイドが「test」と呼んでいても選抜用のセットだ。見出しの数字には事前に登録した確認用の実行を使い、train から holdout に移ると点が縮むと思っておけ。）

「ガイドが test と呼んでいても」の「ガイド」は、読みようによっては隣の `eval-hillclimb.md` のことです。同じスキルの2つのファイルが、同じ言葉を違う意味で使っていて、片方がもう片方に注意書きを付けている。

3つ目は、`cost-hillclimb.md` に出てくる実測の話です。同じ構成が選抜の実行では20問中11問を取り、そのあと3回の確認実行で11、6、11だった、という例が載っています。結論は「cost cut firm, mean quality comparable within noise, NOISIER than baseline」（コスト削減は確か、平均品質は誤差の範囲で同等、ただしベースラインよりばらつく）。ブログの華やかな例の裏で、ガイドはこういう地味な失敗例から規則を作っています。私はブログよりガイドのほうが信用できると思いました。

## 例の数字を、スキル自身の物差しで測る

ブログの割合は、どれも1回あたりの回数に割り切れます。確かめた結果です。

| 段階 | 分割 | 割合 | 3回ずつと見た場合 |
| --- | --- | --- | --- |
| Opus 4.8 high（ベースライン） | 探索30件 | 74.4% | 67/90 |
| Opus 5.5 low ＋ プロンプト監査 | 探索30件 | 87.8% | 79/90 |
| Sonnet 5 low | 探索30件 | 88.9% | 80/90 |
| Sonnet 5 low ＋ プロンプト改善 | 探索30件 | 98.9% | 89/90 |
| 元の構成 | held-out 14件 | 78.6% | 33/42 |
| 最終構成 | held-out 14件 | 90.5% | 38/42 |

1回、2回、4回、5回ずつでは、6つの割合が同時に整数になりません。3回（または6回）ずつなら全部合います。ブログに回数は書かれていないので、これは「3回ずつだと考えるとつじつまが合う」以上のことではありません。

3回ずつだとすると、held-out は42回です。スキルの目安 `1/sqrt(42)` は約 ±15ポイント。90.5% と 78.6% の差は11.9ポイントで、それより小さい。`eval-audit.md` の5節は、この式を「noise floor（誤差の床）」、つまり2つの構成の差を比べる対応ありの差の95%信頼区間の半幅の目安として使っています。「この差は信じていいか」を判定するための、スキル自身の物差しそのものです。

この例は「性能を保ったまま安くする」ことを狙った実行なので、読むべき結論は「約5分の1のコストで、held-out の正解率は下がらなかった」です。これは確かな主張で、十分に価値がある。ただ、記事の最後の一文を「正解率が12ポイント上がった」と読むのは、スキルのガイド自身が止めるはずの読み方です。

Figure 7（inbox-routing の結果ページ、図のキャプションは「schematic（模式図）」）も同じ目で見ると、もっと薄い。24件のうち test は8件、3回ずつで24回。採用された v1 の test は 0.875（21/24）、「train は上がったが test は平ら」として戻された v2 は 0.833（20/24）です。戻すかどうかを決めたのは1回の差でした。模式図なので実測として責めるのは筋違いですが、読者が真似する画面の見本がこの粒度だ、ということは覚えておいていい。

Figure 8 にも1つ引っかかりがありました。2番目の点のラベルは「move to Opus 5.5 & audit prompt」で、モデルの移行とプロンプトの監査が1つの点に入っています。`cost-hillclimb.md` は監査を「安くて1回きりで、ノイズを減らす」最初の工程として置いているので、1ラウンド1変更の規則違反ではありません。ただ、監査だけを当てた点が図にないので、74.4% から 87.8% への跳ね上がりのうち、どれだけがモデルでどれだけがプロンプトなのかは分かりません。本文は安くなった理由の一部を Opus 5.5 の価格（入出力20%安、キャッシュ読み出し60%安）で説明していますが、正解率の上がり方は分けられていない。

held-out の14件そのものについては、ブログは「the search never saw（探索が一度も見なかった）」と書いています。これが最後に1回だけ走らせた確認なら、`eval-hillclimb.md` の既定よりも強い設計です。その場合、弱いのは件数だけです。

## 私の見解

### 1. held-out は OCR を止めない

記事の過学習の節は、OCR の例から始まります。

> consider an evaluation task that benefits from OCR, but OCR is rarely beneficial in your production tasks. The evaluation harness might add an OCR tool to your application, which improves on the benchmark without any impact on production.
>
> （eval のタスクは OCR があると解きやすいが、本番のタスクで OCR が役立つことはまれだとする。hillclimb はアプリに OCR ツールを足すかもしれない。ベンチマークの点は上がるが、本番には何の影響もない。）

Figure 5 はこの形を並べた図で、「タスクの構成が OCR を要求する → OCR ツールが足される」「タスクが /app にある → 『必ず cd /app して pytest』が足される」「言い回しに癖がある → それに合わせたプロンプト」が並んでいます。そしてその直後に「Three things can help address this」として、最初に「Split the cases」が来る。

ここが一番引っかかりました。Figure 5 に並んでいるのは、どれも**eval 全体の性質**です。eval のケースの大半が OCR を必要とするなら、ランダムに分けた train にも test にも OCR が必要なケースが同じ割合で入る。OCR ツールを足せば、両方が一緒に上がる。hillclimb の判定は「両方上がったので採用」です。train だけ上がって test が平らになる、という過学習の合図は出ません。

分割が捕まえられるのは、train の特定のケースに合わせた変更、たとえば失敗したチケットの言い回しをプロンプトに貼り付けた変更です。ガイドが「Never paste failures into the prompt」を別に立てているのもこの種類です。これは本物の問題で、分割は効きます。でも Figure 5 のいちばん上の OCR と /app の例は、分割の網の外にある。

じゃあ何が防ぐのか。記事の原則の1番目、「eval のタスクは本番を映す」しかありません。build-eval が入力を本番のトランスクリプトから取ろうとするのは、たぶんこのためです。つまり OCR 型の過学習は、hillclimb の中ではなく build-eval の段階でしか止められない。記事の構成では、この2つが別の節に分かれていて、つながりが読み取りにくくなっていると思います。

実務でできることを1つ考えました。`eval-hillclimb.md` には「Separate "did the mechanism engage" from "did it help."」という規則があり、エージェントがツールを呼んだ回数などを点数とは別の列で記録させています。この列を本番のログと並べればいい。hillclimb が足したツールや分岐が、eval では60%のケースで動き、本番では2%しか動かないなら、それは OCR です。スキルは eval の中の回数しか数えないので、本番側の回数は自分で持ってくるしかありません。

もう1つ。hillclimb に触らせる対象の選択肢には「Your harness code」が入っていて、記事自身も「ハーネスを自由に直せ、という依頼は行き詰まりやすい」と書いています。OCR 型の追加が起きるのはまさにこの面です。本番の呼び出し回数と突き合わせる手段がないうちは、ハーネスのコードは触らせない一覧に入れておくのが安全だと思います。

### 2. 「test」は、既定の設計では選抜用のセット

2つ目は言葉の問題です。記事は分割を説明するとき、test を「a test set that is never seen（一度も見られないテストセット）」と書いています。hillclimb の分析役は、たしかに test のトランスクリプトを読みません。けれども test の点数は毎ラウンド見られていて、採用か取り消しかの判定と、最後にどのラウンドを勝者にするかに使われる。

ラウンドが増えるほど、「たまたま test で良く出た変更」が採用されやすくなります。24ラウンド回した claude-api スキルの例なら、判定は24回です。最後に報告される test の点数は、定義上、全ラウンドの test の点数の最大値です。構造的に少し甘く出る。`cost-hillclimb.md` の「Selection set != holdout」はまさにこのことを言っていて、同じスキルの中で先に答えが出ています。

私の立場ははっきりしていて、`eval-hillclimb.md` の既定のほうを直したほうがいいと思っています。3つ目のスライスを「150件以上なら任意」としているのは手間の話ですが、件数が少ないほど選抜の甘さは大きくなるので、本当は逆です。件数が少なくて3つに割れないなら、せめて最後に勝者とベースラインだけを別の乱数で走らせ直して、その数字を見出しにする。`cost-hillclimb.md` はそうしろと書いています。

ついでに書いておくと、記事の2つ目の例（claude-api スキル自身）には、train と test の区別がブログにも Figure 9 にも出てきません。66.1% から 87.9% の曲線が、どちらの分割の数字なのかは分からない。

### 3. いちばん価値があったのは、点が止まったときの仕分け

3つ目は、読んでいて一番面白かったところです。claude-api スキルの例で、点が2ラウンド止まったあと、残った失敗を原因別に仕分けたら、こうだった。

> the hillclimber found that the skill content was present but Claude was simply writing older API shapes (e.g., from its trained priors).
>
> （スキルに内容は書いてあったのに、Claude は学習時に覚えた古い API の書き方で書いていた。）

直し方は、スキルの冒頭近くに「覚えている書き方 → 今の書き方」の対応表を置くこと、それから C# と Java の注意書きを、例より上に移すことでした。これで 77% から 80% に上がっています。

内容を足しても直らないのは、足りないのが情報ではなく、モデルが覚えている癖に逆らう力だからです。以前「スキルは効いている」の数字を検証した論文を読んだとき、スキルを取りに行くことと、それに従うことは別の工程だ、という話がありました。この例はその実地版です。スキルは書いてあるだけでは足りず、癖が出る場所の手前に置かなければ効かない。

もう1つ、仕分けで出てきたのは eval 側の壊れ方でした。エラーを1種類捕まえるコードを求めるタスクに、採点器が「最低3段の連鎖」を要求していた。採点器の指示がドキュメントと矛盾していて、実際に API を叩いたらドキュメントが正しかった。Figure 9 の3つ目の区間（80.1% → 87.9%）のラベルは「fixing graders, plus more skill edits」です。この区間の上がり幅のうち、スキルがどれだけ良くなり、採点器がどれだけ正しくなったのかは、記事からは分かりません（ガイドは採点器を直したら全部の版を採点し直せと書いているので、それに従っていれば曲線は同じ物差しでつながっているはずです）。

私はこれを弱点ではなく、hillclimb の本当の使い道だと思っています。点を上げる道具として回しても、実際に一番役に立つ出力は「この eval のここが壊れている」という報告かもしれない。点が止まったら、それを知らせる合図です。

1つ、答えが出せなかった問いを残しておきます。この例の eval はドキュメントから作られていて、hillclimb にはそのドキュメントと SDK を読ませています。正解の出どころを、変更を提案する側が読める。ガイドの「正解をモデルの手の届くところに置くな」という規則は、テスト対象のモデルについての話なので、提案する側については直接は言っていません。スキルの役目がドキュメントの内容を運ぶことなので、これはずるではなく仕事そのものだ、とも言える。ただその場合、ランダムに分けた test のタスクもドキュメントの同じページから作られているので、「test は見ていない」の意味はかなり弱くなります。

## 1つだけ持ち帰るなら

`/claude-api hillclimb` がツールや分岐を足したら、それが eval の中で何回動いたかと、本番のログで何回動くかを並べてください。スキルは前者を数えてくれます。後者は自分で持ってくるしかない。二つの回数が大きく違えば、それが記事の Figure 5 の OCR です。train と test の分割は、その違いを教えてくれません。

割合の逆算は、30件と14件のそれぞれについて1〜6回ずつの場合を総当たりし、ブログの割合（小数第1位）が整数の回数から出るかを確かめました。3回と6回ずつのときだけ全部が合います。誤差の目安は `eval-hillclimb.md` と `eval-audit.md` にある `1/sqrt(n·reps)` をそのまま使いました。`eval-audit.md` の5節はこれを差の信頼区間の目安としても使っています。チケットごとの結果は公開されていないので、正確な対応ありの検定はしていません。
