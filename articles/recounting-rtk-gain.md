先に結論だけ書くと、こうです。

> 私の手元の `rtk gain` は「79.1% 節約」と表示する。同じデータベースを自分で数え直すと、1コマンドあたりの節約率の中央値は 0%、書き換えられた 24,734 件のうち 59% は 1 トークンも減らしていなかった。79% の 74% は、たった 10 回の `cat` と `find` が作った数字だった。RTK が悪いのではない。**私が「節約メーター」だと思って見ていた数字は、「エージェントに見せなかったバイト数」であって、請求書とは別のものだった。**

## この記事について

2026年9月11日、Quesma の Jacek Migdal 氏が「RTK reports huge token savings, but our cost benchmarks disagree」という記事を出しました。RTK（Rust Token Killer）は Claude Code などのコーディングエージェントが実行するシェルコマンドの出力を圧縮する CLI プロキシで、GitHub のスターは私が見た時点で 79,950。Quesma は数日かけて 1,500 ドル分のトークンを使い、RTK あり／なしで 1,740 回タスクを走らせています。Hacker News に上がり、私が 2026年9月12日 0:37（日本時間）に Algolia の API で数えた時点で 83 ポイント、コメント 50 件。

同じことを JetBrains の Denis Shiryaev 氏が 7 月に別のベンチマークで見ていて、そちらも読みました。記事ページから日付が取れなかったので月までしか言えませんが、この結果を根拠に RTK のリポジトリに立った issue #3157 は 7 月 22 日付です。

私の位置を書いておきます。**私は RTK のユーザーです。** 2026年6月13日から、Claude Code のフックで Bash ツールのコマンドを全部 RTK 経由に書き換えさせています。手元のバージョンは 0.44.1 で、これは古い。JetBrains が試したのが 0.43.0、Quesma が 0.45.0、最新は 9 月 11 日に出た v0.49.0 です。だから以下の手元の数字は、いまの RTK の集計方法と同じとは限りません。

もう1つ。私は 8 月 23 日の記事「トークンを41%減らして請求が2倍になった」の中で、こう書きました。

> `rtk` のような出力圧縮 CLI プロキシを噛ませる発想は、たぶんここに効いています（私は効果を計測していません）。

計測した人が 2 組出てきたので、この記事はその宿題です。ただし私自身は RTK あり／なしの A/B を回していません。回したのは、RTK が手元に残していた記録を数え直すことだけです。

後半のほうが長いです。2 本の記事の要約は原文を読めば済むので、手元の数字と見解に字数を使います。

## Quesma は 1,740 回走らせて「一般的な節約手段としては勧めない」と書いた

設定は 2 系統です。Claude Code + Claude Fable 5.0 と、OpenCode + DeepSeek V4 Pro 0813。ベンチマークは端末操作が多い Terminal-Bench 2.1。各タスクを RTK なしで 5 回、ありで 5 回。拒否が出た 4 タスクを除いて Fable 85 タスク、DeepSeek 89 タスク、合計 1,740 回。

結果は、総額で見ると Fable が 5% 安く、DeepSeek が 5% 高い。ただしタスクごとの平均変化で見ると、Fable は +1%（信頼区間が 0 を跨ぐ）、DeepSeek は +17%。そして Fable の節約はほぼ 1 タスク（winning-avg-corewars）に集中していて、それを除くと 1% 未満。

私がいちばん重要だと思った一節はここです。

> rtk gain は、RTK の文書によれば、生の出力から圧縮後の出力を引いたバイト数を 4 で割ったもので、課金されたトークン数ではない。
>
> （中略）これがソーシャルの投稿が間違えるところだ。rtk gain は削った出力を数えているのであって、節約した金額を数えているのではない。高くなった試行を、最適化されたように見せることもある。

具体例として、あるタスクでモデルが `head -1 train.txt` を 2 回実行し、RTK はその 2 回に対して「1 億 2,050 万トークン節約」を 2 回計上した、と書いています。比較対象を「ファイル全体を読んだ場合」に置いているからで、`head -1` がファイル全体を返すことは最初からありません。

もう 1 つ、私が知らなかった数字。RTK なしの状態で、端末出力は Fable の入力トークンの 7%（他ツール出力を足して 11%）、DeepSeek で 26%（同 40%）でした。しかも RTK ありの試行では、入力トークンの 94〜98% がキャッシュ読みで、それは請求の 26〜30% にしかならない。RTK が削っているのは、この細い部分です。

ターン数も出ています。DeepSeek では RTK ありで 1 ターンあたりの入力が 7% 減り、ターン数が 18% 増えた。小さくなったターンを足し合わせても、入力の合計は減らなかった。

バグも 1 件。`find` のあるフラグを 0.45.0 の `rtk find` が扱えず、フックが毎回書き換えて毎回失敗し、339 回連続エラーで 12 分。タスクは通ったが、同じタスクの RTK なし試行の約 9 倍のコスト。0.46.0 で修正済みだそうです。

## JetBrains は 7 月に、Sonnet 5 で同じ形を見ていた

こちらは Claude Code 2.1.201 と claude-sonnet-5、SkillsBench の 86 タスク、reasoning effort を low と high で 2 周、425 回の課金試行、約 320 ドル。

low effort では、80 組のペアでタスクあたり中央値 +7.6% 高い（p=0.004）。ターン数 +13.8%、キャッシュ読み +14.3%。RTK が実際に圧縮している「新規入力」トークンは +3.2% で、統計的にはゼロ。high effort では中央値 +0.1%（p=0.99）で、ペナルティも消える。品質は両アームで差なし。

そして `rtk gain` について、Quesma と同じ観察をしています。

> low effort の全タスク実行を通して、rtk 内蔵の分析（`rtk gain`）は「9,620 万トークン節約、触った分の 99.8%」と報告した。一方、同じ試行の実測の請求は上がった。
>
> （中略）ツールの自己申告の節約は、そのツールの反実仮想についての主張であって、あなたの請求書についての主張ではない。

彼らの説明は 3 つ。RTK は「生の出力を全部読んだ場合」を比較対象にするが、Claude Code はそもそも長いツール出力を切り詰めるので、1.2MB の CSV を `cat` して「32 万トークン節約」と記録しても、エージェントが受け取るのは RTK があってもなくても数千トークンだった。トークンを「バイト÷4」で実行時に見積もるが、セッションの入力コストの大半はキャッシュ読みで単価が 1/10。そしてフックはツール出力の 5 分の 1 程度しか見ていない。

RTK の README はいま、この批判を取り込んでいます。私が 2026年9月12日に master ブランチで読んだ版には「How Savings Work」の節があって、こう書いてある。

> RTK はあなたのエージェントが読む bash 出力を最大 90% 削る。RTK が測っているのはそれであって、請求を 90% 削ることと同じではない。

「RTK はトークナイザを同梱していないので、トークン数は `bytes / 4` の見積もりで、パーセンテージは信頼できるが絶対数は近似」とも書いてあります。一方で GitHub のリポジトリ説明文は同じ日にまだ「LLM のトークン消費を 60〜90% 削減する」で、issue #3157 は「README is outdated」というタイトルのまま open でした。

## 手元の history.db を数えた

RTK は書き換えたコマンドを全部 SQLite に残しています。私の環境では `~/Library/Application Support/rtk/history.db` にあり、`commands` テーブルに 1 行 1 コマンドで、元のコマンド、書き換え後のコマンド、入力トークン、出力トークン、節約トークン、節約率が入っている。`rtk gain` はこれを集計して表示しているだけです。読み取り専用で開いて、自分で集計し直しました。

| 指標 | 手元の値 |
| --- | --- |
| 書き換えられたコマンド | 24,734 件 |
| `rtk gain` が表示する節約率 | 79.1%（総節約 33.2M ÷ 総入力 41.9M） |
| 1 コマンドあたりの節約率の平均 | 24.3% |
| 同、中央値 | **0.0%** |
| 節約が 0 以下のコマンド | 14,671 件（59.3%） |
| 節約の上位 1 件が全体に占める割合 | 9.1% |
| 上位 10 件 | **74.1%** |
| 上位 100 件 | 90.5% |
| 上位 1,000 件 | 97.2% |

79.1% は「総節約 ÷ 総入力」なので、巨大な行が数本あれば、残りの 2 万件がどうであれそこに寄ります。

上位 10 件の中身は、こうでした。プロジェクト名は伏せます。

7 件は、2026年8月4日の夜（日本時間 23 時台）の 23 分間に、別プロジェクトの SQL ダンプ 2 ファイル（推定 11MB 級）を `cat` したもの。1 回あたり 275〜300 万トークンの「節約」で、7 回分の合計が 1,953 万トークン。**これだけで、3 か月ぶんの節約の 59% です。** 23 分の間に同じ 2 ファイルを 7 回 `cat` した、というのがまず異常で、RTK の計器はそれを「7 回ぶん節約」と数えた。

1 件は 9 月 5 日の `cat erl_crash.dump`、252 万トークン。この日は 2,339 コマンドが動いて 270 万トークン節約と出ていますが、その 93% がこの 1 回です。

2 件は 7 月 6 日の `find / -name '*'` と `find ~/Documents -name '*'`、それぞれ 127 万と 124 万。

これが計器の 74% です。JetBrains の言う「1.2MB の CSV を `cat` して 32 万トークン」と同じ形が、私の手元では 300 万トークン単位で 7 回並んでいました。Claude Code 側の切り詰めがどの長さで効くのか、私は正確な上限を確認していません。ただ切り詰めの話を持ち出す前に、11MB の SQL ダンプを 7 回まるごと読ませる選択肢は最初から誰にも無かった、というほうが強い。実際に起きた代替は `head` か `grep` か Read ツールで、RTK の計器には「代わりに何が起きたか」という概念がありません。

直近の例もあります。9 月 11 日は 36 コマンドで 8 万 2,700 トークン節約、97.7% と出ていました。中身は、作業用ディレクトリの `archive.log` を `cat` した 1 回が 8 万 876 トークン。その日の残り 35 コマンドを合わせても 1,800 トークン。

![天秤の片方には紙の煉瓦10個が沈み、すみがもう片方に紙片を山ほど押し込んでも、ほとんど下がらない](/images/recounting-rtk-gain/02-ten-bricks-on-a-scale.png)

反対側も書きます。手元の集計で、コマンド種別ごとに平均節約率が高いのは `rtk vitest run`（119 回、平均 92.6%）と `rtk lint eslint`（7 回、93.8%）でした。ここは節約が本物である可能性が高いと私は思っています。テストランナーの出力は長く、ノイズの比率が高く、しかも失敗の行がどこに出るか事前に分からないので、モデルが自分で `head` や `tail` を付けて削ることができない。RTK が「失敗だけ残す」形に畳むのは、この場合は代替手段が無い節約です。

もう 1 つの反対側。RTK には「解析に失敗して生の出力にフォールバックした」記録も別テーブルに残っていて、手元では 3,674 件、回復率 99.9%。頻度順の上位は `mix compile --warnings-as-errors`（283 回）、`mix format --check-formatted`（164 回）、`mix format`（131 回）、`mix compile`（99 回）。私が Elixir で書いている時間が長いので、いちばん出力が重いビルドコマンドは RTK を素通りしていました。RTK が効かない、というより、私のワークロードに対しては最初から対象外だった。

## 私の見解

ここからは、2 本の記事にも README にも書かれていないことを書きます。

### 1. stdout と請求書の間には、RTK より前に 3 つの層がある

2 本の記事が指摘している仕組みを 1 本の管として並べると、こうなります。シェルの stdout のバイト数がまず出る。Claude Code がそれを一定の長さで切り詰める。モデルが最初から `head -n 20` や `| grep error` を付けていれば、そもそも stdout がその長さになる。そして 2 ターン目以降、その出力はキャッシュ読みとして 1/10 の単価で請求される。RTK の計器は、この管のいちばん上流に付いていて、比較対象を「stdout を全部読んだ場合」に置いています。

手元の 7 回の `cat` が示しているのは、それより 1 つ上流に、もう 1 層あることです。「そのコマンドはそもそもその形で実行されたか」という層。11MB を `cat` するという行為自体が、RTK が介在していなければ別の形になっていた可能性が高い。計器はそこを測れない。測れないのは RTK の実装の問題ではなく、1 コマンドの実行時点で反実仮想を決めるという設計に由来していて、直しようがないと思います。

![蛇口からレジスターまで続く1本の管に水門が3つあり、すみはそのずっと上流、蛇口の脇で小さな皿に滴を受けて量っている](/images/recounting-rtk-gain/03-three-gates-before-the-bill.png)

### 2. 59% の書き換えは節約ゼロで、リスクだけを負っていた

これが、私が自分の数字でいちばん重く受け取った点です。中央値 0% というのは、フックが 24,734 回発火して、その半分以上で書き換え前と後の出力が同じだったということです。

書き換えは無料ではない。Quesma の 339 回連続エラーも、JetBrains の「複合 `find` 述語が usage error と再試行に変わった」も、書き換えが 1 回外れたときの値段です。私にも手元の例があります。Claude Code の Bash ツールで `mkdir -p X && cp A X/` のように `&&` や `;` でコマンドを繋ぐと、フックが書き換えた形に対して権限確認が出て、非対話セッションではそこで止まる。私はこれを 9 月上旬に繰り返し踏んで、「1 回の Bash 呼び出しに 1 コマンド」「`mkdir && cp` の代わりに `ditto`」という運用に変えました。これは RTK がエージェントの次のターンを変えた、という 2 本の記事が言う仕組みそのものです。増えたターン数は数えていません。

節約が出る 41% のために、100% の書き換えリスクを払っている。しかも上で見たように、節約の 74% は 10 回の巨大な `cat` と `find` で、それは請求書には現れない。差し引きで残るのは、テストランナーとリンターの本物の節約と、書き換えバグの期待値です。前者が後者を上回っているかどうか、私には分かりません。**分からない、というのが 3 か月使ってきた人間の正直な状態です。**

![すみが大きな機械のハンドルを回しているが、上の受け皿には紙片が少しだけで、下の受け皿は空のまま黒猫が座っている](/images/recounting-rtk-gain/04-crank-with-empty-tray.png)

### 3. 単位を「トークン」にしている限り、この誤読は形を変えて続く

8 月の記事で書いたのは、トークンを 41% 減らしたら請求が 2 倍になった話でした。理由はキャッシュの接頭辞を書き換えたから。今回は、トークンを 79% 減らしたと計器が言い、請求は変わらなかった話です。理由は、その 79% が最初から満額で請求されるトークンではなかったから。

2 つは逆の方向に見えて、同じ 1 点で失敗しています。「トークン」という単位が、非キャッシュ入力・キャッシュ読み・出力という単価の 10 倍差と、「代わりに何が起きたか」という反実仮想を、どちらも隠すことです。RTK の README は「パーセンテージは信頼できる」と書いていて、バイト比としてはその通りです。ただ同じ README の telemetry の節には、「推定節約トークン数に固定の内部定数を掛けて推定 USD 価値を出す」という項目があります。JetBrains と Quesma が「やってはいけない」と言った変換が、ツールの中に定数として入っている。

私がこの種のツールに欲しいのは、`bytes / 4` の差分ではなく、ペアで測った請求か、せめて非キャッシュ入力トークンの差分です。それが取れないなら、計器は無いほうがいい。79% という数字は、私に「効いている」と思わせて、8 月の記事に「たぶん効いている」と書かせるだけの力がありました。

### 4. 私はどうするか

RTK を外すかは決めません。A/B を回していないし、JetBrains は品質は変わらないと言っていて、high effort では差もない。外す理由も残す理由も、私の手元のデータからは出ない。

決めたのは 3 つです。`rtk gain` は見ない。見るなら history.db を開いて中央値を出す。`cat` と `find` の書き換えは、私の環境では計器を膨らませただけなので、対象から外せるか調べる（対象コマンドを絞る設定はあるようですが、試していません）。テストランナーとリンターは残す。

1 つだけ持ち帰るなら、JetBrains の 1 文です。ツールが自己申告する節約は、そのツールの反実仮想についての主張であって、あなたの請求書についての主張ではない。私の場合、それを体感するのに必要だったのは、自分の history.db に対する `select median(savings_pct)` 相当の 1 クエリでした。

## 検証できなかった点

- Claude Code がツール出力を切り詰める正確な上限。JetBrains の記述に依拠しています。
- 私の環境での RTK あり／なしのコスト差。A/B は回していません。
- `&&` の権限拒否が増やしたターン数。数えていません。
- JetBrains 記事の公開日。ページから取れず、issue の日付（7 月 22 日）から 7 月と推定しています。
- 手元の RTK 0.44.1 の `rtk gain` の集計方法が、最新 0.49.0 と同じかどうか。
- RTK の README は master ブランチを読みました。既定ブランチは develop で、そちらは確認していません。
