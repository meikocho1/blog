先に結論だけ書くと、こうです。

> このガイドの5つのルールのうち、**4つは「もっとやれ」で、制約は1つだけ**。そして事故が起きるのはいつも後者の側です。ベンダーのガイドは構造上、許可の側に厚くなる。だから読み方としては、制約の章（Rule 3）だけ2回読むのが正しい。そして本文でいちばん実用的な一文は、見出しではなく中盤に埋まっている Cainex の **"fix the principle, not the example"** だと思っています。

## この記事について

- 原文: [The Claude Code guide for startups](https://claude.com/blog/claude-code-guide-for-startups) — Michael Segner、2026年8月20日（claude.com）

Anthropic が十数社の急成長スタートアップにインタビューして、Claude Code の使われ方を5つのルールにまとめたものです。ClickHouse、Clay、Omni、Crosby、Heidi、Emergent、Commure、Artemis Security、Cainex、Zingage、Translucent、Higgsfield あたりの創業者コメントが並びます。

立場を先に書いておきます。**これはベンダーが自社製品について書いたガイドです。** それ自体は悪いことではなくて、事例を集められるのはベンダーだけなので、こういう文書には固有の価値があります。ただ読み方は変わる。私は「何が書いてあるか」より「どういう形で書かれているか」を見ました。

正直な開示: PDF版は落としていません。引用されている Code with Claude（2026年5月）の Harvey と Cognition のセッションも見ていません。私が読んだのは Web 版の本文だけです。

5つのルールはこれです。

1. Everyone ships（誰でも出荷する）
2. Automate the tedium（退屈な作業を自動化する）
3. Trust, but verify（信頼せよ、ただし検証せよ）
4. Build for rebuilding（作り直す前提で作る）
5. Prototype, dogfood, productionize（試作し、自分で使い、製品化する）

## 4つは許可で、1つが制約

並べ替えると構造が見えます。

Rule 1 は「エンジニアでない人も出していい」。Rule 2 は「機械的な8割はエージェントに渡していい」。Rule 4 は「作ったものを捨てていい」。Rule 5 は「社内ツールを製品に昇格させていい」。**全部、今までやらなかったことをやっていい、という許可です。**

Rule 3 だけが逆を向いています。「検証の手段がないなら、自動化するな」。原文の一文がそのまま条件文になっています。

> You can't automate a process, unless you have a reliable means of monitoring and verifying the outcome.

そして Rule 3 の章がいちばん長い。テスト基盤、`CLAUDE.md` に不変条件を書く話、golden set の維持、hooks によるハードゲート、Cainex の自己改善ループ。他の4章が事例紹介なのに対して、ここだけ手順の話になっています。

これは編集上の偶然ではないと思います。**許可は売れるが、制約は売れない。** ベンダーのガイドが許可4：制約1の比率になるのは、悪意ではなく構造です。だから読者側でバランスを取る必要がある。私の読み方は「Rule 3 を最初に読んで、それから Rule 1 に戻る」でした。

もう1つ、この非対称を裏づける観察があります。**このガイドに載っている失敗談は、全部 Rule 3 の側で起きています。**

Zingage の Victor Hunt:

> 「初期は Claude に完全な自律性を与えて、AI らしいことをした。もっともらしいコードを速く出荷したのだ。問題は、正しく見えるのに我々のアーキテクチャからずれていく形でドリフトしたこと。だから…すべての不変条件を書き下した。どう問題を枠づけるか。何が絶対に真でなければならないか。自信ありげな答えを信じるのではなく、どう動作を証明するか。**このチームの考え方、567行。**」

Cainex の Uriah Israel:

> 「最初からこんなに綺麗だったわけではない。最初のバージョンは過学習していた。個別ケースをエンコードすることで『修正』してしまい、賢くなるかわりにパッチを溜め込んでいた。」

どちらも「速く出せるようになった」あとに来た問題で、Rule 1・2・4 を実行した先に待っていたものです。順序としては、許可を先に読んで制約を後回しにすると、この2つを自分で再発見することになります。

## いちばん実用的な一文は、見出しになっていない

Cainex は医療コーディング（カルテを読んで、病院の請求を決めるコードを生成する）の会社です。この節が本文中でいちばん密度が高い。

> 「医療コーディングでは、間違ったコードはタイプミスではない。請求とコンプライアンスの事案だ。その一点が、我々の作り方すべてを規定している。」

彼らのループはこうです。エージェントがバッチを処理する → 監査人が社内アプリで出力をレビューする（コードだけでなく**モデルの推論も見て、両方にコメントする**）→ Claude Code が元の予測と全ての訂正とコメントを DB から直接読む → 訂正の種類ごとにタグが付いているので、該当するガイダンスに直行する → **間違いを生んだ指示の箇所を特定して改訂する** → バージョン管理された指示セットに対して変更を加え、失敗したレコードで再テストする。

そして back-test。1つのレコードに複数の妥当なコーディングがありうるので文字列一致では判定できない。受理集合に対する意味的マッチと、「これは本当に誤りか、それとも別の妥当な経路か」を問う judge を組み合わせる。golden set とランダムサンプルに対して候補の変更を走らせ、リグレッションを出荷前に洗い出す。

ここまでが仕組みで、原則が1行です。

> **The rule we enforce: fix the principle, not the example.**

私はこれがガイド全体でいちばん持ち帰れる一文だと思っています。理由は2つ。

**1つめ。これは減法の原則です。** ガイドの他の部分はほぼ加法です。エージェントを増やす、skill を増やす、並列度を上げる、プロトタイプを増やす。この一文だけが「増やすな」と言っている。個別ケースへの対応を足すのではなく、原則のほうを直せ、と。Cainex 自身が「変更に入れられる個別事項の数に上限を設けた」と書いていて、**足せる量に明示的なキャップをかけている**。

**2つめ。これはそのまま `CLAUDE.md` の運用ルールになります。** エージェントが何かを間違える。よくある対処は `CLAUDE.md` に一行足すことです。「〜するな」。それを繰り返すと、原文の言葉どおり「賢くなるかわりにパッチを溜め込む」。私の `CLAUDE.md` はまさにそうなっていて、過去の事故の化石が層になっています。

そして皮肉なことに、この原則の対象には `CLAUDE.md` 自身が含まれます。ガイドの Rule 3 の Tip は「変えられないものを `CLAUDE.md` のルートに置け」と言っていますが、Cainex の原則を適用するなら、置くべきは**事例ではなく原則**です。この2つの Tip は同じ章にあるのに、片方だけを実行するとファイルが太ります。

## 同じ週に、逆向きの信号が出ている

ここからは原文にない話です。

このガイドの2日後（2026年8月22日）に、Maurice Heumann が[自分のセッションログ約2GBを監査した記事](https://momo5502.com/posts/2026-08-22-mw2-decompilation-audit/)を出しています。AI エージェント群に4週間ノンストップでゲームのデコンパイルをやらせた実験の監査です。この記事は別途扱ったので詳細は省きますが、ここでは2点だけ、このガイドと突き合わせます。

**1. サブエージェント。** ガイドはこう言っています。

> Dynamic workflows can be used to fan multiple subagents to analyze large amounts of data in parallel or to conduct an adversarial review of another agent's work.

Commure の事例も「1人のエンジニアが Claude subagents で約13チケットのイニシアチブを並列で回した」です。増やす方向。

一方 Heumann は、47回のサブエージェント実行で読まれた大きいファイルのうち **54.7%が純粋な重複**だったと測って、サブエージェントを無効化しました。重複読みの中位間隔は35分で、親が自分で読んでいればコンテキストに残っていた、という理屈です。

矛盾しているように見えますが、条件が違います。Heumann の項目ではサブエージェントが**実作業をできませんでした**（ワークスペースを並行して安全に書き換えられないため）。だから調査専門になり、調査は重複しやすい。Commure の13チケット並列は、チケットごとに独立した作業単位があります。

つまり分岐点は「並列化する単位が本当に独立しているか」で、ガイドの側にはこの条件が書かれていません。**「fan out multiple subagents と言えばいい」という Tip の粒度では、どちらの状況にいるのかは判定できない。** ここは読者が補う必要があります。

**2. 生産性の指標。** ガイドの冒頭には数字が4つ並びます。

| | |
| --- | --- |
| ClickHouse | 30% more features shipped |
| Omni | 2–3x engineering productivity |
| Clay | 100% of bug triage automated |
| Artemis Security | 6,000+ PRs a week |

方法論は書かれていません。何と比べた30%か、2〜3倍を何で測ったか、週6,000+ PR がどういう単位の PR なのか。全部インタビューでの自己申告です。

これを Heumann の記事と並べると面白い。彼はサブエージェントを切ったあと 1日あたりコミット数が 243.9 → 311.1 に増えたと書いた上で、**自分でこう注記しています**。「コミット数を生産性の指標にするのは必ずしも正確ではない」。

自分に有利な数字が出たときに、その数字の弱さを自分で書く。ガイドの4つの数字にはこの注記がありません。ベンダーのマーケティング素材にそれを期待するのは筋違いなので、批判というより読み方の話です。**この手の数字は「方向の主張」であって「効果量の主張」ではない**と読む。6,000+ PR/week は「PR という単位が壊れるくらい速い」と言っているのであって、6,000という数に意味はない。

![片側でレバーを上げて小さなエージェントを次々に送り出し、もう片側でスイッチを切って同じエージェントを止めている、2人のすみ。中央の分岐標識には「独立しているか」とだけ書かれている](/images/five-rules-only-one-constrains/03-same-week-opposite-signals.png)

## 私が実際に使うと思った3つ

ガイドのチェックリストから、事例ではなく手順として使えるものだけ。

**1. git worktree で「4回作る」を安くする。** Rule 4 の Tip です。v2 を v1 の隣で走らせて、両方に eval をかけて、勝ったほうだけマージする。Clay の Kareem の「作って、また作って、また作る。4回目に全部わかっていて、正しく作れる」という話に、実装の裏づけを与えているのがこの Tip です。私は worktree を「ブランチ切り替えが面倒なとき用」としか思っていませんでした。**作り直しのコストを下げる道具**という位置づけは考えたことがなかった。

**2. hooks をハードゲートとして使う。** Rule 3 の Tip。「モデルが何を決めようと毎回実行される」。lint を通らない書き込みをブロックする、コミット前にテスト通過を要求する、サンドボックスから出る前に secret を除去する。これは前に読んだ Heumann の記事の結論（「ソフトな指示は効かない。ルールを強制するには機械的なブロッカーのほうが効果的」）と完全に一致します。**別々の出所から同じ結論に着いているので、これは信用していい部類**だと思っています。

**3. golden set を複数持ち、定期的に更新する。** Rule 3。「ユーザーが『変更後にエージェントが悪くなった気がする』と報告してきて、推測でしか確認できない」のが破綻点だ、という記述が具体的でよかった。私はこの状態です。

逆に、すぐには使わないと思ったのが Rule 1（everyone ships）です。悪いとは思いません。ただこれは組織の話で、道具の話ではない。1人か2人でやっているなら「全員が出荷する」はもともと真です。このガイドの読者のうち、Rule 1 が実際に何かを変えるのは、非エンジニアの職能が分かれている規模の組織だけだと思います。

## 1つだけ持ち帰るなら

ガイドの内容ではなく、ガイドの読み方です。

**許可と制約を数えてから読む。** 4対1だったら、1のほうを2回読む。ベンダーの文書に限らず、社内の設計ドキュメントでも同じで、「やっていい」が並んでいて「これがないとやるな」が1つしかないなら、事故はその1つの側で起きます。

内容から1つ選ぶなら、**fix the principle, not the example.** これは `CLAUDE.md` に足そうとしている一行を止める効果があります。止めたあと、代わりに何を直すべきかも指してくれる。
