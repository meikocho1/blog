先に結論だけ書くと、こうです。

> この記事は「Uber では PR の70%がエージェント」という話として流通しますが、中身はそこではありません。**総額を減らすのではなく、使用量を7倍にしたまま単価を下げた**という話で、そのための最大の単項手段が **MCP のツール定義をコンテキストから追い出すこと**でした。100個のツールで50K〜70Kトークンのスキーマが毎ターン再送されていた。それをCLI解決とツール検索で消し、さらに code-mode で50%〜90%削っています。

## 数字の話は先に済ませます

冒頭の規模から。

- PR の **70%超**が、ローカルまたはクラウドのエージェントに**帰属**している（attributed to）
- エンジニアが作ったエージェントスキルは **3,600本超**、実行は **1日3万回超**
- 2026年2月→8月中旬で、週次アクティブユーザー **7倍**、週次エージェントリクエスト **9.4倍**
- 一方、AI 支出の総額は **4月以降ほぼ横ばい**
- モデルを固定して自社の最適化分だけを切り出すと（2月→7月）、**1,000モデルリクエストあたりのコストがピークから約34%減**、**セッションあたりコストが6月のピークから52%減**

「70%」は一人歩きしそうな数字ですが、原文の語は attributed です。**エージェントに帰属している**であって、エージェントが書いたとも、人間が関与していないとも言っていません。原文自身、この後に「code review、CI の自己修復、E2E PR、オンコールのトリアージ、バグのデバッグ」を挙げて、**人間のレビュー/エスカレーションを伴う**と書いています。

そして PR 数を生産性の指標にする危うさについては、私は別の記事で扱いました（自分でコミット数を測った人が「コミット数を生産性の指標にするのは必ずしも正確ではない」と自分で注記していた話）。ここでは繰り返しません。**この記事の価値は割合ではなく、単価の分解のほうにあります。**

## コスト方程式：上の2項は増やす

原文の骨格は、エージェントセッションのコストを掛け算の6項に分解することです。そして重要なのは、**全部を減らそうとしていない**ことです。

> 最初の2項は採用と関与を表していて、これは全ユーザーベースにわたって伸ばし続けたいものだ。（中略）中間の3項が最適化の機会を提供する: エンジニアが実際に出した要求の上に、**エージェントが自分自身のために行っている作業**だ。我々の労力のほとんどはそこに向かう。

この切り分けが記事全体の設計になっています。

- 上の2項（使う人、使う回数）＝ **伸ばす**
- 中の3項（エージェントが自分のために増やしている分）＝ **削る**
- 最後の1項（トークン単価）＝ **ルーティングで選ぶ**

だから結論もこうなります。

> より低い単価に頼ったりツールをダウングレードしたりするのではなく、**無駄でゼロ価値のトークン消費を排除する**ことで、使用量を7倍にしながら、同時にすべての指標で単価を下げ、出力品質を改善/維持した。

私が良いと思ったのは、「エージェントが自分自身のために行っている作業」という言い方です。エンジニアが「このバグを直して」と言ったときのトークンと、エージェントが「そのファイルどこだっけ」で使うトークンは、請求書の上では同じ顔をしています。分けて数える枠組みを先に作ったから、削る対象が決まった。

## 本題：MCP をコンテキストから追い出す

ここが持ち帰りの中心です。

Uber は MCP を**ゲートウェイ1本**に集約しています。社内とサードパーティ SaaS を合わせて **1,000以上の MCP サーバー**。認証とポリシー適用を1箇所でやるための設計です。

問題はここから。

> しかし標準的な MCP は、エンジニアがそのセッションで一度も呼ばないかどうかに関係なく、**すべてのツールスキーマをすべてのセッションに読み込む**。たとえば100以上のツールがインストールされている場合、このプリロードは初期プロンプトに**およそ50K〜70Kトークンのスキーマオーバーヘッド**を追加し、それが**コンテキストのターンごとに再送される**。

100ツールで50〜70K。しかも毎ターン。SaaS 側はもっとひどくて、原文の例では**ワークスペース系のスイートが49ツールで約22Kトークン**、メッセージング系が34ツール、プロジェクト管理系が46ツール。原文の表現が的確です。

> ベンダーのサーバーを2つか3つ読み込むと、**ユーザーがプロンプトを入力する前の時点で、編集対象のファイルよりも多くのスキーマオーバーヘッドをエージェントが背負う**ことになる。

対処は3段構えです。

**1. CLI ツール解決。** MCP を直接つなぐのをやめて、モデルにはシェルコマンドを実行させる。CLI が呼び出し時にゲートウェイに対してツールを動的に解決する。結果として、**Uber の MCP スキーマがセッションコンテキストから消える**。社内ゲートウェイの1,000以上の MCP ツールが全部 CLI コマンドとして投影されています。

**2. ツール検索。** モデルがツールカタログを検索して、必要なものだけをオンデマンドで読み込む。ツール数が増えても選択精度が落ちない、という点も挙げられています。

**3. code-mode。** これが一番面白かった。ツールをシェルコマンドとして直接呼べるなら、モデルは**複数のアクションを1つのスクリプトにまとめられる**。おしゃべりなプロトコルほど効きます。

> たとえば1つの SQL クエリを実行するには、リクエストの送信、ステータスの2〜5回のポーリング、出力の取得が必要になる。code-mode はこのフロー全体を自動化された Python ループに落とし込み、**中間のポーリングをモデルのアクティブなコンテキストの外に置く**。

そして測定結果。

> 最初の3行が主要な発見を示している: **レスポンスサイズの上限を大きく下回る最小の結果セットでさえ、code-mode はトークン使用量を50%以上削減する。** これらの効率化は大きなデータペイロードを回避することから来ているのではなく、スキーマ初期化、マルチターンのポーリング、冗長な段階的推論といった**不要なオーバーヘッドの排除**から来ている。
>
> バルクワークフローは効果を複合させる。N回のモデルターンになっていたループが1つのスクリプトになるので、節約は**90%以上**に複合する。

（個々のクエリごとの削減率は原文の表（画像）にあります。私は読めていないので数値は引用しません。）

そして最後の一手が、**デフォルトを安いほうにすること**です。よく使う MCP サーバー向けに **25本以上の code-mode スキルを事前に用意**して、標準的なワークフローが自動的に最も安い経路を通るようにしている。

### これは MCP の使い方の話ではなく、設計の話だと思う

ここから私の読み方です。

MCP の中心的な設計判断は「ツール定義をコンテキストに置く」でした。モデルは自分の目の前にあるものしか呼べないので、当然の設計です。**そしてこれは、ツールが10個のときは正しい。**

問題は、この設計のコストが**ツール数 × ターン数**で効いてくることです。10ツール・5ターンなら誤差ですが、100ツール・50ターンだと、**プロンプトを1文字も打つ前に確定している支出**が全体の大半になりえます。Uber の数字（50〜70K × 毎ターン）はまさにそれです。

Uber の答えは「MCP をやめる」ではありませんでした。ゲートウェイは残っています。彼らがやめたのは **MCP をコンテキストに置くこと**です。プロトコルとしての MCP（統一された認証、ポリシー、発見）は残して、**実行経路だけをシェルに移した**。

これに対する反論は当然あります。「tool search は MCP の側でも用意されているし、スキーマの遅延読み込みは解決済みの問題だ」。私はこの反論は半分正しいと思っています。半分というのは、**遅延読み込みでは code-mode の効果が出ない**からです。code-mode が削っているのは「スキーマの大きさ」ではなく「**ターン数**」です。ポーリング5回を1スクリプトに畳んだときに消えているのは、5回分の往復すべて（そのたびに再送されるコンテキスト全部）です。ツール定義をどう読み込むかを工夫しても、そこは減りません。

だからこの記事の含意は、私の理解ではこうです。**エージェントとツールの間は、関数呼び出しではなくスクリプト実行のほうが構造的に安い。** MCP が定義しているのは前者で、後者に落とすには外側の仕掛けが要る。

## 今日から真似できるデフォルト4つ

Uber の規模の話が多い記事ですが、設定値としてそのまま持ち帰れるものが4つありました。

**1. 自動コンパクションを 400K で。1Mコンテキストのモデルでも。** 原文の理由は「モデル性能と、キャッシュのバーストおよび入力トークンの反復コストとのバランス」。1Mの40%です。

私はここで手が止まりました。この数字は、私が別の記事で扱った Maurice Heumann の監査（1Mウィンドウの93〜100%まで使ってから圧縮していたのを、60%に下げた）と同じ方向を向いています。**片方は数万時間のフリート運用、もう片方は個人の4週間の実験で、独立に「デフォルトよりずっと早く圧縮しろ」に着いている。** これは信用していい部類だと思います。ただし片方が40%、もう片方が60%なので、正確な値は自分のワークロード次第です。

**2. reasoning effort をデフォルト Medium に。** 理由は明快で、推論トークンを含む出力トークンは、主要モデルでは入力トークンの数倍のレートで課金されるから。**一番高いカテゴリを直接削る**設定です。

**3. プロンプトキャッシュの TTL を1時間に（インタラクティブのみ）。** キャッシュ読み込みは通常の入力レートの0.1倍。ただし書き込みのプレミアムが違って、5分エントリは1.25倍、1時間エントリは2倍。Anthropic は5分と1時間、OpenAI は30分。

> エンジニアはインタラクティブなセッションを5分以上アイドルにすることが多いため、デフォルトの5分 TTL から1時間ウィンドウに移行した。この頻繁なアイドルの隙間が、以前はプレフィックスキャッシュを無効化し、全額のコンテキスト再構築を強いていた。

**サブエージェントは5分のまま**にしているのが細かくて良い。実行が短命なので、2倍の書き込みプレミアムを払う理由がない。

**4. サブエージェントのデフォルトモデルを弱いほうに。** 原文はこれを「最も影響の大きいレバーであることが証明されており、その重要性は増し続けている」と書いています。理由は「サブエージェントは入力が指定された明確なタスクを実行するので、フロンティアレベルの推論を必要としないことが多い」。主モデルがタスク分解と評価、サブエージェントが実行。

## 硬い上限を置かない、という選択

もう1つ、対比として面白かった部分。

Uber は**支出の上限でエージェントを止めていません**。原文の言い方は「厳しいキャップを課すことを避けるため（To avoid imposing strict caps）」で、代わりに置いているのが以下です。

- ステータスラインの実時間コストカウンター（ターミナルに常時表示）
- ハーネスをまたいだ共有の支出ティア（ツールごとの予算にはしない）
- **期待支出の50/80/100%で Slack 通知**（計画する時間を与えるため）
- ティア引き上げはマネージャー承認、反映は速く
- コスト内訳を出すダッシュボードスキル

これは、私が以前扱った Microsoft の TokenOps（run 単位で予算を超えたら HALT する仕組み）とは逆側の選択です。TokenOps は「暴走を止める」ことを目的にしていて、Uber は「エンジニアが自分で ROI を判断できるようにする」ことを目的にしている。原文の言い方だと「**エンジニアが独立してタスクの ROI を評価できるようにしつつ、暴走支出を緩和する**」。

どちらが正しいという話ではなくて、**止める対象が違う**のだと思います。TokenOps が守ろうとしているのは自動化された run で、そこには判断する人間がいません。Uber がここで扱っているのはインタラクティブなセッションで、画面の前に人がいる。人がいるなら、止めるより見せるほうが良い。実際 Uber も、管理エージェント（managed agents）には**別のティア**を設けています。

**人がいる経路には可視化を、いない経路には遮断を。** これが2本を並べたときの私の整理です。

## セッション分析ダッシュボードの16項目

最後に、一番真似したくなった部分。ステータスラインは総額しか見せないので、その先を埋めるものとして「セッション分析ダッシュボード」があります。ランタイムに組み込まれていて、セットアップもオプトインも不要。`cost dashboard` スキルを実行すると、ローカルとリモートのサンドボックスをまたいで、そのユーザーの全セッショントレースを分析する。

そして集計値を出すのではなく、**16種類のアンチパターンを検出して、それぞれに金額影響と具体的な対処を添えて出す**。挙げられている例:

- **モデルルーティングの誤り**: Sonnet で十分な単純なマルチターンセッションを Opus で回している
- **コンテキストウィンドウの肥大**: 大きな MCP ペイロード（たとえば40KBのレスポンス）がコンテキストに残り続け、以降のターンで繰り返し課金される
- **キャッシュ失効の非効率**: 長い中断のあとにセッションを再開し、期限切れのプロンプトキャッシュが全額のプレフィックス再構築を強いる
- **プロンプト初期化のオーバーヘッド**: ユーザー入力の前に10万トークンのシステム指示とツール定義をプリロードしている

この4つ、全部**自分のログで数えられる**ものです。16項目の全リストは公開されていませんが、この4つだけでもチェックリストとして使えます。というより、最後の1つは私自身が該当していそうです。

## 1つだけ持ち帰るなら

**プロンプトを打つ前に確定している支出を数える。**

Uber の一番大きい発見は、削る余地がプロンプトの中ではなく、**プロンプトの手前**にあったことだと思います。ツール定義50〜70K、システム指示10万トークン、そして毎ターンの再送。ここは「良いプロンプトを書く」では1トークンも減りません。

自分の環境で数えるのは簡単です。何もせずにセッションを開いて、最初のターンの入力トークンを見る。それが、これから何十ターンも掛け算される定数です。
