先に結論だけ書くと、こうです。

> Warp の「自己改善エージェント」で自動化されているのは、**フィードバックを skill への差分提案にまとめるところまで**。その先はレビューして承認してマージする、普通の PR です。これは弱点ではなく設計として正しい。ただ、そう理解すると成本の項目が1つ増えます。**レビュー対象がコードだけでなく「スキルの PR」にも増える。** そして原文でいちばん重い一文は本文ではなく、末尾の FAQ 表に入っている「フィードバックは間違っているものと想定せよ」でした。難所はループではなく入口です。

## この記事について

- 原文: [How Warp builds self-improving agents on Claude](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude) — Michael Segner、2026年8月26日（claude.com）

AI ターミナルの Warp（2020年創業、CEO は Zach Lloyd）が、社内のコードレビューエージェントの出力が使いものにならなかったところから、skill ベースの自己改善ループを作った、という事例記事です。

前回に続いて Anthropic 自社ブログの記事なので、ベンダー資料としての読み方は同じです。冒頭に並ぶ数字（800K の月間開発者、Fortune 500 の56%、Warp 内で走った Claude Code セッション累計1000万、週40万超）も自己申告値で、私は検証していません。前回その点は書いたので、今回は繰り返しません。**この記事の価値は数字ではなく、機構が具体的なことにあります。**

正直な開示: 記事末尾にリンクされているウェビナー（ライブデモ付き）は見ていません。Warp も使っていません。読んだのは Web 記事の本文だけです。

## 仕組みは本当に単純

まず機構。ここは短く済みます。

- **inner / base skill**: 領域知識と手順を持つ。PR が開かれると、コードレビューエージェントがこの skill を読んでレビューを出す
- **人間のフィードバック**: 出力に対して、人が「良かった」「ここが違う、なぜならうちの規約では…」と書く。書く場所は PR や issue のコメント欄、つまり作業が既に起きている場所
- **outer / improver skill**: 観察者エージェント。タスクごとではなく**スケジュールで**動く。溜まったフィードバックを引いてきて、エージェントの提案と人間の反応を突き合わせ、base skill への**小さく焦点の絞れた編集**を提案する

skill はただのファイルなので、その編集は PR として出てきます。レビューして、承認して、マージする。次に inner skill が動くとき、改善が反映されている。

Zach Lloyd の言葉:

> 「フレームワークは本当に単純で、領域固有の base skill があって、それを洗練する improver skill がある。この単純さがこのアプローチの美点だ」

実際に単純です。そして単純なので、真似できます。ここは素直に良い記事だと思いました。

## で、"self-improving" とは何が自動なのか

引っかかったのは名前です。

このループで機械がやっているのは、**フィードバックを読んで、差分を書いて、PR を出すところまで**。何が base skill に入るかを決めているのは、最後に承認する人間です。原文もそう書いています。

> A human reviews, approves, and merges, and the next run of the triage skill inherits the new knowledge. That final human step closes the loop and keeps a person in control of what actually changes.

つまり正確には **self-improving ではなく auto-drafting** です。自己改善ではなく、自動下書き。

これは批判ではありません。人が最後に立っているからこの仕組みは使えるのであって、勝手に skill が書き換わるなら誰も本番に入れない。**私が言いたいのは、名前が成本を隠しているということです。**

「自己改善」と聞くと、手離れするように聞こえます。実際に起きるのは逆で、**レビューのキューが1本増えます**。

- 従来: コードの PR をレビューする
- 導入後: コードの PR をレビューする ＋ **improver が出してくる skill の PR をレビューする**

しかも後者のレビューは前者より難しい。コードの PR は「この変更は正しいか」を見ればいいですが、skill の PR は「**この一般化は正しいか**」を見ることになります。1件のフィードバックから抽出された原則が、まだ見ていない次の100件に適用されて大丈夫か。これは目視で判定しづらい種類の問いです。

原文の例で言うと、triage エージェントが `ready to spec` ラベルを付け損ねた → メンテナが理由付きで指摘した → improver が「問題が実在するなら、UI/UX の形が未定でも `ready to spec` を付ける」という編集を提案した、という流れです。この編集が妥当かどうかは、**このケースを見ても分からない**。妥当性は将来の issue に対して決まります。

Warp はこの負荷に耐えられる規模です（オープンソースリポジトリに数百人の貢献者、数千件のコードレビュー）。**小さいチームがこのループを入れると、生成される skill の PR に対してレビュー予算が足りなくなる可能性がある**、というのが私の懸念です。原文にはこの話は出てきません。

## 本文より FAQ のほうが重い

原文の末尾に「Best practices from the Warp team」という Q&A の表があります。ここに一番重い話が入っていました。

> **What happens when the feedback is wrong?**
> Assume it will be. Don't let the agent accept feedback blindly — give it context to sanity-check, filter whose input counts, and keep a human in the loop at either the filtering or final-review stage.

「フィードバックは間違っているものと想定せよ」。そして「**誰の入力が数えられるかをフィルタしろ**」。

もう1つ、別の行:

> Where you must use human feedback, restrict it to domain experts — don't open the floodgates.

本文の主張は「フィードバックを集めやすくしろ、摩擦が低いほど信号が流れる」（Make feedback effortless to give）です。FAQ の主張は「誰の声を通すかを絞れ」です。両立はしますが、**同じ方向ではありません**。片方は入口を広げろと言い、もう片方は入口に選別を置けと言っている。

私はこの2つの緊張が、この仕組みのいちばん難しいところだと思っています。そして本文とFAQで扱いの重さが逆になっている。理由は前回の記事で書いたのと同じで、**広げる話は書きやすく、絞る話は書きにくい**からだと思います。

さらに言うと、この2つは再利用性が違います。Zach 自身がこう言っています。

> 「領域固有の知識の部分を除けば、これはかなり再利用可能な機構だ。コードレビューエージェントの improver skill は、他のどんなエージェントの improver skill ともそれほど変わらない」

つまり**パイプは再利用できる**。しかしフィルタは再利用できません。「誰の指摘が skill に入る資格があるか」は組織ごとの、というより人ごとの判断で、コピーできない。**単純なのは配管で、難しいのは入口**です。原文が「この単純さが美点だ」と言っているのは配管のほうで、そこは正しい。ただ、配管を借りてきた側は、自分でフィルタを作らないといけない。

## skill でも memory でもない、第三のもの

FAQ の1行目も良かったので引きます。

> **Are you conflating skills with memory?**
> Skills are procedural and stable—"how to do X," run-agnostic, changed deliberately. Memory is auto-written by the agent at inference time and never stops changing.

skill は手続き的で安定、実行に依存せず、**意図的に**変更される。memory はエージェントが推論時に自動で書き、変化が止まらない。

この区別自体は前から言われている話ですが、面白いのは、**Warp のループがこの2つのどちらでもない第三のものを作っている**ことです。

| | 誰が書くか | いつ変わるか | 承認 |
| --- | --- | --- | --- |
| memory | エージェント | 推論のたび | なし |
| skill（従来） | 人間 | 人が編集したとき | 暗黙（書いた人） |
| Warp のループ | エージェントが起案 | スケジュール実行のたび | **明示的な PR レビュー** |

memory の「エージェントが書く」性質と、skill の「意図的に変わる」性質を組み合わせたものです。自動で変わるが、変わるには承認が要る。

なぜこれが重要かというと、**memory の使いにくさの正体は「自動」ではなく「承認がない」ことだ**と分かるからです。私はこれまで memory 機能を「勝手に変なことを覚えるから信用できない」と扱っていましたが、問題は自動書き込みそのものではなく、書き込みに対する拒否権がなかったこと。Warp の設計はそこに PR という拒否権を挟んでいます。

そう考えると、この記事のタイトルにある self-improving よりも、**"reviewable self-modification"（レビュー可能な自己書き換え）**のほうが、何が新しいのかを正確に指していると思います。

## 3本を並べると、同じ結論に3方向から着いている

私はここ数日、たまたま近い話題を3本読みました。並べると位置関係が見えたので書いておきます。

**1. Warp（この記事）: 「ルールではなく原則を書け」**

> 「賢い人に指示するように skill を構成しろ。コンピュータをプログラムするようにではなく。『重複したコードを探せ』という指示のほうが、変数命名規則を網羅するより良い方向づけになる」

理由も添えろ（Explain the why）、と続きます。理由があればエージェントは推論できるが、規則だけだと硬直する、と。

**2. Cainex（[スタートアップ向けガイド](https://claude.com/blog/claude-code-guide-for-startups)より）: 「事例ではなく原則を直せ」**

医療コーディングの会社が、個別ケースをエンコードして「修正」した結果、賢くなるかわりにパッチを溜め込んだ、という失敗から得た原則です。彼らは**1回の変更に入れられる個別事項の数に上限を設けて**います。

**3. Maurice Heumann（セッションログ2GBの監査）: 「ソフトな指示は効かない。機械的なブロッカーのほうが効果的」**

エージェントに「ローカルでテストを実行するな」と繰り返し言っても聞かなかったので、テスト実行をコード側で無効化した、という話です。

1と2は同じことを言っています。**Warp が機構を与え、Cainex が上限を与えた。** improver skill が「最小の編集を提案する」のと、Cainex が「入れられる具体例の数を制限する」のは、同じ問題への別の処方です。独立した2社が同じ場所に着いているので、これは信用していい部類だと思います。

3は一見逆を向いています。skill はソフトな指示なので、「ソフトな指示は効かない」と正面衝突しているように見える。でも並べると境界線が引けます。

**機械的にブロックできるものは、skill に書かない。skill に書くのは、機械化できない判断だけ。**

Heumann が潰したのは全部、機械化できるものでした（テストを実行するな → 実行を無効化、CI をポーリングするな → webhook で通知、issue の閉鎖を確認するな → `Fix #N` で自動クローズ）。一方 Warp の skill が扱っているのは「この変数名はうちの規約に合っているか」「この issue は spec を書き始められる状態か」で、これは hooks では判定できません。

3本を1文にすると、私の理解ではこうなります。**規則は機械に、原則は skill に、そして skill を変えるときは1件のフィードバックから最小の一般化だけを取る。**

## 私が実際にやる最小版

Warp の規模は真似できないので、削れるところを削ります。

**やること: フィードバックを1箇所に溜める。** これだけは今日からできます。エージェントの出力に対して「これは違う、なぜなら〜」と思った瞬間に書く場所を決める。原文の指摘どおり、**書く場所は作業が起きている場所**であるべきで、別のフォームを開かせた時点で書かれなくなります。

**やらないこと: improver をスケジュール実行にする。** これは PR キューが増える話なので、1人でやっているうちは割に合わないと思います。代わりに、溜まったフィードバックを見るタイミングを自分で決めて、そのときだけ「これを読んで、skill への最小の編集を提案して」とやる。自動化するのは提案の生成であって、実行の頻度ではない、という切り分けです。

**入口のルール: 自分の書いたフィードバックでも、そのまま通さない。** FAQ の「フィードバックは間違っていると想定せよ」は、他人の話に読めますが、1人でやっているなら対象は自分です。イラついて書いた「なんでそうなるんだ」は信号ではありません。私のフィードバックの半分はたぶんこれです。

## 1つだけ持ち帰るなら

**自動化されているのがどこまでか、名前ではなく境界で確認する。**

"self-improving" の実際の境界は「差分の起案まで」でした。境界を確認すると、その先に何が残っているか（＝自分がやることになる作業）が見えます。今回の場合、残っていたのは**レビュー**で、しかも「この一般化は将来の入力に対して正しいか」という、コードレビューより判定の難しいレビューでした。

導入する価値はあると思います。ただ、増えるのはスキルの質だけではありません。
