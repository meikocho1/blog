先に結論だけ書くと、こうです。

> エージェントのトークン代を決めていたのは、コードベースの大きさでも変更箇所の数でもなく、**ノイズ比**（grep のヒット数 ÷ 実際に直すべき箇所の数）だった。29対1のタスクでは3割以上安くなり、1対1に近いタスクでは何も起きない。
> そしてこの数字は製品の性能ではなく、あなたのリポジトリとそのタスクの性質です。買う前に `rg` と `wc -l` で測れます。
>
> もう一点。この計測が**測らなかった側**（見落とし＝サイレントバグ）には、売り手が書いていない逆向きのリスクがあります。読み荒らしが偶然果たしていた安全網が消えるので、失敗の形が「高いが正しい」から「安いが静かに不完全」に移ります。

## 方法論の話を先にする（ここが一番硬い）

ベンダーブログなので数字は疑って読み始めたのですが、方法論の節で態度を変えました。自分に不利になりうる設計が混ざっているからです。

- OSS の**実際にマージされたコミット**を正解と実行可能オラクルにする
- タスクのプロンプトに**ファイル名・シンボル名・行番号を一切書かない**。書けばエージェントの探索能力ではなくプロンプトの品質を測ることになるから ← 自分に不利
- コミットの親をクリーンなワークスペースにチェックアウト、git 履歴を剥がし、ホストレベルでネットワークを遮断、エージェントの web-fetch と web-search を**両群対称に**無効化（答えを外から拾えないように）← 自分に不利
- ビルドとテストで**ゲート**：コンパイルして対象テストが通った run だけを数える
- **片側 n=10**、Opus 4.8 の high effort・サブエージェント有効、平均ではなく中央値を先に出す ← 自分に不利（強いモデルほど探索が上手いので改善幅が縮む。著者も理由をそう書いている）
- コスト変動の原因を「エンジンの効果／eval のバグ／run 間のばらつき」に model-as-a-judge で帰属させ、全トランスクリプトにチート監査

> Gate on build and tests: a run counts only if it compiles and the targeted tests pass, because cost is comparable only when correctness is held equal.
>
> （拙訳）ビルドとテストでゲートする。コンパイルして対象テストが通った run だけを数える。正しさを揃えないとコストは比較できないからだ。

自社に都合の悪い結果も書いてあります。「navigation の run 10回のうち2回はグラフを使わず grep に戻り、平均値の改善を打ち消した」とか、「TypeScript は npm と tsc のビルドループが支配的なのでエンジンが動かせる余地が小さい」とか。ベンチマークで一番信用できる文はいつもこの種の文です。

## grep は文字を照合する。関係は照合しない

エンジンの話より、問題設定のほうが面白いです。そして著者は grep を先に擁護します。

> It is worth being fair to grep first, because in the right use cases, it is often the right tool. For text search it is fast, it needs no index, and it works on any repository in any language the instant the agent arrives. When a name produces roughly as many hits as there are real sites to change (a noise ratio near one to one), grep lands directly on the answer and there is nothing to improve.
>
> （拙訳）まず grep に公平であるべきだ。適切な用途では、たいてい最良の道具だから。テキスト検索としては速く、インデックスを要らず、エージェントが到着した瞬間からどんな言語のどんなリポジトリでも動く。ある名前のヒット数が実際に直すべき箇所の数とだいたい同じ（ノイズ比が1対1に近い）とき、grep は答えの上に直接着地するので、改善する余地はない。

ここが記事全体の軸です。問題は「変更箇所が多いこと」ではない。**テキスト検索がその集合を安く列挙できないこと**です。

壊れ方は3つ挙げられていて、私が読めたのは2つ。

**ノイズの洪水。** 探した名前は直すべき全箇所に確かに出てくるが、直さなくていい箇所にも大量に出てくる。マッチした行のテキストだけでは本物か判別できないので、エージェントはファイルを開いて読む。そして**開いたファイルはその run の残り全部のあいだコンテキストに居座る**。コストは検索ではなく、検索が強制する読み込みと保持のほうにある。

**見えない箇所。** 直すべき場所が、エージェントが検索した文字列とテキストを一切共有していない。だから検索には最初から出てこない。2つのコードの関係がテキストではなく構造で結ばれているとき、これが起きます。

計測された実例が効きます。Java の BloomFilter で自己型付けを入れるタスク。**直すべきは16箇所。型名を grep すると約461件。ノイズ比およそ29対1。** しかもその16実装のうち多くは匿名クラス・ネストクラス・テスト用サブクラスで、宣言部が変更箇所の近くでインターフェース名を書いていない。つまりノイズの洪水と見えない箇所が同時に起きている。

![大量の紙が壁いっぱいに貼られ、赤い×が無数に付いている。その中に青い丸で囲まれた紙が数枚だけあり、すみが脚立の上から橙の矢印でそれを指している。壁の下部に赤字で「461」、青い丸の束に「16」。足元の床には読み終えた紙束が山になり、赤字で「全部コンテキストに残る」。黒猫が山の上に座っている](/images/noise-ratio-predicts-the-token-bill/01-noise-ratio.png)

エンジン側がやっているのは、in-memory のグラフを1つ持って（ノードはモジュール・クラス・インターフェース・enum・レコード／struct・メソッド／関数・フィールド・引数・アノテーション、エッジは呼び出し・参照・実装・継承）、そこに構造クエリを投げさせることです。`get-type-hierarchy`、`get-references`、`trace-callers`、`search-signatures`、`search-bodies`、`get-source`。全ノードと全エッジがファイルパスと行を持っているので、名前ではなく**編集位置**が返る。`{file_path, line}` の重複排除済みリストを直接返すモードもあります。

BloomFilter のケースでは `get-type-hierarchy` が16実装を全部列挙し、`get-references` が行を渡す。構造クエリ2、3本で編集集合が確定して、読み荒らしが起きない。

## 結果

コスト（1 run あたりのドル、片側 n=10、中央値を主とする）。

| タスク | 言語 | コスト差 | 補足 |
| --- | --- | --- | --- |
| BloomFilter 自己型付け | Java | 平均 -36% / 中央値 -34% | 平均 $14.20 → $9.07、中央値 $14.29 → $9.38 |
| BloomFilter パッケージ改名 | Java | -20% | 入力 -11%、出力 -32% |
| SQLAlchemy compiler kwargs | Python | -20% | 入力 -24%、出力 -35% |
| TanStack | TypeScript | 平均 -5% / 中央値 -6% | 平均 $9.58 → $9.09。ビルドループが支配 |
| AssertJ 引数順 | Java | 中央値 -15% / 平均 -4% | 196ヒット対32箇所（約6対1） |
| QuartzNET | C# | -20%（典型 run） | 平均はビルド分散の外れ値で持っている |

（出典：Sabra, 前掲。見出しの「最大36%」は BloomFilter の**平均**の数字で、中央値は -34% です）

入力トークンの中央値も出ています。BloomFilter 自己型付けで 18.8M → 12.9M（-31%）、出力 89k → 78k（-12%）。SQLAlchemy が 1.2M → 891k（-24%）と 29k → 19k（-35%）。18.8M という数字に一瞬たじろぎますが、これは毎ターン再送される常駐コンテキストの累計です。ファイルを1つ開くと、そのファイルは以降のターン数だけ課金される。読み荒らしが高いのは「読んだから」ではなく「読んだものが残るから」です。

エンジンが対応する言語は Java・Python・JavaScript・TypeScript・C#・Rust。ただし勝ちが示されたのは Java・Python・TypeScript・C# の4つです。

## 私の見解1：ノイズ比は製品の性能ではない

この記事から実際に持ち帰る価値があるのは 36% ではないと思っています。著者自身が結論でこう書いている一文のほうです。

> What separated a win from a wash was not how many places needed changing, but whether a plain text search could list them cleanly. Where it could not, the engine helped. Where the work was not about finding code, it stayed out of the way.
>
> （拙訳）勝ちと引き分けを分けたのは、直すべき箇所がいくつあるかではなく、素のテキスト検索がそれを綺麗に列挙できるかどうかだった。できないところではエンジンが効いた。仕事の本体がコードを見つけることでないところでは、邪魔をしなかった。

つまり効果量の予測変数は**タスクとリポジトリの側にある**。29対1なら効く。6対1なら中央値だけ効く。1対1なら何も起きない。ベンダーがコントロールしている変数ではありません。

これは実務的にありがたい性質です。**買う前に自分で測れる。**

直近で「エージェントに投げたら妙に高かった」リファクタリングを1つ思い出して、こうやります。まず変更対象の型名やメソッド名のヒット数を `rg <name> | wc -l` で数える（`rg -c` はファイル単位の件数なので合計にならない）。次に、そのタスクの実際の変更箇所数を数える（マージ済みならその diff、これからならレビュー時の見積もり）。割る。

29対1が出るなら、その請求書の大半はノイズを読み分けた代金です。1対1に近いのに高いなら、原因は探索の外——ビルドとテストのループか、編集そのものの量です。この2つは対処法が正反対なので、切り分けが先です。

ついでに言うと、この指標はエージェントに限った話ではありません。ノイズ比29対1のコードベースは、人間のレビュアーにも同じ税を課しています。ただし人間は IDE を持っていて、エージェントは持っていなかった。

## 私の見解2：測らなかった側が本命で、そこには逆リスクがある

エンジンの効能として、著者は最初に2つ挙げています。1つ目がコスト。2つ目が「より完全な解」——テキスト検索が絶対に surface しない箇所も列挙するので、直すべき場所を見落としにくい。

そして結論部で、こう認めます。

> ...by enumerating sites a text search never surfaces, should be less likely to ship a silent bug, a benefit we argue from the mechanism rather than measure here, since correctness was held equal across both groups.
>
> （拙訳）テキスト検索が決して surface しない箇所を列挙することで、サイレントバグを出荷しにくくなるはずだ。ただしこれは本稿で測ったのではなく、機構から論じている便益だ。両群で正しさを揃えているので。

誠実な但し書きです。そして、ここに構造的な問題があります。

**この計測の設計では、2つ目の便益は原理的に見えません。** ゲートは「コンパイルして対象テストが通ること」。ところが「見えない箇所」を1つ取り落とした変更は、**たいていコンパイルするし、対象テストも通る**。だから通ります。そして両群が同じゲートを通った run だけを比べるので、残るのはコストの差だけになる。

念のため断っておくと、これは「Sonar が失敗 run を捨ててズルをした」という話ではありません。本文には「Tests 10 of 10 both groups」と書かれたタスクがあって、少なくともそこでは落ちた run がない。問題は選別ではなく、**オラクルの解像度**です。サイレントバグを測るには、テストが通ったパッチを正解 diff と箇所単位で突き合わせる必要がある。それはやっていない（少なくとも私が読めた範囲では）。

で、ここが私が売り手と意見の違うところです。

構造グラフは、見落としの確率を下げるのと同時に、**見落としが起きたときの検出確率も下げる**と思っています。

読み荒らしは高い。無駄も多い。でも副作用として、エージェントは無関係なファイルを大量に目にします。関係ないファイルを47個読むあいだに、DI のコンフィグや、文字列キーで実装を引くファクトリや、reflection でクラス名を組み立てている場所を、うっかり見てしまうことがある。あの無駄は偶然の安全網でもありました。

構造クエリが「これが完全な集合です」と返すと、その安全網が外れます。しかもエージェントは列挙を信じます（著者もそこを勝因に挙げている——「the model trusting the structural answer instead of searching by text」）。グラフが見えない場所——動的ディスパッチ、reflection、DI コンテナ、文字列キーのルックアップ、コード生成、設定ファイル、テンプレート——では、その信頼がそのまま静かな取りこぼしになります。

失敗の形が変わる、というのが私の見立てです。

- 変更前：高い。読み荒らしで請求が膨らむ。取りこぼしもする。
- 変更後：安い。構造で結ばれた箇所は取りこぼさない。**構造で結ばれていない箇所を、確信を持って取りこぼす。**

後者のほうがレビューで見つけにくいです。前者はトランスクリプトが荒れているので「こいつ迷子だったな」と分かる。後者は綺麗な diff が出てきます。

Sonar の記事にこのリスクへの言及は見つけられませんでした。「安全に入れっぱなしにできる（safe to leave on）」とは書いてあり、コストの意味ではその通りだと思います。私が引っかかっているのは正しさの側です。

実務的にどうするか。私は「グラフを使わない」ではなく、**グラフの外にあるものを人間の側でリストにしておく**が答えだと思っています。このリポジトリでは reflection もないので楽ですが、DI と文字列キーのディスパッチが多いコードベースなら、それらは構造クエリの返り値に**絶対に出てこない**という前提でレビューする。エージェントが「16箇所すべて修正しました」と言ったとき、確認するのは16の中身ではなく、**17個目の候補があるかどうか**です。

![床に橙のロープで大きな円が引かれ、その内側にすみがクリップボードを持って立ち、足元の紙束には青いチェックが並んで青字「16箇所 完全」。すみは円の内側だけを見ている。ロープには切れて解れた端が1箇所ある。円の外の白い余白には蓋の閉じた小さな木箱が4つ離れて置かれ、赤字で「reflection」「DI」「文字列キー」「codegen」。黒猫だけが円の外にいて、すみに背を向け、さらに遠くのもう1つの箱を見ている。そこに赤字で「17個目」](/images/noise-ratio-predicts-the-token-bill/03-confident-under-edit.png)

## 10回中2回、エージェントは grep に戻った

AssertJ のタスクの記述に、地味だが重要な一文があります。ナビゲーション有効の10 run のうち**2 run がグラフを使わず grep に戻り、平均の改善を消した**。中央値で -15%、平均で -4%（ノイズ内）という結果は、そこから来ています。

これは製品の欠陥ではなく、エージェントに道具を渡すときの一般的な性質だと思います。**道具の可用性は、道具の使用ではない。** システムプロンプトに構造クエリの説明を積んでも、モデルは慣れた `grep` に戻ることがある。しかも戻った run は失敗しません。ちゃんと通る。ただ高い。

この形は覚えておく価値があります。MCP を1つ入れて、コストを測って、「あまり効かないな」と結論する。ところがトランスクリプトを開くと、そのツールが一度も呼ばれていない run が半分ある。**ツールの効果を測っているつもりで、ツールの採用率を測っている。** 測定としては別物なのに、出てくる数字は同じ形をしています。

![線路の分岐点にしゃがんだすみが、片手で転轍レバーを握り、もう一方の手に青字「採用率」と書かれた小さな札を持っている。橙の主線は8台のトロッコを引き連れて右の箱型の機械へ吸い込まれていき、青字で「8/10」。分岐から左後方へ伸びる荒れた側線には2台だけが外れて紙束の山へ向かい、赤字で「2/10 grepに戻った」。機械へ向かう最後のトロッコの上に黒猫が座っている](/images/noise-ratio-predicts-the-token-bill/04-adoption-rate.png)

だからこの種の測定を自分でやるなら、コストの前に採用率を出したほうがいいです。**構造クエリが1回以上呼ばれた run の割合。** これが 8/10 なら効果の数字を読む価値があり、3/10 なら読むのはまだ早い。Sonar は「Subagents used in 5 of 10 navigation runs」みたいな内訳を出していて、この開示は良いと思います。

## なぜ LSP ではないのか

記事を読み終えて残った疑問がこれです。

`get-type-hierarchy`、`get-references`、`trace-callers`、`get-source`。この4つは、**過去15年ほとんどの IDE がローカルで無料でやってきたこと**です。LSP のリクエスト名でいえば `typeHierarchy`、`references`、`callHierarchy`、`definition`。機構としての主張——「シンボル同一性で解決するクエリはテキスト照合より安く正確」——は、私は正しいと思います。だからこそ、それが Sonar の発明ではないことも書いておくべきだと思う。

Sonar 版の届き方はドキュメント側に書かれていて、SonarQube CLI がインストールするスキル経由か、ローカルで動く SonarQube MCP Server 経由。そしてどちらも **SonarQube Cloud に接続します**。組織のコードのインデックスがどこに行くかは、導入判断の前に確認する項目です（記事はここに触れていません）。

ローカル完結の選択肢はすでにあります。Claude Code には LSP ツールがありますし、コードグラフを持つローカル MCP も存在します（このリポジトリのセッションにも1つ繋がっています）。私はそれらが Vortex と同じ性能だとは言えません——比較していないので。言えるのは、**この記事が測ったのは「グラフ >>> grep」という機構であって、「Sonar のグラフ >>> 他のグラフ」ではない**ということです。前者は誰でも今日使える。後者はこの記事には入っていません。

## 1つだけ持ち帰るなら

36% ではありません。それは他人のリポジトリの、6つのタスクの、2か月前の数字です。

持ち帰るのはこれです。**エージェントの請求書のうち「探索」が占める割合は、grep のヒット数と実際の変更箇所数の比で予測できる。** 比が大きいタスクは、道具を替えれば安くなる。比が1に近いタスクは、道具を替えても安くならない。この切り分けは、コマンド2つで今日できます。

そして、比が大きいタスクほど**取りこぼしのリスクも高い**——テキストで列挙できない集合を扱っているので。構造グラフはそこを埋めますが、埋めるのは構造で結ばれた箇所だけです。埋まらない側のリスト（reflection、DI、文字列キー、codegen）は、エージェントではなくあなたが持つ必要があります。

Sonar が測ったのは安いほうです。高いほうは、この記事では測られていません。
