## この記事について

2026年に出たコードレビュー関連のデータを扱います。中心になるのは4つ。Faros AI のテレメトリレポート "The Acceleration Whiplash"（開発者22,000人・約4,000チーム）、CircleCI の 2026 State of Software Delivery（CI ワークフロー実行2,800万件超・22,000組織超）、LinearB の 2026 Software Engineering Benchmarks（PR 810万件）、そして GitHub Blog の Andrea Griffiths 氏による2026年5月7日の記事 "Agent pull requests are everywhere. Here's how to review them."

この記事は2部構成です。

- **第1部**：4つのデータセットが何を言っているか
- **第2部**：**この故障の場所について私が考えていること**。どのソースにも書かれていない読み方

後半のほうが長いです。数字の整理は元記事を読めば済むので。

以前「AIコーディング論争は、事実では揉めていない」という記事で、同じデータから正反対の結論が出る理由を書きました。あれは解釈の割れ方の話でした。今回は違う話をします。レビューという工程そのものが、どこで壊れているかの話です。

先に開示しておきます。私が本文まで読めたのは GitHub Blog の記事と David R. Longnecker 氏のブログ、それに各レポートの公開サマリです。arXiv の2本（"More Code, Less Reuse" 2601.21276、Cotroneo ら 2508.21634）は要約と二次言及までで、論文本体は読めていません。第2部は既存の数字を突き合わせて出てきた解釈で、私が計測した結果ではありません。

## 第1部 — 数字が示していること

### 結論を先に

> レビューが遅くなった原因を「量が増えたから」と診断すると、処方は「レビュー能力を増やす」になる。だがデータが示しているのは、レビュアーが**時間をかけたうえで、より簡単に通している**という姿だ。これは容量の不足ではない。長年レビュアーが頼ってきた判定材料そのものが機能しなくなった、という故障だ。

### 生産が上がったのは本物

まず、AI 側に有利な数字から。Faros AI のテレメトリでは、開発者あたりのタスクスループットが約34%増。AI が生成したコードを無編集で受け入れる割合は1年で20%から60%に上がりました。CircleCI 側でも全体スループットは前年比59%増です。

このデータセットの80%のチームが、すでに「週次アクティブで AI ツールを使う人が過半数」の水準を超えています。もう先進事例の話ではありません。

### 同じテレメトリの、別の列

同じ Faros のレポートに、こういう列が並んでいます。

- コードレビューに費やす時間の中央値：441.5%増
- 初回レビューまでの時間の中央値：156.6%増
- 開発者あたりのバグ：54%増
- 本番インシデント数 ÷ PR 数：242.7%増
- コードチャーン（書かれてから2週間以内に書き直された割合）：861%増
- レビューなしでマージされた PR：約31%増

最後の項目に、レポートは注釈をつけています。どのチームもレビュー方針を変えていない。レビュアーが到着量に追いつけなくなった結果として、そうなった。

CircleCI 側の内訳も同じ方向を指します。フィーチャーブランチのスループットは中央値で15%増えた一方、main ブランチのスループットは約7%減り、main の成功率は70.8%まで落ちました。パイプラインに入る量は増え、本番に無事着く割合は下がっている。

### GitHub が名前をつけた故障

GitHub Blog の記事は、一文目からこう始まります。

> あなたはおそらく、それと気づかずに1つ承認している。テストは通っていた。コードはきれいだった。マージした。
> だがそれはエージェントが生成したものだった——そして**その承認のしやすさこそが問題なのだ**。

記事が引くのは2026年1月の研究 "More Code, Less Reuse" で、エージェント生成コードは変更あたりの冗長性と技術的負債が人間の書いたものより多い、という結果です。それでも人間のレビュアーはそちらを通しやすい。

GitHub のチームは、この失敗に名前をつけています。幻覚的正しさ（hallucinated correctness）。存在しない API を呼ぶような分かりやすい幻覚は CI が捕まえる。危険なのは、コンパイルが通り、既存テストが全部通り、それでも間違っているコードのほうです。ページネーションの off-by-one。テストが到達しない分岐に権限チェックがない。エージェントが想定しなかったエッジケースで短絡するバリデーション。スケールしてから初めて出るレースコンディション。

記事の処方は「スキャンするな、辿れ」です。差分の中で最も重要な経路を1つ選び、入力から出力まで変換を全部追う。そして、その修正が直したと主張するバグに対して、変更前のコードで落ちるテストを要求する。エージェントがそのテストを書けないなら、修正が不完全か、理解が間違っている。

![左に「汚いコード」の紙、右に「きれいなコード」の紙。見た目は正反対だが、どちらの裏にも同じ形の赤いバグが同じ位置に隠れている。すみが右の紙だけを安心した顔で受け取っている](/images/code-review-broken-instrument/01-same-bug-two-surfaces.png)

### ここに矛盾がある

以上は各ソースの記述です。ここから先は私の並べ方になりますが、2つの数字を隣に置くと妙なことになります。

LinearB のベンチマークでは、エージェント AI の PR はレビュアーに拾われるまでの時間が、AI 非使用の PR の5.3倍長い。AI 支援の PR は2.47倍。ところが GitHub 側の話は、AI が書いた PR はより簡単に承認される、です。

純粋な容量不足なら、両方遅くなるはずです。人手が足りないなら拾うのも遅く、通すのも遅い。両方速くなるならレビューを諦めたということで、これも筋が通る。だが「拾うのは極端に遅く、拾ったあとは通りやすい」は、そのどちらでもない形をしています。

## 第2部 — 私の見解：壊れたのは計器のほうだ

### レビューは検証ではなく、抜き取り検査だった

ここが出発点です。私たちは長いこと、コードレビューを「変更が正しいことの確認」だと呼んできました。実際にやっていたことは違います。差分を上から下まで読んで、書き手が手を抜いた痕跡を探していた。

命名が揃っていない。スタイルが周囲と違う。エラーハンドリングが1箇所だけ抜けている。関数が不自然に長い。コピペの痕。こういうものは、それ自体がバグではありません。バグの代理指標です。そして代理指標として、驚くほどよく機能していました。理由は単純で、スタイルに雑な人間は論理にも雑だからです。相関があった。

だからレビューは安く済んだ。10分で1000行をスキャンして、引っかかった数箇所を深掘りする。全経路を辿らなくても、雑さの分布から「危ないのはこの辺」を推定できた。この推定が効くという前提の上に、承認という制度が乗っていました。

### LLM は、その相関を切った

流暢さは、モデルが最適化している対象そのものです。命名は一貫し、スタイルは周囲に馴染み、エラーハンドリングは形式上そこにある。表面は均一にきれいになる——論理が間違っている場所も含めて均一に。

これが決定的です。AI コードは代理指標の値を下げたのではなく、代理指標と実際の欠陥の**相関を切った**。針が振れなくなったのではありません。針が「異常なし」を指し続けるようになった。

計器としては、壊れて動かないより悪い状態です。動かない計器は、動かないことが分かる。誤った値を高い確信度で返す計器は、それを信じた判断を汚染します。

そしてこの見方だと、さっきの矛盾がほどけます。レビュアーは、エージェントの PR を開くのが気が重い。何かがおかしいという感覚はあるからです。だから拾うのが5.3倍遅い。しかし開いてしまえば、いつも指摘に使っている材料が1つも見つからない。反対する根拠がない。だから通す。躊躇のあとの降伏、という形です。

ここは私の推測だと明示しておきます。Codacy の記事は同じ5.3倍を「レビュアーがより時間をかけて評価している証拠」と読んでいて、私の読みとは逆です。そして LinearB の同じレポートには、AI 支援の PR は約2.5倍大きいという数字もある。大きい差分は誰が書いても拾われにくく、レビューに時間がかかります。この交絡は本物です。あとで戻ります。

![大きな丸い計器の文字盤に「異常なし」と書かれ、針が糊で固定されて動かない。計器の裏側からは赤いバグが何匹も漏れ出して床に溜まっているが、すみは正面から針だけを見て手帳に記録している](/images/code-review-broken-instrument/02-needle-stuck-on-clean.png)

### だから「時間をかける」では直らない

Faros の数字の中で、私がいちばん重く見ているのは441.5%と861%の組み合わせです。レビュー時間の中央値が4.4倍になり、それでもコードチャーンは8.6倍、本番インシデント/PR 比は3.4倍。

時間をかけて、悪化している。

容量不足の症状ではありません。容量不足なら、時間をかけた分は取り返せるはずです。壊れた計器の症状です。目盛りが実態を反映していない計器は、長く見つめても正しい値を返さない。むしろ、長く見つめたぶんだけ「ちゃんと確認した」という確信が積み上がる。

### 業界の処方は、二台目の同じ計器

ここが、この記事でいちばん反対されそうな主張です。

LeadDev の 2026年のレポートによれば、AI がレビュー手法に影響したと答えた回答者の86%が、人間のレビュー前の事前スクリーニングに AI を使っています。これが現在の主流の処方です。生成が速くなったなら、検査も機械化して追いつかせる。

私はこの処方が、故障箇所を外していると考えています。

AI レビュアーが確実に捕まえるのは、決定論的に判定できるものです。リンタ、型、既知の脆弱性パターン、カバレッジ閾値、複雑度。Codacy の記事が挙げている一覧がまさにそれで、正しい一覧です。ただ、それらは元から問題ではなかった。CI が10年前から捕まえてきた領域です。

一方、幻覚的正しさに対して AI レビュアーはどうか。差分を読んで妥当性を評価するモデルは、流暢で一貫したコードを「妥当」と判定する方向にバイアスがかかります。人間のレビュアーを騙したのと同じ表面が、同じように効く。つまり事前スクリーニングは、**壊れた代理指標に合わせて校正された二台目の計器**を並べる行為です。一台目が見落とすものを、二台目も見落とす。しかもダッシュボードの緑が2つになるので、確信だけが増える。

と書くと、GitHub の記事はそれを推奨しているじゃないかと思うかもしれません。あの記事の3つの持ち帰りは「CI の弱体化は即停止」「エージェントに先にスキャンさせ、あなたは重要経路を辿る」「複雑な PR にはレッドフラグのチェックリスト」でした。

でもこれ、よく見ると私の主張を先に認めています。スキャン（代理指標を読む作業）を機械に渡し、辿る（実際に動かして確かめる作業）を人間に残すという分割になっている。代理指標がもう人間の判断材料として使えないことを、前提にしないと出てこない配分です。

私が同意しないのは締め方だけです。あの記事は「判断がボトルネックだ、そしてそれでいい」（Judgment is the bottleneck, and that's fine）で終わります。良くないと思います。動く計器がない状態の判断は、判断ではなく雰囲気です。

![一台目の計器の隣に、すみが脚立に乗ってレンチでまったく同じ形の二台目を取りつけている。二台の針はどちらも同じ位置で止まっていて、両方にチェックマークがついている。足元には赤いバグの山ができている](/images/code-review-broken-instrument/03-second-identical-gauge.png)

### 信号を取り戻すのは、偽装できないものだけ

では何が使えるか。基準は1つで、**モデルが表面を整えることで満たせないもの**かどうかです。

変更前のコードで落ちるテスト。これは強い。通るテストを書くのは簡単ですが、「この変更がなければ落ちる」テストは、変更が何を直したのかを述べる主張です。GitHub がこれを要求しているのは正しい。

1本の経路を端から端まで辿ること。読むのではなく、境界値（0、最大、空）を入れて実際に何が起きるか確かめる。表面の見た目とは独立した情報が出ます。

そして事後の指標。FlowVerify の記事が「エージェントが関わった PR のレビューリードタイムとリバート率を見ろ、マージされた PR 数ではなく」と書いていて、これは指標選択として正しい方向です。リバート率は代理指標ではありません。本番が下した判定です。流暢さでは動かせない。

逆に言えば、これは「レビューを厳しくする」話ではありません。読む量を増やす方向は全部間違いです。読むのをやめて、動かす方向に予算を移す話です。

![左隅に布をかけられて使われなくなった計器が小さく置かれている。すみは中央で木槌を振り、「変更前のコード」を挟んだ枠の上に吊られた鐘を叩いて、実際に音を鳴らしている](/images/code-review-broken-instrument/04-stop-reading-start-running.png)

### 承認という儀式について

もう一段だけ踏み込みます。

Approve ボタンは、最初から検証の証明ではありませんでした。**検証の代わりに置かれた社会的な儀式**です。誰かが名前を出して責任の一部を引き受ける。それで済んでいたのは、代理指標が効いていたからです。10分のスキャンで見つかる問題の割合が十分高かったので、儀式と実質がだいたい一致していた。

相関が切れた今、選べる道は2つだと思います。

1つは、検証を本物にして安くする。変更前に落ちるテスト、経路のトレース、強いロールバック、リバート率の監視。そのうえで承認を格下げする。実際、Codacy の記事が触れている「テストとロールバックで守られた変更はマージ先行・レビュー後追い」「人間のレビューは高リスク領域とアーキテクチャ変更に限定」という実験は、この方向です。

もう1つは、儀式を残したまま、未検証のコードに署名して出荷していることを認める。

多くのチームは2番目をやりながら、自分は1番目をやっていると思っている。Faros の「レビューなしマージが約31%増、ただしどのチームも方針を変えていない」は、その儀式が誰にも決定されずに崩れていく音だと私は読みました。方針として決めていないぶん、崩れたことも記録に残りません。

### 私が間違っているとしたら

この解釈が崩れる筋を書いておきます。

いちばん大きいのは**PR サイズ**です。AI 支援の PR は約2.5倍大きい。差分が2.5倍なら、レビュー時間も、拾われるまでの時間も、検出される issue の数も、誰が書いていても増えます。もしサイズで正規化したときにレビュー時間の膨張が大部分消えるなら、私の「計器が壊れた」話は主要な支えを失い、「差分が大きくなっただけ」という退屈で正しい説明が残ります。私が見た限り、どのレポートもこの正規化をしていません。

欠陥の量そのものも、実は安定していません。Longnecker 氏が丁寧に書いているのですが、CodeRabbit の「AI 共著 PR は平均10.83件、人間のみは6.45件」（約1.7倍）という数字は、ベンダーのレポートで、PR サイズも言語構成もコホートの作り方も正規化されていません。氏がそれでもこの方向を信じたのは、Cotroneo・Improta・Liguori らの査読済み研究（50万件超のマッチドサンプル）が別のデータと別の検出器で似た方向を出したからです。ただしその研究の中でも、AI コードは人間の実装より構造的に単純で、どちらのコホートの欠陥が多いかはモデルによって逆転しています。

Longnecker 氏の指摘で私が受け取ったのはここです。「1.7倍」を「AI が問題だ、制限しろ」と読むチームは、上流で実際に得ている速度を失う。数の多さよりカテゴリの内訳（セキュリティ、null/エラー処理、ビジネスロジック）のほうが行動を変える情報だ、と。私の話も同じで、これは AI を減らす議論ではありません。検査の方法を変える議論です。

もう1つ。エージェントの PR のリバート率が、サイズを揃えたあとで人間の PR と変わらないなら、幻覚的正しさは本番まで到達していないことになります。その場合、計器は壊れていない。私はこの数字を探しましたが、公開されているものを見つけられませんでした。自分のチームで取れる人がいれば、この記事の主張はそこで検証できます。

そして今回の中心データはほぼ全部、AI レビューツールを売っている会社のテレメトリです（Faros、LinearB、CircleCI、CodeRabbit、Codacy）。「あなたの検査工程は壊れている」という結論に商業的な利害がある側から出た相関データを、私は主張の骨格に使っています。それは弱点です。

---

## まとめ

1つだけ持ち帰るなら、これです。**レビュー時間を4.4倍払ってもチャーンが8.6倍になるなら、足りないのは時間ではない。** 読む量を増やす方向の対策——レビュアーを増やす、AI に事前スクリーニングさせる、チェックリストを長くする——は全部、同じ計器をもっと熱心に読む行為です。

次にやることを1つ選ぶなら、AI が関わった PR に「この変更がなければ落ちるテスト」を要求するところから始めるのがいちばん安いと思います。ツールもプロセス変更もいらず、幻覚的正しさに正面から当たる唯一の要求だからです。

そして、リバート率を測り始めてください。私の主張が正しいかどうかも、それで分かります。
