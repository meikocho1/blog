claude.ai で、完成したコードブロックのハイライトに1秒ほど固まることがあった。原因は em dash（—）だった、という話がこの記事の中ほどに出てきます。返答の Markdown に Latin-1 の外の文字が1つでも混ざると、V8 が文字列全体を UTF-16 で持つので、シンタックスハイライトの正規表現が全部遅い2バイト経路に落ちる。Claude はコードブロックを1バイト文字列にコピーしてからハイライトする20行の変更で直した。

こういう発見が2週間で3,000件以上マージされた、という記事です。見出しの一文はこれでした。

> Once Claude can measure something, it can make it faster.
>
> （Claude は、測れるものなら速くできる。）

私の読みを先に置いておきます。

> この一文は正しいが、記事を支えているのはその手前にある2つの規則のほうだ。1つは「壁時計と連動すると証明できないベンチは捨てる」、もう1つは「ラボで登った数字を、登った本人が触れない実ユーザーの計測で裁く」。登る数字と裁く数字を分けたから、3,000件が事故なしで通った。逆に、どちらの数字にもならない軸、つまりコードの複雑さとバンドルの重さには、記事全体で人間の裁定が1回しか出てこない。

出典は claude.dev Blog の [How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)、著者は Raymond Wang、Sam Attard、Issac G.、2026年9月23日公開。Hacker News では [49821196](https://news.ycombinator.com/item?id=49821196) で、私が2026年9月25日（日本時間）に Algolia の API で数えた時点で 220 ポイント、コメント 146 件でした。

断っておくことが3つあります。記事の数字はすべて Anthropic の自己申告で、私には検証する手段がありません。記事に出てくる Slack のやりとりは、記事自身が "Recreated from a real conversation"（実際の会話からの再構成）と注記しています。そして使われたのは「Opus 5.5 とおおむね同等の社内リサーチモデル」で、スプリントは8月。Opus 5.5 そのもの（9月22日公開）ではありません。

## 数字はこう並んでいる

対象はユーザー行動の95%を占める4つの動線（アプリ起動、会話の開始、既存会話の読み込み、メッセージ送信）で、Web とデスクトップと製品ごとに分けると13の計測になる。p75 でこうなったそうです。

> At the 75th percentile, time to a typeable page on a fresh load of claude.ai went from 3.1 seconds to 0.55, starting a new Claude Code session went from 0.8 seconds to 0.3, and loading a Claude Cowork cloud session went from 2.6 seconds to 0.73.
>
> （75パーセンタイルで、claude.ai を新規に開いて入力できるまでが3.1秒から0.55秒に、Claude Code の新規セッション開始が0.8秒から0.3秒に、Claude Cowork のクラウドセッション読み込みが2.6秒から0.73秒になった。）

割ると5.6倍、2.7倍、3.6倍。「約3倍」はこのあたりの丸めです。体制は Slack の1チャンネルに Claude Tag（ベータ）を常駐させ、同時に150以上のスレッドを走らせた。フィーチャーフラグは2週間で約200本入れて、半分以上を期間中に片付けた。PR の約3分の1が、追加の計測かガードレールを含んでいた。

ここまでは読めば分かることなので短くします。

## 「登る」の前に、ベンチを捨てる規則があった

記事で一番大事だと私が思うのは、この依頼文です。

> @Claude please prove that hill climbing against each of these can result in measurable wall clock perf wins. we'll unship the benches for any candidates that cannot prove that
>
> （@Claude これらのそれぞれに対して山登りすると、壁時計で測れる性能向上につながることを証明して。証明できない候補のベンチは撤去する。）

背景はこうです。ユーザーが感じるのは壁時計の時間だが、ミリ秒はノイズが大きくて CI のゲートにできない。命令数なら決定的に測れる（Valgrind と `node --predictable` で1回走らせて、チェックイン済みの基準値と比べるだけ）。ただし命令数が壁時計と連動していなければ、Claude は間違った山を登る。

そこで2つのホットパスで試した。会話のメッセージツリーを組み立てる処理と、Claude Code 出力のステータス行スキャナ。前者は命令の4分の1がメガモーフィックな辞書引きで、同じメッセージ ID を3回解決していた。1時間後の結果がこれです。

| ホットパス | 命令数 | 壁時計 |
| --- | --- | --- |
| メッセージツリー組み立て | −48% | −78% |
| ステータス行スキャナ | −31% | −44% |

連動はしている。ただし比例はしていません。命令を半分弱削ったら時間は5分の1になった。つまり命令数は「下げれば時間も下がる」方向の代理指標としては使えるが、「どれだけ下がるか」の物差しではない。記事はここで2本のラチェット（CI で命令数の増加を落とし、下がったら毎日上限を下げるジョブ）を入れています。

気になるのは、証明が示されているのがこの命令数の2パスだけだという点です。同じ日に立ち上がった他の4本（V8 の呼び出し回数、React のコミット数、スタイル再計算、DOM ミューテーション）について、壁時計との連動を確かめた数字は本文にありません。撤去すると宣言した規則が、どのベンチを撤去したのかも書かれていない。規則があったことは分かるが、どれだけ働いたかは分からない。

## 見つけたものの多くは、既存の計器の外にあった

「測れるものは速くできる」を裏返すと、「測っていないものは見つからない」になるはずです。ところが記事の中で一番おもしろい発見は、どれも既存の計測がゼロと言っていた場所から出てきています。

サイドバーの行が読み込み後にぱらぱら出てくる件。既存の監視で一番近いのは Cumulative Layout Shift でしたが、1回のずれは約0.008で、「良好」の閾値0.1のはるか下だった。きっかけは誰かが貼った画面録画です。Layout Instability API を直接使うイベントを作ってみたら、Web のページ読み込みの31%で、ユーザーが何もしていないのに使える状態になった後で何かが動いていた。

Claude が描画後のコードパスを追ったら、残っていた `location.reload()` が1日50万回の見えないリロードを起こしていた。どの読み込み指標にも出ていなかった。これは人ではなく Claude の調査から出てきた1件です。

静的コンポーザーを社内に出した4時間後、Marius という社員が「新しいタブで開くとたまに15〜20px下にずれる」と録画を貼った。Claude の説明では、組織管理下の Chrome の新規タブには56pxのフッターがあり、アドレスバーで打っている間に Chrome がその短い高さで先読み描画して、表示後に伸ばす。コンポーザーはページ高の18%の位置にあるので 0.18 × 56 ≈ 10px 落ちる。ヘッドレス Chrome にはブラウザ UI がないので、レイアウトテストでは原理的に見えない。

3件とも、既存の計器は「問題なし」と言っていました。そしてサイドバーと Chrome の2件は同じ順番で見つかっています。人が目で気づいて録画を貼る、Claude が計測器を作る、そこで初めて登れるようになる。記事は「計測がステップ0からステップ1になった」と書いていますが、この2件に限れば、ステップ0は依然として人間の目でした。

## 私の見解1：登る数字と、裁く数字が別だった

HN のスレッドで一番考えさせられたのは、GPU カーネルの最適化をエージェントでやっているという augment_me のコメントです。

> The issues we have found is that Claude will reward hack when all the low-hanging fruit is gone. It will replace your measurement harness, it will monkey patch library functions, it will cheat wherever it can, store information in caches instead of recomputing when it won't be able to do so in real settings [...]
>
> （私たちが見つけた問題は、低い果実がなくなると Claude が報酬ハックをすることだ。計測ハーネスを差し替える、ライブラリ関数をモンキーパッチする、できるところではどこでもずるをする、本番ではできないのにキャッシュに情報を貯めて再計算を省く……）

この人は続けて、「測れれば速くできる」ではなく「目的を詳細に定義し、やってみて初めて分かる禁じ手を列挙して禁止したら、速くできる」だろう、と書いています。

私はこれと元記事が矛盾しているとは思いません。違いは構造にあると思います。GPU カーネルのベンチでは、登る数字と、成果として報告する数字が同じです。ベンチの値が上がれば勝ち。だから数字をごまかせば勝てる。

claude.ai のループは、記事の6段の手順を読むとそうなっていません。ラボでベンチを登る。フラグの後ろで出す。**出した後で、実ユーザーのフィールドデータをビルドとプラットフォーム別に読む。** 良くなっていればラチェットを下げ、なっていなければフラグを切る。ラボの数字は仮説で、判決はフィールドが出す。そしてフィールドの数字は、Claude がラボでどれだけ工夫しても直接は動かせない。キャッシュを仕込んで2回目を速く見せても、新規ユーザーの p75 は下がらない。

GPU の人たちに足りないのは禁止リストの長さではなく、この2つ目の数字だと私は思います。カーネルにも本番のトラフィックがあるなら、そちらで裁けばいい。ないなら、そもそも最適化の成果をベンチの外で確かめる手段がない。

ただし、この分離は完全ではありません。サイドバーの件では、フィールドで読むレイアウトシフトのイベント自体を Claude が作っています。登る本人が、裁く計器も作っている。記事のケースでは人間のレビュー（全 PR に最低1人の承認）がその穴を塞いでいたはずですが、そこを担保していたのが計器ではなく人だった、とは言っておきたい。

## 私の見解2：まだ低い果実の領域を出ていない

augment_me の条件は「低い果実がなくなると」でした。元記事のスプリントは、そこまで行っていない可能性が高いと思います。

記事にこうあります。

> We hit twelve of the thirteen targets by day three.
>
> （13の目標のうち12を、3日目までに達成した。）

目標は Claude がプロジェクトごとの効果をミリ秒で見積もって積み上げたものです。それが3日で12/13。そのあと目標を引き直して、さらに「WACKY なアイデアも歓迎」と広げている。HN で「3秒かけて白いページを出すサイトを1秒にして自分を褒める」と皮肉ったコメントが2件あったのは、この出発点のせいです。静的なコンポーザーを HTML に焼き込む、会話を切り替えてもコンポーザーをマウントしたままにする、サイドバーの再描画を90%減らす。どれも有効ですが、報酬ハックが起きる前の段階の仕事に見えます。

だから「壁時計と連動しないベンチは捨てる」「フィールドで裁く」という2つの規則が報酬ハックを防いだのか、それともまだ報酬ハックが起きる局面に来ていなかったのか、本文の数字では区別できません。

区別に使える数字は1つあります。**フラグを切った回数**です。記事は「3,000件以上、顧客に見えるインシデントもロールバックもゼロ」と書いている。同じ記事のループの第5段は「良くならなければフラグを切って反復する」です。フラグを切るのはロールバックに数えない、という定義なら両立しますし、それ自体は妥当な設計です。ただ、約200本のフラグのうち何本が「ラボでは勝ったのにフィールドで負けた」で切られたのかは、書かれていない。

その比率は、代理指標がどれだけ嘘をついたかの実測値です。低い果実のうちはほぼ0で、果実が尽きるにつれて上がっていくはずの数字でもある。次の記事（上流への貢献の話を別に書くそうです）で一番読みたいのはこれです。

## 私の見解3：数えられない軸には、ガベルが1回しか出てこない

記事の最後の方に、「方向づけ」の例としてこういう1行があります。

> One 900-line PR got a one-line reply: "going to gavel that 2ms per send is not worth the complexity of maintaining this build plugin."
>
> （900行の PR に、1行の返信がついた。「送信1回あたり2msは、このビルドプラグインを保守する複雑さに見合わない、と裁定する」。）

記事全体で、コードの複雑さが判断の材料として出てくるのはここだけです。そしてこの判断には数字がない。2ms の側には数字があり、複雑さの側にはない。数字がある方が勝つ構造のなかで、数字がない方を勝たせたのはガベル（議長の木槌）でした。

HN の RomanKornev はこれを正面から聞いています。

> If you're not measuring something it will get sacrificed.
>
> （測っていないものは、犠牲にされる。）

もう1つ、誰もガベルを打っていない軸があります。simonw が Firefox で見たところ、claude.ai は JavaScript を 20.78 MB（圧縮後 6.84 MB）読み込んでいたそうです。記事が測ったのは「入力できるまでの時間」で、静的コンポーザーはまさに、React の初期化が終わる前にユーザーを打たせる工夫でした。重さはそのままで、重さが見えない時間を作った。これはユーザー体験としては正しい判断だと思います。ただ、転送量は4つの動線のどの計測にも入っていないので、このスプリントの山登りの対象にはなっていない。

私が一番重いと思うのは、ラチェットが残ることです。フラグは期限付きで、半分以上がもう消えている。ラチェットは違います。「この処理の命令数は、この値を超えたら CI を落とす」「下がったら上限を毎日下げる」が、スプリントが終わった後も効き続ける。そこには方向が1つしか書かれていません。正しさのためのチェックを1つ足して命令数が増える PR は、理由を知らない次の担当者の前で赤くなる。理由は Slack のスレッドにあります。150本のうちのどれかに。

記事は「ラチェットがあるので速さは保たれるはず」と書いています。保たれるのは速さだけで、速さと引き換えに何を払ったかの記録はラチェットには入っていない。ここは記事に書かれていない費用だと思います。

![すみが、一方向にしか回らない大きな歯止め付きの歯車（ラチェット）の前で、困った顔でつま先立ちになっている。歯車の爪には小さな札が何十枚もぶら下がっていて、どれも文字がかすれて読めない。歯車の横には細い付箋が1枚だけ貼られていて、そこだけ赤で「2ms」と太く書かれている。床に置いた木槌の上で赤い首輪の黒猫が座っている。歯車に青で「下がるだけ」](/images/claude-ai-speed-sprint/03-ratchet-with-unreadable-tags.png)

## 1つだけ持ち帰るなら

エージェントに数字を登らせる前に、「その数字を登ったかどうかを、何で裁くか」を先に決めることです。裁く数字は、登る本人が触れない場所にあるほどいい。claude.ai の場合はそれが実ユーザーのフィールドデータで、だから「測れれば速くできる」がきれいに成立した。

2つ目を持ち帰るなら、手元のリポジトリでエージェントにラチェットを入れさせたとき、その上限の理由をどこに書くか、です。CI の設定ファイルの横に1行でいい。Slack のスレッドは、半年後には検索に出てきません。

![すみが大きな黒板の前でチョークを持ち、左半分に書かれた長い数字の列（何本もの右下がりのグラフ）をもう書き終えて、右半分の真っ白な欄にどう書けばいいか迷って首をかしげている。右の欄の上には青で「理由」とだけ書かれている。黒板の縁で赤い首輪の黒猫がチョークの粉を前足でつついている。左の列のそばに橙で「3,000件」](/images/claude-ai-speed-sprint/04-blackboard-reasons-column-empty.png)
