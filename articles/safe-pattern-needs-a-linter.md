## この記事について

2026年8月17日に Wiz Research が公開した、Snowflake の公開リポジトリにおける GitHub Actions のスクリプトインジェクション事例を扱います。著者は Gal Nagli 氏。

- 出典: [Wiz Red Agent Finds Its Way Into Snowflake's Internal Jira Through a Flaw in a GitHub Copilot–Assisted PR](https://www.wiz.io/blog/red-agent-snowflake-copilot-cicd-bug)（Gal Nagli、2026年8月17日）
- 該当PR: [snowflakedb/snowflake-connector-net#1218](https://github.com/snowflakedb/snowflake-connector-net/pull/1218)（脆弱性が入った側）、[#1402](https://github.com/snowflakedb/snowflake-connector-net/pull/1402)（修正側）

この記事は2部構成です。第1部が経緯、第2部が**私が差分を自分で読み、自分でリンタを走らせて出てきた話**。後半のほうが長いです。事件の経緯はWizのブログを読めば済むので。

先に、何を自分で確認して何を確認していないかを開示します。

自分で確認したこと。GitHub API で PR #1218 と #1402 のマージ日時とコミットSHA（`4a1b8ce` / `1dc7766`）が Wiz の記述と一致すること。両PRの実際の差分。そして脆弱なリビジョン `4a1b8ce` の `jira_issue.yml` を取得して、2026年8月時点の `zizmor@latest` を走らせた結果。

確認していないこと。GitHub Advanced Security がこのファイルをスキャンして何も報告しなかったという点、Copilot がPRを「問題なし」と判定したという点、そして実際の攻撃が成功したという点。これらは全部 Wiz の主張であって、私が外から検証できるものではありません。以下でこの3つに触れるときは、Wizがそう書いている、という形で書きます。

---

## 第1部 — 何が起きたか

### 結論を先に

> 安全な書き方は、コードの「形」としてだけ存在していた。なぜその形なのかを強制する仕組みはどこにもなかった。だから書き直しの過程で消えた。そして消えたことに、人間のレビューもAIのレビューも気づかなかった。一方で、設定ゼロの無料リンタは、実際に攻撃された行そのものを High で指す。守るべきだったのは注意力ではなく、機械可読なルールだ。

### 5日

Wiz によれば、時系列はこうです。2026年6月18日にPR #1218 がマージされて脆弱性が本番になった。6月23日に Wiz の自律型セキュリティエージェント「Red Agent」がこれを発見し、実際に悪用して Snowflake の社内 Jira への読み取りアクセスを得た。同日 HackerOne 経由で報告され、Snowflake は同日パッチを当てた。翌日トークンをローテーション。監査ログの照合で、露出期間中にアクセスしたのは Wiz のテスト用IPだけだったことが確認されています。

穴が開いていたのは5日間です。

### 壊し方

問題のワークフローは `issues: opened` で起動します。つまり GitHub の誰でも、issue を1本立てれば発火させられる。そのタイトルが、`run:` ブロックの中に直接展開されていました。

```yaml
run: |
  # Escape special characters in title and body
  TITLE=$(echo '${{ github.event.issue.title }}' | sed 's/"/\\"/g' | sed "s/'/\\\'/g")
```

コメントには「特殊文字をエスケープする」と書いてあります。そして実際に `sed` でシングルクォートを潰しています。それでも壊れる。

順番が逆だからです。`${{ }}` の展開は GitHub 側がYAMLをシェルに渡す前に済ませます。`sed` が走るのはそのあと、つまり生成済みのシェルスクリプトの実行時です。タイトルに `'` を1文字入れれば、`echo '...'` の文字列がそこで閉じ、以降が普通のコマンドとして解釈される。エスケープ処理は、自分より前に終わっている置換を守れません。

Wiz はこの経路でシークレット（`JIRA_API_TOKEN` など）を外部に送出させ、`qa@snowflake.net` として Snowflake の Atlassian に認証できたと書いています。エンジニアリング、セキュリティコンプライアンス、バグバウンティのトラッキングプロジェクトへの読み取りアクセスが取れた、と。

Red Agent の挙動として面白いのは、最初の試行が bash の構文エラーで失敗した点です。ペイロードに `#` を使ったところ `TITLE=$(...)` の閉じ括弧まで飲み込んでしまった。エージェントはそこで止まらず、エラーを読んでペイロードを `; echo '` の形に直し、成功させています。

![すみが門の南京錠を布で丁寧に磨いている。しかしその門につながる塀は途中で途切れていて、橙の点線の経路が塀の切れ目から入り、赤い封筒を運んですみの背後を素通りして右へ抜けていく](/images/safe-pattern-needs-a-linter/01-escaping-after-expansion.png)

### 飾りだったゲート

ワークフローには、いかにも防御っぽい条件が付いていました。

```yaml
if: (github.event_name == 'issues' && github.event.pull_request.user.login != 'whitesource-for-github-com[bot]')
```

`issues` イベントでは `github.event.pull_request` は常に `null` です。だから条件は `null != 'whitesource-for-github-com[bot]'` に縮退して、常に真になる。誰でも通ります。

ここで、差分を読んで分かったことを1つ足します。**この壊れたゲートは、PR #1218 が持ち込んだものではありません。** #1218 の差分では、この `if:` 行は削除側（`-`）と追加側（`+`）の両方に同じ内容で現れます。変わったのはインデントだけです。つまり常に真の条件は、この事件よりも前から置かれていた。Wiz のブログはゲートの壊れ方を説明していますが、PRが持ち込んだとは書いていません。今回の回帰は純粋に、`env:` + `jq --arg` から直接展開への差し替えのほうです。

## 第2部 — 私が考えていること

### まず、自分で走らせた

第1部までは要約です。ここからが本題。

脆弱なリビジョン `4a1b8ce` の `jira_issue.yml` を取ってきて、GitHub Actions 用の静的解析ツール [zizmor](https://docs.zizmor.sh/) を当てました。インストールもしていません。1行です。

```
uvx zizmor@latest .github/workflows/jira_issue.yml
```

結果。`template-injection` が High / 確信度 High で、24行目を指しました。24行目というのは、これです。

```
TITLE=$(echo '${{ github.event.issue.title }}' | sed 's/"/\\"/g' | sed "s/'/\\\'/g")
```

実際に悪用された行です。同じ監査は25行目（`BODY`）と42行目（`description` 内の `html_url`）も High で拾い、さらに `secrets-outside-env` が Medium で「シークレットが `run:` ブロックから触れる位置にある」と指摘しました。auditor ペルソナでの総計は16件。

念のため書きますが、これは「当時これを使っていれば防げた」という主張ではありません。私が走らせたのは2026年8月時点の最新版です。当時のバージョンで同じ結果が出たかは確認していません。それでも、この検出は `template-injection` というzizmorの中核監査そのもので、`${{ }}` が `run:` に入っていたら指す、という単純な規則です。設定ファイルは書いていない。除外リストもいじっていない。所要時間は1分未満でした。

一方 Wiz は、GitHub Advanced Security がこの脆弱なワークフローを含む最終リビジョンをスキャンし、明示的にこのファイルを抽出したうえで、このインジェクションを報告しなかったと書いています。Copilot は同じPRの共著者としてコードを確認し、問題なしと判定したとも。

同じファイルです。片方は1コマンド。もう片方は、企業向けのセキュリティ製品とAIレビュアーの二重チェック。

![真っ白な壁に同じ形の穴が1つ。左側では大きな箱型の機械が2台、壁の前で「ALL CLEAR」の札を上げている。右側ではすみが虫めがねを1つ持って穴を指さしている](/images/safe-pattern-needs-a-linter/02-one-command-vs-two-gates.png)

### 「AIが危険なコードを書いた」という話ではない

この事件は「AI支援のPRが脆弱性を入れた」という見出しで流通しました。でもそこは、開示された事実より一歩踏み込んでいます。Wiz 自身が公開当日の1957 UTCに追記を入れて、Copilot はマージ済みPRを確認した共著者であり、**コード変更自体がAI支援だったかは不明**だと明記しています。

なので私は、この事件のAI要素を2つに分けたい。書いた側は不明。**通した側は、AIだったと開示されている。**

この区別はどうでもいい細部ではありません。「AIに危ないコードを書かせるな」という教訓と、「AIに安全性の判定をさせるな」という教訓は、打つ手が全く違います。前者はコード生成の制限に向かう。後者は、判定を機械可読なルールに落とせという話になる。今回の開示内容が支えているのは後者です。

### 消えたのは1つの防御ではなく、3つだった

差分を読むと、書き換え前のコードは3重に守っていました。

`ISSUE_TITLE` / `ISSUE_BODY` / `ISSUE_URL` を `env:` に置いて、シェル変数として参照していた。これが1つ目で、テンプレート展開を経由させない唯一の正解です。JSONの組み立ては `jq -n --arg` に任せていた。これが2つ目、クォートも制御文字も `jq` が責任を持つ。さらにバックティックの明示エスケープ（`${ISSUE_TITLE//\`/\\\`}`）と、本文を一時ファイルに落とす処理まで入っていた。

書き換え後、3つとも消えています。`env:` から3変数が落ち、`jq -n` が生の `-d '{...}'` に置き換わり、バックティック処理も一時ファイルも無くなった。

これを書いた人（あるいは何か）に悪意はないと思います。むしろ読みやすくなっている。`jq` のパイプラインを組み立てるより、JSONを直接書いたほうが短いし、初見で分かる。防御3つは、どれも**それが防御であることが読めない形**をしていました。`--arg` を使う理由はコードのどこにも書かれていない。バックティックエスケープの1行は、意図を知らなければただのノイズです。

セキュリティの意図が、コードの形にしか存在していなかった。コメントにも、テストにも、CIのルールにも無かった。形は書き換えで消えます。

![すみが古い装置から3本の見えないつっかえ棒を無造作に抜き取り、代わりに短くてすっきりした1本の棒を差している。抜いた3本には理由が何も書かれていない白い札がぶら下がっている](/images/safe-pattern-needs-a-linter/03-three-props-removed.png)

### テストで守れない性質を、レビューで守ろうとしていた

もっと一般化します。

このクラスの安全性は、**負の性質**です。「注入が起きないこと」を主張するテストは書けない。単体テストは、やることをやるかどうかを確かめるものです。やらないはずのことを全部やらない、という証明はできません。だからこの手の不変条件は、テストスイートの外に置かれる。

置かれた先が「慣習」でした。慣習は、そのファイルの変更頻度に反比例して生き延びます。そして2026年に何が起きたか。**書き換えが安くなった。** 生成であれ支援であれ、YAMLを丸ごと書き直すコストは激減しました。変更頻度が上がった先が、たまたま「正しさがテストではなく慣習で担保されている領域」だった。

つまり問題は、AIが安全性を理解していないことではありません。**AIは、テストで守られていない領域の書き換えレートを上げた。** そこは元々、人間の記憶だけで守られていた場所です。

以前「レビューは詰まっていない、計器が壊れている」という記事で、AIコードが「汚さ」という判定材料を焼き切った話を書きました。今回はその続きではなく、別の故障です。あちらは判定材料が壊れた話。こちらは、**判定材料が最初から存在しなかった領域**の話です。CIのYAMLに「汚さ」の警告灯は元々付いていない。

### 差分の見た目の大きさと、意味的な危険は無相関

もう1つ、差分を読まないと出てこない点。

PR #1218 は `jira_issue.yml` のインデントを4スペースから2スペースに変えています。その結果、このブロックのほぼ全行が変更行として表示されます。実際にはブロックの中身も書き換わっているので「インデント整理だけのPR」ではありません。ただ、**危険な意味の変化が、全行チャーンの中に埋もれた**のは確かです。

レビューでこの差分を開くと、目に入るのは大量の緑と赤です。人間の注意力は、そこで「これは整形だな」という早いパターンマッチに落ちます。落ちるのが悪いわけではなく、そう落ちるように出来ている。

差分の視覚的な大きさは、意味的なリスクを何も教えてくれません。1文字の変更が権限チェックを消すこともあるし、200行の変更が全部インデントのこともある。レビュアーはこの2つを見た目から区別できません。だから区別を人間にやらせてはいけない、というのが私の結論です。`.github/workflows/**` に触る差分は、行数がいくつであろうと、無条件にリンタの判定を通す。判定を人間の集中力の関数にしない。

### 「5日」の読み方を間違えないこと

最後がいちばん言いたいところです。

Wiz の教訓セクションは「発見の窓が縮んでいる、パッチサイクルを速くしろ」と書いています。半分同意します。でも「パッチを速くする」を主対策にすると、負ける勝負に乗ることになる。

5日というのは、自律エージェントが組織のGitHubを常時スキャンして、見つけて、失敗から回復して、悪用まで完走した時間です。この数字は今後**短くなる**側にしか動きません。人間の承認とデプロイが噛むパッチサイクルが、この曲線に追いつくことはない。速さで競っている限り、いつも相手のほうが速い。

構造的な答えは2つだと思っています。

1つは、**盗まれても価値のないシークレットにする**こと。今回抜かれたのは長命な Jira の API トークンでした。露出から失効まで、実際には6日かかっています（6月18日に露出、6月24日にローテーション）。仮に発見が5日でなく50日だったら、ずっと有効なままです。ここで効くのは検出速度ではなく、そもそも長命な認証情報を `secrets` に置かない設計です。OIDC で短命トークンを取る、権限を1プロジェクトに絞る、`permissions:` を最小にする。zizmor が Medium で出した `excessive-permissions` と `secrets-outside-env` は、まさにこの層の指摘でした。

もう1つは、**カテゴリごと禁止する**こと。「この `${{ }}` は安全か」をレビューで毎回判定するのをやめる。`run:` ブロック内の `${{ }}` は、安全なものも含めて全部落とす。安全な例が数件巻き込まれても構いません。判定を人間から機械に移すことのほうが価値が高い。zizmor が確信度 Low で出した `steps.create.outputs.jira_key` の行も、実際には攻撃者が制御できる値ではないでしょう。修正PR #1402 はそこも直しています。悪用可能だったからではなく、カテゴリで落としたからだと私は読みました。それが正しいやり方です。

余談ですが、修正PRのタイトルは `NO-SNOW adjust jira yml files` です。社内Jira番号も付いていない、いかにも雑用みたいな見た目。実際には5日開いていた穴を閉じるコミットでした。ここにも同じ問題が出ています。**その変更が何を守っているかは、見た目からは分からない。**

---

## 1つだけ持ち帰るなら

パッチを速くすることではありません。AIにコードを書かせるのをやめることでもありません。

`.github/workflows/**` を触るPRに、`zizmor` を1本足すことです。今日できて、`uvx zizmor@latest` で終わる。設定ファイルは要りません。

そのうえで、自分のリポジトリに「テストでは守れないが慣習で守っている不変条件」がほかにどれだけあるか、一度数えてみるといいと思います。書き換えのコストが下がった世界では、慣習は資産ではなく負債の側に回ります。誰も理由を書き残さなかった正しい形は、次の書き換えで消えます。今回消えたのは3つでした。

**機械が読めないルールは、もうルールではない。**
