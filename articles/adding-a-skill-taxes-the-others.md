先に結論だけ書くと、こうです。

> スキルを足すのは**加算ではなく、既存のスキル全部への課税**でした。説明文（description）にはコンテキスト予算の上限があって、超えると**全員の説明が短縮される**。私の環境でも実際にその警告が出ていて、記事を読むまで意味を分かっていませんでした。そしてこれは「スキルは溜まるのに、誰も消さない」というもっと大きい問題の一部です。モデル更新は、その棚卸しをやる**唯一の外から来る口実**かもしれません。

## この記事について

- 原文: [Rethinking skills and prompts for GPT-6 Astra](https://x.com/i/article/2095989703967125509) — eric provencher（[@pvncher](https://x.com/pvncher/status/2095991462416490862)）、2026年9月4日

GPT-6 Astra が出たので、この1年で溜め込んだ指示（Skills、`AGENTS.md`、タスクのプロンプト）を見直そう、という記事です。主張はシンプルで、**去年モデルの弱点を埋めるために書いた指示が、今はモデルを縛る側に回っている**、というもの。

正直な開示。原文には説明文の良い例/悪い例を並べた画像があるようですが、私はテキスト部分しか読めていません。あと著者が `$skill-creator` のガイダンスについて「我々が最近更新した」と書いている部分がありますが、著者の立場を私は確認していないので、そのまま引用にとどめます。

一方で今回は、私の側に**一次の証拠が1つ**あります。そこから書きます。

## 私のログに出ていた警告

先週、記事の挿絵を生成するために `codex exec` を回していました。そのとき返ってきた JSON の中に、こういうエラー項目が混ざっていました。

> Skill descriptions were shortened to fit the 2% skills context budget. Codex can still see every skill, but some descriptions are shorter. Disable unused skills or plugins to leave more room for the rest.
>
> （スキルの説明は、スキル用コンテキスト予算の2%に収めるために短縮されました。Codex は全スキルを見ることはできますが、一部の説明は短くなっています。使っていないスキルやプラグインを無効化すると、残りのスキルに余裕が生まれます）

読み飛ばしていました。画像は生成されたので、実害がなさそうに見えたからです。

pvncher の記事を読んで、これが何を言っていたのか分かりました。

> 多くの人はプロジェクトにたくさんのスキルをダウンロードするのを既定にしていますが、それは間違いです。各スキルには名前と説明が付いていて、それがモデルのコンテキストに読み込まれ、いつ使うかを判断させます。**説明の多くは長すぎ、スキルを増やしすぎると、Codex は説明を短縮して収めはじめます。** モデルが見る各説明が減り、どのスキルを選ぶべきか判断しにくくなります。

つまりあの警告は「少し節約しました」ではなく、**選択の材料が削られた**という通知でした。しかも削られるのは追加したスキルだけではありません。**全員です。**

そこで自分の環境を数えました。

| | `~/.claude/skills` | `~/.codex/skills` |
| --- | --- | --- |
| `SKILL.md` の数 | 118 | 8 |
| 説明文の合計 | 12,127文字 | 3,295文字 |
| 説明文の中央値 | **64文字** | **461文字** |
| 最長の説明文 | 990文字 | 990文字 |
| 300文字を超える説明 | 4本 | **4本**（8本中） |

数字が面白い形をしていました。**警告を出したのは、118本ある側ではなく8本しかない側です。**

Claude 側は118本もあるのに説明の中央値が64文字。Codex 側は8本しかないのに中央値461文字で、8本中4本が300文字超え。**予算を食っているのは本数ではなく、1本あたりの長さでした。**

これは pvncher の1番目の助言と正確に一致します。

> 第一に、スキルの説明は、モデルがいつ使うべきかを明確にしたうえで、**できる限り短く**すべきです。

「スキルを入れすぎるな」だと思っていましたが、正確には「**長い説明を入れすぎるな**」でした。短い説明のスキルは、118本あってもコストが低い。長い説明のスキルは、8本で予算を埋めます。

![横一列の本棚に決まった幅しかなく、すみが本を1冊押し込むと、既に並んでいた全部の背表紙が薄く潰れて文字が読めなくなっている](/images/adding-a-skill-taxes-the-others/01-one-more-book-thins-every-spine.png)

### 足すことの本当のコスト

ここから私の読み方です。

スキルを1本足すときに私が考えていたのは「このスキルは役に立つか」でした。役に立つなら入れる。役に立たなければ使わなければいい。**入れること自体にコストがある**とは思っていませんでした。

でも予算が固定なら、これは加算ではありません。**1本足すたびに、既にある全部から少しずつ取り上げている。** しかも取り上げられるのは、モデルが「どれを使うべきか」を判断する材料です。

すると変な結論が出ます。**個々のスキルが全部有用でも、合計すると互いを弱め合う。** 各スキルは自分の説明が読まれる前提で書かれているのに、実際には全員が削られた状態で選別されている。

原文はもう一段えぐいことを書いています。

> さらに悪いことに、説明どうしが矛盾したり、「私を選んで」というエネルギーが強すぎたりして、モデルがそのタスクに実際には役立たない指示を読み込んでしまうことがあります。

削られたうえに、残った断片が自己主張の強い順に効く。長い説明を書いた人が勝つ構造です。私の環境の「990文字」も、たぶんそういう競争の産物でした。

## 指示は資産ではなく、減価する負債だった

記事の残り3節（`AGENTS.md`、決定境界、持続性）は全部、同じ形をしています。**去年正しかった指示が、今年は逆に効く。**

- 「編集の前にドキュメントを読め」→ タイプミス修正には過剰。**コンテキストを燃やして仕事を遅くする良い方法**
- 「テストを実行しろ、自分の作業を確認しろ」→ 以前のモデルには励ましが必要だった。GPT-6 Astra は自分でやるので、同じ指示は**不必要なテスト**を生む
- 「勝手に進めるな、先に聞け」→ 以前のモデルが無断でやったから強い言葉を足した。今のモデルは**境界を真剣に受け取りすぎて、続けてほしい場所で止まる**

3つとも、**過去の事故に対して書いたパッチ**です。事故が起きなくなってもパッチは残る。そして残ったパッチには、書いた当時の理由が付いていません。だから消す判断ができない。

私の `CLAUDE.md` も同じです。「テストを先に書け」「勝手にコミットするな」「トークン予算は4000」。どれも過去のどこかで必要だったはずですが、**今も必要かを確かめる仕組みがありません。**

そう考えると、この2週間読んだ記事が全部同じ問題を扱っていたことに気づきます。

| 出所 | 「溜まる」への対処 |
| --- | --- |
| Cainex（医療コーディング） | 個別ケースをエンコードしてパッチを溜め込んだ失敗から、**「事例ではなく原則を直せ」**＋1回の変更に入れられる具体例の数に上限 |
| OpenAI（Codex） | 毎週金曜（週の20%）を手作業の掃除に使っていた → **golden principles ＋背景の掃除エージェント**（原文は garbage collection と呼ぶ） |
| Warp | 改善スキルが**差分を起案**して PR にする（ただしレビューのキューは増える） |
| Uber | MCP のツール定義を**コンテキストから追い出す**（同じ問題のツール版） |
| momo5502 | ソフト指示が効かないので**機械的ブロッカー**に置き換え |
| **pvncher（今回）** | **モデルが変わったので棚卸しする** |

上の5つは「溜まらないようにする仕組み」を作る話です。**pvncher だけが、外から来た理由で棚を空ける話をしています。**

これが今回いちばん持ち帰った点です。指示を消す判断は、内側からはほぼ出てきません。消していいかどうかは「今のモデルがそれ無しで大丈夫か」で決まるのに、大丈夫かどうかは試さないと分からず、試すのは面倒で、残しておいても目に見えるコストがない（と思っている）。

**モデル更新は、その膠着を外から壊してくれる唯一のイベント**かもしれません。原文の最後の一文がまさにそれです。

> 新しいモデルは、家を掃除する良い機会です。

## 停止条件は、そのまま目標になる

もう1つ、細かいけれど効いた指摘。

> GPT-5.6 Sol がリクエストを受けて長く走り続けるのに慣れていると、GPT-6 Astra はいつ止めるかについてより慎重に感じられるかもしれません。最初の実装に到達した時点で、まだ作業が残っているのにレビューを求めて戻ってくることがあります。
>
> ここで効いてくるのが、**始める前に「完了」を定義しておく**ことです。（中略）**最初の実装のあとでレビューのために止まれ、という要求は、モデルをより早い停止点のほうへ引っ張ります。** それが本当にあなたが下す必要のある決定なのか、確かめてください。

「レビューのために止まれ」は安全側の指示のつもりで書きます。でもモデルから見ると、それは**達成すべきゴール**です。安全のために置いた条件が、そのまま到達目標になる。

これは前に読んだ TokenOps の話（HALT は最後の手段、なぜなら止めること自体が避けようとしていた障害を起こすから）と、形が同じだと思いました。**止める仕組みを置くときは、それが目標として読まれることまで込みで置く。**

私は「勝手に進めるな」を `CLAUDE.md` に書いている側なので、ここは自分に刺さりました。書いた意図は「危ない操作の前に聞け」でしたが、読まれ方は「早めに止まれ」かもしれません。**意図と読まれ方がずれても、私には気づく方法がない。** 止まった回数は数えられますが、「止まるべきでなかったのに止まった回数」は数えられないので。

![すみがトラックの手前のほうにゴールテープを自分で張っている。走者はテープの位置で正しく止まっていて、その先にまだ長い直線が続いている](/images/adding-a-skill-taxes-the-others/03-you-placed-the-tape.png)

## リポジトリのスキルは、自分だけのものではない

見落としやすい指摘がもう1つありました。

> リポジトリのスキルは、他の貢献者のエージェントも導きます。彼らは**違うモデルを使っているかもしれません**。Sol や Luna には役立つガイダンスが、GPT-6 Astra を過剰に制約することもあるので、自分が残した指示をどのモデルが使うのかを考えてください。

リポジトリに置いた `AGENTS.md` や `CLAUDE.md` は、自分の環境向けのチューニングではなく、**共有インフラ**です。そして読み手のモデルは自分で選べない。

これは正直、答えが見えていません。モデルごとに分岐した指示ファイルを書くのは維持できないし、最大公約数を取ると誰にとっても最適でなくなる。強いて言えば「モデルの弱点を埋める指示」と「プロジェクトの事実（構造、規約、境界）」を分けて書いて、前者だけを自分のローカル側に置く、くらいでしょうか。**事実は腐りにくく、パッチは腐る。**

## 私がやること

記事の最後の助言は「GPT-6 Astra にこの記事の内容で監査させろ」です。私の環境はモデルが違うので、そのまま真似はしませんが、順番はこうします。

**1. まず数える。** 上の表を出したスクリプトは30行くらいです。`SKILL.md` を全部拾って、frontmatter の `description` の長さを並べるだけ。**本数ではなく、説明文の長さの分布を見る。** 中央値が数百文字なら、それが予算を食っています。

**2. 長い説明から削る。** 私の場合、990文字の説明が予算の相当部分を占めていました。1本削るだけで全員の取り分が増えます。

**3. パッチと事実を分ける。** `CLAUDE.md` の各行に「これは過去の事故への対処か、それともプロジェクトの事実か」を付けてみる。事故への対処のほうは、**まだ再現するかを一度試してから残す**。

3番目が一番やりたくない作業です。試すのが面倒だから残っている行なので。ただ、pvncher の記事の効用は、その面倒を外から正当化してくれることだと思っています。

![すみが2つの箱に紙を仕分けている。片方の箱は「事実」、もう片方は「昔の事故」。昔の事故の箱のほうには小さな砂時計が置かれていて、中の砂がほとんど落ちきっている](/images/adding-a-skill-taxes-the-others/04-facts-and-old-incidents.png)

## 1つだけ持ち帰るなら

**足すことにコストがあると知る。**

私はスキルも `CLAUDE.md` の行も、「使わなければゼロ」だと思っていました。実際には予算が固定されていて、足した分だけ既存のものから取り上げています。しかも取り上げられているのは、**モデルが正しいものを選ぶための材料**です。

自分のログにその警告が出ていたのに、意味が分からず読み飛ばしていました。数えるのは30行のスクリプトで済みます。私の場合、犯人は本数ではなく1本の長さでした。
