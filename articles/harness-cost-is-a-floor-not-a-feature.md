先に結論だけ書くと、こうです。

> ハーネスの請求額は、機能の値段ではなく「床」の値段だった。床（system prompt + ツール定義）× ターン数で、重いハーネスの請求のほとんどが説明できる。
> ただしこの説明は、あなたが実際に使っているハーネスを説明しない可能性が高い。Claude Code は12構成のうち床が5番目に軽く、1タスクあたりのトークンも4番目に少ない。それでいて別実験では、成功1件あたりのコストが最下位だった。

後半のほうが長いです。前半の数字の整理は元記事でも読めるので。

## 何が測られたのか

12個のハーネス構成（Aider、Aider の architect mode、Claude Code、Codex、Goose、Hermes、Kilo、Kimi Code、Nanobot、OpenClaw、Opencode、Qwen Code）に、同じ12個の小さな Python タスクを与える。全部 OpenRouter 経由なので、叩いている API とモデルは同一。トークンを全部数える。そして丸ごともう一度、別モデルで走らせて再現性を見る。

1回目が DeepSeek V4 Flash、2回目が Nvidia Nemotron 3 Ultra。Lawrence 氏は2回目に無料枠のあるモデルを選んでいて、「再現したいならタダでできる」と書いています。この一文で信用度がだいぶ上がりました。

結果の表がこれです（1タスク解くまでに使ったトークン数、2モデルのレンジ）。

## 床は機能ではなく定数だった

差の正体として著者が名指すのが startup tax です。プロンプトが仕事を始める前に、ハーネスが自分の荷物を送る。system prompt、ツールの説明、環境のセットアップ。

> Aider in architect mode ships about 700 tokens of overhead. OpenClaw ships about 26,000. That's a 40x difference before any work has started.
>
> This was the most stable number in the whole benchmark. It came out nearly identical on both models, for every harness. It behaves like a constant of the software, the way a binary has a size.
>
> （拙訳）Aider の architect mode は約700トークンのオーバーヘッドを積む。OpenClaw は約26,000。何ひとつ仕事が始まる前に40倍の差だ。
> これはベンチマーク全体で一番安定した数字だった。両方のモデルで、どのハーネスでも、ほぼ同一の値が出た。バイナリにサイズがあるのと同じように、ソフトウェアの定数として振る舞う。

「ソフトウェアの定数」という言い方が正確だと思います。モデルを替えても動かない数字は、モデルの性質ではなくハーネスの性質です。

そして床は一度しか払わないものではない。モデルは呼び出しをまたいで何も覚えていないので、会話全体が荷物ごと毎ターン再送されます。26k の床を持つハーネスが15ターン回れば、実際の作業を数える前に足場だけで約39万入力トークン。

The New Stack はここに回帰の話を足しています。startup tax × ターン数で「1タスクあたりのトークン数」を予測すると、両モデルで R² = 0.99。

R² = 0.99 を「よく予測できた」と読むのは、たぶん半分しか読めていません。もっと実務的な読み方はこうです。**測らなくても計算できる。** 床を1回測って、ターン数を数えれば、請求の大部分が出てしまう。ダッシュボードを眺めて「なぜか高い」と唸る段階を飛ばせる。

一方、驚くのは差を説明**しない**もののほうです。コンテキストの伸び方（1ターンあたり数百トークン）はどのハーネスもほぼ同じでした。高いハーネスはコンテキストを溜め込んでいるのではなく、重い床を担いでいるだけ。

なので、実務の一手目は「軽いハーネスに乗り換える」ではありません。**同じハーネスの床を削る**です。MCP サーバーを1つ足せばツール定義が床に乗ります。スキルの説明文も乗ります。CLAUDE.md も乗ります。そして毎ターン再送されます。MCP をコンテキストウィンドウの外に出す議論も、`/compact` がキャッシュを壊して請求を倍にする話も、根はここと同じで「毎ターン再送される前置きに何を置くか」です。

## 私の見解：この説明は Claude Code を説明しない

ここが本題です。

床×ターン数という機構は、OpenClaw（床26,000）、Qwen Code（20,000）、Kimi Code（16,000）、Kilo（14,700）を実にきれいに説明します。重い、だから高い。話が閉じている。

では表の Claude Code を見てください。**起動時オーバーヘッド約4,500。12構成のうち5番目に軽い。** 1タスクあたり52,000〜55,000も、少ない側から4番目です。床の理屈でも、1タスクあたりのトークン数でも、Claude Code は「安い側」に分類されるはずのハーネスです。

ところが Claude Code に起きたことは全部逆でした。

Composio の別実験（8ハーネス、30ワークフロー、900秒上限、LLM ではなくプログラムによる採点、240ラン中129成功）では、成功1件あたりのコストが Pi Agent の $0.028 から Claude Code の $0.195 まで。DeepAgents は Claude Code とまったく同じ合格率で、成功あたり4分の1のコストでした。つまり Claude Code はこの実験で一番高い。

理由としてキャッシュ比率が挙がっています。Composio の開示では、Claude Code が入力トークンのうちキャッシュから引いたのは 1.5%。Codex は約70%でした。新規入力はキャッシュ入力の約5倍の値段なので、トークン消費が同等でも請求書は同等になりません。

ここで注意が必要で、私は最初この因果を混線させました。「OpenRouter が Anthropic 方言を変換してキャッシュを落としていた」という診断は、Composio の実験ではなく Lawrence 氏の6月実験のものです。

> That's the twist I didn't see coming: Claude Code's zero cache share turned out not to be its prompts at all. It's the only harness that talks to OpenRouter through the Anthropic-style messages endpoint, and the gateway's translation of that dialect was dropping cache hits that identical traffic earns through the OpenAI-style endpoint, on the same providers.
>
> （拙訳）予想していなかったひねりがこれだ。Claude Code のキャッシュ比率がゼロだったのは、そのプロンプトのせいではまったくなかった。OpenRouter に Anthropic 形式の messages エンドポイント経由で話しかけている唯一のハーネスがこれで、ゲートウェイによるその方言の変換が、同じプロバイダで OpenAI 形式のエンドポイントなら得られるキャッシュヒットを落としていた。

Composio がどのゲートウェイを使ったかは、私が確認した範囲には書かれていません。だから「Composio の $0.195 はゲートウェイのアーティファクトだ」と言うことは私にはできません。言えるのは、同じ症状（Claude Code のキャッシュ比率が異常に低い）が2つの独立した実験で観測され、そのうち1つでは原因がハーネスの外にあった、ということです。

もうひとつ、Claude Code だけに起きたことがあります。コンテキストにゴミを詰める実験です。同じ12タスクの前に、無関係なログを 20k / 50k / 100k トークン分注入する。

Aider は 100k の塊を丸ごと1回のコールでモデルに渡して、それでも 12/12 解いた。著者の言葉では「モデルは腐らない」。長いコンテキストがモデルを馬鹿にするという俗説は、100k・このタスクでは成立しなかった。

Claude Code は 50k まで完璧で、100k で 12問中2問に落ちました。コンテキストは忠実に送っている。送ったあと、2〜3コールで筋を見失う。最後は編集なしで終わる。同じモデルで Aider は 12/12 だったのに。著者は同系列のより強いモデル（DeepSeek V4 Pro）で再試行して、同じ崩壊（予算切れまで0/6）を得ています。つまり崩壊は、モデルではなくハーネスに付いてくる。

まとめると、Claude Code のコスト問題と品質問題は、どちらも床ではありませんでした。片方はサービングパス（ゲートウェイの方言変換）、もう片方はコンテキストパイプラインです。

そしてこの2つには共通点があります。**どちらもトークンダッシュボードには映らない。** 床は測れます。ターン数も数えられます。「同じトラフィックが別のエンドポイント経由ならキャッシュに当たっていた」は、請求書を2つ並べて初めて見えます。「50k までは平気で 100k で崩れる」は、100k を注入して初めて見えます。

だから記事の見出しの機構（床×ターン数、R²=0.99）を持ち帰って自分の環境に当てても、たぶん外れます。R² が高いのは、この機構が支配する範囲での話です。多くの読者が実際に使っているハーネスは、その範囲の外にいます。

![大きく傾いた天秤。上がった左の皿には小さな箱と黒猫、そこに「床は軽い」。深く下がった右の皿には長いレシートの束が山積みで、赤字「請求は重い」。すみがしゃがんで皿の裏を覗き込み、そこから伸びる橙の細い糸2本を見つけている。糸の先には青字で「ゲートウェイ」「配管」、皿の下に赤字で「床では説明できない」](/images/harness-cost-is-a-floor-not-a-feature/02-not-the-floor.png)

## 「安い」の正体を確かめる列がない

もうひとつ、記事の中でいちばん軽く扱われていて、いちばん重いと思った結果があります。

ゴミ注入実験の Kilo です。曲線が完全にフラットで、しかも不気味に安い。どのノイズ量でも全部解く。トークン数もほとんど増えない。

理由は、プロンプトの大半を黙って捨てていたからでした。100k のペイロードがモデルに届いたときには 13k になっていた。末尾を残す実装で、著者の注入したノイズの後ろにタスクが置かれていたので、たまたま生き残っていた。

> It looks robust on a chart, but a harness that quietly drops your input when it gets large is not something I'd call robust.
>
> （拙訳）チャート上は頑健に見えるが、入力が大きくなると黙って捨てるハーネスを、私は頑健とは呼ばない。

これは節約ではなく、成功に見える失敗です。The New Stack もこれを表にしていて、「silent truncation は、ハーネスの出力上、成功とまったく同じ見た目になるから危険だ」と書いています。

私が引っかかったのは、**この列がベンチマークの主表にない**ことです。主表は「1タスクあたりトークン」と「起動時オーバーヘッド」。安いハーネスが安い理由が「送っていないから」なのかを、主表からは判別できません。Kilo は末尾にタスクがあったから助かりましたが、タスクが冒頭にあれば同じ実装で沈黙のまま全滅していたはずです。

ハーネスを評価するとき、コスト表の隣に置くべき列はこれだと思います。**送ったバイト数 ÷ 送ろうとしたバイト数。** 1.0 でないハーネスのコスト数字は、そのぶん割り引いて読む。

![踏み台に立つすみが、巨大な漏斗の口に大量の紙束を流し込んでいる（「入れた分」）。漏斗の側面の隠れたハッチから紙が大量にこぼれて床に山を作り、赤字で「黙って捨てた」。細い注ぎ口から出てくるのは紙1枚だけで、橙の矢印がそれを小さなトレイへ導き「届いた分」。傍らのクリップボードには全部チェックが入り、青字で「全問成功」。すみの足元に赤字で「見えない」、黒猫が捨てられた山を見上げている](/images/harness-cost-is-a-floor-not-a-feature/03-silent-truncation.png)

## 難しい問題では、18倍払って結果は同じ

「重い足場は難問で元を取るのでは」という当然の反論を、著者は自分で潰しています。コスト帯を跨ぐ4つ（Aider、Claude Code、Codex、Kilo）に、実物の SWE-bench Lite を10問、緩い上限で。

4つとも、10問中ちょうど1問を解きました。同じ1問を。

Aider は 0.8M トークン、Claude Code は 5.3M、Kilo は 12.3M、Codex は 15M。18倍の支出差で、結果は同一。著者は Claude Code に5倍の予算を与えて再試行もしていて、10問中9問で本物のパッチは出たものの、追加で解けた問題は1問もありませんでした。

> Capability comes from the model. The harness decides how expensive it is to find that out.
>
> （拙訳）能力はモデルから来る。ハーネスが決めるのは、それを知るのにいくらかかるかだ。

![横に張ったワイヤーから、長さのまったく違う4本のレシートが吊られている。一番長い1本は床でとぐろを巻き、黒字で「18倍」。4本ともその上を走る橙の線には届かず、赤字で「越えない」、線の上には「モデルの天井」。床には同じ形の南京錠が4つ並び、赤字で「同じ1問」。少し離れて開いた南京錠が1つ、青字で「足場では届かない」。右端ですみが小さな鍵を1本つまんで掲げている](/images/harness-cost-is-a-floor-not-a-feature/04-same-single-result.png)

10問・1モデルなので一般化には薄い、と著者自身も書いています。ただ方向は覚えておく価値があります。The New Stack がこの点を丁寧に補正していて、Composio の合格率は OpenCode の 46.7% から Pi Agent の 66.7% まで20ポイント開いている。ハーネスはコストを「倍数」で動かし、成功率を「パーセントポイント」で動かす。逆方向ではなく、桁が違う。

## 二次資料と一次資料で食い違った箇所

正直に書いておきます。The New Stack の記述と Lawrence 氏のブログで、私が突き合わせて一致させられなかった箇所が1つあります。

The New Stack は忠実性テストについて「12構成のうち7つがプロンプトを忠実に送信し、Kilo と Opencode は83〜89%を落としながら成功を報告、OpenClaw は実行を拒否、Kimi Code はクラッシュ」と、12構成の話として書いています。一方 Lawrence 氏のブログ本体で私が読めた記述は「同じ4つのハーネス」（Aider、Claude Code、Codex、Kilo）でのノイズ注入実験です。

12構成を対象にした忠実性の表が PDF 側にあるのか、The New Stack が別の測定と統合して書いているのかは、PDF を読んでいない私には判別できません。なので本文では、私がブログ本体で確認できた4ハーネスの記述を主に使い、12構成の内訳は The New Stack の記述として出典を分けました。

こういう食い違いは、二次資料を1本だけ読んで書くと絶対に見えません。

## じゃあ何を測るか

乗り換え候補を探すより先に、自分の環境で3つの数字を取るほうが早いと思います。

**床。** 会話1ターン目の入力トークン数がほぼそれです。MCP サーバーを全部切った状態と、いつもの状態で1回ずつ測って差分を見る。「便利だから入れてある」サーバーの値札がここで出ます。

**ターン数。** 1タスクが何往復で終わっているか。床×ターン数が請求の主項なので、この2つの積を下げる手は等価です。プロンプトを丁寧に書いて往復を3回減らすのと、床を3分の1にするのは、同じ効果になります。

**キャッシュ比率。** これが一番忘れられます。生の入力トークンとキャッシュ読みを分けて見る。Codex の例では、100万トークン超のうち77%がキャッシュ読みで、通常の約10分の1の価格。生のトークン数では最悪クラスなのに、請求書ベースでは Claude Code（生トークンは半分）より安くなっていました。ダッシュボードのグレーの棒と、実際に払う青い棒は別の話です。

そして Lawrence 氏の3つ目の教訓が効いてきます。キャッシュの割引は「ハーネス」の性質ではなく「ハーネス→ゲートウェイ→プロバイダ」のパス全体の性質です。だから自分のパスが本当に割引を受けているかを確認しろ、と。Claude Code のキャッシュ比率1.5%は、Claude Code が悪いのではなく、そのパスが払っていなかった。

## 1つだけ持ち帰るなら

床×ターン数の話ではありません。それは元記事を読めば書いてあります。

持ち帰る価値があるのはこれです。**このベンチマークは「安いハーネス」を見つけたのではなく、「高い理由が3種類ある」ことを見つけた。** 重い床（OpenClaw 型）、払われないキャッシュ割引（パスの問題）、大きな入力で壊れるコンテキスト配管（Claude Code 型）と、大きな入力を黙って捨てる実装（Kilo 型）。

そして自分のハーネスがどの型かは、ランキングを見ても分かりません。床を測り、キャッシュ比率を見て、100k のゴミを1回注入する。3つとも、半日あれば自分の環境でできます。

ランキングの70倍は、他人の環境の数字です。自分の請求書に出てくる倍数は、自分で測るしかない。
