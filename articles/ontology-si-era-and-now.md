ここ1年ほど、「オントロジー」という言葉を AI エージェントの文脈でよく見るようになりました。Palantir が自社製品の中心に Ontology を置いていることもあって、データ基盤の話をしているとだいたい出てきます。

ただ、この言葉自体は新しくありません。2000年代のセマンティックWeb、そのあとの SI 案件でも、オントロジーは一度ちゃんと流行っています。そして、多くの現場で「作ったけど使われなかった」ものとして終わっています。

なので、この記事では SI の頃と今とで、オントロジーを作るときの手順とやるべきことを並べてみます。先に断っておくと、ここで書く SI 時代の手順は当時の一般的な進め方を整理したもので、特定の案件の体験談ではありません。

先に結論だけ書くと、こうです。

> AI で楽になったのは「書く」工程で、オントロジーの本体である「業務側と定義を合意する」工程は楽になっていない。下書きが一瞬で出るようになったぶん、合意を飛ばしたオントロジーが量産される危険のほうが大きい。今やるべきことは、エージェントが読む前提で、定義を少なく、検証できる形で持つこと。

## オントロジーとは

よく引かれる定義は Tom Gruber の1993年の論文のものです。

> An ontology is an explicit specification of a conceptualization.
>
> （オントロジーとは、概念化の明示的な仕様である。）

これだけだと分かりにくいので、私の言葉に直すと「ある業務の世界に何があって、それらがどう関係しているかを、人と機械の両方が同じ意味で読めるように書いたもの」です。

たとえば町の自転車修理店なら、「客」「自転車」「修理」「部品」「見積」といったものがあり、「自転車は客が持ち込む」「見積は修理と部品を参照する」といった関係があります。ここまでは ER 図でも書けます。

ER 図と違うのは、意味まで持たせるところです。「持ち込んだ人」は「客」の一種だが、「自転車の持ち主」とは限らない。「見積」と「請求」は似ているが別物で、見積は確定前、請求は確定後。こうした区別を、テーブル設計の都合ではなく業務の言葉のまま書きます。データベースは「何を保存するか」、オントロジーは「それが何を意味するか」を担当する、と分けると近いと思います。

## SI の頃のステップ

SI 時代のオントロジー構築は、だいたい次の順で進みました。

1. **スコープと用語集**：対象業務を決め、ヒアリングで用語を集める。同じものに3つの呼び名がある、といった揺れをここで潰す。
2. **概念モデル**：クラス（概念）の階層と、プロパティ（関係・属性）を決める。Protégé のようなエディタで OWL として書くことが多かった。
3. **既存データとの対応付け**：RDB や CSV の列が、どのクラス・プロパティに当たるかを決め、RDF に変換する ETL を作る。
4. **推論と検索**：推論エンジンで暗黙の事実を導き、SPARQL で問い合わせる画面や API を作る。
5. **納品と保守**：仕様書とセットで納品し、変更は保守契約の中で受ける。

このうち工数の大半を食ったのは1と3でした。用語の揺れを潰すにはヒアリングを何周もする必要があり、対応付けは既存システムの癖をひとつずつ吸収する作業だからです。

そして失敗しやすかったのは5です。オントロジーが「納品物」になると、業務が変わっても誰も更新しません。更新しないオントロジーは半年で現実とずれ、ずれたものは使われなくなります。使われていないので、ずれていても誰も困らない。この循環で静かに終わったプロジェクトが多かったはずです。

![](/images/ontology-si-era-and-now/02-delivered-and-left-behind.png)

もうひとつ、当時は「機械が推論する」ことに期待が寄りすぎていました。OWL で厳密に書けば、推論エンジンが新しい知識を導いてくれる。でも実際の業務で欲しかったのは推論より「この言葉は何を指すのか、全員が同じ答えを持っている状態」で、そこには推論エンジンは要りませんでした。

## 今のステップ

LLM が入って、手順はこう変わったと私は見ています。

1. **エージェントにやらせたい判断から逆算する**：「全業務を網羅する」から始めない。「見積の差し戻し理由を判定させたい」のように、AI に任せたい判断を1つ決め、そこに要る概念だけを拾う。
2. **既存資料から LLM に候補を出させる**：マニュアル、DB スキーマ、問い合わせ履歴を読ませて、概念と関係の候補を出させる。ここは本当に速くなった。
3. **人が合意する**：候補を業務側と突き合わせ、定義を決める。「持ち主でない人の修理を受けてよいか」に答えられるのは LLM ではなく現場の人。
4. **オブジェクトとアクションで持つ**：概念だけでなく、それに対して何ができるか（見積を確定する、部品を取り寄せる）まで定義する。Palantir の Ontology がアクションを一級市民にしているのはこのためだと思います。
5. **エージェントのツールとして公開する**：オントロジーをそのまま、エージェントが呼べる関数と、その引数の説明にする。
6. **評価で回す**：エージェントが定義どおりに判断したかを、テストケースで毎回確かめる。ずれたら定義を直す。

SI の頃との違いを表にするとこうなります。

| | SI の頃 | 今 |
| --- | --- | --- |
| 誰が読むか | 推論エンジンと開発者 | LLM エージェントと業務担当者 |
| 範囲 | 業務全体を網羅 | 任せたい判断に要る分だけ |
| 一番重い工程 | 用語の収集と ETL | 定義の合意 |
| 書き方 | OWL / RDF で厳密に | 型付きのスキーマと自然言語の説明 |
| 終わり方 | 納品 | 評価が通り続ける限り運用 |

## 楽になったのは書く工程だけ

ここが一番言いたいところです。

今のステップの2は、SI の頃なら数週間かかった作業が数分で終わります。LLM はそれらしいクラス階層を、それらしい説明付きで出してきます。

ただ、それらしいだけです。LLM が出した「見積」の定義は、一般的な見積の定義であって、その会社の見積ではありません。その会社では「仮見積」と「本見積」を分けているかもしれないし、口頭で伝えた金額を見積と呼んでいるかもしれない。それを知っているのは現場の人だけで、聞かないと分かりません。

SI の頃は、書くのが遅かったので、書いている間にどうしても人に聞くことになりました。遅さが合意を強制していた、とも言えます。今は聞かなくても形になります。形になったものは、レビューする側も「まあ合っていそう」と通してしまいやすい。

だから私は、今のオントロジー構築の危険は「作れないこと」ではなく「合意していないものが作れてしまうこと」だと考えています。しかも今回はエージェントがそれを読んで実際に動くので、SI の頃のように「使われずに終わる」では済みません。間違った定義のまま、見積を確定するアクションが呼ばれます。

## 今やるべきこと

この見方に立つと、やるべきことは3つに絞れます。

**定義を少なく持つ。** 網羅したくなる気持ちを抑えて、エージェントに任せる判断に要るものだけにする。定義が増えるほど合意のコストが増え、合意していない定義が混ざる確率も上がります。

**定義ごとに「誰が合意したか」を残す。** LLM が出した候補なのか、現場の誰かが確認したものなのかを区別できるようにしておく。SI の頃の仕様書には書いてあったけれど、今のスキーマには抜けがちな情報です。

**評価を先に作る。** 「この入力ならこう判断する」というケースを業務側と一緒に作り、オントロジーを変えるたびに流す。SI の頃の「納品したら終わり」をやめて、評価が通り続けることを完成の条件にする。これで、業務が変わったときに定義のずれが検知できるようになります。

![](/images/ontology-si-era-and-now/04-few-definitions-on-a-loop.png)

1つだけ持ち帰るなら、LLM に出させた下書きを、合意の代わりにしないこと。オントロジーは昔も今も、技術より先に「言葉をそろえる仕事」です。AI はその仕事を速くしてくれましたが、肩代わりはしてくれません。
